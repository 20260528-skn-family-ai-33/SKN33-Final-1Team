# 추가 설계 7단계 — 인증·권한 상세 계약

작성일: 2026-10-16

상태: **7단계 설계 완료.** 이메일 로그인, 개발용 `admin/admin`, 사용자·세션·프로젝트 권한·계정 관리·오류·검증 기준을 확정한다. 아래는 7단계 설계 시점의 기록이다. 당시 산출물은 Markdown이었으며 실제 구현/검증은 이후 [C08 — 인증과 계정 관리](구현_C08_인증과계정관리.md)에서 완료했다. 실제 화면·브라우저·파일 경로의 미완료 범위는 C08 대응표를 따른다.

## 1. 범위와 근거

근거는 [사용자·파일 설계](물리설계_02_사용자와파일.md), [전체 정합성](물리설계_06_전체정합성.md), [제약 목록](물리설계_06_제약목록.md), [프로젝트 명세](../project-specification.md), [현재 개발용 인증](../../backend/app/local_auth.py), [검수 API](../../backend/app/api.py), [인증 요청](../../frontend/src/api/auth.js), [인증 상태 관리](../../frontend/src/auth/AuthProvider.jsx), [로그인 화면](../../frontend/src/pages/LoginPage.jsx), [프런트 프록시](../../frontend/vite.config.js)다.

| 구분 | 현재 확인한 구현 | 목표 계약 |
|---|---|---|
| 로그인 | username/password의 admin/admin만 검사 | email/password와 명시적 개발 username/password 분기 |
| 세션 | 앱 인스턴스의 메모리 dict, 8시간 | user_sessions의 난수 토큰 해시·만료·폐기 |
| 개발 사용자 | id=local-admin 문자열 | account_kind=developer인 실제 사용자 UUID |
| 개발 접근 | 실제 접속 peer·요청 hostname의 loopback 확인, LOCAL_ADMIN_LOGIN 설정 | 위 경계를 유지하고 환경·프록시·모든 보호 요청에서도 재검사 |
| CSRF | 쿠키/헤더 토큰 일치·Origin 검사, 로그인/로그아웃에 적용 | 세션/로그인 전 주체에 서명으로 결합, 모든 변경 요청 보호 |
| 프런트 인증 | login 후 me 재확인, 늦은 응답 무시, 로그아웃 실패 시 상태 유지 | 같은 동작 유지, 이메일 입력·새 쿠키·오류 계약 연결 |
| 업무 API | 검수 제출·조회·이미지에 사용자/프로젝트 권한 검사가 아직 없음 | 신규·기존 보호 경로 모두 동일한 인증·권한 검사 |

첫 범위는 관리자 발급 이메일 계정이다. 공개 회원가입·이메일 소유 확인 메일·셀프 비밀번호 재설정·SSO·MFA·멤버 관리 화면은 별도 확장이다. 관리자는 웹의 만능 사용자 역할이 아니라 보호된 운영 명령을 실행하는 운영 주체다. 개발 admin을 운영 관리자로 취급하지 않는다.

아래 기본값·제한·환경 조합은 이번 프로젝트의 설계 결정이다. OWASP의 일반 지침과 이미 실행한 검증 결과를 혼동하지 않는다.

## 2. 사용자 종류와 DB 식별자

모든 사용자 행에 이메일·해시를 요구하면 개발 계정을 위해 가짜 이메일이나 가짜 비밀번호 해시가 필요해진다. 이를 피하기 위해 **users.account_kind를 추가**하고 정식 계정의 필수 조건을 조건부 CHECK로 유지한다. 테이블 수는 26개 그대로이며 총 컬럼은 394개에서 395개가 된다.

| 컬럼·제약 | 최종 설계 |
|---|---|
| account_kind | VARCHAR(20), NOT NULL, 기본 email. email/developer만 허용 |
| email | VARCHAR(254), SQL NULL 허용. email 종류에서는 필수·정규화·비어 있지 않음·유일, developer에서는 NULL |
| password_hash | TEXT, SQL NULL 허용. email 종류에서는 실제 비밀번호 해시 필수, developer에서는 NULL |
| user_id | 기존 앱 발급 UUID v4. 생성 뒤 변경하지 않음 |
| uq_users_email | 기존 UNIQUE(email) 유지. 개발 계정 NULL은 이메일 로그인 ID가 아님 |
| uq_users_developer_kind | account_kind=developer인 행에만 UNIQUE(account_kind). 비활성 행 포함 DB당 개발 주체 최대 하나 |
| ck_users_domain | 종류별 이메일/해시 조건과 display_name 비어 있지 않음을 강제 |
| 종류 변경 | 일반 앱·관리 명령에서 account_kind 변경 금지. 다른 종류는 새 사용자로 생성 |

이메일 계정에는 여전히 이메일·비밀번호 해시가 반드시 있어야 한다. 개발 주체의 예외를 정식 계정에 적용하지 않는다. 별도 login_name·가짜 이메일·고정 UUID를 추가하지 않는다. user_sessions는 기존 user_id FK로 종류를 확인하므로 세션 테이블에 종류를 중복 저장하지 않는다.

개발 인증의 문자열 `local-admin`은 과거 UI/JSON의 외부 식별자다. 새 DB 업무 기록과 신규 auth/me 응답은 개발 사용자 UUID를 사용한다. 과거 문자열을 UUID 컬럼에 넣거나 과거 기록 전체를 개발 사용자에게 자동 귀속하지 않는다. 실제 이력 이전은 9단계에서 별도로 수행한다.

### 개발 주체·프로젝트의 시드

개발 주체는 명시적 개발 초기화 명령에서 한 번 생성한다. 재실행 시 account_kind=developer 행을 조회해 같은 UUID를 재사용하고, 비활성 계정을 자동으로 활성화하거나 권한을 늘리지 않는다. 동시 초기화는 부분 유일 인덱스 충돌을 롤백한 뒤 기존 행을 조회한다.

개발 프로젝트는 명시적으로 지정한 `DEV_PROJECT_ID` UUID에 생성하며, 개발 사용자 owner 멤버십을 같은 트랜잭션에서 만든다. UUID는 최초 초기화 때 한 번 발급·출력해 로컬 설정에 보존한다. 재실행은 그 UUID를 요구하며 이름으로 프로젝트를 찾아 합치거나 새 프로젝트를 계속 생성하지 않는다. 이미 다른 프로젝트·다른 소유 구성에 대응하면 충돌로 중단한다.

일반 앱 시작·마이그레이션 실행이 계정이나 프로젝트를 자동으로 시드하지 않는다. DB 연결을 사용하는 개발 로그인에서는 개발 주체·프로젝트·멤버십이 준비됐는지 확인하고, 없으면 AUTH_SETUP_REQUIRED로 거부한다. 실제 UUID·정식 사용자 이메일·비밀번호는 구현/초기화 때 공급하며 이 문서에 임의 값을 넣지 않는다.

## 3. 이메일 계정 발급과 비밀번호

| 항목 | 프로젝트 정책 |
|---|---|
| 계정 발급 | 운영 관리 명령에서 실제 이메일·표시 이름·초기 비밀번호를 명시적으로 받음 |
| 이메일 입력 | 앞뒤 공백 제거·전체 소문자화. 최초 범위는 ASCII 이메일·최대 254자, 국제화 이메일은 별도 확장 |
| 중복 이메일 | 정규화 후 DB UNIQUE 충돌이면 EMAIL_ALREADY_EXISTS. 다른 사용자를 덮어쓰지 않음 |
| 초기/재설정 비밀번호 | Unicode 코드포인트 15~128자. 공백·한글·기호 허용, trim/lower/Unicode 정규화·잘라내기 금지 |
| 로그인 비밀번호 입력 | 1~128자. 발급 정책과 별개로 유효한 자격 증명인지 검사. 개발 분기의 admin은 별도 고정 계약 |
| 비밀번호 저장 | Argon2id 인코딩 문자열. 초기 최소 m=19456 KiB, t=2, p=1, salt는 검증된 라이브러리 생성 |
| 해시 교체 | 로그인 성공 후 현재 비용보다 낮은 해시만 재해시. 10단계에서 argon2-cffi 25.1.0·동시 2개 선택. 실제 비용은 구현 때 측정 |
| 비밀번호 전달 | 보호된 관리 입력에서 에코 없이 받음. 명령행 인자·소스·마이그레이션·일반 로그에 평문을 두지 않음 |

최소 길이와 Argon2id 기준은 [OWASP 인증 안내](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#implement-proper-password-strength-controls), [비밀번호 저장 안내](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#argon2id)를 참고했다. 길이 128자·ASCII 이메일 범위·발급 방식은 프로젝트 결정이다.

계정 생성은 로그인 완료나 이메일 소유 확인을 뜻하지 않는다. 이메일 계정은 user_id·email·실제 해시를 생성하고 프로젝트 멤버십은 별도로 지정한다. 개발 계정의 password_hash=NULL을 Argon2 검증기에 넘기지 않는다. 서버가 사용자 종류를 보고 올바른 자격 증명 경로만 사용한다.

## 4. 로그인 요청·검증 순서

인증 기본 경로는 `/api/v1/auth`를 유지한다. 현재 개발 요청의 username/password를 보존하면서 정식 email/password를 추가한다. 비밀번호 실패 뒤 다른 로그인 종류로 자동 전환하지 않는다.

| 요청 | 해석·결과 |
|---|---|
| email + password | 정규화한 이메일과 account_kind=email 사용자만 검사 |
| username=admin + password=admin | 개발 환경·loopback·설정 조건 통과 시 developer 사용자로 인증 |
| email과 username 둘 다 제공 | 422 INVALID_AUTH_REQUEST |
| 식별자 없음·알 수 없는 추가 필드·타입/길이 오류 | 422 INVALID_AUTH_REQUEST |
| 다른 개발 username/password | 허용된 개발 경로 안에서는 401 INVALID_CREDENTIALS |
| 개발 로그인 조건 불충족 | 404 AUTH_ROUTE_NOT_FOUND. 이메일 계정 경로는 계속 제공 |

1. 본문 크기·Content-Type·필드 구조와 Origin/CSRF를 확인한다. 로그인 JSON 본문은 최초 4 KiB 이내로 제한한다.
2. 로그인 종류를 명시적으로 판정하고 개발 환경 조건·시도 제한을 적용한다.
3. 이메일 사용자·현재 해시·활성 여부를 읽고 DB 트랜잭션을 닫은 뒤 Argon2를 검증한다. 사용자가 없거나 비활성이어도 준비한 더미 해시를 검증해 단순한 빠른 실패 분기를 피하고 같은 401 메시지를 사용한다.
4. 짧은 쓰기 트랜잭션에서 사용자 행을 잠그고 종류·활성 상태·검증에 사용한 해시가 여전히 같은지 재확인한다. 이전 쿠키의 세션이 다른 사용자에게 속하면 해당 사용자까지 UUID 순서로 먼저 잠근 뒤 세션을 잠근다. 동시에 비밀번호/활성 상태가 바뀌었으면 새 세션을 만들지 않는다. 재해시는 같은 검증 스냅샷에 대해서만 반영한다.
5. 브라우저가 가진 이전 DB 세션을 폐기하고 새로운 세션 행을 만든 뒤 커밋한다. 다른 기기의 세션까지 이 로그인 때문에 폐기하지 않는다.
6. 커밋 성공 뒤 새 세션 쿠키·그 세션에 결합한 CSRF 쿠키와 공개 사용자 정보를 응답한다. 쿠키 전달이 유실되면 인증 성공으로 화면을 이동하지 않고 me를 재확인한다.

개발 분기는 상수 시간 비교로 admin/admin을 확인한 뒤 developer 사용자 UUID·활성 상태·개발 프로젝트 멤버십을 검증한다. DB 장애·초기화 누락을 이유로 예전 메모리 인증으로 조용히 우회하지 않는다. 개발 계정의 요청 제한도 적용한다.

## 5. DB 세션과 쿠키

세션 토큰은 암호학적 난수 32바이트 이상을 URL-safe 문자열로 인코딩한다. DB에는 원문 토큰의 SHA256만 저장한다. session_id UUID와 user_id는 쿠키 자격 증명이 아니며, 세션 토큰·해시는 API에 공개하지 않는다.

| 정책 | 결정 |
|---|---|
| 세션 수명 | 발급부터 절대 8시간. 요청마다 연장하거나 expires_at을 갱신하지 않음 |
| 여러 기기 | 사용자별 여러 세션 허용. 같은 브라우저의 새 로그인은 이전 쿠키의 세션을 폐기 |
| 인증 성공 조건 | 해시 일치, revoked_at=NULL, DB 실제 현재 시각 < expires_at, 사용자 is_active=true, 사용자 종류의 환경 조건 충족 |
| 세션 조회 | 요청마다 DB 확인. 사용자 활성·멤버십·역할을 오래 캐시해 권한 변경을 놓치지 않음 |
| 서버 재시작 | DB 세션 유지. 이전 메모리 dict 세션은 이관하지 않고 다시 로그인 |
| 비밀번호/이메일 변경·계정 비활성화 | 사용자 변경과 관련 세션 전체 폐기를 같은 트랜잭션에 반영 |
| 응답 캐시 | 모든 인증 응답과 사용자별 보호 응답에 Cache-Control: no-store |

| 쿠키 | HTTPS 운영 | HTTP localhost 개발 | 속성·수명 |
|---|---|---|---|
| 세션 | __Host-baro_session | baro_session | HttpOnly, SameSite=Strict, Path=/, Domain 미설정. Max-Age=28800 |
| CSRF 토큰 | __Host-csrftoken | csrftoken | JS가 읽을 수 있음, SameSite=Strict, Path=/, Domain 미설정. 15분 |
| 로그인 전 CSRF seed | __Host-baro_csrf_seed | baro_csrf_seed | HttpOnly, SameSite=Strict, Path=/, Domain 미설정. 15분 |

운영 쿠키 세 종류 모두 Secure를 사용한다. 개발의 HTTP 예외는 APP_ENV=development/test·loopback에서만 적용한다. 운영을 HTTP로 실행하면서 Secure를 자동으로 끄지 않는다. `__Host-` 조건과 HttpOnly·SameSite의 역할은 [OWASP 세션 관리 안내](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#cookies)를 참고한다.

기존 baro_local_session은 새 인증에서 신뢰하지 않는다. 전환 시 삭제하고 재로그인하며, 동일한 admin/admin 자격 증명은 개발 분기에서 계속 사용한다. 쿠키 이름이 두 환경에 동시에 보이면 현재 환경의 이름 하나만 읽고 임의 우선순위나 fallback으로 다른 주체를 선택하지 않는다.

## 6. CSRF·Origin·프록시

목표는 **세션에 결합한 서명 double-submit**이다. 쿠키와 X-CSRFToken이 같은지만 검사하는 현재 방식에서 서명·세션 결합을 보강한다. 설계 기준은 [OWASP CSRF 안내](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#signed-double-submit-cookie-recommended)다.

- GET /csrf는 유효한 기존 CSRF 쿠키를 재사용하고, 없거나 만료되면 난수 nonce와 발급 시각·HMAC-SHA256 서명을 만든다. 응답 본문에 csrf_token을 제공한다.
- 세션 쿠키가 있으면 그 **원문 세션 토큰**을 HMAC의 비공개 결합 입력으로 사용한다. 토큰 본문에는 세션 토큰·사용자 ID를 넣지 않는다. 세션이 이미 만료됐어도 로그아웃의 CSRF 검증을 위해 이 결합 규칙은 동일하다. CSRF 검증 성공 자체는 인증 성공이 아니다.
- 세션 쿠키가 없으면 HttpOnly의 난수 pre-auth seed를 만들고 그 seed에 결합한다. seed는 DB 사용자·로그인 세션을 생성하지 않는다.
- 서명 입력은 버전·용도(session/pre-auth)·길이가 구분된 결합값·nonce·발급 시각이다. 토큰은 발급 시각/nonce/서명만 전달하며 최초 최대 256바이트, 수명 900초, 미래 시각 허용 오차 30초로 제한한다.
- POST/PATCH/DELETE 등 변경 요청은 쿠키/헤더 토큰의 일치, 서명·용도·현재 쿠키 결합·수명을 검사한다. 로그인·로그아웃·업로드·기준 확정·재검수도 예외가 아니다. GET으로 계정·업무 데이터를 변경하지 않는다.
- 로그인 성공 시 seed를 삭제하고 새 세션에 결합한 CSRF 토큰을 발급한다. 이전 탭의 토큰을 자동 승인하지 않는다. 실패하면 403 CSRF_FAILED이며 업무 트랜잭션을 시작하지 않는다.
- HMAC 키는 서버의 별도 CSRF_SECRET으로 공급한다. 키를 바꾸면 기존 CSRF 토큰은 다시 준비해야 하지만 DB 로그인 세션이 자동으로 새 주체가 되지는 않는다.

변경 요청의 Origin은 서버에 설정한 정확한 공개 origin과 일치해야 한다. 없으면 Referer의 scheme/host/port를 검사하고, 둘 다 없거나 `null`이면 첫 브라우저 API 범위에서 403으로 거부한다. Host 헤더에서 허용 origin을 즉석 생성하지 않는다. 개발 허용 목록은 실제 사용하는 localhost/127.0.0.1 origin만 명시하며 두 호스트의 쿠키가 공유된다고 가정하지 않는다.

브라우저는 같은 origin 프록시를 사용하고 credentials를 전달한다. 운영은 같은 HTTPS origin의 React·FastAPI로 제공한다. 개발 Vite 프록시는 로컬 backend로 연결하며, 웹·Vite 모두 loopback에 바인딩한다. 개발 인증을 원격 reverse proxy나 터널로 제공하지 않는다. loopback 프록시의 peer 주소만으로 원 사용자가 로컬이라고 단정하지 않는다.

운영 프록시의 forwarded 헤더는 명시적으로 신뢰한 프록시 주소에서만 해석한다. 개발 인증은 기본적으로 forwarded 헤더 경로를 거부하고 직접 loopback 또는 검증한 로컬 Vite 경로만 허용한다. 헤더 이름·프록시 옵션·연결 방식은 [10단계](추가설계_10_구현구조와검증명세.md) 구성에서 정했으며 구현 때 외부 브라우저→프록시→loopback backend 사례로 시험한다. 임의 X-Forwarded-For를 사용자 IP나 개발 권한의 근거로 쓰지 않는다.

## 7. 개발 계정의 활성 조건

| 조건 | 개발 자격 증명·개발 세션 |
|---|---|
| APP_ENV=development/test, LOCAL_ADMIN_LOGIN=1, loopback 및 origin/프록시 조건 충족 | 허용. 실제 DB 개발 주체·멤버십 필요 |
| LOCAL_ADMIN_LOGIN=0 | 개발 로그인 404, 기존 developer 세션도 보호 API에서 인증 거부 |
| APP_ENV=production 또는 미지정 | 개발 기능 비활성. production과 LOCAL_ADMIN_LOGIN=1 조합은 시작 구성 오류 |
| 원격 peer·비 loopback Host·검증되지 않은 proxy 경로 | 개발 로그인 404, developer 세션도 인증 거부 |
| 개발 DB 주체 없음·비활성·개발 프로젝트 미설정 | 503 AUTH_SETUP_REQUIRED. 자동 시드·자동 활성화하지 않음 |

이 조건은 로그인할 때뿐 아니라 **developer 세션으로 호출하는 모든 프로젝트·파일·결과 API**에서 다시 적용한다. 운영에서 이메일 로그인을 시도하면 account_kind=email만 조회하므로 developer 행을 이메일 계정으로 인증할 수 없다.

운영 DB에는 개발 주체를 새로 시드하지 않는다. 이전 이력을 위해 developer 행이 남아 있으면 비활성으로 보존하고, 운영 시작 전 active developer 주체가 없는지 점검한다. 개발 주체를 비활성화하기 전에 마지막 owner인 프로젝트의 소유권을 실제 이메일 사용자에게 이전한다. 이 작업을 시작 과정에서 몰래 수행하지 않는다.

## 8. 로그아웃·폐기·동시 변경

POST /logout은 Origin/CSRF를 먼저 확인하고 현재 쿠키의 token_hash에 대응하는 세션을 폐기한다. 이미 없거나 만료·폐기된 세션이면 같은 204를 반환하고 쿠키를 지운다. 세션 쿠키가 없으면 pre-auth CSRF를 준비한 뒤 동일하게 처리한다. 다른 기기의 세션은 유지한다.

DB에 세션이 있을 수 있는데 DB 장애로 폐기 여부를 확인할 수 없으면 503 AUTH_UNAVAILABLE을 반환한다. 성공했다고 표시하거나 쿠키만 지우고 서버 폐기를 완료했다고 주장하지 않는다. 현재 AuthProvider처럼 로그아웃 실패 시 화면의 인증 상태를 유지하고 재시도할 수 있게 한다.

로그인과 비밀번호 재설정이 경합하면 사용자 행 잠금 이후 해시·활성 상태를 다시 검사한다. reset/disable이 먼저 커밋되면 이전 해시 검증 결과로 새 세션을 만들 수 없다. 새 로그인 세션이 먼저 커밋되면 뒤의 reset/disable이 그 세션까지 폐기한다. 이전 쿠키로 같은 세션을 되살리지 않는다.

세션 폐기 시 revoked_at은 최초 시각을 보존한다. expires_at을 과거로 수정하거나 세션 행을 삭제해 폐기를 표현하지 않는다. [9단계](추가설계_09_저장과이전복구.md)에서 첫 범위의 사용자·세션 행은 자동 물리 삭제하지 않기로 정했다. 복원 후에는 미폐기 세션을 모두 폐기하며 유효 세션의 삭제로 보존 정책을 구현하지 않는다.

## 9. 프로젝트별 권한

| 동작 | viewer | editor | owner | 운영 관리 경로 |
|---|---|---|---|---|
| 소속 프로젝트·기준·검수·근거 조회 | 허용 | 허용 | 허용 | 필요한 운영 점검만 |
| 권한 검사된 이미지·원문/결과 JSON 다운로드 | 허용 | 허용 | 허용 | 별도 관리 권한 |
| 활성 프로젝트의 업로드·초안 편집·기준 확정 | 거부 | 허용 | 허용 | 일반 업무 사용자로 가장하지 않음 |
| 활성 프로젝트의 검수·재검수 | 거부 | 허용 | 허용 | 일반 업무 사용자로 가장하지 않음 |
| 프로젝트 이름 변경·보관/복원 | 거부 | 거부 | 허용 | 운영 복구 절차 |
| 멤버 추가·역할 변경·탈퇴 처리 | 거부 | 거부 | 첫 범위의 웹 API에서는 거부 | 보호된 관리 명령만 |
| 이메일 계정 발급·비밀번호 재설정·계정 비활성화 | 거부 | 거부 | 거부 | 보호된 관리 명령만 |
| 전역 규격 등록·공유 범위 변경 | 거부 | 거부 | 거부 | 보호된 관리 명령만 |

인증된 활성 사용자는 새 프로젝트를 생성할 수 있고 생성자 owner를 같은 트랜잭션에서 만든다. 프로젝트 생성 전에 다른 프로젝트의 owner 역할을 요구하지 않는다. 개발 주체는 개발 프로젝트의 owner로 시작하며 다른 프로젝트의 권한을 자동으로 얻지 않는다.

보관 프로젝트는 소속 사용자의 이력 조회만 허용하고 새 업로드·편집·확정·검수·재검수는 409 PROJECT_ARCHIVED다. owner의 복원은 허용한다. 탈퇴·계정 비활성화 이후에는 과거 본인이 요청한 실행도 소속 권한 없이 조회할 수 없다. requested_by·created_by가 현재 접근 권한을 대체하지 않는다.

파일은 원 소유 프로젝트를 기준으로 검사한다. URL의 run/project UUID와 파일·기준·결과의 실제 소속을 DB에서 확인한다. .runtime 디렉터리를 정적 공개하지 않고, JSON 다운로드도 같은 검사 경로를 거친다. global service_shared 규격의 검증 사용 허용과 원본 다운로드 권한은 6단계대로 분리한다.

worker는 이미 접수한 실행을 서비스 주체로 처리한다. 요청자의 브라우저 세션이 만료되거나 프로젝트가 보관돼도 접수 당시 고정한 입력으로 마감한다. 이 정책이 새 접수·사용자 조회의 권한 우회를 뜻하지 않는다. 계정 비활성화·멤버십 변경으로 기존 실행을 자동 취소하는 기능은 첫 범위에 포함하지 않는다.

## 10. 권한 변경과 업무 저장의 트랜잭션 경계

초기 인증 의존성에서 로그인 여부를 검사하고, 실제 쓰기 트랜잭션에서도 현재 상태를 재확인한다. 긴 파일 수신·OCR·비밀번호 해시 계산 동안 DB 잠금을 유지하지 않는다.

- 프로젝트 업무의 짧은 저장은 프로젝트 → 사용자 → 세션 → 멤버십 → 업무 행 순서로 잠그고 권한을 재검증한다. 사용자·세션·멤버십에는 변경과 경합을 직렬화할 공유 잠금을 사용하며 단순한 FK용 KEY SHARE만으로 비활성화가 막힌다고 가정하지 않는다.
- 여러 프로젝트/사용자/세션은 각각 UUID 순서로 잠근다. 로그인·단일 로그아웃처럼 프로젝트가 없는 작업은 사용자 → 세션 순서만 사용한다.
- 계정 비활성화는 관련 프로젝트 목록을 먼저 구하고 프로젝트를 잠근 뒤 사용자·세션·멤버십을 확인한다. 사용자 잠금 뒤 목록을 다시 조회해 새 프로젝트가 생겼으면 롤백 후 전체 잠금 순서부터 재시도한다. 멤버 추가도 사용자 활성 검사를 같은 순서로 수행한다.
- 마지막 활성 owner를 제거·비활성화할 수 없다. 먼저 소유권을 이전해야 하며, 위반하면 409 LAST_OWNER_REQUIRED로 전체 롤백한다. 프로젝트 생성/owner 생성과 비활성화/세션 폐기도 부분 커밋하지 않는다.
- 권한 변경 커밋 전에 이미 승인·잠근 짧은 업무는 먼저 완료될 수 있다. 변경 이후의 새 승인 지점에서는 거부한다. 이미 전송을 시작한 이미지 응답의 바이트까지 되돌린다고 표현하지 않는다.

기준 확정의 project→draft, 실행 마감의 run→attempt 순서는 앞선 설계대로 유지하며 필요하면 위 공통 상위 잠금 뒤에 둔다. 구체적인 저장 함수·재시도 상한·오류 변환은 9단계에서 연결한다.

## 11. 인증 API·오류·화면 계약

| 경로 | 응답·인증 조건 |
|---|---|
| GET /api/v1/auth/csrf | 200 csrf_token. 로그인 전에도 제공, 세션/seed 결합. Cache-Control: no-store |
| POST /api/v1/auth/login | 성공 200 user·새 쿠키. email/username 분기, Origin/CSRF 필수 |
| GET /api/v1/auth/me | 정상 확인이면 200 authenticated:true/false와 user 또는 null. DB 장애를 false로 바꾸지 않음 |
| POST /api/v1/auth/logout | 성공/이미 폐기 204. Origin/CSRF 필수, DB 폐기 실패는 503 |

공개 사용자 객체는 `id` UUID·`account_kind`·`display_name`·`email`(개발은 null)만 포함한다. password_hash·세션·CSRF 서명 키·DB 역할은 포함하지 않는다. 프로젝트 role은 특정 프로젝트의 멤버십으로 별도 조회한다. 전역 role=owner/admin 같은 필드로 모든 프로젝트 권한을 표현하지 않는다.

| 상황 | 상태·코드 | 화면·클라이언트 처리 |
|---|---|---|
| 이메일 없음·비밀번호 불일치·비활성 이메일 계정 | 401 INVALID_CREDENTIALS | 동일한 이메일/비밀번호 확인 안내. 계정 존재·비활성 여부를 구분해 공개하지 않음 |
| 보호 API의 세션 없음·만료·폐기·비활성 주체 | 401 AUTHENTICATION_REQUIRED | 인증 상태 해제·로그인 이동. DB 상태로 남은 실행은 유지 |
| Origin/CSRF 실패 | 403 CSRF_FAILED | 세션 자동 삭제 금지. CSRF 재준비 후 사용자가 재시도 |
| 소속은 있지만 필요한 role 부족 | 403 PROJECT_PERMISSION_DENIED | 로그인 상태 유지·권한 안내 |
| 접근 불가 프로젝트·다른 프로젝트 파일/결과·없는 UUID | 404 RESOURCE_NOT_FOUND | 존재 여부 구분 없이 찾을 수 없음 |
| 입력 구조·길이 오류 | 422 INVALID_AUTH_REQUEST | 해당 필드 안내. 비밀번호를 서버 응답에 재출력하지 않음 |
| 시도/동시 해시 제한 | 429 AUTH_RATE_LIMITED | Retry-After와 대기 안내. 자동 로그인 반복 금지 |
| DB/필수 인증 구성 장애 | 503 AUTH_UNAVAILABLE 또는 AUTH_SETUP_REQUIRED | 연결/설정 오류. 미로그인 성공 응답으로 치환하지 않음 |

오류 객체는 프로젝트 목표의 error.code/message/fields로 통일하고 기존 FastAPI detail·현 프런트 파서 전환은 8단계에서 명시한다. 현재 code의 대소문자 정규화와 늦은 응답 무시 동작을 유지한다. 로그인은 성공 응답 뒤 me로 새 세션을 확인하고, 401과 일반 403/503을 구분한다.

프런트는 이메일 입력과 개발 계정 입력을 명시적으로 구분한다. 개발 입력은 서버가 허용한 개발 환경에서만 표시하고 실제 허용 여부는 항상 서버가 검사한다. 비밀번호·세션 토큰을 localStorage/sessionStorage에 저장하지 않는다. 로그인 후 돌아갈 주소는 허용한 내부 경로만 사용하며 외부 URL로 보내지 않는다. 구체적인 업무 URL/이력 복원은 8단계에서 확정한다.

## 12. 로그인 시도 제한과 운영 기록

| 제한 | 최초 설정·범위 |
|---|---|
| IP 기준 | 로그인 시도 30회/60초. 신뢰한 실제 peer/프록시 규칙으로 계산 |
| 정규화한 로그인 식별자 기준 | 실패 5회/15분이면 해당 식별자에 15분 냉각. 없는 이메일도 같은 규칙 |
| 해시 검증 동시성 | 프로세스당 최대 2개. 초과는 무제한 대기 대신 429 |
| 카운터 저장 | 초기 단일 웹 프로세스의 제한된 메모리, 최대 10,000개 키·TTL. 가득 차면 새 검사 제한 |
| 여러 웹 worker | 첫 구현은 단일 프로세스 TTL 카운터·웹 worker=1. 공유 제한 도입·검증 전에는 여러 웹 worker 금지 |

이 값은 초기 프로젝트 정책이며 실제 비용·접속량을 측정해 조정한다. 현재 코드에 제한이 있다는 뜻은 아니다. 메모리 카운터는 재시작 시 사라지므로 영속·다중 프로세스 제한이라고 표현하지 않는다. 영구 계정 잠금·CAPTCHA·추가 테이블을 이번 단계에 도입하지 않는다. 시도 제한의 배경은 [OWASP 로그인 제한 안내](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling)를 참고한다.

로그인 성공/실패·로그아웃·세션 폐기·설정 거부는 구조화된 보안 로그에 request_id·이벤트 종류·안전한 사유·확인된 사용자 UUID를 기록한다. 식별자 카운터 키는 서버 HMAC으로 처리하며 원문 비밀번호·세션/CSRF 토큰·해시·서명 키를 로그에 넣지 않는다.

audit_events는 project_id가 필수다. 프로젝트 없는 로그인 사건에 가짜 프로젝트를 넣지 않고 보안 로그로 남긴다. 실제 프로젝트의 멤버십 변경·보관·검수 등은 audit_events에 actor_kind=user/developer/system과 실제 actor_user_id를 기록한다. 운영 관리 명령은 운영 주체·대상·변경 전후와 관련 프로젝트를 기록하며 사용자 비활성화 전체가 롤백되면 성공 감사 이벤트도 남기지 않는다.

이번 단계는 위 사례와 문서 연결·컬럼·키·인덱스의 정적 검토다. 실제 로그인·Argon2 성능·DB 경쟁·브라우저 쿠키·CSRF 테스트는 구현 뒤 PostgreSQL/E2E로 수행한다. 현재 개발용 로그인 테스트를 새 이메일 인증의 검증 증거로 사용하지 않는다.

## 15. 변경 반영과 다음 단계

- users.account_kind 1개와 이메일/해시의 종류별 필수 조건, 개발 주체 1개 제한 인덱스를 사용자 설계·전체 정합성·제약 목록에 반영한다. 현재 범위는 26개 테이블·395개 컬럼·PK 26개·UNIQUE 41개·FK 81개·부분 유일 인덱스 2개다.
- 6단계 검토 기록은 당시 394개 컬럼의 이력으로 보존한다. [7단계 정적 기록](verification/2026-10-16-auth-design-stage7.json), [8단계 API 기록](verification/2026-10-17-api-design-stage8.json), [9단계 기록](verification/2026-10-17-storage-design-stage9.json)도 당시 이력으로 보존한다. 최신 문서 검토는 [10단계 기록](verification/2026-10-17-implementation-design-stage10.json)에 남긴다. ERD 가져오기용 SQL의 기존 email/password_hash NOT NULL은 최종 마이그레이션에서 종류별 CHECK로 대체할 변경 대상이다.
- admin/admin 개발 자격 증명을 유지하며 가짜 이메일·정식 고정 기본 비밀번호로 바꾸지 않는다. 실제 개발 UUID·프로젝트 ID·정식 계정 값은 아직 발급하지 않았다.
