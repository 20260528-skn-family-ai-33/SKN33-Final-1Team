## 2. 버전·의존성 추가 계획

C09에서 rfc8785 0.1.4·portalocker 3.2.0도 설치·검증했다. 아래는 **도입할 고정 기준**이며 설치·해결·플랫폼 성능 통과 기록이 아니다.

프런트는 현재 lock의 React/ReactDOM 19.3.0, react-router 7.18.4, Vite 7.3.7, Playwright 1.62.1과 Node 22 계열을 유지한다. 이번 설계 때문에 React/OCR/PyTorch/Paddle을 업그레이드하지 않는다. Pydantic은 v1 계약 구현 시 현재 검증 기준인 2.13.5를 직접 고정하고 FastAPI/Starlette 조합을 다시 확인한다.

C01에서 requirements-db.txt에 SQLAlchemy·psycopg[binary] 두 직접 의존성만 추가한다. Alembic은 C02에 같은 파일로 추가한다. requirements-v1.txt는 C08부터 DB 묶음과 인증 패키지, C09부터 JCS·잠금을 포함하도록 확장한다. 기존 requirements-test.txt의 offline/OCR 무다운로드 목적을 보존하고 v1/DB CI는 두 묶음을 명시적으로 설치한다. 각 OS의 실제 전이 의존성·설치 보고서와 pip check를 검증 기록에 남긴다. 직접 핀만으로 모든 전이 의존성까지 잠갔다고 표현하지 않는다.

호출은 routes → services → repositories/storage/execution 순서다. metadata/contracts/hashing은 API/worker가 공통으로 사용하되 현재 api.py의 app 초기화를 import하지 않는다. schema 모듈 import는 metadata 정의만 수행한다. 모델 가중치/외부 네트워크/환경 파일 쓰기는 실행 어댑터에서 명시적으로 수행한다.

사용자·파일·기준·run의 도메인 객체와 HTTP DTO를 분리한다. Connection 종료 뒤 lazy 조회가 일어나거나 password_hash/worker_token/storage_key가 응답으로 따라오지 않도록 allowlist DTO로 투영한다. JSON 안의 ID와 관계 컬럼의 실제 문맥은 저장 서비스가 대조한다.

프런트는 api/auth·프로젝트·이미지·초안·기준·검수 클라이언트, 서버 리소스 상태와 미저장 편집 상태, URL 복원·pending 요청 키를 분리한다. 기존 결과 컴포넌트는 새 결과/근거 지연 조회 어댑터를 통해 사용한다. 서버 결과와 브라우저에서 추정한 실패를 같은 상태로 덮어쓰지 않는다.

## 4. 동기 Connection·스레드·트랜잭션

Engine/연결 pool은 프로세스별 하나, Connection은 서비스 호출/트랜잭션마다 하나다. Connection을 글로벌·요청 간·스레드/프로세스 간 공유하지 않는다. 독립 worker는 자기 Engine을 만들고 웹이 열어둔 연결을 전달받지 않는다. [Engine/Connection 안내](https://docs.sqlalchemy.org/en/21/core/connections.html)

| 항목 | 최초 값·행위 |
|---|---|
| 드라이버/격리 | postgresql+psycopg, READ COMMITTED |
| pool | 웹 pool_size=5·max_overflow=0·pool_timeout=5초·pool_pre_ping=true |
| worker pool | 프로세스당 2·overflow=0. 프로세스 수와 합산 DB 연결 예산 확인 |
| 연결 | connect_timeout=5초, UTF-8, timezone UTC 확인 |
| 짧은 쓰기 | 9단계 lock_timeout=2초·statement_timeout=10초를 SET LOCAL로 적용 |
| 수입 | 최종 저장 statement_timeout=60초. 한도 초과를 부분 완료로 처리하지 않음 |
| 종료 | 예외 시 확인 가능한 rollback·Connection 반환, 프로세스 종료 때 Engine dispose |

SQLAlchemy pool만 사용하고 psycopg_pool을 겹쳐 두지 않는다. pre_ping은 낡은 연결 확인이며 실행 중 COMMIT의 결과 미확인을 해결하지 않는다. DB 오류 SQLSTATE와 저장 단계·서버 응답을 함께 분류하고 모든 OperationalError를 rollback 확정으로 바꾸지 않는다. [pool 안내](https://docs.sqlalchemy.org/en/21/core/pooling.html)

동기 def 경로는 서비스를 같은 실행 스레드에서 완료한다. async 업로드는 파일 수신을 await하고 DB 구간 전체를 하나의 run_in_threadpool 호출 안에서 열고 사용하고 닫는다. Depends/yield에서 만든 Connection을 서로 다른 스레드로 넘기거나 여러 threadpool 호출 사이에서 보관하지 않는다. 파일/Argon2/OCR 중 DB 잠금 유지 금지, repository 내부 commit 금지다.

명시적 UoW가 최종 성공을 확인한 뒤 HTTP 성공을 만든다. deferred constraint 오류도 commit 오류로 수집한다. 40001/40P01처럼 rollback 확인 가능한 충돌은 9단계 한도 안에서 같은 입력 저장만 재시도한다. 커밋 미확인·유료 원격 제출 미확인에서는 새 키/새 추론 대신 확인 경로로 전환한다. 정렬된 project/user/session/member·run/attempt·storage 잠금 순서는 앞선 계약을 그대로 사용한다.

## 5. 마이그레이션 순서와 권한

모든 revision은 빈 격리 DB에서 시작해 owner로 실행한다. 중간 revision은 작업용 상태이며 v1 쓰기를 공개하지 않는다. metadata.create_all·autogenerate 결과만으로 물리 제약/트리거가 완성됐다고 보지 않는다. Alembic autogenerate는 검토용 후보이며 명시적 CHECK·복합 FK·부분 인덱스·봉인 함수/트리거·컬럼별 GRANT는 따로 검토한다. [Alembic 안내](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)

| revision | 대상·순서 | 누적 업무 테이블 |
|---|---|---:|
| M001 identity | 먼저 owner의 app 기본 테이블 DML 권한을 회수. users/user_sessions/projects/project_members의 컬럼·PK/UQ/CHECK | 4 |
| M002 files | assets/asset_versions/stored_files/image_coordinate_frames/record_aliases | 9 |
| M003 OCR | schema_definitions/import_packages/audit_events/ocr_runs/ocr_tokens/poster_extractions/poster_field_observations/evidence_records/evidence_ocr_tokens | 18 |
| M004 criteria | criteria_sets/criteria_drafts/criteria_versions/criteria_items | 22 |
| M005 reviews | review_runs/review_attempts/item_results/run_item_selections | 26 |
| M006 relations | 전체 테이블 존재 후 81개 이름 있는 FK를 RESTRICT·즉시 검사·MATCH SIMPLE로 생성 | 26 |
| M007 guards | 일반 인덱스 25개·부분 유일 2개·30개 검증 규칙의 함수/실제 트리거 인스턴스 | 26 |
| M008 grants | 앱 DELETE/DDL·불변 테이블 UPDATE 회수, 컬럼별 UPDATE·readonly/insert/seal 권한·최종 inventory 점검 | 26 |

초기 M001~M005는 컬럼·PK/UQ/CHECK를 생성하고 FK를 M006에서 명시적으로 추가한다. 중간 데이터를 넣기 위해 FK를 껐다 켜는 방식이 아니다. 빈 DB→head의 기본 실행은 PostgreSQL transactional DDL 안에서 전체 성공/실패를 구분한다. partial revision을 수동 적용한 DB는 readiness가 거부한다. 최초 head 외의 자동 downgrade는 제공하지 않으며 업무 데이터가 생긴 뒤는 9단계 보존/복원 절차를 따른다.

현재 init 스크립트는 owner가 앞으로 만드는 테이블에 app의 SELECT/INSERT/UPDATE/DELETE를 기본 부여한다. 따라서 M001의 기본 권한 회수와 M008의 명시적 재부여가 필수다. owner는 NOSUPERUSER/NOCREATEROLE인 기존 역할을 유지하고 앱이 owner의 멤버가 아니어야 한다. 첫 웹·worker는 기존 creative_checker_app 역할을 사용하며 별도 worker 최소 권한 역할을 이미 제공한다고 주장하지 않는다. 관리 명령·복원은 별도 보호된 owner/관리 연결만 사용한다.

완료 검사는 이름 수만 보지 않고 테이블/컬럼 자료형·NULL/default, PK/UQ/FK 컬럼 순서·정책, CHECK 조건, 인덱스 predicate/order, 트리거의 대상/시점/지연/함수와 컬럼 권한을 대조한다. 30개 규칙 중 여러 테이블에 적용되는 것은 실제 인스턴스를 모두 검사한다. Alembic revision·함수 정의 지문과 업무 schema inventory를 검증 기록에 함께 남긴다. C07c에서 별도 읽기 전용 CLI·계약을 구현했으며 API 시작 점검도 C08의 새 main에서 연결했다.

## 6. 계정·seed·시작/정지 순서

| 순서 | 행위 |
|---|---|
| DB 준비 | 이미 있는 Compose/볼륨·owner/app 연결을 확인. 기존 볼륨을 초기화해 비밀번호를 바꾸지 않음 |
| upgrade | owner 연결로 검토한 head까지 적용. 앱 자동 실행/seed 없음 |
| 관리 계정 발급 | 실제 이메일·표시명·보호된 비밀번호 입력. UUID/Argon2 인코딩, 평문 로그 없음 |
| 개발 초기화 | development/test·LOCAL_ADMIN_LOGIN=1에서 명시 명령. developer UUID·DEV_PROJECT_ID·owner 원자적 생성/재사용 |
| preflight | schema/권한·설정/비밀·저장소 capability·역할·모델/실행 설정·누락/복구 상태 검사 |
| 서비스 | 초기 웹 1프로세스·서비스 잠금·시작 복구 후 readiness. 그 뒤에만 업무 요청 접수 |
| 독립 worker | 명시 프로필에서 별도 시작. executor_kind별 큐·lease·종료 처리 |
| 정지 | 접수 차단→인수 중지→짧은 확정 마감/진단→연결/잠금 반환. 원격 완료를 추정하지 않음 |

개발 계정의 email/password_hash=NULL, 정식 email 계정의 실제 값 필수 CHECK와 부분 유일 인덱스를 유지한다. admin/admin을 정식 사용자 비밀번호로 시드하거나 앱 시작 때 비활성 개발 주체를 되살리지 않는다. 세션은 난수 원문 대신 DB 해시·절대 만료/폐기를 사용한다.

Argon2id는 memory_cost=19456 KiB·time_cost=2·parallelism=1을 명시하고 라이브러리 기본값에 맡기지 않는다. 코드포인트 15~128·정규화 금지·더미 해시·동시 해시 최대 2개·식별자/IP 제한은 7단계를 따른다. 현재 비용 이상인 해시를 더 낮은 설정으로 재해시하지 않는다. email-validator는 ASCII 선검사·allow_smtputf8=false·check_deliverability=false로 외부 DNS 없이 형식만 검사하며 최종 저장 식별자는 7단계 lower/trim 정책이다.

로그인 제한은 별도 외부 패키지 없이 단일 웹 프로세스의 잠금으로 보호한 TTL 카운터로 구현한다. monotonic 시계, IP 30회/60초·식별자 실패 5회/15분 후 15분 냉각, 전체 최대 10,000개 키·가득 차면 신규 검사 429를 적용한다. 식별자는 CSRF_SECRET에 용도 문자열 cc-auth-limit-v1과 식별자 종류를 결합한 HMAC-SHA256 키로 관리하고 원문을 보안 로그에 남기지 않는다. Redis/다중 웹 프로세스의 공유 제한은 첫 범위에 포함하지 않는다. 첫 v1에서 AUTH_SESSION_SECONDS=28800·AUTH_CSRF_SECONDS=900·AUTH_MAX_CONCURRENT_HASHES=2만 허용하며 다른 값은 구성 오류로 거부한다. 이후 변경은 비용 측정과 세션/토큰 영향 검토를 함께 한다.

JCS는 새로 만든 자체 serializer 대신 rfc8785를 사용한다. 서비스의 strict 숫자/문자/중복 키 검사 뒤 canonical bytes를 얻고 8·9단계 30개 지문 예제, 누락/null·UTF-16 순서·숫자 경계와 RFC 규격 예제를 실제 라이브러리로 대조한다. PyPI 버전 확인이나 기존 임시 검산 함수의 통과가 라이브러리 실행 검증을 대신하지 않는다.

첫 C01은 신규 설정/연결 함수만 추가한다. 기존 api:app·run.sh/run.cmd·LOCAL_ADMIN_LOGIN 동작을 바꾸지 않는다. v1 main app factory와 launcher 연결은 C08/C12의 별도 작업이며, 그때 production+legacy_json·production+개발 활성·schema 미완성은 시작 오류로 거부한다. 기존 로컬 프로필을 유지하는 것과 운영에서 구형 무권한 API를 허용하는 것은 구분한다.

개발 Vite/server/preview는 127.0.0.1 바인딩·strictPort=true, 명시 localhost Host/origin으로 고정한다. /api proxy는 로컬 backend만 대상으로 changeOrigin=false·xfwd=false를 사용하고 API 개발 프로필은 Uvicorn proxy headers를 해석하지 않는다. 전달된 Forwarded/X-Forwarded-* 헤더가 있으면 개발 인증을 거부한다. Vite의 Host 기본 예외(IP/.localhost 등)만으로 서버의 개발 권한을 결정하지 않고 API가 정확한 Host·실제 peer·Origin/Referer를 다시 확인한다. [Vite 7 서버 설정](https://v7.vite.dev/config/server-options)

운영은 같은 HTTPS origin의 React/API이며 앞단 프록시가 외부 forwarded 헤더를 제거·재설정한다. Uvicorn의 신뢰 proxy 주소를 명시하고 X-Forwarded-For/Proto만 정한 배포 경로에서 해석한다. 와일드카드 신뢰·개발 계정 원격 제공은 금지한다. 운영 Secure/__Host 쿠키 검증은 HTTPS 브라우저 프로필에서 수행하며 HTTP 개발 테스트로 대체하지 않는다. [Uvicorn 설정](https://uvicorn.dev/settings/)

최초 운영 저장소 검증 대상은 **단일 Linux 호스트의 로컬 파일시스템**이다. 현재 macOS는 개발·DB/기능/잠금 검증 대상, Windows는 기존 launcher/offline 및 DB 연결 검증을 유지한다. macOS/Windows의 v1 파일 내구성·공유 잠금·디렉터리 동기화까지 통과하기 전에는 해당 OS를 운영 저장 프로필로 인증하지 않는다. 기능 동작과 전원/프로세스 장애 후 내구성 보장을 구분하며 조용히 안전 기능을 끄지 않는다.

Linux 파일 구현은 Python 표준 os/stat의 루트 dir_fd·O_NOFOLLOW·fstat로 디렉터리/일반 파일·장치/inode·링크 수를 확인한다. 같은 저장 볼륨에서 O_CREAT|O_EXCL staging 작성→파일 fsync→기존 목적지를 덮어쓰지 않는 hard-link 게시→부모 디렉터리 fsync→staging 이름 제거/동기화를 사용한다. 입력 하드 링크는 거부하며 게시 중 자신이 만든 일시적 링크는 저널의 같은 inode/작업으로 식별한다. 기존 목적지가 있으면 동일 바이트/소유권을 검증하거나 충돌로 중단하고 replace로 덮어쓰지 않는다. 플랫폼별 실제 capability와 장애 후 결과는 C09/C14에서 검증하며, 이 문서만으로 내구성 통과를 선언하지 않는다.

실행 진입점은 후속 C08의 python -m backend.app.management <관리 명령>과 uvicorn backend.app.main:create_app --factory --host 127.0.0.1 --port 8000 --workers 1 --no-proxy-headers, C13의 python -m backend.app.worker를 기준으로 한다. C08의 계정 관리와 main app factory는 [C08 기록](구현_C08_인증과계정관리.md)에서 구현·실행 검증했다. worker 진입점은 [C13 기록](구현_C13_독립Worker와회수.md)에서 구현·검증했다. 운영 launcher는 허용 origin·TLS 프록시·신뢰 주소와 APP_ENV를 명시하고 owner 비밀을 웹/worker 환경에 전달하지 않는다.

## 8. 실제 테스트 환경·계층

SQLite·mock DB로 PostgreSQL의 JSONB/NULLS NOT DISTINCT/부분 인덱스·잠금·deferred trigger를 통과했다고 판단하지 않는다. 단위 테스트는 변환/정책을 빠르게 확인하고 DB/파일/브라우저 보장은 해당 실제 계층에서 검증한다.

| 계층 | 실행 대상·증거 |
|---|---|
| 단위/정적 | strict DTO·해시 payload·상태 분류·경로 검증. DB/OCR/네트워크 없는 오류/정책 검사 |
| PostgreSQL 통합 | 별도 DB의 owner/app, 실제 17 서버, commit/rollback·락 경합·제약·권한·재시작 |
| 파일/프로세스 통합 | 임시 전용 STORAGE_ROOT, 하위 프로세스·barrier로 확정/GC/죽은 프로세스 뒤 commit 경합 |
| API 통합 | 실제 v1 app + PostgreSQL + 파일 저장소, OCR은 명시한 결정적 test adapter |
| 브라우저 E2E | Playwright의 고정 Chromium, 실제 API/DB. HTTP 개발/HTTPS 운영 cookie·CSRF·복원 별도 |
| 실제 OCR | 선택 pipeline/장치/모델별 별도 실행 기록. test adapter 통과와 구분 |
| 백업/복원 | 별도 DB/루트·실제 dump/restore·해시/봉인/권한/세션 폐기·시간 측정 |

DB 테스트는 전용 PostgreSQL service/container의 임의 이름 creative_checker_test_<run UUID>를 사용한다. 테스트 시작에 명시 test 표식·DB명·대상·권한을 검사하고 일반 creative_checker DB를 거부한다. 생성/삭제는 테스트 관리 연결만, 업무 동작은 실제 app 역할로 수행한다. 테스트 스크립트가 .env의 운영/일상 DB로 자동 fallback하지 않는다. C01의 테스트용 probe schema/table은 owner가 만들고 검증 뒤 해당 테스트 DB 안에서만 정리한다. 이는 26개 업무 schema 구현이 아니다.

경쟁 테스트는 독립 Connection/프로세스와 barrier로 순서를 제어하고 단순 sleep 성공에 의존하지 않는다. 강제 종료·네트워크/COMMIT 장애 주입은 격리 DB/worker에서만 수행한다. file GC는 temp root 밖 경로가 들어가면 테스트 자체가 중단되도록 한다. 실제 RunPod·외부 모델 다운로드·유료 추론은 기본 CI에 넣지 않는다.

pytest 마커는 db_integration/filesystem/e2e/ocr_external로 구분하고 등록한다. 기본 offline job은 기존 범위를 유지한다. DB job에서 db_integration을 선택했는데 전용 DB나 드라이버가 없으면 실패로 처리하며 모두 skip된 결과를 성공 DB 검증으로 보고하지 않는다. 실제 OCR 프로필의 미실행은 not_run/해당 배포 프로필 비활성으로 남긴다.

기존 CI에 PostgreSQL/v1 API·브라우저·Linux 파일 장애 job을 추가하고 path filter에 migration/새 requirements/필요 설정을 포함한다. Python 3.12와 Node 22 기준을 유지하며 Chrome channel의 자동 변화 대신 Playwright 고정 Chromium을 사용한다. 테스트 TLS 인증서/키는 임시 테스트 전용으로 만들고 운영 인증서를 가져오지 않는다. 실제 도구·브라우저 revision·OS·실행 명령/종료 코드·artifact를 보고한다.

| IMPL-06 | schema | 26/395와 모든 키·조건·트리거 인스턴스·revision 일치 |
| IMPL-07 | migration | 빈 DB→head·실패 롤백·부분 head readiness 거부·자동 seed 없음 |
| IMPL-08 | DB 권한 | app DDL/DELETE/불변 UPDATE 거부·허용 컬럼 동작·owner 미노출 |
| IMPL-09 | 계정 관리 | 실제 입력/UUID·Argon2 설정·개발 초기화 재사용/동시성 |
| IMPL-10 | 실행 프로필 | BackgroundTasks 단일 서비스·다른 executor 큐 혼용 없음 |
| IMPL-11 | JCS | 실제 선택 라이브러리와 30개 기존 벡터·규격 경계 일치 |
| IMPL-12 | 저장소 capability | 공유/배타/비차단·fsync/rename·OS별 결과, 미검증 운영 차단 |
| IMPL-13 | dev proxy | 직접/Vite·Origin/Host/forwarded 위조·원격 요청 모두 검증 |
| IMPL-14 | 운영 HTTPS | __Host/Secure·SameSite/CSRF·신뢰 프록시·개발 계정 비활성 |

최종 운영 공개는 선택한 배포 프로필의 필수 DB/AUTH/API/STORE/IMPL 사례가 실제 검증되고, 풀/권한/스키마·파일 capability·복원 훈련·실행 준비 상태가 확인된 경우다. 성능/RPO/RTO·모델 정확도·GPU 지원은 실제 측정한 값만 보고한다. 본 단계의 완료는 이 **검증 명세 확정**이며 운영 공개 완료가 아니다.

## 10. 한 번에 하나씩 진행할 코드 작업

## 11. C01의 구체적 완료 기준

C01의 파일 범위는 config.py, persistence/__init__.py·database.py·transaction.py, requirements-db.txt, 전용 DB 연결 테스트/점검 명령, 필요한 .env.example와 실행 문서다. 기존 api.py/local_auth.py·React·OCR·compose 볼륨·업무 이력에는 연결 변경을 하지 않는다. metadata/마이그레이션/사용자·세션 테이블·로그인 기능은 C02 이후다.

1. 기존 .env의 DB_HOST/PORT/POSTGRES_DB/APP 이름을 재사용하고 PERSISTENCE_MODE가 꺼져 있으면 DB 없이 새 모듈을 읽을 수 있다. 비밀이 없는 안전한 설정/점검 결과만 노출한다.
2. 명시적으로 켠 DB 모드에서 잘못된 포트·누락 비밀·owner를 app 사용자로 지정하는 구성을 거부하고 SQLAlchemy URL.create로 비밀번호 특수문자를 보존한다.
3. 실제 PostgreSQL에 app 역할로 접속해 SELECT 1·current_user·UTC·서버 버전과 연결 닫힘을 확인한다. 값을 로그에 출력할 때 DSN/비밀번호는 제외한다.
4. 격리 test DB의 owner가 만든 probe에서 app의 commit·의도한 예외 rollback·실패 뒤 새 연결 재사용을 검증한다. probe는 업무 테이블이 아니며 대상/정리를 test DB 밖으로 확장하지 않는다.
5. DB 모드 오류는 명확한 설정/연결 예외로 전달하고 JSON 저장·다른 DSN·owner로 조용히 우회하지 않는다. 기존 API/개발 로그인 offline 회귀를 확인한다.
6. 실제 설치 버전·명령·DB 대상의 안전한 식별 정보·실행한 테스트/미실행 항목을 기록하고 **C01만** 완료로 보고한다. 실제 통합 검증이 막혔으면 정적 검사를 접속/롤백 성공으로 바꾸지 않는다.

DB 통합 테스트는 C01에서 새 테스트 DB·그 안의 임시 probe만 변경한다. 일상 creative_checker 업무 테이블·계정 seed·파일 이력은 생성/이전/삭제하지 않는다. 이 작은 연결 단위를 검토한 뒤 다음 마이그레이션 작업으로 넘어간다.
