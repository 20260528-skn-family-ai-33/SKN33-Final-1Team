# C07c — M008 권한과 최종 스키마 점검

작성일: 2026-10-18

상태: **C07c 구현·격리 PostgreSQL 검증 완료. 정식 Alembic head는 M008이다. 이후 [C08](구현_C08_인증과계정관리.md)도 완료했으며 [C09 — 파일 저장과 기준 확정](구현_C09_파일저장과기준확정.md)도 완료했으며 [C10 — 검수 접수와 원자적 결과](구현_C10_검수접수와원자적결과.md)도 완료했으며 다음은 C11이다. 아래는 C07c 시점의 기록이다.** 첫 범위의 DB 구조와 앱 역할 권한을 완성했다. 일상 DB에는 적용하지 않았고 기존 admin/admin·JSON API·React·OCR·launcher는 유지한다. HTTP 인증과 프로젝트별 접근 통제는 C08 이후의 별도 구현이다.

## 2. 앱 역할의 최소 권한

기준은 [전체 정합성 설계의 컬럼 정책](물리설계_06_전체정합성.md#6-불변성과-상태-전이의-강제-방식)이다.

| 대상 | M008 이후 허용 |
|---|---|
| 업무 테이블 26개 | 모두 SELECT |
| schema_definitions | SELECT만. 전역 규격 등록·변경은 관리 연결 책임 |
| 나머지 업무 테이블 25개 | SELECT·INSERT |
| 수정 가능한 테이블 14개 | 설계에 열거된 **82개 컬럼만 UPDATE**. 테이블 전체 UPDATE 없음 |
| 추가 전용 테이블 11개 | UPDATE 없음. 자식 추가도 M007 가드가 부모 봉인·문맥 검사 |
| 모든 업무 테이블 | DELETE/TRUNCATE/REFERENCES/TRIGGER/MAINTAIN 및 grant option 없음 |
| alembic_version | SELECT만. 앱의 migration 버전 변경 금지 |
| 가드 함수 19개 | 호출되는 보조 함수 14개만 EXECUTE. 트리거 진입 함수 4개와 관리용 cc_schema_files는 직접 실행 불가 |
| public schema·현재 DB | schema USAGE·DB CONNECT. schema/DB CREATE·TEMPORARY 없음 |
| owner의 미래 객체 | 전역·public의 TABLES/SEQUENCES/FUNCTIONS에 app/PUBLIC 자동 부여 없음 |

테이블 권한 회수만으로 기존 컬럼 ACL이 사라지지 않으므로 모든 기존 컬럼 권한도 먼저 회수하고 82개를 명시적으로 부여한다. 권한은 더해서 적용되므로 넓은 UPDATE나 PUBLIC 권한을 남겨두지 않는다. [PostgreSQL GRANT](https://www.postgresql.org/docs/17/sql-grant.html)

함수는 기존 SECURITY INVOKER·VOLATILE·고정 search_path를 유지한다. installed trigger 실행에 진입 함수의 앱 직접 EXECUTE를 열 필요가 없다는 점은 실제 앱 그래프 커밋으로 확인했다. 보조 함수가 사용하는 행 잠금은 허용된 컬럼 UPDATE 권한으로 실행된다. [트리거 생성 권한](https://www.postgresql.org/docs/17/sql-createtrigger.html)·[SELECT 행 잠금 권한](https://www.postgresql.org/docs/17/sql-select.html)

DB의 app 역할은 웹/worker가 공유하는 서비스 주체다. 이 권한이 로그인 사용자별 프로젝트 접근 통제를 대신하지 않는다. 다른 프로젝트의 존재하는 ID를 섞는 것은 복합 FK로 거부하지만, 어떤 사용자가 해당 프로젝트를 읽거나 쓸 수 있는지는 C08/API에서 검사해야 한다. owner/superuser의 관리 DDL까지 금지하는 설계도 아니다.

## 3. 최종 inventory와 읽기 전용 점검

| 업무 객체 | 개수 |
|---|---:|
| 업무 테이블 / 컬럼 | 26 / 395 |
| PK / UNIQUE / CHECK / FK | 26 / 41 / 77 / 81 |
| 추가 인덱스 | 27 = 조회 25 + 부분 유일 2 |
| 업무 인덱스 전체 | 94 = PK/UQ 지원 67 + 추가 27 |
| 검증 규칙 이름 / 실제 트리거 | 30 / 35 |
| BEFORE / 지연 AFTER ROW 트리거 | 17 / 18 |
| PL/pgSQL 함수 | 19 |

도구 테이블 alembic_version을 포함하면 관계 27개·컬럼 396개·인덱스 95개다. pg_constraint에는 업무 제약 225개, 도구 PK 1개와 제약 트리거 18개가 있어 **244행**이다. 244를 업무 FK/CHECK 수로 해석하지 않는다.

점검은 M008 revision 한 줄, 테이블/컬럼 자료형·NULL/default·생성 속성·collation, PK/UQ/FK/CHECK의 전체 정의·정책·지연/검증 플래그, 인덱스 정의·정렬·predicate·유효성, 트리거 대상/이벤트·지연·활성 상태, 함수 본문/설정/소유자·타입·RLS/정책 및 앱/PUBLIC/default ACL을 비교한다. OID·역할 이름·업무 행은 계약에서 제외하고 소유자가 현재 DB owner인지 비교한다. 새로운 DB 이름에도 같은 계약을 사용한다.

독립 설계에서 권한 기대값을 만들고 실제 값과 대조했다. 구조는 frozen M001~M007에서 만든 격리 DB를 캡처한 뒤 현재 metadata·설계의 FK/인덱스/트리거 목록·고정 함수 본문과 별도로 대조했다. 테스트가 실행 때 현재 DB를 정답으로 다시 저장하는 방식은 제공하지 않는다. source hash는 정적 회귀 검증용이며 runtime은 패키지의 검토된 계약을 신뢰한다. PostgreSQL 카탈로그 표현을 사용하므로 다른 major 버전으로 바꾸려면 계약 재검토가 필요하다.

check_schema는 제한된 앱 identity를 다시 확인하고 REPEATABLE READ·READ ONLY에서 일관된 카탈로그 스냅샷을 읽는다. 실제 점검에서 쓰기 transaction ID가 배정되지 않았음을 확인했다. 정상 결과는 schema_ready/revision/개수/구조 SHA256만 반환한다. 비교 실패 때 자동 수정하지 않는다.

| 오류 | 의미 |
|---|---|
| DB_SCHEMA_CONTRACT_INVALID | 패키지 계약 파일 누락·오류 |
| DB_SCHEMA_INCOMPLETE | 버전을 읽을 수 있지만 M008 한 줄이 아님 |
| DB_SCHEMA_UNREADABLE | 빈 DB·필수 객체 누락·필수 조회 권한 부족 등으로 검사 불가 |
| DB_SCHEMA_DRIFT | revision은 맞지만 구조/함수/트리거 등이 계약과 다름 |
| DB_PRIVILEGES_INVALID | 구조는 맞지만 앱/PUBLIC/default 권한이 계약과 다름 |
| DB_ROLE_REJECTED | 예상 앱 역할·DB와 다르거나 높은 역할 권한을 가진 연결 |

M001~M007은 앱의 alembic_version SELECT 자체가 닫혀 있어 앱 점검에서 UNREADABLE로 거부된다. owner 관찰에서는 같은 상태를 INCOMPLETE로 확인했다. 이 차이를 자동 업그레이드의 근거로 사용하지 않는다. API app factory·health·운영 시작 거부 연결은 C08에서 진행한다.

## 4. 검증 결과와 적용 절차

- 기본 Python **441 passed, 7 subtests passed**. C07c 정적 검사 8개를 추가했다.
- 실제 PostgreSQL **1,093 passed**. 기존 회귀 984개와 C07c 109개다.
- 실제 앱 계정으로 합성 이메일 사용자·프로젝트·파일/OCR/기준/근거·최종 채택까지 COMMIT했다. 비밀번호 해시는 테스트 문자열이며 인증 구현이나 실제 파일/OCR 실행은 아니다.
- 14개 mutable 테이블에서 실제 행 수정과 제약 검증, 모든 불변 컬럼의 UPDATE 및 모든 업무 테이블의 DELETE/TRUNCATE 거부를 확인했다. 봉인된 행은 허용 컬럼의 같은 값 UPDATE도 23514로 거부됐다.
- 미봉인 OCR의 실제 COMMIT 실패에서 부모·토큰·감사 행이 함께 롤백됐다. 앱의 두 owner 강등 경합은 하나만 성공했고, 늦은 결과 저장은 실제 잠금 대기를 관찰한 뒤 봉인을 읽고 거부됐다.
- M008 끝 오류에서 기존 행·객체 OID/정의·컬럼/테이블/함수/schema/DB/default ACL·revision이 모두 보존됐다. 정상 적용은 넓은 권한만 축소하고 행/가드 정의는 유지했다. 재요청은 변화가 없고 downgrade는 거부했다.
- 기본값·타입·NULL·collation·CHECK/FK 정책·인덱스 정렬/predicate·함수 본문/권한·트리거 활성·RLS·추가 객체·ACL 변조를 거부했다. 미래 owner 테이블/시퀀스/함수도 실제 앱 연결에서 접근이 거부됐다.
- 일상 DB의 public 관계/OID·기본 ACL은 전후 동일하며 무작위 테스트 DB를 모두 정리했다. 보호 기준 파일 70개, 과거 증거와 설계 계획의 해시를 보존했다.

기본 및 실제 DB 회귀 검증 명령은 기존과 같다. DB 테스트는 [C01의 명시적 TEST_DB_* 설정](구현_C01_DB연결과트랜잭션.md#4-전용-postgresql-테스트-실행)을 사용하고 업무 DB 이름을 테스트 대상으로 받지 않는다.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest -m db_integration -q
```

별도의 관리 환경에서 검토한 마이그레이션을 적용한 뒤 앱 전용 환경으로 스키마 점검을 실행한다. 아래는 **후속 환경 적용 절차**이며 이번에 일상 DB에서 실행한 명령이 아니다. 설정 파일에는 각 역할에 필요한 연결 설정만 전달한다. 비밀번호는 명령행에 넣지 않는다.

```bash
CC_MIGRATION_ENV_FILE=/absolute/path/to/owner.env .venv/bin/python -m alembic -c backend/migrations/alembic.ini upgrade head
.venv/bin/python -m scripts.check_schema --env-file /absolute/path/to/app.env
```

성공 시 종료 코드 0과 schema_ready를 출력하며 실패는 안전한 code/message와 종료 코드 1이다. --env-file은 명시적 선택이고 프로세스 값이 우선한다. PERSISTENCE_MODE=postgres가 필요하다. 점검 import만으로 DB를 열거나 일상 .env로 조용히 우회하지 않는다.

macOS/Python 3.12.14·PostgreSQL 17.11에서 검증했고 새 패키지는 설치하지 않았다. 파일 저장소 내구성·실제 JSON 정규화/해시·HTTP/CSRF·브라우저·실제 OCR·토큰 인수/worker·backup/restore는 후속 범위다. [대응표](검증_C07c_DB01-18_대응표.md)에 이 경계를 남겼다.
