## 2. 1~3단계: Docker DB부터 준비하기

### 1단계 — Docker 엔진 실행 확인

최초 문서 수립 시에는 Docker 엔진에 연결되지 않았지만, 2026-10-16 실제 검증에서는 엔진 연결과 DB 컨테이너의 `running`·`healthy` 상태를 확인했다. 다른 환경에서 준비하거나 다시 작업할 때는 상태를 재확인한다.

Docker Desktop을 실행한 뒤 다음 명령으로 확인한다.

```bash
docker --version
docker compose version
docker info
```

**완료 기준:** `docker info`에서 서버 정보가 정상적으로 출력된다.

### 2단계 — 프로젝트에 DB 실행 설정 추가

프로젝트 루트의 `compose.yaml`, `.env.example`의 DB 항목, `docker/postgres/init/01-create-roles.sh`가 준비되어 있다. 2026-10-16 실제 DB에서 owner·app 계정과 스키마 권한·기본 테이블/시퀀스 권한이 적용된 것을 확인했다.

| 설정 | 적용 내용 |
|---|---|
| 서비스 이름 | `db` |
| 이미지 | `postgres:17.11-bookworm` |
| 포트 | `127.0.0.1:5432:5432` |
| 데이터 보존 | 이름 있는 볼륨 `pgdata` |
| 볼륨 연결 위치 | `/var/lib/postgresql/data` |
| 상태 확인 | `pg_isready`를 이용한 healthcheck |
| 재시작 정책 | `unless-stopped` |
| 문자 인코딩·시간 | UTF-8·UTC |

PostgreSQL 17의 데이터 볼륨은 위 경로에 연결한다. 초기 계정·DB 생성 설정은 **데이터 디렉터리가 비어 있을 때 적용**되므로, 이후 테이블 변경은 Alembic으로 처리한다. [공식 이미지의 초기화·볼륨 안내](https://hub.docker.com/_/postgres)

계정은 다음처럼 구분한다.

- `postgres`: 최초 DB·계정·권한 설정
- `creative_checker_owner`: 테이블 생성·변경을 수행하는 마이그레이션 계정
- `creative_checker_app`: FastAPI에서 사용하는 데이터 조회·저장 계정

비밀번호는 로컬 환경변수 파일로 관리하고, 저장소에는 설정 이름과 예시만 남긴다.

**완료 기준:** DB 실행 설정과 계정별 접속 설정을 팀원이 동일하게 준비할 수 있다.

### 3단계 — 컨테이너 실행·접속·보존 확인

설정 파일을 준비한 다음 프로젝트 루트에서 실행할 순서다.

```bash
docker compose config --quiet
docker compose up -d --wait db
docker compose ps
docker compose logs --tail=50 db
```

`--wait`는 서비스가 실행되거나 healthcheck를 통과할 때까지 기다리는 옵션이다. [Docker Compose 실행 옵션](https://docs.docker.com/reference/cli/docker/compose/up/)

이후 애플리케이션 계정으로 접속해서 다음을 확인한다.

- 실제 DB 접속 및 `SELECT 1` 성공
- DB 이름·사용자·UTC 설정 확인
- 임시 데이터 저장 후 컨테이너 재시작
- 재접속했을 때 데이터 유지

**완료 기준:** 컨테이너 실행뿐 아니라 실제 접속과 데이터 보존까지 확인된다.

**2026-10-16 검증 결과: 통과**

업무 테이블 생성 전에 검증할 수 있도록 owner 계정으로 고유한 이름의 일반 테스트 테이블을 만들었다. 앱 계정으로 TCP 비밀번호 인증 후 데이터를 커밋하고, 재시작·재생성 뒤 같은 행을 다시 읽었다. 검증 후 owner 계정으로 테스트 테이블과 연결된 identity 시퀀스를 정리했다.

| 확인 항목 | 실제 결과 |
|---|---|
| 앱 계정 접속 | `creative_checker` DB에 `creative_checker_app`으로 접속 성공 |
| 권한 분리 | 앱의 `public` 스키마 CREATE 권한은 없음. owner가 만든 테스트 테이블의 SELECT·INSERT·UPDATE·DELETE 권한은 있음 |
| 저장·조회·수정·삭제 | 앱 계정으로 모두 성공. 자동 증가 identity 시퀀스를 이용한 INSERT도 성공 |
| 롤백 | 별도 트랜잭션에 넣고 롤백한 행이 조회되지 않음 |
| 시간대 | 앱 접속에서 `UTC` 확인 |
| 컨테이너 재시작 | 같은 컨테이너가 재시작된 뒤 커밋한 행 유지 |
| 컨테이너 재생성 | 컨테이너 ID가 변경되고, 같은 이미지·이름 있는 볼륨에서 같은 행 유지 |
| 데이터 볼륨 | `skn33-final-1team_pgdata` 유지 |
| 정리 결과 | 테스트 전후 `public` 테이블 목록이 동일하게 빈 목록임 |

컨테이너 재시작·재생성에는 다음 명령을 사용했다. 각 작업 후 `healthy` 상태와 앱 계정 재접속·데이터 일치를 확인했다.

```bash
docker compose restart --timeout 30 db
docker compose up -d --wait --wait-timeout 60 --force-recreate --pull never --no-deps db
```

원시 확인값은 [1~3단계 검증 기록](verification/2026-10-16-postgres-stage3.json)에 남겼다. 테스트용 일반 테이블은 이 검증에서만 사용했으며, 26개 업무 테이블이나 Alembic 마이그레이션을 생성한 것은 아니다. 4단계 물리 설계와 추가 설계 7~10도 이후 문서로 완료했다. C01 연결 계층의 실제 검증도 마쳤으며 C06 M005/M006까지 구현·격리 DB 검증했고 [C07a — 인덱스와 조회 계획](구현_C07a_인덱스와조회계획.md) 초안 검증도 완료했으며 [C07b — 봉인·전이와 M007](구현_C07b_봉인전이와M007.md)도 완료했으며 [C07c — 권한과 최종 스키마](구현_C07c_권한과최종스키마.md)도 완료했으며 [C08 — 인증과 계정 관리](구현_C08_인증과계정관리.md)도 완료했으며 다음 작업은 C09이다.

## 3. 4~7단계: 물리 설계와 FastAPI 연결

### 4단계 — ERD를 PostgreSQL 물리 설계로 정리

기존 46개 테이블에 이메일 로그인용 `user_sessions`를 추가한 **47개 테이블**이 전체 설계다. 첫 연결에서는 다음 **26개 업무 테이블**을 대상으로 한다. 실제 로그인 기능은 별도 구현하되 그에 필요한 계정·세션 구조를 첫 스키마에 포함한다.

| 영역 | 테이블 |
|---|---|
| 사용자·세션·프로젝트 4개 | `users`, `user_sessions`, `projects`, `project_members` |
| 자료·파일·좌표 5개 | `assets`, `asset_versions`, `stored_files`, `image_coordinate_frames`, `record_aliases` |
| 규격·인계·감사 3개 | `schema_definitions`, `import_packages`, `audit_events` |
| OCR·추출·근거 6개 | `ocr_runs`, `ocr_tokens`, `poster_extractions`, `poster_field_observations`, `evidence_records`, `evidence_ocr_tokens` |
| 검수 기준 4개 | `criteria_sets`, `criteria_drafts`, `criteria_versions`, `criteria_items` |
| 실행·결과 4개 | `review_runs`, `review_attempts`, `item_results`, `run_item_selections` |

Alembic의 변경 이력 테이블은 이 26개와 별도다.

기존 [DB 구조 설계](/Users/choejiheum/Documents/Codex/2026-09-25/x20-x20/outputs/모닝컵_가상납품검수_예제/크리에이티브체커_DB_구조설계_v0.2_2026-10-14.md)를 기준으로 다음을 확정한다. 기존 설계의 Django 관련 표현은 최신 React + FastAPI 명세를 우선해 해석한다.

- 물리 이름은 영어 `snake_case`, 한글 설명은 PostgreSQL의 `COMMENT ON`으로 관리한다.
- 내부 식별자는 `UUID`, 기록 시각은 UTC 기준 `TIMESTAMPTZ`로 정한다.
- 가변 구조의 기대값·표준 스냅샷·모델 설정은 `JSONB`로 저장한다.
- 이미지·원문 JSON 파일은 파일 저장소에 두고, DB에는 경로·해시·메타데이터를 저장한다.
- 확정 기준과 이미지 버전은 수정 대신 새 버전을 생성한다.
- 실행 상태와 항목 판정 `pass/fail/review`를 별도로 저장한다.
- 같은 검사 규칙을 여러 기준에 적용할 수 있도록 `rule_code` 중복을 허용한다.
- 첫 단계에 없는 멀티에이전트·외부 비교·승인 테이블을 참조하는 컬럼과 FK는 해당 단계에서 추가한다.

**앞서 제공한 ERDCloud용 SQL을 그대로 실행하지 않고, 이 기준으로 PostgreSQL 물리 스키마를 작성한다.** PostgreSQL 코멘트와 ERDCloud의 독립된 한글 논리명 설정도 구분한다.

**완료 기준:** 각 테이블의 컬럼·자료형·필수 여부·PK·FK·유일 제약·주요 인덱스가 확정된다.

### 5단계 — DB 연결 계층 구성 — C01 완료

[10단계](추가설계_10_구현구조와검증명세.md)에서 SQLAlchemy Core 2.1.5·psycopg[binary] 3.3.6 동기 Connection을 선택했다. C01은 설정·연결·UoW와 격리 DB 접속/롤백 검증을 완료했다. 실행 방법·결과는 [C01 기록](구현_C01_DB연결과트랜잭션.md)을 따른다. FastAPI API 연결은 후속 단위다. [SQLAlchemy의 psycopg 연결 안내](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#module-sqlalchemy.dialects.postgresql.psycopg)

연결 계층은 다음 책임을 가진다.

- 환경변수 파일을 명시적으로 읽고 접속 설정을 검증
- 애플리케이션용·마이그레이션용 접속 설정 분리
- 서비스 트랜잭션마다 독립 Connection을 같은 스레드에서 열고 사용하고 닫음
- 성공 시 커밋, 실패 시 롤백, 종료 시 Connection 반환
- 현재 비동기 업로드 API에서는 동기 DB 처리를 스레드풀로 실행
- OCR을 수행하는 동안 DB 트랜잭션을 계속 열어 두지 않음

**C01 완료 기준:** 새 연결 계층에서 app 역할 조회와 격리 probe의 commit/rollback·오류 뒤 연결 회복을 검증한다. 기존 FastAPI API에는 아직 연결하지 않는다.

### 6단계 — Alembic으로 테이블 생성 — M007 정식 head·C07b 가드 검증 완료

C02의 [M001 구현·실행 기록](구현_C02_Alembic과사용자스키마.md)에서 identity 4개 테이블의 컬럼·PK/UQ/CHECK와 기본 권한 회수를 구현·검증했다. [C03](구현_C03_파일스키마와M002.md)에서 M002 파일 5개 테이블도 구현·검증했다. [C04 — 규격·인계·OCR 스키마/M003](구현_C04_OCR스키마와M003.md)의 M003도 구현·검증했다. [C05 — 검수 기준 스키마/M004](구현_C05_검수기준스키마와M004.md)의 M004도 구현·검증했다. [C06 — 실행·결과와 전체 FK](구현_C06_실행결과와전체FK.md)에서 M005의 나머지 4개 테이블과 M006의 전체 FK를 연결했다. [C07a — 인덱스와 조회 계획](구현_C07a_인덱스와조회계획.md)의 인덱스 초안 검증도 완료했다. [C07b — 봉인·전이와 M007](구현_C07b_봉인전이와M007.md)의 가드·정식 M007도 검증했고 [C07c — 권한과 최종 스키마](구현_C07c_권한과최종스키마.md)에서 M008의 컬럼 권한·최종 inventory도 검증했다. 초기 마이그레이션 전체는 다음 순서로 구성한다.

1. M001에서 owner의 app 기본 DML 권한을 먼저 회수하고 M001~M005에서 26개 테이블의 컬럼·PK/UQ/CHECK·코멘트 생성
2. M006에서 순환 참조를 포함한 81개 FK 추가
3. M007에서 일반/부분 인덱스·봉인/전이 트리거, M008에서 최종 컬럼 권한·schema inventory 검증
4. 마이그레이션과 분리한 C08 명시적 개발 초기화 명령으로 개발용 사용자·프로젝트 등록

개발용 `admin/admin` 로그인은 유지하며 과거 식별자인 `local-admin`은 내부 UUID와 구분한다. [7단계 인증 설계](추가설계_07_인증과권한.md)에 따라 account_kind=developer 사용자 UUID와 지정 `DEV_PROJECT_ID`의 owner를 한 번 생성·재사용한다. 정식 이메일 계정은 실제 이메일·비밀번호 해시가 필수이며 developer 행만 둘 다 NULL이다. 정식 초기 계정은 실제 이메일과 비밀번호를 명시적으로 제공받아 해시로 저장한다. 개발 인증의 고정 자격 증명을 정식 이메일 계정의 비밀번호로 시드하지 않는다.

이후 변경은 마이그레이션 파일로 남긴다. 자동 생성 결과도 FK·제약·자료형·코멘트를 검토한 뒤 적용한다. [Alembic 마이그레이션 안내](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)

**완료 기준:** 빈 DB에 마이그레이션만 적용해서 동일한 구조를 재현할 수 있다.

### 7단계 — 새 검수의 저장·조회를 DB로 연결

[추가 설계 8단계](추가설계_08_API와화면JSON.md)에 따라 v1의 이미지 업로드·초안·기준 확정·검수 API를 DB 저장 계층으로 연결한다. 기존 multipart의 자동 DB 어댑터는 첫 구현 경로로 채택하지 않는다.

| 시점 | DB에 기록할 내용 |
|---|---|
| 검수 전 준비 | 프로젝트·자료 버전·파일 메타데이터·초안·확정 기준을 각각의 API에서 저장 |
| 검수 접수 | 이미 고정한 입력에 연결한 검수 실행·멱등 기록 |
| 처리 시작 | 처리 시도·현재 단계·진행 상태 |
| OCR·검수 산출물 검증 | 원문 파일·엔진 정보·문구·좌표·추출·판정의 실제 출력 검증 |
| 검수 완료 | OCR·추출·항목 판정·근거·채택·manifest·봉인을 최종 트랜잭션으로 저장 |
| 처리 실패 | 실패 상태·실패 단계·안전한 오류 사유 |

연결 시 지킬 계약은 다음과 같다.

- v1 API·React 요청을 함께 전환하고, 검증 뒤 구형 `POST /api/reviews`는 명시적으로 410으로 종료한다. 지금 경로를 변경한 것은 아니다.
- 클라이언트의 기준 번호·문자열 항목 ID와 내부 DB UUID를 구분해 보존한다.
- 프로젝트 이름이 같다는 이유로 서로 다른 프로젝트를 자동 병합하지 않는다.
- 신규 검수의 존재 여부와 상태는 DB를 기준으로 판단한다.
- 기존 JSON은 자동 귀속하지 않는다. 개발 loopback의 명시적 구형 읽기만 보존하고 운영 이력은 9단계의 명시적 수입·권한 매핑을 거친다.
- DB 장애는 명시적인 오류로 반환하며 신규 기록을 JSON에 조용히 우회 저장하지 않는다.
- 원본·표시 이미지는 기존 파일 저장소에 보존하고 DB 메타데이터와 연결한다.

이번 단계에서는 현재 `BackgroundTasks` 실행 방식을 유지한다. 서버 재시작으로 중단된 검수는 DB에도 실패 상태를 기록한다. **자동 재개·독립 worker는 다음 단계다.**

**완료 기준:** 새 검수 한 건을 실행하면 이미지·기준·OCR·판정·근거가 연결되고, API를 재시작한 뒤에도 완료 기록을 다시 조회할 수 있다.

## 4. 8단계: 검증·백업과 다음 확장

### 8단계 — 실제 PostgreSQL 검증과 백업·복구

최소한 다음 시나리오를 실제 PostgreSQL에서 확인한다.

| 검증 | 통과 기준 |
|---|---|
| 새 DB 구축 | 마이그레이션으로 전체 구조 생성 |
| 검수 저장 | 기준 항목과 결과·근거가 정확히 연결 |
| 서버 재시작 | 완료 기록과 이미지 재조회 가능 |
| 컨테이너 재시작 | 저장한 데이터 유지 |
| 저장 실패 | 일부 결과만 남는 불완전한 커밋 방지 |
| 데이터 정합성 | 다른 프로젝트의 파일·기준·결과 연결 거부 |
| 기존 기능 | 기존 JSON 기록과 React 검수 화면 정상 동작 |
| 백업·복구 | 별도 DB로 복원한 뒤 기록·참조·이미지 연결 확인 |

백업은 [9단계 저장·복구 계약](추가설계_09_저장과이전복구.md)에 따라 쓰기/worker/GC 중지 후 PostgreSQL custom-format dump·파일 inventory·설정/schema 버전을 한 세트로 묶는다. 복원 검증은 새 DB와 새 파일 루트에서 수행하며 세션 폐기·전체 무결성 검사 전 공개/worker 시작을 금지한다. DB 접속 성공만으로 복원 완료를 판단하지 않는다. [PostgreSQL 백업 안내](https://www.postgresql.org/docs/17/backup-dump.html)

이번 단계의 완료 기준은 **새 검수가 DB에 저장되고 재시작 후 다시 조회되는 것**이다.
