## 2. 강제하는 조건과 보존하는 구분

- 자료는 poster_image이며 이름은 비어 있지 않아야 한다. 직접 자기 참조를 거부한다. 버전 번호·네 이미지 치수는 양수, 원본 해시는 소문자 SHA256, 측정 정보는 JSON 객체다. 확인 상태는 unverified를 유지한다.
- 저장 파일은 local, 7개 정의된 역할, stored/missing 상태를 사용한다. 바이트 수는 BIGINT의 비음수 값이며 이미지 역할은 양수 크기와 비어 있지 않은 MIME이 필요하다. 출처 정보는 JSON 객체, 저장 위치는 유일하다. **파일 해시에는 유일 제약을 두지 않는다.**
- 좌표계는 종류·좌표 기준·양수 치수·unverified를 검사한다. 부모와 변환 객체는 함께 있거나 모두 SQL NULL이어야 한다. Python None은 선택 변환의 SQL NULL로 저장하고 JSON null·배열·스칼라 변환은 거부한다. 행렬 내용·실제 좌표 대응을 검증했다는 뜻은 아니다.
- 외부 별칭은 프로젝트·인계 묶음·namespace·원문 ID를 묶어 UNIQUE NULLS NOT DISTINCT를 적용한다. 인계 묶음이 NULL인 중복도 거부하며 서로 다른 묶음/프로젝트의 같은 ID는 보존한다. 원문 ID는 자동 정규화·잘라내기를 하지 않는다. [PostgreSQL UNIQUE 문서](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)
- 생성/수정 시각은 유한값과 해당 순서를 검사한다. 서버 발급 UUID를 사용하며 DB UUID 기본값·사용자/업무 seed는 추가하지 않았다.

M001의 코드는 변경하지 않았다. C02의 테스트는 M001 revision과 identity 4개 metadata로 범위를 고정해 이후 head가 바뀌어도 같은 회귀를 검증하도록 조정했다. 이전 JSON 검증 기록은 당시 이력으로 보존한다. 신규 패키지나 owner/app 설정 변경은 없다.

## 3. 실행과 적용 경계

owner 설정과 테스트 전용 환경은 [C02 실행 방법](구현_C02_Alembic과사용자스키마.md#3-명시적-실행-방법)·[C01 테스트 설정](구현_C01_DB연결과트랜잭션.md#4-전용-postgresql-테스트-실행)을 따른다. 저장소 루트에서 실행한다.

```bash
.venv/bin/python -m alembic -c backend/migrations/alembic.ini heads

# M001→M002의 검토용 SQL. DB 접속/적용 없음.
CC_MIGRATION_ENV_FILE=.env.owner-test .venv/bin/python -m alembic -c backend/migrations/alembic.ini upgrade M001:M002 --sql

# 명시한 격리 DB에만 적용. M001이면 증분, 빈 DB이면 M001부터 적용.
CC_MIGRATION_ENV_FILE=.env.owner-test .venv/bin/python -m alembic -c backend/migrations/alembic.ini upgrade M002
```

현재 head는 **M002**이며 최종 M008까지 준비됐다는 뜻은 아니다. 일반 앱·launcher에서 자동 upgrade하지 않는다. 기존 이름의 대상 테이블이 있으면 오류로 중단하며 덮어쓰기·자동 채택하지 않는다. M002의 파괴적 downgrade도 거부한다.

이번에는 임의 UUID의 전용 테스트 DB에서만 upgrade를 실행했다. 일상 DB는 테스트 전후 public 관계와 기본 ACL을 읽어 비교했으며 변경하지 않았다. 실제 이미지/JSON 파일 이동·바이트 기록·외부 이관도 수행하지 않았다.

## 4. 검증 결과

```bash
.venv/bin/python -m pytest -q
TEST_DB_ENV_FILE=.env.db-test .venv/bin/python -m pytest -m db_integration -q
```

- 기본 Python **408 passed**, 추가 subtest 7 passed, DB 통합 111개는 기본 실행에서 제외했다. 신규 C03 정적 사례는 4개다.
- 실제 PostgreSQL **111 passed**: C01/C02 회귀 46개와 C03의 파일/전체 적용 사례 65개다. macOS Python 3.12.14·기존 PostgreSQL 17.11을 사용했다.
- 9개 테이블·88개 컬럼의 실제 inventory와 metadata 자료형·NULL/default·PK/UQ/CHECK·코멘트를 대조했다. 신규 5개 테이블은 빈 상태이며, 증분 검증용으로 넣은 기존 M001 테스트 데이터는 보존됐다.
- 해시·치수·JSON 외형/NULL·역할·상태·시각·자기 참조·문자열 길이·중복 키의 오류를 실제 DB에서 거부했다. 같은 해시의 파일 여러 개, BIGINT 크기, 일반 파일의 미확인 MIME, 여러 좌표계, 서로 다른 별칭 문맥은 허용했다. 이 테스트는 실제 3GB 파일 등을 생성하지 않고 메타데이터 자료형만 검사한다.
- 기존 stored_files 충돌이 나면 앞서 만든 M002 테이블도 롤백되고 기존 객체/데이터는 보존됐다. M002 끝의 의도적 오류는 신규 테이블·버전 변경을 롤백하고 M001 테이블·데이터·기본 권한을 보존했다.
- **빈 DB→M001→M002** 전체 적용의 마지막 오류 주입에서도 전체 DDL·버전·기본 ACL이 함께 롤백됐다. 정상 전체 적용에서는 누적 9개 테이블이 빈 상태로 생성됐다.
- app의 새 테이블 권한은 계속 없으며 동일 revision 재실행과 downgrade 거부를 확인했다. 테스트 DB를 정리했고 일상 DB의 관계·기본 ACL은 같았다. pip check·구문 검사·문서 링크/지문 검토도 통과했다.

[C03 실행 검증 기록](verification/2026-10-17-implementation-C03.json)에 실제 결과·명령·파일 지문을 저장한다. 실제 네트워크 COMMIT 장애·Linux/Windows·브라우저·OCR·파일 내구성 검증은 실행하지 않았다.
