# PostgreSQL 물리 설계 2단계 — 사용자·프로젝트·자료·파일

작성일: 2026-10-16

상태: **설계 2단계 작성 완료 — 추가 설계 7단계의 계정 종류 반영.** [1단계](물리설계_01_범위와관계.md)의 첫 구축 범위는 기존 25개에 `user_sessions`를 추가한 26개다. 이번 문서는 사용자·세션·프로젝트·자료·파일 영역 9개 테이블의 컬럼·자료형·필수값·키를 다룬다. 전체 정합성·CHECK·인덱스는 6단계 문서, 인증 상세는 [7단계 문서](추가설계_07_인증과권한.md)를 따른다. ERD 가져오기용 SQL의 이메일·해시 NOT NULL은 아래 종류별 CHECK로 바꿀 대상이며 실제 DB 적용은 후속 단계다.

## 1. 대상과 설계 근거

대상은 `users`, `user_sessions`, `projects`, `project_members`, `assets`, `asset_versions`, `stored_files`, `image_coordinate_frames`, `record_aliases`다.

| [ERD 초안](../ERD_물리.md) | 기존 8개 테이블과 새 사용자세션의 컬럼·PK·FK | 기존 물리 이름을 유지하고 변경·추가 이유를 기록 |

아래 기본값·상태 코드는 이번 설계의 서비스 내부 결정이다. 외부 포스터 규격의 확정 enum이나 현재 구현값이라고 해석하지 않는다.

## 2. 공통 규칙

- 표의 **필수**는 NULL 불가, **선택**은 NULL 허용이다. 기본값이 없는 필수 컬럼은 저장 계층이 반드시 제공한다.
- 각 단일 PK는 `UUID`이며 애플리케이션에서 UUID v4를 한 번 발급한다. UUID PK에 DB 기본값은 두지 않는다. 복합 PK의 UUID는 참조 행의 값을 사용한다.
- 시각은 `TIMESTAMPTZ`로 저장하고 DB·연결 세션은 UTC로 사용한다. `created_at`의 DB 기본값은 `CURRENT_TIMESTAMP`다. `updated_at`도 최초에는 같은 기본값을 쓰고 이후 수정 시 저장 계층이 갱신한다. 자동 갱신 트리거가 구현됐다는 뜻은 아니다.
- `JSONB`는 중첩 메타데이터에 사용한다. PK·FK·핵심 상태·파일 위치는 별도 컬럼으로 둔다. 파일과 원문 JSON 바이트는 파일 저장소에 보존한다.
- 이름은 식별 키로 사용하지 않는다. 같은 프로젝트명·자료명·파일 해시를 이유로 서로 다른 업무 기록을 병합하지 않는다.
- 프로젝트 경계를 확인할 수 있도록 자료 버전·좌표계·별칭에도 `project_id`를 둔다. 아래 복합 유일 키는 복합 FK의 참조 대상이다. 최종 제약 이름과 일반 조회 인덱스는 [6단계 제약 목록](물리설계_06_제약목록.md)에 정리했다.
- 아래 FK의 삭제 정책은 우선 `RESTRICT`로 잡는다. 기록을 연쇄 삭제하는 정책은 도입하지 않는다. 사용자·멤버십 비활성화와 프로젝트 보관으로 업무 상태를 관리한다.

`TIMESTAMPTZ`의 시간대 변환은 [PostgreSQL 날짜·시각 안내](https://www.postgresql.org/docs/17/datatype-datetime.html), 메타데이터 자료형은 [JSON 안내](https://www.postgresql.org/docs/17/datatype-json.html)를 기준으로 한다.

## 3. users — 사용자

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `user_id` | `UUID` | 필수 | 앱 발급 | 내부 사용자 PK |
| `account_kind` | `VARCHAR(20)` | 필수 | `email` | `email`·`developer`. 생성 뒤 변경 금지 |
| `email` | `VARCHAR(254)` | 선택 | NULL | email 종류는 필수·정규화, developer 종류는 NULL |
| `password_hash` | `TEXT` | 선택 | NULL | email 종류는 실제 비밀번호 해시 필수, developer 종류는 NULL |
| `display_name` | `VARCHAR(100)` | 필수 | 없음 | 화면 표시 이름 |
| `is_active` | `BOOLEAN` | 필수 | true | 사용자 활성 여부 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 생성 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 변경 시각 |

키는 PK `user_id`, UNIQUE `email`이다. 정식 이메일 계정은 CHECK로 email·password_hash의 NOT NULL·비어 있지 않음을 강제한다. developer 행은 둘 다 NULL이어야 하며 `uq_users_developer_kind` 부분 유일 인덱스로 비활성 행을 포함해 DB당 하나만 허용한다. account_kind는 email/developer만 허용한다. 이메일을 로그인 식별자로 사용하므로 별도의 `login_name`은 두지 않는다. 서비스 정책은 이메일 앞뒤 공백 제거·전체 소문자화 후 저장·조회하는 것으로 정한다. 저장값의 정규화는 CHECK, 실제 형식·ASCII·254자 한도는 인증 계층에서도 검증한다. 비밀번호에는 이메일 정규화를 적용하지 않는다.

비밀번호는 Argon2id 인코딩 결과만 저장한다. 초기 최소 비용은 m=19456 KiB·t=2·p=1이며 라이브러리·버전·동시 실행 한도는 [10단계](추가설계_10_구현구조와검증명세.md)에서 선택했으며 실제 비용은 구현 때 측정한다. 발급/재설정은 Unicode 코드포인트 15~128자이며 비밀번호를 자르거나 정규화하지 않는다. 일반 SHA256을 비밀번호 해시로 쓰지 않는다. [OWASP 비밀번호 저장 안내](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

정식 초기 계정은 실제 로그인에 사용할 이메일과 비밀번호를 명시적으로 제공받아 생성한다. 사용자 UUID는 한 번 발급해 재사용하며 정식 계정의 평문 비밀번호·고정 기본 비밀번호를 마이그레이션이나 ERD에 넣지 않는다.

**개발용 `admin/admin`은 유지한다.** 이메일 로그인 추가 후에도 개발 모드에서 별도로 제공한다. localhost 접근 제한과 `LOCAL_ADMIN_LOGIN` 경계를 모든 개발 세션 요청에 유지하며 정식 이메일 계정의 비밀번호로 해석하지 않는다. `local-admin`은 과거 개발 인증의 문자열 식별자이며 DB UUID가 아니다. 명시적 개발 초기화로 developer 사용자 UUID와 `DEV_PROJECT_ID`의 owner를 생성·재사용하고, 신규 업무 기록은 그 UUID를 사용한다. 앱 시작·마이그레이션에서 자동 생성하지 않는다. 정식 계정의 이메일 필수 조건과 모든 계정의 프로젝트 권한 검사는 유지한다. 환경·초기화·전환 계약은 [7단계](추가설계_07_인증과권한.md)를 따른다.

공개 회원가입·이메일 소유 확인·셀프 비밀번호 재설정은 별도 확장이다. 보호된 관리 명령의 계정 발급·비밀번호 재설정 계약은 7단계에서 정했으며 실제 기능은 아직 구현하지 않았다.

## 4. user_sessions — 사용자세션

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `session_id` | `UUID` | 필수 | 앱 발급 | DB 내부 세션 PK |
| `user_id` | `UUID` | 필수 | 없음 | 로그인한 사용자 |
| `token_hash` | `VARCHAR(64)` | 필수 | 없음 | 브라우저에 발급한 난수 세션 토큰의 SHA256 소문자 64자리 해시 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 발급 시각 |
| `expires_at` | `TIMESTAMPTZ` | 필수 | 없음 | 설정한 세션 수명에 따른 만료 시각 |
| `revoked_at` | `TIMESTAMPTZ` | 선택 | NULL | 로그아웃·관리자 조치 등으로 폐기한 시각 |

키는 PK `session_id`, UNIQUE `token_hash`, FK `user_id → users.user_id`이며 삭제 정책은 `RESTRICT`다. 한 사용자에게 여러 세션을 허용한다. ERD에 토큰 해시 형식·만료가 발급 이후인 조건·폐기가 발급 이전이 아닌 조건을 반영했다.

인증 구현 시 암호학적 난수 32바이트 이상으로 세션 토큰을 발급한다. 원문 토큰은 HttpOnly 쿠키로 전달하고 DB에는 해시만 보관한다. `session_id`는 쿠키 자격 증명으로 사용하지 않는다. 인증 성공은 해시가 일치하는 세션의 `revoked_at`이 NULL이고 현재 시각이 `expires_at` 이전이며 연결한 사용자가 활성 상태일 때로 정한다. 쿠키 속성·만료·서버 폐기 처리는 [OWASP 세션 관리 안내](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)를 참고해 구현한다.

로그인 성공 시 새 토큰을 발급하고 로그아웃 시 서버 세션을 폐기한다. 비밀번호 변경·계정 비활성화 시 관련 세션을 폐기하는 계약도 인증 구현에 포함한다. 이 설계는 현재 프로세스 메모리 세션을 DB로 전환할 수 있도록 준비한 것이며, 현재 인증 코드의 동작을 변경하지 않았다.

## 5. projects — 프로젝트

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `project_id` | `UUID` | 필수 | 앱 발급 | 프로젝트 PK |
| `created_by` | `UUID` | 필수 | 없음 | 생성 사용자 |
| `name` | `VARCHAR(200)` | 필수 | 없음 | 프로젝트명 |
| `purpose` | `TEXT` | 선택 | NULL | 발주·검수 목적 |
| `use_channels` | `JSONB` | 필수 | `[]` | 예정 사용처 문자열 배열 |
| `due_at` | `TIMESTAMPTZ` | 선택 | NULL | 납기 |
| `business_state` | `VARCHAR(40)` | 필수 | `active` | 프로젝트 업무 상태 |
| `archived_at` | `TIMESTAMPTZ` | 선택 | NULL | 보관 전환 시각 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 생성 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 변경 시각 |

PK는 `project_id`, FK는 `created_by → users.user_id`다. 프로젝트명에는 UNIQUE를 두지 않는다. 현재 검수 API의 프로젝트명 입력 한도 120자는 유지할 수 있으며, DB의 200자 한도를 이유로 API 계약을 이 단계에서 변경하지 않는다.

첫 업무 상태는 `active`·`archived`로 정한다. `archived`일 때만 `archived_at`이 존재하도록 후속 CHECK를 설계한다. 프로젝트 생성과 생성자의 `project_members` owner 행 추가는 같은 트랜잭션으로 처리할 계약이다. `created_by`는 생성 이력이며 현재 소유권을 대신하지 않는다.

## 6. project_members — 프로젝트 참여자

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `project_id` | `UUID` | 필수 | 없음 | 프로젝트 |
| `user_id` | `UUID` | 필수 | 없음 | 참여 사용자 |
| `role` | `VARCHAR(40)` | 필수 | `viewer` | `owner`·`editor`·`viewer` |
| `is_active` | `BOOLEAN` | 필수 | true | 참여 활성 여부 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 최초 참여 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 역할·활성 여부 변경 시각 |

복합 PK는 `(project_id, user_id)`다. FK는 `project_id → projects.project_id`, `user_id → users.user_id`다. 탈퇴·재참여는 같은 행의 활성 여부와 변경 시각을 갱신하고 감사 이벤트로 이력을 남길 계약이다. owner의 생성·변경 규칙은 설계 6단계에서 트랜잭션 조건과 함께 검토한다.

이 테이블은 소속 데이터를 저장하기 위한 설계다. 현재 검수 API에 프로젝트별 접근 통제가 적용됐다는 뜻은 아니다.

## 7. assets — 자료

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `asset_id` | `UUID` | 필수 | 앱 발급 | 자료 PK |
| `project_id` | `UUID` | 필수 | 없음 | 소속 프로젝트 |
| `parent_asset_id` | `UUID` | 선택 | NULL | 같은 프로젝트의 상위 자료 |
| `asset_kind` | `VARCHAR(50)` | 필수 | `poster_image` | 초기 입력인 포스터 이미지 자료 종류 |
| `name` | `VARCHAR(200)` | 필수 | 없음 | 자료 표시 이름 |
| `created_by` | `UUID` | 필수 | 없음 | 최초 등록 사용자 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 등록 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 표시 정보 변경 시각 |

키는 PK `asset_id`, 복합 UNIQUE `(project_id, asset_id)`다. FK는 `project_id → projects.project_id`, `created_by → users.user_id`, `(project_id, parent_asset_id) → assets(project_id, asset_id)`다. 부모가 없으면 `parent_asset_id`만 NULL로 둔다.

자료명 변경은 버전의 이미지 내용을 수정하지 않는다. 이미지가 바뀌면 별도의 `asset_versions` 행을 만든다. 부모를 자신으로 지정하거나 조상·자손을 뒤집는 순환 관계를 막는 규칙은 설계 6단계에서 DB와 저장 계층의 책임으로 나눈다.

## 8. asset_versions — 자료 버전

첫 연결 범위는 검증에 성공한 단일 포스터 이미지다. 따라서 원본·표시 파일과 각 치수는 필수다. 파일이 없는 인계 자료를 이미지 버전의 빈 행으로 먼저 만들지 않는다.

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `asset_version_id` | `UUID` | 필수 | 앱 발급 | 자료 버전 PK |
| `project_id` | `UUID` | 필수 | 없음 | 자료와 동일한 프로젝트 |
| `asset_id` | `UUID` | 필수 | 없음 | 소속 자료 |
| `version_no` | `INTEGER` | 필수 | 없음 | 자료 안의 1 이상 버전 번호 |
| `original_file_id` | `UUID` | 필수 | 없음 | 원본 바이트 파일 |
| `display_file_id` | `UUID` | 필수 | 없음 | EXIF 방향·배경·RGB를 정규화한 표시 PNG |
| `original_sha256` | `VARCHAR(64)` | 필수 | 없음 | 원본 바이트의 소문자 64자리 SHA256 |
| `original_width` | `INTEGER` | 필수 | 없음 | EXIF 방향 적용 전 원본 가로 픽셀 |
| `original_height` | `INTEGER` | 필수 | 없음 | EXIF 방향 적용 전 원본 세로 픽셀 |
| `display_width` | `INTEGER` | 필수 | 없음 | 표시 이미지 가로 픽셀 |
| `display_height` | `INTEGER` | 필수 | 없음 | 표시 이미지 세로 픽셀 |
| `verification_state` | `VARCHAR(40)` | 필수 | `unverified` | 원본 확인 상태. 디코딩 성공을 사람의 확인으로 취급하지 않음 |
| `measurement_metadata` | `JSONB` | 필수 | `{}` | 실제 형식·원본 크기·정규화 방식 등 측정 내용 |
| `created_by` | `UUID` | 필수 | 없음 | 이 버전의 등록 사용자 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 버전 생성 시각 |

키는 PK `asset_version_id`, UNIQUE `(asset_id, version_no)`, UNIQUE `(project_id, asset_version_id)`다. FK는 다음과 같다.

- `(project_id, asset_id) → assets(project_id, asset_id)`
- `(project_id, original_file_id) → stored_files(project_id, file_id)`
- `(project_id, display_file_id) → stored_files(project_id, file_id)`
- `created_by → users.user_id`

버전 번호는 트랜잭션에서 배정하고 UNIQUE 충돌을 처리한다. 동시 요청에서 잠금 없이 최댓값에 1을 더하는 방식으로 확정하지 않는다. 프로젝트·소속 자료·버전 번호·파일·해시·치수·측정 내용은 생성 후 불변으로 다룬다. 원본 확인 상태의 추가 값과 변경 주체는 후속 검토 업무 도입 시 정의하고, 초기값을 자동으로 승인 상태로 올리지 않는다.

원본 해시는 원본 파일 행의 `sha256`과 일치해야 한다. 표시 이미지의 해시는 표시 파일 행에서 따로 보존한다. 두 파일의 역할·실제 바이트·치수가 맞는지는 파일 검증 및 같은 저장 트랜잭션에서 확인할 계약이며, 단순 FK만으로 보장되는 조건은 아니다.

| `state` | `VARCHAR(40)` | 필수 | `stored` | `stored`·`missing`: 저장 완료 또는 보존 경로의 파일 누락 |
| `source_metadata` | `JSONB` | 필수 | `{}` | 출처·변환·인계 메타데이터 |

키는 PK `file_id`, UNIQUE `(project_id, file_id)`, UNIQUE `(storage_backend, storage_key)`다. 해시에는 UNIQUE를 두지 않는다. FK는 다음과 같다.

- `project_id → projects.project_id`
- `(project_id, parent_file_id) → stored_files(project_id, file_id)`
- `(project_id, import_package_id) → import_packages(project_id, import_id)` — 대상 복합 유일 키는 설계 3단계의 연결 조건
- `created_by → users.user_id`

현재 파일 경로는 `.runtime/reviews/<검수 UUID>/…`다. [추가 설계 9단계](추가설계_09_저장과이전복구.md)에서 신규 v1은 별도 STORAGE_ROOT(예시 `.runtime/storage-v1`)와 `objects/projects/<project UUID>/files/<file UUID>/payload.bin` 키를 사용하도록 확정했다. 기존 JSON/파일은 그대로 보존한다. 환경별 절대 경로는 DB에 넣지 않는다. 루트/링크 검사·동일 볼륨 확정·fsync·작업 저널과 커밋 결과 확인은 9단계를 따른다.

초기 이미지 역할 코드는 `original_image`, `display_image`, `ocr_input`, 원문 JSON은 `source_json`으로 정한다. 인계 매니페스트·규격 파일의 역할 값은 설계 3단계에서 추가로 정리한다. 이미지는 실제 MIME이 필수이며 이미지 업로드의 빈 파일은 현재 API처럼 거부한다. 일반 파일의 MIME 미확인은 NULL로 보존할 수 있다.

원본 이름은 현재 업로드 API에서 길이를 제한하는 계약이 없으므로 `TEXT`로 보존한다. 확장자와 실제 형식을 동일하게 가정하지 않는다. 표시 파일의 원천은 원본, OCR 입력 파일의 원천은 표시 파일로 연결한다. 내용·해시·저장 키를 덮어쓰는 대신 새 파일 행을 만든다. 현재 키에 파일이 없어졌을 때는 기존 메타데이터를 유지하며 `missing`으로 기록할 계약이다.

`stored_files.import_package_id`는 NULL을 허용한다. 매니페스트 파일을 먼저 등록하거나 received 인계를 먼저 만드는 순서로 순환 참조를 해소하며 completed 전에 연결한다. 9단계에서 커밋 경계·미확인 결과 보존·gate/작업 잠금·primary 확인 뒤 미참조 격리를 확정했다. DB 오류라는 이유만으로 바로 파일을 삭제하지 않는다. 구현과 실제 장애 검증은 후속 단계다.

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `frame_id` | `UUID` | 필수 | 앱 발급 | 좌표계 PK |
| `project_id` | `UUID` | 필수 | 없음 | 소속 프로젝트 |
| `asset_version_id` | `UUID` | 필수 | 없음 | 대상 자료 버전 |
| `file_id` | `UUID` | 필수 | 없음 | 해당 좌표의 기준 파일 |
| `parent_frame_id` | `UUID` | 선택 | NULL | 같은 프로젝트·자료 버전의 상위 프레임 |
| `frame_kind` | `VARCHAR(50)` | 필수 | 없음 | 내부 구분: `original`·`display`·`ocr_input`·`crop` |
| `coordinate_space` | `VARCHAR(100)` | 필수 | 없음 | 입력·출력 계약의 좌표 기준 문자열 |
| `width` | `INTEGER` | 필수 | 없음 | 이 프레임의 가로 픽셀, 1 이상 |
| `height` | `INTEGER` | 필수 | 없음 | 이 프레임의 세로 픽셀, 1 이상 |
| `verification_state` | `VARCHAR(40)` | 필수 | `unverified` | 출처와 좌표 대응의 확인 상태 |
| `transform_jsonb` | `JSONB` | 선택 | NULL | 현재 프레임에서 상위 프레임으로 가는 변환 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 생성 시각 |

키는 PK `frame_id`, UNIQUE `(project_id, asset_version_id, frame_id)`다. FK는 다음과 같다.

- `(project_id, asset_version_id) → asset_versions(project_id, asset_version_id)`
- `(project_id, file_id) → stored_files(project_id, file_id)`
- `(project_id, asset_version_id, parent_frame_id) → image_coordinate_frames(project_id, asset_version_id, frame_id)`

여러 크롭이나 OCR 입력 프레임을 보존할 수 있도록 `frame_kind` 자체에는 UNIQUE를 두지 않는다.

변환은 현재 좌표를 열벡터 `[x, y, 1]`로 놓았을 때 상위 좌표를 얻는 3×3 행렬과 방법·버전 정보를 JSON 객체에 담는다. 부모가 없는 기준 프레임은 부모와 변환을 모두 NULL로 둔다. 부모를 지정했다면 변환 정보가 있어야 한다. 대응을 모르면 임의의 단위 행렬로 연결하지 않는다.

| 실제 파일·레코드 | 저장할 기준 | 연결·변환 규칙 |
|---|---|---|
| `original.bin` | 원본 픽셀의 별도 프레임, `coordinate_space=original_pixels` | 원본 저장 방향 기준. 표시 이미지와 같은 좌표라고 가정하지 않음 |
| `normalized.png` | 표시 프레임, `coordinate_space=normalized_original_pixels` | 현재 API가 반환하는 최종 bbox·polygon의 기준. 초기에는 기준 프레임으로 둘 수 있음 |
| `ocr_input.png` | OCR 입력 프레임, `coordinate_space=ocr_input_pixels` | 표시 프레임을 부모로 하며 현재 입력은 가로·세로 2배. OCR 입력→표시 행렬은 대각 성분이 `0.5, 0.5, 1` |
| 복원된 API OCR 근거 | 표시 프레임 참조 | 이미 표시 좌표인 bbox·polygon은 그대로 저장 |
| 외부 인계의 `display_pixels` 선언 | 원래 선언을 보존한 프레임 | 실제 기준 파일·치수·방향을 확인한 뒤 대응을 기록. 이름만 보고 다시 2로 나누지 않음 |

EXIF 전후 변환은 실제 방향 정보가 있을 때만 기록한다. 현재 메타데이터에는 원본·표시 치수가 있지만 EXIF 변환 행렬은 없으므로, 원본과 표시 크기가 같다는 이유만으로 두 좌표계를 동일하게 연결하지 않는다. 좌표계 확인 상태는 담당자의 검수 승인·정답 라벨 승인과 별개다.

## 11. record_aliases — 외부 식별 별칭

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `alias_id` | `UUID` | 필수 | 앱 발급 | 별칭 PK |
| `project_id` | `UUID` | 필수 | 없음 | 자료 버전과 동일한 프로젝트 |

PK는 `alias_id`다. FK는 `(project_id, asset_version_id) → asset_versions(project_id, asset_version_id)`, `(project_id, import_package_id) → import_packages(project_id, import_id)`다. 후자는 설계 3단계에서 대상 키를 맞춘다.

유일 키는 `(project_id, import_package_id, namespace, external_record_id)`이며 **NULLS NOT DISTINCT**를 적용하는 것으로 설계한다. 인계 묶음이 없는 같은 프로젝트·출처·외부 ID가 서로 다른 버전에 중복 연결되는 것을 막고, 서로 다른 인계 묶음의 같은 외부 ID는 보존한다. 인계 묶음 내부의 같은 ID가 다른 버전을 가리키면 덮어쓰지 않고 충돌로 처리한다. 이 NULL 처리 방식은 [PostgreSQL 17 UNIQUE 안내](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)에 따른다.

저장 연동 시 새로 계산·기록해야 할 값은 표시/OCR 입력 파일의 바이트 해시·크기, 생성한 파일 키, 각 프레임의 명시적 좌표 기준이다. 이번 문서는 그 필드를 설계했으며 현재 API의 JSON 저장 코드를 변경한 것은 아니다.

| 측정·출처·좌표 변환 TEXT를 JSONB로 변경 | 문자열 JSON과 구조화된 값의 혼용 방지 |
| 프레임에 `coordinate_space` 추가 | 내부 프레임 종류와 입출력 좌표 계약을 별도로 보존 |
| 별칭 유일 키의 범위·NULL 처리 정의 | 인계 유무와 다른 프로젝트·묶음의 같은 외부 ID 구분 |

설계 3단계의 `import_packages`에는 `(project_id, import_id)` 유일 키가 필요하다. `manifest_file_id`는 같은 프로젝트의 `stored_files`를 참조하고, 파일·인계 묶음의 상호 연결 순서를 유지해야 한다. 이 문서는 해당 테이블의 전체 컬럼을 설계하거나 생성하지 않는다.

설계 6단계에서는 기본값·문자열 빈 값·SHA256 형식·양수 치수·JSON 형태·보관 상태·부모 연결과 사용 중인 파일의 불변성을 검토한다. FK로 보장할 프로젝트 경계와 파일 내용·자료 버전의 일치처럼 저장 계층에서 검증해야 할 조건을 구분한다.
