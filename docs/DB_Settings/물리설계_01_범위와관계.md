# PostgreSQL 물리 설계 1단계 — 범위와 관계

작성일: 2026-10-16

상태: **설계 1단계 완료 — 이메일 로그인 범위 추가 반영.** 이번 문서는 테이블 범위와 ERD의 참조 관계를 정리한다. 컬럼 상세는 영역별 문서에서 설계하고 최종 제약·ORM·마이그레이션은 후속 단계에서 확정한다.

## 1. 진행 기준

기존 [Docker·PostgreSQL 안내](도커%20및%20포스트그리SQL세팅.md)의 1~3단계 DB 준비·보존 검증은 완료됐다. 지금부터는 그 안내의 **4단계인 물리 설계**를 아래 세부 단계로 나눠 진행한다.

| 설계 세부 단계 | 산출물 | 상태 |
|---|---|---|
| 1 | 26개 테이블의 역할·참조 대상·후속으로 미룰 관계 | 완료 — 현재 문서 |
| 2 | 사용자·세션·프로젝트·자료·파일 영역 9개 테이블의 컬럼·자료형·필수값·키 | 완료 — [2단계 문서](물리설계_02_사용자와파일.md) |
| 3 | 규격·인계·감사·OCR·근거 영역 9개 테이블의 컬럼·자료형·필수값·키 | 완료 — [3단계 문서](물리설계_03_규격과OCR근거.md) |
| 4 | 검수 기준 영역 4개 테이블의 컬럼·자료형·필수값·키 | 완료 — [4단계 문서](물리설계_04_검수기준.md) |
| 5 | 검수 실행·결과 영역 4개 테이블의 컬럼·자료형·필수값·키 | 완료 — [5단계 문서](물리설계_05_검수실행과결과.md) |
| 6 | 전체 관계·프로젝트 경계·CHECK·유일 제약·인덱스의 정합성 검토 | 완료 — [6단계 문서](물리설계_06_전체정합성.md)·[제약 목록](물리설계_06_제약목록.md) |

| 8 | 서버 초안·API/화면·JSON 한도·해시 규격과 고정 예제 | 완료 — [API·화면·JSON 문서](추가설계_08_API와화면JSON.md) |
| 9 | 파일/DB 커밋·봉인·GC·수입·백업/복원·되돌리기 | 완료 — [저장·복구 문서](추가설계_09_저장과이전복구.md) |

한 번에 한 세부 단계만 수행한다. 현재 단계의 결과를 전달한 뒤 사용자가 **“다음”**이라고 하면 다음 단계로 진행한다. 물리 설계 세부 1~6 이후에도 [추가 설계 7~10단계](물리설계_06_전체정합성.md#11-다음-설계와-완료-기준)의 인증·API·저장/복구·구현/검증 계약을 먼저 보강한다. DB 연결·마이그레이션 코드는 그 뒤 별도 단계로 진행한다.

근거는 [ERD 초안](../ERD_물리.md), [현재 프로젝트 명세](../project-specification.md), Docker·PostgreSQL 안내의 26개 테이블 목록이다. 2026-10-16 이메일 로그인 요구사항에 따라 기존 전체 46개·첫 범위 25개에 `user_sessions`를 추가해 전체 47개·첫 범위 26개로 갱신했다. ERD 초안은 관계도 가져오기용이며 운영용 스키마 확정 여부는 이 설계 진행 상태로 판단한다.

## 2. 첫 스키마에 포함할 26개 테이블

아래 참조 대상은 ERD의 FK 중 이번 26개 테이블 안에서 연결되는 대상이다. 같은 테이블을 여러 컬럼으로 참조하는 경우 대상 이름은 한 번만 적었다. 최종 FK의 컬럼 구성과 필수 여부는 후속 설계에서 확정한다.

| 영역 | 테이블 | 역할 | 이번 범위의 직접 참조 대상 |
|---|---|---|---|
| 사용자·프로젝트 | `users` | 이메일 계정 및 검수 요청·확정·감사 기록의 사용자 식별 | 없음 |
| 사용자·프로젝트 | `user_sessions` | 로그인 세션의 토큰 해시·만료·폐기 기록 | `users` |
| 사용자·프로젝트 | `projects` | 검수 자료와 기준을 묶는 업무 단위 | `users` |
| 사용자·프로젝트 | `project_members` | 프로젝트와 사용자 사이의 소속·역할 | `projects`, `users` |
| 자료·파일·좌표 | `assets` | 프로젝트에 속한 자료와 자료 간 계층 | `projects`, `assets` |
| 자료·파일·좌표 | `asset_versions` | 자료의 불변 버전과 원본·표시 파일 연결 | `assets`, `stored_files` |
| 자료·파일·좌표 | `stored_files` | 실제 파일의 위치·해시·크기 등 메타데이터 | `projects`, `stored_files`, `import_packages` |
| 자료·파일·좌표 | `image_coordinate_frames` | 이미지의 좌표계·크기·변환 관계 | `asset_versions`, `stored_files`, `image_coordinate_frames` |
| 자료·파일·좌표 | `record_aliases` | 외부 레코드 식별자와 내부 자료 버전의 대응 | `asset_versions`, `import_packages` |
| 규격·인계·감사 | `schema_definitions` | 적용 규격의 이름·버전·정의 파일 연결 | `stored_files` |
| 규격·인계·감사 | `import_packages` | 인계 묶음과 매니페스트·교체 관계 | `projects`, `stored_files`, `import_packages` |
| 규격·인계·감사 | `audit_events` | 사용자·프로젝트의 변경·실행 사건 기록 | `projects`, `users` |
| OCR·추출·근거 | `ocr_runs` | 처리 시도별 OCR 실행과 사용한 자료·규격·좌표계 | `asset_versions`, `review_attempts`, `import_packages`, `schema_definitions`, `stored_files`, `image_coordinate_frames` |
| OCR·추출·근거 | `ocr_tokens` | OCR이 읽은 개별 문구·점수·좌표 | `ocr_runs` |
| OCR·추출·근거 | `poster_extractions` | OCR에서 구성한 행사 정보 추출본 | `asset_versions`, `schema_definitions`, `ocr_runs`, `poster_extractions`, `stored_files` |
| OCR·추출·근거 | `poster_field_observations` | 행사 정보의 필드별 관측값과 상태 | `poster_extractions` |
| OCR·추출·근거 | `evidence_records` | 추출·검수 판단에 사용한 파일·좌표·OCR 근거 | `poster_field_observations`, `item_results`, `asset_versions`, `stored_files`, `image_coordinate_frames`, `ocr_runs` |
| OCR·추출·근거 | `evidence_ocr_tokens` | 근거와 OCR 문구 사이의 연결 | `evidence_records`, `ocr_tokens` |
| 검수 기준 | `criteria_sets` | 프로젝트별 검수 기준 묶음 | `projects` |
| 검수 기준 | `criteria_drafts` | 편집 중인 기준 초안 | `criteria_sets`, `asset_versions`, `users` |
| 검수 기준 | `criteria_versions` | 확정된 불변 기준 버전과 출처 | `criteria_sets`, `asset_versions`, `criteria_drafts`, `criteria_versions`, `import_packages`, `users` |
| 검수 기준 | `criteria_items` | 기준 버전에 속한 개별 검사 항목 | `criteria_versions`, `asset_versions` |
| 검수 실행·결과 | `review_runs` | 이미지 버전·기준 버전을 고정한 검수 실행 | `projects`, `asset_versions`, `criteria_versions`, `review_runs` |
| 검수 실행·결과 | `review_attempts` | 한 검수 실행의 처리 시도·단계·오류 | `review_runs` |
| 검수 실행·결과 | `item_results` | 처리 시도에서 나온 항목별 판정 | `review_runs`, `review_attempts`, `criteria_items`, `ocr_runs`, `poster_extractions` |
| 검수 실행·결과 | `run_item_selections` | 실행의 기준 항목마다 현재 채택한 결과 | `review_runs`, `criteria_items`, `item_results` |

포함 수는 사용자·세션·프로젝트 4개 + 자료·파일·좌표 5개 + 규격·인계·감사 3개 + OCR·추출·근거 6개 + 검수 기준 4개 + 검수 실행·결과 4개 = **26개**다. Alembic 변경 이력 테이블은 별도다.

이메일 기반 정식 로그인에 필요한 `users`·`user_sessions`와 프로젝트 소속인 `project_members`를 설계 범위에 포함한다. 설계 시점에는 실제 인증이 후속이었으며 이후 [C08](구현_C08_인증과계정관리.md)에서 이메일/개발 DB 인증·세션·권한 helper를 구현했다. 실제 업무 API/React 연결은 후속이다. 기존 `admin/admin`은 개발용 계정으로 유지하며 정식 이메일 계정과 구분한다.

## 4. 첫 스키마에서 제외할 컬럼과 FK 11개

기존 ERD에서는 아래 컬럼이 후속 테이블을 참조한다. 첫 스키마에서는 **컬럼과 FK를 함께 제외**하고, 대상 테이블을 도입하는 마이그레이션에서 함께 추가한다. FK만 없애고 연결되지 않는 UUID 컬럼을 먼저 남겨 두지 않는다.

| 포함 테이블 | 후속으로 미룰 컬럼 | 참조 대상 |
|---|---|---|
| `evidence_records` | `reference_field_result_id` | `reference_field_results` |
| `evidence_records` | `human_decision_id` | `human_result_decisions` |
| `evidence_records` | `reference_record_id` | `reference_records` |
| `criteria_items` | `source_reference_record_id` | `reference_records` |
| `review_runs` | `submission_version_id` | `submission_versions` |
| `review_attempts` | `work_unit_id` | `review_work_units` |
| `item_results` | `work_unit_id` | `review_work_units` |
| `item_results` | `agent_execution_id` | `agent_executions` |
| `item_results` | `adjudicates_conflict_id` | `result_conflicts` |
| `item_results` | `reference_check_id` | `reference_checks` |
| `run_item_selections` | `selection_event_id` | `result_selection_events` |

## 5. 관계 정리에서 발견한 후속 설계 항목

| 항목 | 확인한 사실 | 다룰 단계 |
|---|---|---|
| 처리 시도 번호의 유일성 | 기존 `review_attempts`는 `(work_unit_id, attempt_no)`를 유일 키로 사용한다. `work_unit_id`를 제외하므로 이 제약을 그대로 가져올 수 없다. 현재 프로젝트 명세의 실행별 시도 번호 `(run_id, attempt_no)`를 기준으로 설계한다. | 설계 5단계 |
| 파일·인계 묶음의 순환 참조 | `stored_files.import_package_id`가 `import_packages`를, `import_packages.manifest_file_id`가 `stored_files`를 참조한다. 테이블 정의와 FK 추가 순서를 분리하고, 최초 삽입 시 필요한 NULL 허용·연결 순서를 확정해야 한다. | 설계 2·3·6단계 |
| 자기 참조 7개 | `assets`, `stored_files`, `image_coordinate_frames`, `import_packages`, `poster_extractions`, `criteria_versions`, `review_runs`에 부모·이전 버전·재시도 연결이 있다. 삭제 정책과 잘못된 자기 연결을 막는 규칙을 검토한다. | 해당 영역과 설계 6단계 |
| 프로젝트 경계 | 현재 ERD의 개별 ID FK 목록만으로 서로 다른 프로젝트의 자료·기준·결과 연결 방지가 확정되지는 않는다. 같은 프로젝트·기준 버전·실행에 속해야 하는 연결을 별도로 검증한다. | 설계 6단계 |
| 실행과 판정의 분리 | `review_runs`·`review_attempts`·`item_results`의 실행 상태와 항목 판정을 구분한다. 기준 버전 안의 `rule_code` 중복도 허용한다. | 설계 4·5·6단계 |

ERD에서 이번 26개 테이블이 출발점인 FK는 **81개**다. 이번 범위 안의 대상에 연결되는 검토 대상은 **70개**, 후속 테이블을 참조해 제외하는 대상은 **11개**다. 사용자세션 FK 1개가 추가된 분류 결과이며, 정합성 검토 후 확정할 실제 FK 개수와는 다를 수 있다.

## 6. 이번 단계 완료 확인

- 이메일 로그인 요구사항을 반영한 ERD의 47개 테이블을 포함 26개와 후속 21개로 중복 없이 분류했다.
- 26개 테이블의 역할과 이번 범위의 직접 참조 대상을 정리했다.
- 후속 테이블을 참조하는 6개 테이블의 11개 컬럼·FK를 찾아 제외 대상으로 기록했다.
- 순환 참조 1개 묶음과 자기 참조 7개, 제외 컬럼을 사용하는 유일 제약을 확인했다.
- 이메일 로그인 구조는 논리·물리 ERD와 설계 문서에 반영했다. 실제 DB 테이블·ORM·마이그레이션·인증 코드·패키지·컨테이너에는 변경을 적용하지 않았다.

진행 갱신: [설계 6단계 — 전체 정합성](물리설계_06_전체정합성.md)과 제약 목록, [추가 설계 7단계 — 인증·권한](추가설계_07_인증과권한.md)과 [추가 설계 8단계 — API·화면·JSON](추가설계_08_API와화면JSON.md)과 [추가 설계 9단계 — 저장·복구](추가설계_09_저장과이전복구.md)까지 작성했다. 현재 설계는 26개 테이블·395개 컬럼·PK 26개·UNIQUE 41개·FK 81개·부분 유일 인덱스 2개다.
