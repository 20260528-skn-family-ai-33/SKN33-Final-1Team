# C09 — 파일 저장과 기준 확정

작성일: 2026-10-18

상태: **C09 구현·검증 완료.** 기본 559개·하위 7개, PostgreSQL/API/실제 HTTP 1,215개가 통과했다. C09 신규 사례는 125개다.

C09는 별도 v1 앱에 프로젝트·이미지·기준 묶음·초안·기준 확정 API를 연결한다. PostgreSQL의 실제 app 역할과 전용 로컬 저장소를 사용한다. 기존 React·JSON API·launcher는 기존 경로를 유지한다. 마이그레이션은 추가하지 않고 **M008**을 유지한다. 이후 [C10 — 검수 접수와 원자적 결과](구현_C10_검수접수와원자적결과.md)도 완료했다. 다음은 C11이다.

파일 바이트/디코딩/해시는 DB 연결을 잡지 않은 상태에서 처리한다. 파일 준비 뒤 최종 저장 트랜잭션에서 계정·세션·멤버·프로젝트 보관 상태를 다시 확인한다. 응답은 명시한 필드만 투영하며 storage_key·서버 경로·DB 예외·비밀번호·세션 토큰은 노출하지 않는다.

## 2. 실행 전제와 초기화

[C08 앱/계정 설정](구현_C08_인증과계정관리.md)과 [C07c M008/권한 점검](구현_C07c_권한과최종스키마.md)을 먼저 따른다. C09 검증은 일상 DB에 migration·seed를 적용하지 않았다. 일상 DB가 비어 있다면 아래 웹 앱을 바로 실행할 수 있다는 뜻이 아니다.

프로젝트 가상환경의 [requirements-v1.txt](../../requirements-v1.txt)를 사용한다. rfc8785 **0.1.4**, portalocker **3.2.0**, Pillow **12.3.0**, python-multipart **0.0.32**를 직접 고정했다. 이번에 새로 설치한 패키지는 앞의 두 개다. 실제 JCS 직렬화는 [rfc8785 공식 배포](https://pypi.org/project/rfc8785/0.1.4/), 잠금은 [portalocker 공식 문서](https://portalocker.readthedocs.io/en/latest/)의 공유·배타·비차단 기능을 사용한다. 직접 의존성 고정은 모든 플랫폼의 전체 전이 의존성 잠금을 뜻하지 않는다.

저장소는 서비스 전용 계정이 소유한 **새 절대 경로**로 직접 초기화한다. 이미 존재하는 경로는 덮어쓰지 않는다. 아래 경로는 사용자가 정할 예시이며 실제 저장소를 생성해 놓은 것이 아니다.

```bash
.venv/bin/python -m backend.app.storage --root /absolute/private/creative-checker-files init
.venv/bin/python -m backend.app.storage --root /absolute/private/creative-checker-files check
```

app 전용 환경 파일에 `STORAGE_ROOT=/absolute/private/creative-checker-files`를 명시한다. 기존 `CC_APP_ENV_FILE` 절대 경로 선택 방식을 유지하며 루트 `.env`를 웹이 자동으로 읽지 않는다. owner/admin 자격 증명을 웹에 넘기지 않는다.

```bash
CC_APP_ENV_FILE=/absolute/private/app.env .venv/bin/python -m uvicorn backend.app.main:create_app --factory --host 127.0.0.1 --port 8000 --workers 1 --no-proxy-headers
```

웹 시작 시 루트를 자동 생성하지 않는다. 루트 marker·실제 파일시스템 기능·서비스 배타 잠금·저널/primary DB 대조가 성공해야 ready가 된다. STORAGE_ROOT를 생략하면 C08 인증 전용 모드와 그 검증을 유지한다. 업무 모드에서도 health는 검수/worker/model이 연결되지 않아 degraded이며 storage의 ready만 별도로 표시한다.

## 3. 공개 API

접두부 `/api/v1`, 계약 `cc-api-v1`, 세션·서명 CSRF·현재 프로젝트 권한은 C08을 사용한다. POST 성공은 201과 Location, 일반 조회·수정은 200이다.

| 경로 | 메서드 | 내용 |
|---|---|---|
| /projects | GET, POST | 현재 멤버의 프로젝트 목록·owner로 프로젝트 생성 |
| /projects/{project_id} | GET, PATCH | 현재 역할·보관 상태 조회, owner 이름/보관/복구 변경 |
| /projects/{project_id}/images | GET, POST | 이미지 버전 목록, image 파일 한 개 업로드 |
| /images/{image_id} | GET | 표시 이미지 DTO |
| /images/{image_id}/content | GET | 실제 프로젝트 권한 검사 후 표시 PNG |
| /projects/{project_id}/criteria-sets | GET, POST | 기준 묶음 목록/생성 |
| /projects/{project_id}/criteria-drafts | GET, POST | 초안 목록/생성 |
| /projects/{project_id}/criteria-drafts/{draft_id} | GET, PUT | 초안 조회/전체 편집값 저장 |
| /projects/{project_id}/criteria-versions | GET, POST | 확정 버전 목록/멱등 확정 |
| /projects/{project_id}/criteria-versions/{criteria_version_id} | GET | 과거 불변 내용과 현재 draft_is_current 조회 |

일반 목록은 `(created_at DESC,id DESC)`, 기준 버전은 `(version_no DESC,id DESC)` 키셋이다. limit 기본 20·최대 100, items/has_more/next_cursor를 반환하며 total_count를 추정하지 않는다. cursor는 actor·프로젝트·종류·정규화 필터·limit·마지막 키·24시간 만료를 HMAC으로 결합한다. 매 페이지 현재 권한을 다시 확인한다. 위조·다른 문맥·만료는 CURSOR_INVALID 400, 알 수 없는/중복 query와 잘못된 limit은 422다.

프로젝트 archived 필터는 exclude/include/only다. 초안/버전은 image_id/criteria_set_id 필터를 허용한다. 다른 프로젝트의 필터 ID도 404다. 보관 프로젝트는 조회와 과거 성공의 멱등 재전송을 허용하고 새 쓰기를 거부한다. 재전송도 현재 active editor/owner 권한이 필요하다.

## 4. 이미지와 파일 일관성

멀티파트는 `image` 한 개만 받는다. 실제 스트림 전체는 20 MiB + 256 KiB framing 한도, 파일 자체는 **20 MiB**다. Content-Length·이름·확장자·클라이언트 MIME을 신뢰하지 않는다. parser 실패/한도/연결 종료 시 임시 파일도 닫는다.

실제 정적 PNG/JPEG/WEBP만 완전히 디코딩한다. 애니메이션, 한 변 8192 초과, 1천만 픽셀 초과는 거부한다. 원본 바이트/SHA256을 그대로 저장하고 EXIF 회전을 한 번 적용한 뒤 투명을 흰 배경에 합성한 RGB PNG를 별도 저장한다. 변환 식별자는 cc-display-rgb-white-exif-v1이다. 원본/표시 치수와 프레임 두 개를 기록한다. normalized_original_pixels는 표시 이미지 좌표이며 OCR의 2배 좌표를 만들지 않는다. verification_state는 기존 스키마의 unverified를 유지한다.

매 업로드는 새 asset·version 1·파일 UUID를 발급한다. 같은 바이트도 합치지 않는다. 클라이언트 파일명은 경로로 사용하지 않는다.

1. 작업 잠금 아래 ID·파일 의도·해시/크기·프레임·변환 정보를 저널에 기록한다.
2. 같은 볼륨의 staging에 O_EXCL로 쓰고 파일/부모 디렉터리를 fsync한다.
3. 공유 gate에서 hard-link로 최종 경로를 게시하고 최종 부모를 fsync한 뒤 자신의 staging 이름만 제거/동기화한다. payload에 replace를 사용하지 않는다.
4. 트랜잭션 advisory 작업 잠금 → 프로젝트 → 사용자/세션/멤버를 검사하고 두 파일·asset·version·두 프레임·감사 이벤트를 한 트랜잭션에 저장한다.
5. 성공한 커밋을 확인한 뒤 응답한다. 확정 rollback의 40001/40P01만 같은 준비 데이터로 최대 3회 시도한다.

루트에서 모든 경로를 dir_fd/O_NOFOLLOW로 연다. 소유자·권한·장치/inode·일반 파일·링크 수를 검사하고 심볼릭 링크·임의 하드 링크·FIFO·다른 볼륨·바뀐 루트를 거부한다. 게시 중 자신의 staging과 같은 inode인 일시적 링크만 저널에 따라 마무리한다. 최종 경로 충돌 시 기존 바이트를 덮어쓰지 않는다.

파일 조회는 권한 검사의 UoW가 끝난 후 실제 크기·SHA256을 검사한 열린 fd를 스트리밍한다. 응답은 PNG/nosniff/no-store다. 누락·변조는 FILE_UNAVAILABLE 503이며 GET으로 DB의 state/sha256을 바꾸지 않는다.

## 5. 저널과 커밋 미확인

저널의 phase는 planned/staged/finalized다. db_outcome은 운영 메모이며 실제 DB의 대체물이 아니다. COMMIT 응답 유실은 새 primary 연결에서 작업 advisory try-lock을 얻고 파일·asset·version·프레임·감사 레코드의 식별자와 의도를 대조한다.

| 대조 결과 | 처리 |
|---|---|
| 모든 참조/의도가 일치 | committed, 기존 이미지 UUID의 성공 복원 |
| 모두 없고 작업 DB 잠금을 얻음 | not_committed, 파일 보존·503. 새 UUID를 자동 발급/재저장하지 않음 |
| 일부만 존재하거나 의도가 다름 | conflict, 보존·503/시작 차단 |
| DB 불가·replica·진행 중 잠금 | unresolved, 보존·503/시작 차단 |

재시작은 서비스/gate 배타 잠금과 작업 잠금 아래 같은 대조를 수행한다. committed 파일은 실제 크기/해시도 확인한다. 미참조 파일과 staging을 자동 삭제하거나 격리하지 않는다. C14에서 유예·dry-run·검토한 GC/수입/백업 복원 절차를 연결한다. `storage check`는 파일시스템 기능 검사이며 DB reconciliation은 웹 시작 시 별도로 수행한다.

## 6. 초안과 기준 확정

JSON은 최대 256 KiB·깊이 32·노드 100000이다. 중복 키·NaN/Infinity·NUL·고립 surrogate·2^53-1을 넘는 JSON 정수는 거부한다. revision은 1..9223372036854775807의 **십진 문자열**이다.

초안 생성은 image/set/출처 자료의 실제 프로젝트를 확인한다. items 최대 100개, 고유 id와 text/type/source/selected만 받는다. source_documents 미제공/null은 null, []은 []로 보존한다. 선택된 빈 문구도 편집 중에는 저장할 수 있다.

PUT은 expected_revision과 전체 raw_requirements/items/source_documents를 요구한다. revision 불일치를 먼저 409로 거부한다. 같은 내용은 revision/작성자/시각을 유지하고 바뀐 내용만 +1 한다. 최대 revision의 실제 변경은 REVISION_LIMIT_REACHED다.

확정은 UUID v4 Idempotency-Key와 `{draft_id,expected_revision}`만 받는다. 실제 actor·operation·project·본문을 요청 지문에 포함한다. `(confirmed_by,confirmation_key)` 전역 범위와 advisory 잠금을 사용해 서로 다른 프로젝트에서도 같은 키의 다른 요청은 409로 거부한다. 같은 성공은 revision/보관 변경 후에도 같은 UUID로 200·Idempotency-Replayed:true를 반환한다.

확정할 선택 항목은 1..100개·비공백 문구여야 한다. 선택 항목만 1부터 복사하고 새 기준 버전·항목·감사·멱등 정보를 같은 트랜잭션에서 봉인한다. 프로젝트별 version_no를 발급한다. 누락된 rule/field/expected/is_required/source_asset/locator/applicability/check_scope는 SQL NULL이며 가짜 규칙·출처를 만들지 않는다.

전체 초안과 선택 스냅샷의 JCS 해시는 서로 다르다. 항목 UUID·발급 번호·시각·키는 내용 해시에서 제외한다. 같은 내용의 새 키는 새 버전과 같은 criteria_hash가 가능하다. source_item은 원래 다섯 필드를 보존한다. draft_is_current는 조회 당시 revision/state 비교이며 불변 해시에 포함하지 않는다.

## 7. 검증과 후속 범위

최종 실행 수·환경·원본 보존·소스 지문은 [C09 검증 JSON](verification/2026-10-18-implementation-C09.json), 설계 ID별 범위는 [API/STORE 대응표](검증_C09_API와STORE_대응표.md)를 따른다.

검증 코드는 [계약/실제 파일·프로세스](../../backend/tests/test_c09_contracts_storage.py), [실제 PostgreSQL/ASGI](../../backend/tests/test_c09_business_integration.py), [실제 HTTP/프로세스 재시작](../../backend/tests/test_c09_live_integration.py)이다. 단위 검증은 .venv/bin/python -m pytest로 실행하며 DB 검증은 명시한 TEST_DB_* 격리 자격 증명이 필요하다. DB 시험은 무작위 creative_checker_test_ 이름만 생성/삭제하고 일상 DB와 owner default ACL을 전후 대조한다.

현재 macOS에서 fsync·no-clobber·다른 프로세스의 공유/배타/비차단 잠금과 강제 프로세스 종료 복구를 확인했다. **Linux 운영 호스트, Windows 저장 기능, 네트워크 파일시스템, 전원 장애 내구성은 이번에 인증하지 않았다.** Linux 단일 호스트의 실제 운영 검증·프록시/브라우저·릴리스 인증은 C12/C15에서 남아 있다. 서비스 잠금은 단일 저장소/단일 프로세스 범위다.

C10 검수/OCR 접수·결과, C11 화면 연결, C13 독립 worker, C14 GC/이전/백업 복원, C15 운영 적용은 이번 산출물의 완료 범위에 넣지 않는다. C10 백엔드도 완료했으며 사용자가 다음 단계를 지시하면 C11만 진행한다.
