## 2. 이번에 강제하는 조건

- 기준 묶음 이름은 비어 있지 않아야 한다. 같은 표시명의 여러 묶음을 허용하며 과거 등록자를 모르면 created_by=NULL을 유지한다.
- 편집 초안 revision은 1 이상의 BIGINT, 상태는 editing/archived다. 초안 항목은 배열이며 처음에는 빈 배열을 허용한다. 원문·미선택 항목·순서를 보존한다. 실제 초안 수정의 expected_revision 경쟁 검사와 항목별 DTO 검증은 C09다.
- 버전 번호는 기준 묶음이 아닌 **프로젝트 안에서 유일**하다. 다른 묶음의 같은 번호도 거부하고 다른 프로젝트의 같은 번호는 허용한다. 실제 프로젝트 잠금·번호 발급 서비스는 후속이다.
- service_confirmation은 confirmed와 실제 초안 ID·revision·초안 해시·비어 있지 않은 원문·확정자·확정 시각·멱등키·요청 해시·비어 있지 않은 요청 해시 규격을 모두 요구한다. 각 필수값을 하나씩 NULL로 만드는 경우도 거부한다.
- imported는 인계 묶음과 원문 스냅샷, legacy_snapshot은 원문 스냅샷과 원래 버전 값을 요구한다. 두 경로는 unconfirmed이며 로컬 확정자/시각·요청 키/해시/규격은 모두 NULL이다. 출처가 reported confirmed여도 로컬 확정으로 승격하지 않는다.
- 기준·초안·요청 해시는 소문자 SHA256 형식이다. 이 단계에서 JCS 직렬화나 실제 내용 해시 계산·일치를 구현한 것은 아니다. 같은 내용 해시의 여러 버전을 허용한다.
- UNIQUE (confirmed_by, confirmation_key)는 같은 사용자의 키 재사용을 다른 프로젝트에서도 거부한다. 다른 사용자 또는 다른 키는 구분한다. 동일 요청 반환·내용 충돌의 HTTP 409·현재 권한 재검사까지 구현했다는 뜻은 아니다.
- 항목 position은 1 이상, category는 information/visual/unknown이며 문구와 제공한 외부 ID는 비어 있지 않아야 한다. 같은 버전의 position·외부 ID 중복은 거부한다. 외부 ID가 NULL인 복수 항목, 다른 버전의 같은 외부 ID, 같은 rule_code의 복수 항목은 허용한다. [PostgreSQL UNIQUE와 NULL](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)
- is_required·expected_value의 미제공은 SQL NULL로 보존한다. 선택된 항목이라는 이유로 is_required=true를 채우지 않는다. expected_value의 실제 스칼라·배열·객체와 명시 JSON null은 저장할 수 있으며 원문 필드 누락과 null은 source_item_jsonb로 구분한다.
- 출처 문서는 배열, 원문 스냅샷·항목·출처 위치·적용 조건·검사 범위는 객체다. 이 컬럼들의 JSON null·잘못된 외형은 거부한다. Python None은 SQL NULL, 명시 JSON.NULL은 JSON null로 구분한다. [SQLAlchemy JSON NULL 구분](https://docs.sqlalchemy.org/en/21/core/type_basics.html#sqlalchemy.types.JSON)
- source_version_jsonb는 과거 버전의 원래 값과 타입을 보존하므로 객체로 제한하지 않는다. 숫자 1과 문자열 "1", boolean·배열·객체·명시 JSON null을 구분해 저장한다. legacy 경로의 필수값은 SQL NULL을 금지하며, 원문이 명시한 JSON null은 원문 값으로 보존한다. 이 해석을 [전체 정합성의 가변 JSON 규칙](물리설계_06_전체정합성.md#3-단일-행-check의-공통-규칙)에 명확히 적었다. 원문이 없는데 JSON null로 채우는 수입 어댑터를 구현한 것은 아니다.
- 제공한 시각은 유한값이며 updated_at은 created_at보다 이를 수 없다. 직접 자기 자신을 복사 출처로 지정하는 행은 거부한다. 긴 순환·파일/프로젝트 일치·항목 완결성과 봉인은 후속 검사다.

이 제약은 저장 구조와 한 행의 조건을 검사한다. 실제 기준 확정·해시 계산·사용자 권한·JSON 내부 ID·항목 전체의 일치와 불변성을 완성한 것으로 표시하지 않는다.

## 3. 적용과 실행 경계

M001·M002·M003 revision은 바꾸지 않았다. C04의 전체 inventory 테스트는 M003에 포함된 18개 metadata로 고정해 이후 head가 늘어도 같은 회귀를 검증한다. 이전 JSON 검증 기록은 당시 이력으로 보존한다. 새 패키지와 owner/app 설정 변경은 없다.

```bash
.venv/bin/python -m alembic -c backend/migrations/alembic.ini heads

# 검토용 증분 SQL만 생성. DB 접속·적용 없음.
CC_MIGRATION_ENV_FILE=.env.owner-test .venv/bin/python -m alembic -c backend/migrations/alembic.ini upgrade M003:M004 --sql

# 명시한 격리 DB에만 적용. 일상 DB에는 아직 실행하지 않는다.
CC_MIGRATION_ENV_FILE=.env.owner-test .venv/bin/python -m alembic -c backend/migrations/alembic.ini upgrade M004
```

owner 파일과 테스트 설정은 [C02 실행 방법](구현_C02_Alembic과사용자스키마.md#3-명시적-실행-방법)·[C01 테스트 설정](구현_C01_DB연결과트랜잭션.md#4-전용-postgresql-테스트-실행)을 따른다. 파일명은 사용자가 준비할 명시 설정의 예시이며 자격증명 파일을 저장소에 생성하지 않았다. 일반 앱·launcher의 자동 upgrade, 기존 객체 자동 채택·덮어쓰기와 파괴적 downgrade는 제공하지 않는다. 현재 M004는 M008까지 완성한 스키마가 아니므로 v1 쓰기를 공개할 수 없다.

## 4. 실제 검증 결과

```bash
.venv/bin/python -m pytest -q
TEST_DB_ENV_FILE=.env.db-test .venv/bin/python -m pytest -m db_integration -q
```

- 기본 Python **418 passed**, 추가 subtest 7 passed. DB 통합 491개는 기본 실행에서 제외했다. 신규 C05 정적 사례는 5개다.
- 실제 PostgreSQL **491 passed**: C01~C04/전체 적용 회귀 361개와 신규 C05 사례 130개다. macOS Python 3.12.14·기존 PostgreSQL 17.11을 사용했다.
- 실제 실행은 기존 로컬 역할 값을 명시적인 TEST_DB_* 자식 프로세스 환경으로 전달했다. 비밀은 명령행·출력·검증 JSON에 기록하지 않았으며 업무 DB명은 테스트 fixture에 전달하지 않았다. 일반 DB 설정의 자동 복사·업무 DB fallback은 없다.
- 22개 테이블·299개 컬럼의 실제 inventory와 metadata의 자료형·NULL/default·PK/UQ 컬럼 순서·CHECK 이름·코멘트를 대조했다. 신규 4개 테이블은 비어 있었고 이전 18개 테이블의 행 내용을 증분 전후 비교해 보존을 확인했다.
- 신규 CHECK 11개 묶음 모두에 대해 잘못된 행을 실제 DB가 거부했다. 세 생성 경로, 필수값 NULL, JSON 객체/배열, BIGINT 범위, 해시·시각·문자열·버전/항목 키를 검증했다.
- 숫자/문자열 원래 버전, SQL/JSON NULL, 미확인 필수 여부, 초안 미선택 항목·순서, 반복 rule_code·NULL 외부 ID·동일 내용 해시의 여러 버전을 보존했다. 2^53+1과 BIGINT 최댓값의 DB 저장을 확인했으며 브라우저 왕복 검증은 수행하지 않았다.
- 서로 다른 연결/트랜잭션의 프로젝트 버전 번호 경쟁과 동일 사용자·확정 키 경쟁에서 각각 하나만 커밋되고 나머지는 UNIQUE 위반 23505로 거부됐다. 이는 DB 유일성 검증이며 번호 발급·HTTP 멱등 응답 서비스의 완료가 아니다.
- 기존 criteria_versions 충돌은 앞서 만든 criteria_sets/drafts도 롤백하고 기존 객체·내용을 보존했다. M004 끝의 오류 주입은 M003의 객체 OID·행 내용·버전·기본 ACL을 보존했다. 빈 DB→M001→M002→M003→M004 전체 실패도 DDL·버전·기본 ACL을 함께 롤백했다.
- app의 새 테이블 권한 없음과 실제 SELECT 거부, 같은 revision 재실행, 파괴적 downgrade 거부를 확인했다. 일상 DB의 public 관계·기본 ACL은 전후 같았고 생성한 임시 DB는 모두 정리했다.
- pip check·구문 검사·과거 revision/기존 기능 소스 지문·문서 링크 검사를 통과했다. 기존 API·admin/admin·React·OCR·launcher는 변경하지 않았다.

실행 결과와 파일 지문은 [C05 검증 기록](verification/2026-10-17-implementation-C05.json)에 저장한다. Linux/Windows·브라우저·실제 OCR·네트워크 COMMIT 장애·파일 내구성·백업 복원은 이번에 실행하지 않았다.
