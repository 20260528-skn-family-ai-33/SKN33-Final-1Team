# C10 — 검수 접수와 원자적 결과 저장

작성일: 2026-10-18

상태: **C10 구현·검증 완료.** 기본 592개·하위 7개, PostgreSQL/API/실제 HTTP 1,265개 통과. C10 신규 사례는 83개다.

C10은 별도 v1 앱에서 검수 접수·멱등 재전송·명시적 재검수·BackgroundTasks 실행·결과/근거/OCR 조회·JSON 다운로드를 구현한다. **정식 head는 M008이며 새 migration은 없다.** 기존 admin/admin 개발 계정, React·JSON 시제품·launcher·OCR 알고리즘은 유지한다. 다음은 **C11 — React 연결과 URL/편집 상태 복원**이다.

## 2. 활성화와 기본값

[C08 인증/계정 설정](구현_C08_인증과계정관리.md)과 [C09 저장소 초기화](구현_C09_파일저장과기준확정.md)를 따른다. 일상 DB migration·실제 계정/프로젝트 seed·운영 배포는 이번에 실행하지 않았다. 기존 launcher는 계속 시제품을 실행한다.

[app 환경 예제](../../.env.v1.example)에 `REVIEW_PIPELINE=disabled`가 기본이다. 이 상태에서도 C09 API와 이미 저장된 검수 이력/멱등 재전송을 읽을 수 있지만 새 검수는 REVIEW_RUNTIME_UNAVAILABLE 503이다. 실행을 켜려면 명시적으로 초기화한 STORAGE_ROOT와 함께 다음을 지정한다.

```dotenv
REVIEW_PIPELINE=paddle-only
RUN_TARGET=local
```

기존 `.runtime/paddle-env`와 고정 모델이 준비되어 있어야 한다. 이번 단계는 모델을 설치/다운로드하거나 실제 모델 추론을 실행하지 않았다. 실제 OCR 선택 경로·브라우저·proxy 검증은 예정된 C12다. C10 통합 검증은 **APP_ENV=test의 명시적 합성 어댑터**를 사용했고, production에서 어댑터 주입은 거부한다. 테스트용 factory는 backend.tests 아래에 있으며 일반 환경 변수로 합성 판정 경로를 선택할 수 없다.

Paddle 어댑터는 모델 파일/manifest 무결성과 코드 식별자를 확인하고 기존 recognize_paddle·보수적 검수/행사 추출을 호출한다. 실제 local/cpu·입력 치수·pipeline 출력을 다시 확인한다. RunPod·원격 제출·독립 worker·자동 fallback을 추가하지 않았다. 준비 상태가 불명확하면 성공으로 표시하거나 다른 경로로 전환하지 않는다.

실행 프로필은 웹 한 프로세스·동시 추론 1개·queued/running 합계 16개로 제한한다. 같은 실행의 중복 BackgroundTasks 전달은 슬롯 대기 전에 제거한다. DB app 요청 pool 외에 서비스 소유권을 위한 **autocommit 연결 한 개**를 추가로 사용한다. 이 연결은 트랜잭션을 유지하지 않으며 추론/파일 I/O 동안 요청 UoW나 행 잠금은 잡지 않는다.

같은 DB의 다른 저장소 경로로도 두 번째 실행 프로세스를 시작할 수 없다. 서비스 advisory 잠금의 연결이 끊기면 기존 프로세스는 권한을 잃고 자동 재획득하지 않는다. disabled 앱은 작업을 인수/재시작 마감하지 않는다. 실행 프로필을 명시적으로 다시 시작해 복구한다.

## 3. 접수·재전송·재검수

| 메서드/경로 | 입력/동작 |
|---|---|
| POST /api/v1/reviews | `{project_id,image_id,criteria_version_id}`와 UUID v4 Idempotency-Key, 세션/CSRF |
| POST /api/v1/reviews/{run_id}/retry | `{}`와 새 사용자 동작의 키. terminal 서비스 실행만 허용 |
| GET /api/v1/reviews/{run_id} | 고정 입력/기준·현재 상태·채택 결과 요약 |
| GET /api/v1/projects/{project_id}/reviews | status/image_id 필터, created_at/id 내림차순 키셋 |
| GET /api/v1/reviews/{run_id}/ocr-records | 채택 OCR의 order/id 오름차순 페이지 |
| GET /api/v1/reviews/{run_id}/results/{result_id}/evidence | 해당 실행/채택 결과 근거의 id 오름차순 페이지 |
| GET /api/v1/reviews/{run_id}/export | 비밀/저장 경로 없는 cc-review-export-v1 JSON 다운로드 |

생성 성공은 queued 행과 감사 이벤트의 커밋을 확인한 **202 + Location**이다. 추론 완료를 뜻하지 않는다. 응답을 보낸 뒤 BackgroundTasks에 전달한다. 같은 키/본문은 **200·같은 run UUID·현재 실제 상태·Idempotency-Replayed:true**를 반환한다. queued 응답을 받은 실행이 완료됐다면 재전송은 completed를 반환한다.

요청 지문은 cc-request-jcs-v1 / create_review 또는 retry_review다. actor/operation/정규화 본문, retry의 source_run_id를 포함한다. 현재 설정·시각·키는 포함하지 않는다. DB 유일 범위 `(requested_by,request_operation,idempotency_key)`와 advisory 잠금으로 다른 본문은 409로 거부한다. 서로 다른 actor와 create/retry는 독립 범위다.

기존 키의 권한·지문을 먼저 검사하므로 초안/설정 변경·프로젝트 보관 후에도 과거 성공을 복원한다. 현재 editor/owner 권한은 여전히 필요하다. viewer는 이력 조회만 가능하다. 접수 커밋 응답 유실은 새 primary/동일 키 잠금 대조로 기존 행을 확인하며 새 UUID를 자동 발급하지 않는다.

새 요청은 활성 프로젝트·실제 같은 프로젝트/image의 봉인된 서비스 확정 기준·현재 draft revision/state·검증한 파일·실제 실행 설정을 검사한다. 초안이 바뀌면 CRITERIA_STALE다. retry는 원 실행 completed/failed일 때만 허용하며 진행 중은 REVIEW_NOT_TERMINAL, 외부 이력은 SOURCE_NOT_RETRYABLE다. 과거 실행/결과를 바꾸거나 새로운 입력을 retry 본문에 넣을 수 없다.

## 4. 고정 입력과 처리 시도

접수 시 project_name_snapshot, 이미지/기준 UUID, 원본/표시 SHA256·치수, 2배 전처리 정책, 모델/코드 식별, workflow·all_selected_v1·총 시도 1회를 고정한다. cc-manifest-jcs-v1 / review_input 지문에 아직 생성하지 않은 OCR 입력 파일 해시를 넣지 않는다. 이후 프로젝트 이름이나 편집 초안이 바뀌어도 접수된 실행의 고정 입력은 유지한다.

queued 실행을 잠근 뒤 새 attempt·랜덤 worker_token·active 포인터·running을 한 트랜잭션에서 기록한다. 추론은 트랜잭션 밖에서 한다. 완료/실패 쓰기는 run→현재 attempt의 상태·포인터·토큰을 다시 확인한다. 오래된 토큰·이미 마감된 시도·다른 executor는 저장할 수 없다. 토큰은 응답/export/저널에 넣지 않는다.

표시 PNG를 읽고 2배 LANCZOS 입력을 만든다. OCR 입력 좌표는 표시 좌표로 **한 번만** 복원하며 normalized_original_pixels는 표시 프레임을 뜻한다. 실제 OCR 입력 파일/2배 프레임도 별도로 기록한다. confidence/bbox가 없으면 NULL이며 0이나 가상 박스로 채우지 않는다. 외부 숫자/문자 OCR ID는 타입과 함께 실제 token UUID로 대응한다.

단계 진입/실제 처리 경계에서 preprocessing→ocr→review를 보고한다. 타이머로 진행률을 증가시키지 않는다. health의 모델 파일 준비와 실제 추론 성공도 구분한다. 설정된 모델 파일을 확인해도 해당 설정으로 성공한 추론이 없으면 ocr_runtime은 unknown이다. worker heartbeat는 이번에 측정하지 않는다.

## 5. 준비 파일과 원자적 완료

출력은 실제 local/cpu·치수·형식·개수·유한 좌표/점수·고유 ID·모든 기준 항목·실제 근거 출처를 검사한다. OCR 최대 1000개, 근거 최대 10000개, 개별 JSON 출력 16 MiB, 준비 plan 48 MiB, 내부 JCS의 노드/깊이 한도를 함께 적용한다. 한도는 상한이며 합성 그래프의 노드 한도가 먼저 적용될 수 있다. 잘못된 항목을 잘라내 completed로 만들지 않는다.

OCR 입력 PNG, 수신 OCR 객체의 검증된 JSON, 행사 추출 JSON, 검사기 출력 JSON을 private staging에 준비하고 파일 크기/SHA256을 계산한다. 모델 고유 출력/진단 파일은 staging에 보존한다. 수신 객체를 직렬화한 JSON과 모델 프로세스가 작성한 원래 파일 바이트를 같은 파일이라고 부르지 않는다. 잘못된 출력도 가능한 범위의 진단 JSON으로 보존하며 공개 API에 임의 예외를 노출하지 않는다.

준비 plan은 모든 token/result/observation/evidence UUID와 연결·값을 확정한다. result manifest는 실제 verdict/사유/관찰/검사 버전·OCR/추출/검사 원문 해시·토큰·근거·필드 관찰·연결 ID를 포함한다. 요청 시각·조회 URL·meta는 제외한다. 준비 plan 자체도 SHA256으로 저널에 결합한다.

C09의 공유 gate·작업 잠금 아래 네 파일을 덮어쓰기 없이 게시한 뒤 작업 DB advisory 잠금→프로젝트/run/attempt를 잠근다. 다음 전체를 **한 UoW**에서 저장한다.

1. stored_files 네 개·실제 OCR 입력 프레임.
2. OCR run·문구 전체·OCR 봉인.
3. 행사 추출·필드 관찰·실제 OCR 출처 근거·추출 봉인.
4. 모든 불변 기준 항목의 결과·근거·token 연결·단일 attempt의 전체 채택.
5. attempt succeeded·run completed/요약/결과 manifest·run 봉인·감사 이벤트.

M007 deferred 가드까지 커밋된 뒤 결과가 완료된다. 중간 SQL/제약 실패는 위 그래프 전체가 롤백된다. 이미 게시한 바이트를 자동 삭제하지 않는다. 확인된 40001/40P01 롤백만 같은 준비 출력으로 최대 3회 DB 저장을 시도하며 OCR을 다시 호출하지 않는다. 일반 계약/DB 오류를 무한 재시도로 바꾸지 않는다.

전체 항목은 있어도 failed/unsupported가 있으면 verdict는 NULL이고 표시 status는 review다. all_selected_v1은 fail 하나 이상→fail, 그 외 failed/unsupported/review→review, 모두 completed/pass→pass다. completed는 자동 처리 집합의 완료이며 사람 승인/학습 라벨이 아니다. 추출 null/빈 OCR만으로 absent/resolved를 만들지 않으며 외부 표준 미확보는 schema_unavailable로 남긴다.

## 6. 커밋 미확인·재시작

결과 COMMIT 응답 유실은 새 primary·작업 try-lock·run/채택 attempt/manifest·파일 의도를 대조한다. 같은 성공이면 기존 완료로 확인한다. 다르거나 DB/잠금이 불명확하면 파일/저널을 보존하고 실행을 임의로 failed/completed로 추정하지 않는다. unresolved는 running으로 남을 수 있으며 운영 대조 또는 실행 프로필의 명시적 재시작이 필요하다.

시작 시 서비스 소유권과 저장소 잠금을 얻은 뒤 결과 저널을 먼저 대조한다. 이미 커밋된 결과는 그대로 유지하고 파일 해시/크기도 확인한다. 그 다음 이 프로필의 남은 작업을 마감한다.

| 발견 상태 | 처리 |
|---|---|
| queued·attempt 없음 | RESTART_BEFORE_START failed |
| running·active attempt | attempt unknown·포인터 해제·RESTART_DURING_EXECUTION failed·outcome_unknown |
| completed/failed/imported | 상태/판정 보존 |
| postgres_worker 행 | 인수/회수/마감하지 않음 |

자동 재추론·원격 재제출·lease 회수는 없다. 새 사용자 동작의 retry만 새 실행을 만든다. GC·격리·물리 DELETE·백업 복원은 C14에 남아 있다. staging/진단/저널/미참조 게시 파일은 이번에 정리하지 않는다.

## 7. 조회와 다운로드

상세는 position 순 결과 최대 100개와 OCR/추출 요약을 제공한다. 근거 본문은 []로 두되 evidence_count/evidence_complete/evidence_url을 함께 제공한다. OCR/근거는 limit 기본 20·최대 100의 현재 권한·actor/run/OCR/result 문맥에 결합한 서명 cursor를 사용한다. 채택 전 OCR은 pending/none이며 빈 목록을 근거 부재로 확정하지 않는다.

results_complete는 봉인과 채택 attempt, 기준 전체 집합이 확인된 때만 true다. 불완전 외부 이력이 imported라는 이유만으로 true가 되지 않는다. 구조화 observed_value는 observed_text로 stringify하지 않는다. 원래 source·실행 상태와 로컬 자동 verdict를 구분한다. 실제 importer·외부 이력 전체 호환 검증은 C14에 남아 있다.

일반 JSON은 2 MiB를 넘으면 RESPONSE_TOO_LARGE 503과 export 주소를 반환한다. JSON 다운로드는 생성 단계에서 50 MiB를 검사한 뒤 스트리밍한다. export는 meta/토큰/비밀번호/storage_key/DB·원격 주소 없이 고정 식별자·해시·허용된 설정·채택 결과/근거·OCR 문구·추출 요약과 private 원문 파일 참조를 제공한다. private 원문은 embedded=false·사유·가용성 미검증으로 명시하며 외부 handoff 표준 준수를 주장하지 않는다. 서버 UUID 파일명·nosniff·no-store를 적용한다.

## 8. 검증 기록과 다음 단계

기본 검사는 .venv/bin/python -m pytest -q로 실행한다. DB 검증에는 C08과 같은 명시적 TEST_DB_* 자격 증명이 필요하며, TEST_DB_ALLOW_CREATE=1과 함께 테스트 전용 파일을 지정할 수 있다. fixture는 지정한 업무 DB 이름을 사용하지 않고 무작위 테스트 DB만 생성/삭제한다.

```bash
TEST_DB_ENV_FILE=/absolute/private/test-db.env .venv/bin/python -m pytest backend/tests/test_c10_reviews_integration.py backend/tests/test_c10_live_integration.py -m db_integration -q
```

정확한 최종 개수·환경·실행별 SHA256·소스/기존 파일 보존·DB 전후 대조는 [C10 JSON](verification/2026-10-18-implementation-C10.json), 설계별 범위는 [대응표](검증_C10_API와STORE_대응표.md)를 따른다.

[독립 계약 검사](../../backend/tests/test_c10_contracts.py), [실제 DB/파일/ASGI](../../backend/tests/test_c10_reviews_integration.py), [실제 HTTP·강제 종료/재시작](../../backend/tests/test_c10_live_integration.py)을 실행했다. 마지막 검사는 실제 Uvicorn의 202 응답 뒤 합성 OCR을 의도적으로 대기시키고 SIGKILL한 다음, 새 프로세스에서 기존 완료 보존·중단 실패·자동 추론 없음·명시적 retry만 실행함을 확인한다. 실제 DB 커밋 응답 유실은 커밋 전후 오류 주입이며 네트워크 장비에서 패킷을 제거한 실험은 아니다.

검증은 무작위 creative_checker_test_ DB·합성 사용자·전용 임시 저장소만 사용했다. 일상 DB의 public/OID/default ACL과 테스트 DB 목록을 전후 대조한다. macOS 기능 검증이며 Linux 운영·전원 장애 내구성·실제 OCR 품질/성능·브라우저/proxy·영속 worker·수입/복원·배포 인증은 아니다.
