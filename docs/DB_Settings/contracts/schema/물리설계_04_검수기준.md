## 1. 근거와 공통 규칙

근거는 [범위·관계](../../DB_통합설계서.html#source-02), [사용자·파일](../../DB_통합설계서.html#source-03), [규격·OCR·근거](../../DB_통합설계서.html#source-04), [ERD 초안](../../../ERD_물리.md), [프로젝트 명세](../../../project-specification.md), [현재 화면 상태 관리](../../../../frontend/src/workflow.js), [화면의 API 연결](../../../../frontend/src/pages/review/ReviewProvider.jsx), [검수 API](../../../../backend/app/api.py), [현재 검사기](../../../../backend/app/review_rules.py), [최초 DB 구조 설계](<../../../../../../Documents/Codex/2026-09-25/x20-x20/outputs/모닝컵_가상납품검수_예제/크리에이티브체커_DB_구조설계_v0.2_2026-10-14.md>)다. 현재 React + FastAPI 명세와 단계별 결정이 초기 설계의 Django 표현보다 우선한다.

- PK는 앱이 발급하는 `UUID`, 시각은 UTC 기준 `TIMESTAMPTZ`다. `현재 시각`은 DB의 `CURRENT_TIMESTAMP`이며 `updated_at`은 실제 수정 시 저장 계층이 갱신한다.
- **필수**는 NULL 불가, **선택**은 NULL 허용이다. 선택값도 생성 경로별로 필요하면 반드시 제공한다. 모르는 원문·확정자·시각·필수 여부를 추측해 채우지 않는다.
- 네 테이블 모두 `project_id`를 둔다. 대상 이미지와 기준·초안·출처는 프로젝트를 포함한 복합 FK로 연결하고 삭제 정책은 우선 `RESTRICT`다.
- 편집 가능한 초안과 불변 버전·항목을 분리한다. 기준 확정은 **실행에 사용할 입력을 고정하는 행위**이며 자동 판정이나 사람의 검수 결과 승인을 뜻하지 않는다.
- `admin/admin`은 개발용 계정으로 유지한다. 이메일 로그인·DB 세션은 별도 구현이다. 개발 계정의 `local-admin` 문자열을 사용자 UUID에 넣지 않으며, DB 쓰기 단계에서 실제 개발 사용자와 명시적으로 매핑한다.

### 현재 동작과 목표 저장 구조

| 항목 | 현재 코드에서 확인한 동작 | 목표 저장 계약 |
|---|---|---|
| 기준 편집 | 브라우저가 요구사항을 줄별로 나누고 문구·종류·선택 상태를 관리 | 저장하는 초안에는 원문과 제외 항목까지 보존 |
| 확정 | 브라우저가 선택 항목만 복사하고 로컬 정수를 증가 | 서버가 이미지 UUID에 결합한 불변 기준 UUID·프로젝트 버전 발급 |
| 서버 저장 | 검수 요청의 기준 배열·정수 버전을 `snapshot.json`에 저장 | 초안·확정 버전·항목을 구분하고 실행은 버전 UUID 참조 |
| 항목 ID | `criterion-1`·`custom-UUID` 같은 문자열, 요청 안에서 유일 | 내부 UUID와 외부 항목 문자열을 별도 보존 |
| 기준 변경 | 화면의 현재 확정·결과 연결을 해제 | 과거 버전·실행은 보존하고 다음 실행에 새 확정 요구 |
| 검사 규칙 | 현재 검사기는 `id/text/type` 등을 사용 | `rule_code`·구조화 기대값 도입은 후속 검사기 연결 작업 |

현재 API는 항목 1~100개, 항목 ID 1~100자, 문구·출처 1~500자, `type=information|visual`을 검증한다. 이 설계의 넓은 DB 자료형을 이유로 공개 API의 제한을 바꾸지 않는다. 서버 초안 API와 기준 확정 API가 이미 존재하는 것으로 표현하지 않는다. 초안을 저장할 수 있는 구조는 마련하되, 미확정 초안의 새로고침 복원 UI는 현재 명세의 초기 구현 범위 밖이다.

## 2. criteria_sets — 검수 기준 묶음

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `criteria_set_id` | `UUID` | 필수 | 앱 발급 | 기준 묶음 PK |
| `project_id` | `UUID` | 필수 | 없음 | 소속 프로젝트 |
| `name` | `VARCHAR(200)` | 필수 | 없음 | 기준 묶음 표시명 |
| `created_by` | `UUID` | 선택 | NULL | 실제 확인 가능한 등록 사용자 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 로컬 등록 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 표시명 변경 시각 |

키는 PK `criteria_set_id`, UNIQUE `(project_id, criteria_set_id)`다. FK는 `project_id → projects.project_id`, `created_by → users.user_id`다. 서비스 사용자가 만들면 `created_by`를 제공하고, 사용자 정보가 없는 과거 수입은 NULL과 수입 출처를 보존한다.

표시명이 같다는 이유로 묶음을 합치지 않는다. 묶음은 기준의 논리적 그룹이고 이미지 고정은 각 초안·버전이 담당한다. 같은 묶음에도 서로 다른 이미지 버전의 초안·확정본을 둘 수 있다. 묶음 이름을 바꿔도 과거 기준 내용·버전 번호·실행 입력은 바뀌지 않는다.

## 3. criteria_drafts — 편집 초안

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `draft_id` | `UUID` | 필수 | 앱 발급 | 초안 PK |
| `project_id` | `UUID` | 필수 | 없음 | 소속 프로젝트 |
| `criteria_set_id` | `UUID` | 필수 | 없음 | 기준 묶음 |
| `target_asset_version_id` | `UUID` | 필수 | 없음 | 확정 대상으로 고정할 이미지 버전 |
| `revision` | `BIGINT` | 필수 | 1 | 초안 수정 번호 |
| `raw_requirements` | `TEXT` | 필수 | 없음 | 편집 중 요구사항 원문 |
| `items_jsonb` | `JSONB` | 필수 | 없음 | 순서·임시 ID·문구·종류·출처·선택 상태를 포함한 편집 배열 |
| `source_documents_jsonb` | `JSONB` | 선택 | NULL | 실제 제공된 출처 문서·위치 메타데이터 |
| `state` | `VARCHAR(40)` | 필수 | `editing` | `editing`·`archived` |
| `updated_by` | `UUID` | 필수 | 없음 | 마지막 편집 사용자 |
| `created_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 초안 생성 시각 |
| `updated_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 최종 수정 시각 |

키는 PK `draft_id`, UNIQUE `(project_id, criteria_set_id, target_asset_version_id, draft_id)`다. FK는 다음과 같다.

- `(project_id, criteria_set_id) → criteria_sets(project_id, criteria_set_id)`
- `(project_id, target_asset_version_id) → asset_versions(project_id, asset_version_id)`
- `updated_by → users.user_id`

초안 변경은 요청의 `expected_revision`과 현재 `revision`이 같고 `state=editing`일 때만 반영한다. 문구·종류·선택·순서·원문·출처 중 하나라도 변경하면 같은 트랜잭션에서 revision을 1 올린다. 충돌은 `409`로 돌려주고 다른 편집 내용을 덮어쓰지 않는다. `updated_at` 비교만으로 동시 수정을 검증하지 않는다.

배열의 임시 항목 ID는 초안 안에서 유일해야 한다. 선택하지 않은 항목도 초안에 남기고 확정본에는 복사하지 않는다. 확정 성공 후에도 같은 초안을 편집할 수 있으며, 과거 버전의 `source_draft_revision`·해시·복사된 원문은 수정하지 않는다. 대상 이미지·묶음을 바꿀 때는 새 초안을 만든다.

출처 JSON의 파일·자료 ID가 있으면 저장 계층이 존재·프로젝트·접근 권한을 검증한다. JSON 내부 ID는 FK 검증을 대신하지 않는다. 현재 요구사항이 텍스트 입력뿐이면 문서 출처를 만들어 넣지 않는다.

키는 다음과 같다.

- PK `criteria_version_id`
- UNIQUE `(project_id, version_no)` — 프로젝트 안의 서버 버전 번호

- `(project_id, criteria_set_id) → criteria_sets(project_id, criteria_set_id)`
- `(project_id, target_asset_version_id) → asset_versions(project_id, asset_version_id)`
- `(project_id, criteria_set_id, target_asset_version_id, source_draft_id) → criteria_drafts(project_id, criteria_set_id, target_asset_version_id, draft_id)`
- `(project_id, source_criteria_version_id) → criteria_versions(project_id, criteria_version_id)`
- `(project_id, import_package_id) → import_packages(project_id, import_id)`
- `(project_id, source_file_id) → stored_files(project_id, file_id)`
- `confirmed_by → users.user_id`

### 버전 번호와 출처

기존 ERD의 `(criteria_set_id, version_no)` 대신 **최신 프로젝트 명세의 `(project_id, version_no)`**를 버전 번호 유일 키로 채택한다. 기준 묶음이 달라도 같은 프로젝트에서는 번호가 겹치지 않는다. 발급은 프로젝트 행을 잠근 짧은 트랜잭션 안에서 현재 최대 번호 다음 값을 정하고 DB 유일 제약으로 검증한다. 모든 버전 등록 경로가 같은 규칙을 사용하며, 성공한 버전은 삭제·재번호 부여하지 않는다. 번호에 업무상 연속성을 의존하지 않는다. [PostgreSQL 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html)

현재 브라우저의 정수 `criteria_version`은 서버 전역 식별자가 아니다. `source_version_jsonb`에 원래 숫자를 보존하고 내부 UUID·서버 번호를 별도 발급한다. 같은 숫자에 다른 내용이 있으면 별도 기준 버전으로 남긴다. 기존 API 응답의 숫자 의미와 DB 서버 번호를 조용히 바꾸지 않으며, 저장 전환 때 기존 값과 새 UUID·서버 번호의 응답 매핑을 검증한다.

| 생성 경로 | 로컬 확정 상태·필수 정보 | 실행·재확정 계약 |
|---|---|---|
| `service_confirmation` | `confirmed`; 초안 ID·revision·초안 해시·원문, 확정자·시각, 멱등키·요청 해시·규격 버전 필수 | 현재 이미지에 대한 새 실행 입력으로 사용 가능 |
| `imported` | `unconfirmed`; 인계 묶음 필수. 출처 상태·버전·원문을 가능한 범위에서 보존 | 출처의 confirmed만으로 로컬 확정 처리하지 않음 |
| `legacy_snapshot` | `unconfirmed`; 기존 JSON 기준 스냅샷·원래 정수 버전 보존 | 과거 실행의 입력 기록. 서버가 별도로 확정한 것으로 취급하지 않음 |

수입·과거 기록의 `confirmed_by/confirmed_at/confirmation_key/confirmation_request_hash/request_hash_version`은 NULL이다. 외부 확정자·시각이 있으면 원문 스냅샷에 보존한다. 로컬 재확정은 기존 행의 상태 변경 대신 새 초안과 `service_confirmation` 버전을 만든다. 실제 복사 관계를 입증하고 지원하는 경로가 있을 때만 `source_criteria_version_id`로 연결한다. 복사 출처는 다른 이미지·묶음일 수 있지만 프로젝트는 같아야 한다. 새 이미지에 이전 확정 UUID를 재사용하지 않는다.

9단계에서 첫 v1의 재확정은 실제 로그인 사용자의 새 초안·정상 확정 요청으로 제한했다. 첫 API에는 별도 자동 복제/계보 입력이 없으므로 입증한 source_criteria_version_id가 없으면 NULL이다. 계보 컬럼을 채우려고 과거 주체를 가장하거나 미지원 요청 필드를 추가하지 않는다. 수입 기준의 해시는 서비스 내용 지문과 구분한 cc-import-projection-v1을 사용한다.

과거 JSON에는 요구사항 원문·전체 초안 revision이 없을 수 있다. 선택 항목을 이어 붙여 원문인 것처럼 만들거나 브라우저 버전을 초안 revision으로 쓰지 않는다. [추가 설계 8단계](../../DB_통합설계서.html#source-10)에서 첫 DB 쓰기는 v1의 서버 초안→확정 경로로 통일하고 기존 multipart의 자동 DB 어댑터는 채택하지 않기로 정했다. 구형 JSON의 수입·재확정은 9단계에서 연결하며 이번 문서는 기존 API 동작을 변경하지 않는다.

### 불변 내용과 해시

버전과 항목은 같은 트랜잭션에서 모두 저장하고 sealed_at을 마지막에 1회 기록한다. 6단계에서 봉인 후 항목 INSERT까지 거부하도록 보강했다. 생성 중 sealed_at만 NULL일 수 있고 봉인하지 않은 버전의 커밋은 지연 제약으로 거부한다. 확정 이후 항목 추가·삭제·재정렬·기대값 변경이나 확정 상태 승격을 허용하지 않는다. 초안이 바뀌어도 이 버전은 복사된 원문·출처·선택 항목만으로 재조회·실행할 수 있어야 한다.

`criteria_hash` 입력에는 프로젝트·대상 이미지 UUID, 원문·출처 복사본, 순서대로 정규화한 모든 선택 항목의 외부 ID·문구·분류·출처·규칙·기대값·필수 여부·적용 범위·수신 항목 원문을 포함한다. 서버가 새로 만든 버전/항목 UUID·버전 번호·생성 시각·멱등키는 내용 지문에서 제외한다. `source_draft_hash`는 제외 항목·선택 상태까지 포함한 확정 당시 전체 초안의 지문이다. 둘은 용도가 다르다.

해시는 JSONB 내부 표현이나 원문 파일 바이트의 해시와 구분한다. `hash_version`이 정의한 UTF-8 직렬화·객체 키 정렬·배열 순서·숫자 표현·누락/명시적 null 구분으로 계산한다. [8단계 해시 계약](../../DB_통합설계서.html#source-10--12-내용요청manifest-해시)에서 cc-content-jcs-v1과 초안/선택 스냅샷 입력·고정 예제를 확정했다. `criteria_hash`에 UNIQUE를 두지 않는다. 내용이 같아도 사용자의 별도 확정·새 이미지·새 요청은 새 버전일 수 있다.

### 기준 확정의 멱등성

첫 26개 테이블에서는 명세의 논리적 `IdempotencyRecord` 중 기준 확정 기록을 위 세 요청 컬럼과 `confirmed_by`에 함께 저장한다. operation은 기준 확정으로 고정하므로 UNIQUE `(confirmed_by, confirmation_key)`가 사용자·operation·키 범위를 나타낸다. 다른 프로젝트에서도 같은 사용자·키를 재사용하면 요청 지문의 프로젝트가 달라져 충돌한다. 27번째 범용 테이블을 이번 범위에 추가하지 않는다.

같은 사용자·키·요청 지문이면 기존 버전을 반환하고, 같은 키에 다른 내용이면 `409`다. 키가 다르면 같은 내용도 명시적 새 확정이다. 8단계에서 요청을 경로의 project_id와 본문의 draft_id·expected_revision으로 고정했다. 요청 지문은 이 값과 인증된 사용자·confirm_criteria operation·규격 버전을 포함하며 image/set/선택 항목은 잠근 초안에서 읽는다. 멱등키 자체와 요청에 없는 현재 초안 내용은 지문에 넣지 않는다. 서버가 확정 시 읽은 내용은 별도의 초안·기준 해시로 검증한다. 재전송 검사는 현재 초안 revision 검사보다 먼저 하되, 기존 리소스의 현재 접근 권한을 검증한 뒤 반환한다. 원 요청의 내용이 성공 후 초안에서 바뀌어도 동일 요청 재전송은 기존 버전을 찾을 수 있어야 한다.

버전·항목·멱등 정보는 한 트랜잭션으로 저장한다. 동시 요청으로 유일 제약이 충돌하면 해당 트랜잭션을 롤백하고 기존 행을 읽어 지문을 비교한다. 현재 API에 멱등성이 구현됐다는 뜻은 아니다. 검수 생성·재검수 operation의 물리 매핑은 [설계 5단계](../../DB_통합설계서.html#source-06)의 run 행으로 정리했으며 전체 키 범위는 6단계에서 대조한다.

## 5. criteria_items — 기준 버전의 항목

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `criteria_item_id` | `UUID` | 필수 | 앱 발급 | 불변 기준 항목 PK |
| `project_id` | `UUID` | 필수 | 없음 | 소속 프로젝트 |
| `target_asset_version_id` | `UUID` | 필수 | 없음 | 부모 버전과 같은 검수 대상 이미지 |
| `criteria_version_id` | `UUID` | 필수 | 없음 | 소속 불변 기준 버전 |
| `external_item_id` | `TEXT` | 선택 | NULL | 브라우저·외부 원문의 항목 문자열 ID |

| `source_asset_version_id` | `UUID` | 선택 | NULL | 실제 등록된 출처 자료 버전 |

키는 PK `criteria_item_id`, UNIQUE `(criteria_version_id, position)`, UNIQUE `(criteria_version_id, external_item_id)`, UNIQUE `(project_id, target_asset_version_id, criteria_version_id, criteria_item_id)`다. 외부 ID가 없는 여러 항목은 NULL을 허용한다. FK는 다음과 같다.

- `(project_id, target_asset_version_id, criteria_version_id) → criteria_versions(project_id, target_asset_version_id, criteria_version_id)`
- `(project_id, source_asset_version_id) → asset_versions(project_id, asset_version_id)`

`external_item_id`는 현재 API 문자열을 그대로 보존하며 내부 PK로 쓰지 않는다. 실행 응답에서 외부 ID를 쓰는 경로는 해당 버전 안의 ID로 되돌려 연결한다. 여러 버전에 `criterion-1`이 반복돼도 정상이며 문자열만으로 다른 버전의 결과를 찾지 않는다.

`rule_code`에는 UNIQUE를 두지 않는다. 예를 들어 `venue_contains`가 여러 장소 조건에 반복돼도 각각의 문구·기대값·순서·결과를 유지한다. 현재 UI의 정규식 분류를 정교한 규칙 코드·정답 추출의 근거로 삼지 않는다. 외부 분류를 현재 분류로 해석할 수 없으면 `unknown`과 원문을 보존하고 새 서비스 실행 전에 사용자가 지원 분류로 재확정하도록 한다.

`selected`는 실행에 포함할지 여부이며 초안에만 둔다. `is_required`는 업무상 반드시 충족해야 하는 조건인지 여부다. 현재 API는 이를 보내지 않으므로 선택됐다는 이유로 true를 채우지 않고 NULL로 둔다. NULL은 항목을 검사하지 않는다는 뜻이 아니다. 필수 여부가 없는 항목의 집계는 실행에 고정할 정책으로 명시하며 설계 5단계에서 다룬다.

기대값을 모르면 SQL NULL로 두고 누락과 명시적 JSON null은 `source_item_jsonb`에서 구분한다. TEXT로 임시 지정된 기대값·출처 위치·적용 조건·검사 범위는 JSONB로 설계한다. 실제 원문 바이트는 연결한 파일에 보존한다. 초안 JSON 전체를 실행 시점에 다시 해석하여 확정 항목을 대체하지 않는다.

1단계에서 제외한 **`source_reference_record_id`는 컬럼·FK 모두 이번 범위에 넣지 않는다.** 외부 기준 테이블 도입 시 함께 추가한다. 현재 `asset_versions`에 등록할 수 없는 문서를 이미지 버전인 것처럼 만들지 않고 출처 메타데이터·실제 파일로 보존한다.

## 6. 확정 저장 순서와 다음 설계의 연결

서버 기준 확정의 목표 순서는 다음과 같다. 모두 후속 구현이며 실제 PostgreSQL 경쟁 검증도 별도로 수행한다.

1. 인증·프로젝트 권한을 확인하고 요청 내용·멱등키·지문을 검증한다. 기존 키가 있으면 현재 권한·지문을 확인하여 반환하거나 충돌 처리한다.
2. 프로젝트 행 → 대상 초안 행 순서로 잠그고 초안 상태·expected revision·이미지·선택 항목을 검증한다. 다른 경로도 같은 잠금 순서를 사용한다.
3. 프로젝트별 서버 번호를 발급하고 초안 revision·원문·출처·해시와 선택 항목을 새 버전·항목으로 복사한다.
4. 확정자·시각·요청 키·지문·감사 이벤트까지 같은 트랜잭션에 저장한다. 항목 0개·현재 API 제한 초과·중복 임시 ID·지원하지 않는 분류는 저장 전에 거부한다.
5. 커밋 후 UUID·서버 번호를 반환한다. 다른 내용의 재확정은 새 요청 키와 버전을 사용한다. OCR·외부 호출을 이 트랜잭션에서 수행하지 않는다.

프로젝트·이미지·기준 일치는 복합 FK, 버전·항목·요청 키의 중복은 유일 제약으로 검증한다. 초안 revision 경쟁·원문 해시·선택 항목 전체 일치·사용자 권한은 저장 계층의 트랜잭션 검사가 필요하다. 여러 행의 항목 개수나 부모 상태를 단일 행 CHECK로 검증했다고 가정하지 않는다. 불변 행의 UPDATE·DELETE 차단 방식과 단일 행 CHECK는 6단계에서 확정한다. [PostgreSQL 제약 조건](https://www.postgresql.org/docs/17/ddl-constraints.html)

| 다음 연결 | 이번에 제공하는 키·계약 | 설계 5·6단계 확인 |
|---|---|---|
| `review_runs` | 기준 버전의 UNIQUE `(project_id, target_asset_version_id, criteria_version_id)` | 실행의 `asset_version_id`와 기준 대상 이미지가 같은 복합 FK, 새 실행의 로컬 확정 상태 검증 |
| `item_results` | 항목의 UNIQUE `(project_id, target_asset_version_id, criteria_version_id, criteria_item_id)` | 실행·이미지·기준 버전·항목의 문맥 일치 |
| `run_item_selections` | 결과와 같은 불변 항목 ID 사용 | 다른 기준 버전 결과의 잘못된 채택 방지 |
| 집계 정책 | 미제공 `is_required=NULL`, 기준 포함 여부와 분리 | 현재 `pass/fail/review` 집계와 정책 버전 고정 |
| 멱등 기록 | 기준 확정은 버전 행에 원자적으로 보존 | 검수 생성·재검수 operation 매핑과 사용자별 키 범위 |
| 수입·과거 JSON | 원래 숫자·항목 ID·원문·출처 확정 상태 보존 | 과거 실행 조회와 새 실행의 서버 확정 경로 구분 |

필수 검증 사례는 같은 초안 revision의 동시 수정, 동일 키의 동시 확정, 같은 키의 내용 변경, 성공 후 초안 변경 뒤 동일 요청 재전송, 서로 다른 묶음의 프로젝트 버전 경쟁, 새 이미지에 이전 기준 연결 거부, 원문에만 있는 confirmed의 승격 방지, 동일 `rule_code`의 복수 항목 보존이다. 이번 단계에서는 사례와 계약을 정리했으며 DB 실행 검증을 수행한 것으로 기록하지 않는다.

## 7. 기존 ERD 초안 대비 변경과 완료 확인

- 4개 테이블의 기존 컬럼을 보존하고, 범위에서 제외한 `criteria_items.source_reference_record_id`만 뺐다.
- 프로젝트·이미지 경계의 복합 키, 내부 UUID와 원래 항목 ID, 브라우저 버전과 서버 버전의 구분을 추가했다.
- 최신 명세에 맞춰 서버 번호의 유일 범위를 묶음별에서 프로젝트별로 정리했다.
- 초안 revision을 BIGINT, 시각을 TIMESTAMPTZ, 편집 배열·기대값·위치·조건·스냅샷을 JSONB로 설계했다.
- 편집 원문·제외 항목, 확정 당시 복사본, 원문 해시·요청 지문, 로컬 확정과 출처 상태를 분리했다.
- 현재 입력이 제공하지 않는 필수 여부는 NULL로 보존하도록 기존 ERD의 NOT NULL을 조정했다.
- 기준 확정의 멱등 기록을 기존 26개 범위 안에 매핑했다. 실제 ERD 가져오기용 SQL·DB·인증 코드·실행 코드에는 적용하지 않았다.
