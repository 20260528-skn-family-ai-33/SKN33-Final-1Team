## 1. 근거와 공통 규칙

근거는 [범위·관계](../../DB_통합설계서.html#source-02), [사용자·파일](../../DB_통합설계서.html#source-03), [규격·OCR·근거](../../DB_통합설계서.html#source-04), [검수 기준](../../DB_통합설계서.html#source-05), [ERD 초안](../../../ERD_물리.md), [프로젝트 명세](../../../project-specification.md), [현재 검수 API](../../../../backend/app/api.py), [항목 검사기](../../../../backend/app/review_rules.py), [결과 화면](../../../../frontend/src/pages/review/ResultsPage.jsx), [최초 DB 구조 설계](<../../../../../../Documents/Codex/2026-09-25/x20-x20/outputs/모닝컵_가상납품검수_예제/크리에이티브체커_DB_구조설계_v0.2_2026-10-14.md>)다. 최신 명세와 첫 26개 테이블 범위가 초기 멀티에이전트 설계보다 우선한다.

- 단일 PK는 앱 발급 `UUID`, 시각은 UTC 기준 `TIMESTAMPTZ`다. `현재 시각` 기본값은 DB의 `CURRENT_TIMESTAMP`이며 실제 수정 때 `updated_at`을 갱신한다.
- **필수**는 NULL 불가, **선택**은 NULL 허용이다. 서비스 신규 실행의 조건부 필수값과 과거 수입의 미보고 값을 구분한다. 원문에 없는 모델 버전·시각·비용·요청자를 만들지 않는다.
- 네 테이블 모두 `project_id`·`asset_version_id`를 두고 기준 버전·시도·결과를 복합 FK로 연결한다. 삭제 정책은 우선 `RESTRICT`다.
- 처리 완료, `pass/fail/review`, 결과 집계, 사람의 검토·승인·정답 라벨 승인은 별개다. `run_item_selections`는 실행 결과의 채택 기록이며 사람의 승인 기록이 아니다.
- `admin/admin`은 개발용 계정으로 유지한다. DB 쓰기 단계에서는 실제 개발 사용자 UUID에 명시적으로 매핑하며, 이메일 로그인·DB 세션 구현과 구분한다.

- PK `run_id`

### 신규 접수와 고정 입력

서비스 신규 실행은 `requested_by`·operation·멱등키·요청 해시/규격, 코드·집계 정책 버전, 실제 실행 대상·설정, 입력 지문/규격, 재시도 정책·인수 가능 시각을 제공한다. 최초 상태는 `queued`, 단계는 `queued`이며 현재 시도·채택 시도는 NULL이다. 실행에 쓸 수 없는 설정·확인하지 않은 버전을 추측해 채우지 않고 접수 전에 구성 오류로 거부한다.

새 실행은 요청자의 프로젝트 권한, 이미지·기준의 같은 프로젝트/이미지 여부, 기준의 `confirmation_state=confirmed`를 확인한다. 연결된 초안이 확정 당시 revision 이후 수정됐으면 재확정을 요구한다. 이 검사는 기준 확정과 같은 프로젝트 → 초안 잠금 순서의 짧은 트랜잭션에서 수행해 편집과 경합을 제어한다. 이미 접수한 실행은 이후 초안·프로젝트명이 바뀌어도 고정된 입력으로 계속 처리한다.

입력 지문은 프로젝트·이미지 UUID와 실제 파일 해시·좌표/전처리 계약, 기준 UUID·내용 해시, 서버가 확정한 실행 설정·코드·집계/재시도 정책을 묶는다. `requested_config`에 토큰·API 키·사용자 지정 서버 주소를 저장하지 않는다. 원본 파일명·정답 라벨로 OCR을 보정하지 않는다. [추가 설계 8단계](../../DB_통합설계서.html#source-10--12-내용요청manifest-해시)에서 cc-manifest-jcs-v1의 직렬화·입력/결과 범위·고정 예제를 확정했다. 접수 때 아직 없는 OCR 입력 파일 해시는 추측하지 않는다.

`retry_of_run_id`가 있으면 `retry_review`, 없으면 `create_review`다. 재검수는 종료된 원 실행과 같은 이미지·기준을 사용하고 새 `run_id`·요청 키를 발급한다. 원 실행 상태·권한·자기 참조 금지는 접수 트랜잭션에서 확인한다. 입력을 바꾸려면 일반 신규 검수로 접수한다. 원 실행의 결과·시도 번호를 덮어쓰지 않는다.

### 요청 재전송의 멱등성

기존 ERD의 UNIQUE `(project_id, idempotency_key)`를 최신 명세의 사용자·operation 범위에 맞춰 위 키로 바꾼다. 키 자료형은 목표 API의 UUID 계약을 따르며, 원래 문자열 키가 있는 수입은 원문에 보존한다. 서비스 접수에서는 관련 컬럼이 모두 필수이고, 요청자·키를 알 수 없는 수입은 NULL이다.

같은 사용자·operation·키와 같은 요청 지문은 기존 run과 **현재 실제 상태**를 반환한다. 같은 키의 다른 요청은 `409`다. 이미지·기준 조합에는 UNIQUE를 두지 않는다. `create_review`·`retry_review`는 operation이 달라 같은 UUID 키를 쓸 수 있으며, 같은 operation에서 프로젝트가 달라지면 지문 차이로 충돌한다. 기준 확정 operation은 4단계의 버전 행에서 따로 관리한다.

요청 지문은 원 요청의 프로젝트·이미지·기준·재검수 원 실행 ID, 명시적으로 허용한 요청 옵션, 인증된 사용자·operation·규격 버전으로 계산한다. 재전송 때 달라질 수 있는 서버의 현재 모델 설정·초안 내용은 넣지 않는다. 기존 키 조회·권한·지문 검사를 현재 초안 revision 검사보다 먼저 하여, 성공 후 초안이 바뀌어도 동일 요청은 원 run을 반환한다. 해시 규격이 바뀌면 기존 기록의 규격으로 비교한다.

run·멱등 정보·접수 감사 이벤트는 한 트랜잭션에 저장한다. 동시 유일 제약 충돌은 전체 롤백 후 기존 행과 지문을 확인한다. 이 매핑으로 논리적 `IdempotencyRecord`를 첫 26개 테이블 안에 유지한다. 이미 실행이 끝난 재전송을 새 추론·새 시도로 바꾸지 않는다.

### 수입과 과거 JSON

`imported_result`·`legacy_result`는 `execution_status=imported`, `executor_kind=imported`, `orchestration_mode=imported`로 등록한다. 원래 완료·실패·중단 상태는 `source_status`·원문에 보존하고 작업 큐에서 제외한다. 외부 인계는 `import_package_id`, 기존 JSON은 실제 스냅샷·원래 ID·파일을 보존한다. 실제로 확인한 이미지·기준·항목을 먼저 매핑하며 누락 입력을 허위 행으로 채우지 않는다.

이 경로는 원 요청자·요청 키·정책·시각을 모르면 NULL로 둔다. 수입한 사용자를 과거 요청자로 치환하지 않는다. `created_at`은 로컬 등록 시각이고 원래 생성 시각은 원문에 남긴다. 로컬에서 계산하지 않은 요약 판정·실행 시각을 만들지 않는다. 6단계에서 수입 결과도 구조 검증·자식 연결을 완성한 뒤 실제 로컬 sealed_at과 manifest 지문을 남기도록 보강했다. 이는 과거 추론 완료나 자동 판정 재검증을 뜻하지 않는다. 과거 기준의 `unconfirmed`는 이력 보존용 연결만 허용하며 새로운 서비스 실행에는 사용할 수 없다.

## 3. review_attempts — 실행 전체의 처리 시도

| 컬럼 | 자료형 | 필수 여부 | 기본값 | 의미 |
|---|---|---|---|---|
| `attempt_id` | `UUID` | 필수 | 앱 발급 | 처리 시도 PK |

키는 PK `attempt_id`, UNIQUE `(run_id, attempt_no)`, UNIQUE `(project_id, asset_version_id, attempt_id)`, UNIQUE `(project_id, asset_version_id, run_id, attempt_id)`다. FK는 `(project_id, asset_version_id, run_id) → review_runs(project_id, asset_version_id, run_id)`다. `execution_status=active`인 행은 6단계의 `uq_review_attempts_active_run` 부분 유일 인덱스로 run당 최대 하나로 제한한다. 실제 적용은 후속 마이그레이션에서 수행한다.

이번 시도는 OCR 단계별 작업이 아니라 **전처리부터 판정·저장까지 실행 전체를 한 번 처리하는 단위**다. 최신 명세대로 `(run_id, attempt_no)`를 사용하고 기존 `(work_unit_id, attempt_no)`는 사용하지 않는다. `stage` 변경마다 시도 번호를 늘리지 않는다. 현재 OCR runtime의 `attempts`가 장치 fallback·재인식 이력이라면 `actual_runtime`에 원래 의미로 남기고 각각을 검수 전체의 DB 시도로 승격하지 않는다.

`ocr_runs`의 시도 연결은 프로젝트뿐 아니라 이미지도 포함하는 `(project_id, asset_version_id, attempt_id)`로 보강한다. 같은 프로젝트의 다른 이미지 시도를 참조하지 못하게 하며 3단계 문서에도 반영한다.

서비스 인수 시 `stage`·`started_at`·`worker_token`·요청 설정을 제공한다. `background_tasks` 경로도 현재 시도 포인터·토큰을 비교하여 재시작 처리 후의 늦은 결과를 거부한다. lease·heartbeat는 후속 `postgres_worker` 경로에서 필수다. 초기 DB 저장 연결에 영속 자동 복구가 이미 포함되는 것으로 표현하지 않는다.

수입에 실제 시도 이력이 없으면 `execution_status=imported`인 로컬 결과 묶음 행을 만들 수 있다. 이때 `attempt_no=1`은 로컬 등록 순서이며 실제 추론 횟수가 아니다. 토큰·lease·시작/종료 시각은 NULL, 원 시도 번호는 미확인으로 남긴다. 해당 묶음과의 연결이 확인되는 OCR만 연결하고, 수입을 위해 과거 실행 시각·원격 job을 만들지 않는다.

### 현재 시도와 실행 권한

run·attempt의 순환 FK는 **현재/채택 시도 NULL인 run 생성 → 시도 생성 → run의 현재 시도 연결** 순서로 처리한다. 시도 생성·현재 포인터·running 전환은 같은 트랜잭션에서 커밋한다. 완료·실패·회수는 run → 해당 attempt 순서로 잠그고 한 트랜잭션에서 상태와 포인터를 변경한다. 독립 worker는 `origin_kind=service_execution`, `executor_kind=postgres_worker`이며 queued·`available_at` 도달 조건을 만족하는 run을 `FOR UPDATE SKIP LOCKED` 방식으로 인수하고 잠금을 풀고 추론한다. BackgroundTasks용 queued 행을 별도 worker가 함께 가져가지 않는다. [PostgreSQL SELECT](https://www.postgresql.org/docs/17/sql-select.html)

heartbeat·외부 호출 직전의 제출 상태 기록·결과 반영은 run이 running이고 `active_attempt_id`·시도 ID·`worker_token`이 일치하며 시도가 active인지 확인한다. DB worker는 여기에 `lease_expires_at > DB 실제 현재 시각`을 요구한다. 잠금 획득 후 검증 시점의 `clock_timestamp()`를 기준으로 비교하며, 트랜잭션 시작 시각인 `CURRENT_TIMESTAMP`로 만료를 판정하지 않는다. 같은 검사에서 살아 있는 lease만 연장하며 이미 만료된 권한을 되살리지 않는다. [PostgreSQL 현재 시각 함수](https://www.postgresql.org/docs/17/functions-datetime.html)

lease는 각 보호 동작의 권한 검사 시점에 유효해야 하며, 검증·쓰기 트랜잭션을 짧게 유지한다. 결과 반영 중 run/attempt 잠금은 회수와 경합을 직렬화한다. 파일·OCR 호출·원격 응답 대기를 DB 잠금 안에서 수행하지 않는다. 최초 worker 제안은 heartbeat 15초·lease 90초이며 구현 시 실제 측정으로 검증한다.

### 제출·실패·재시도

| 상황 | 기록·처리 |
|---|---|
| OCR 호출 전 | 권한 검사 후 `dispatching`을 먼저 DB에 저장하고 호출 |
| 원격 job ID 확인 | `remote_job_id`와 `submitted` 저장. 같은 job의 조회 재시도만 허용 |
| 로컬 동기 OCR | 원격 job ID를 만들지 않음. dispatching 이후 성공/실패/결과 불명을 별도 수명 상태로 기록 |
| 실행 전 거절 확인 | 안전 재시도 분류·총 횟수·정책을 모두 만족할 때만 failed 시도를 종료하고 run을 queued로 전환 |
| timeout·응답 유실·종료 미확인 | 시도 unknown, run failed, 결과 불명 오류. 자동 재제출하지 않음 |
| lease 만료 | 회수자가 현재 포인터·실제 만료를 확인. 실행 전임이 입증된 경우만 재대기, 제출 이후 불명은 unknown/failed |
| 결과 저장 실패 | 실행 권한이 유효하면 받은 결과의 DB 저장만 재시도. 새 OCR 호출로 대체하지 않음 |
| 사용자 재검수 | 별도 run·새 키·`retry_of_run_id`, 시도 번호는 새 run에서 다시 시작 |

안전 자동 재시도는 같은 run의 새 attempt다. 이전 시도를 종료하고 현재 포인터를 비운 뒤 다음 `available_at`과 queued를 같은 트랜잭션에 기록한다. `finished_at`은 아직 끝나지 않은 run에는 넣지 않는다. 최종 실패이면 run의 종료 시각·오류를 기록한다. `started_at`은 run의 최초 시작 시각으로 유지한다.

초기 `background_tasks` 저장 연결은 자동 재시도 없이 총 1회로 고정하고, 서버 재시작 시 중단된 run과 active 시도를 실패·결과 불명 여부와 함께 마감한다. 후속 DB worker는 명세의 기본 총 3회 이내와 제한 backoff를 실제 설정에 고정한다. 장치 fallback 횟수와 이 상한을 혼용하지 않는다. `retryable=true`만으로 유료 제출·추론을 반복하지 않으며, DB 중복 방지와 추론의 정확히 한 번 실행을 같은 보장으로 표현하지 않는다.

- `(project_id, asset_version_id, extraction_id) → poster_extractions(project_id, asset_version_id, extraction_id)`

서비스 결과는 reason·실제 checker version·부모의 입력 지문을 제공하고, `completed`일 때만 verdict를 갖는다. 실패·미지원은 verdict=NULL과 사유를 기록한다. 현재 검사기가 시각 항목에 `review`를 반환하면 `completed/review`로 저장하며 임의로 처리 실패로 바꾸지 않는다. 로고의 문자 대리 판정 같은 `check_method`는 method_code와 검사 범위 설명에 보존하고 도형 인식으로 확인한 결과라고 표시하지 않는다.

OCR·추출을 실제로 사용할 때만 대응 FK를 채운다. 첫 단일 파이프라인에서는 서비스 결과의 OCR이 해당 attempt에 속하고 추출본이 같은 OCR에 기반하는지 저장 트랜잭션에서 확인한다. 위 FK만으로 같은 이미지 안의 다른 시도 OCR까지 배제했다고 표현하지 않는다. OCR 문구를 직접 비교하면 extraction_id=NULL을 허용하고, 찾지 못한 원문 문구 ID로 가상의 근거를 만들지 않는다.

근거는 3단계의 `evidence_records.item_result_id`와 `evidence_ocr_tokens`로 연결한다. 같은 이미지의 다른 OCR을 근거에 섞지 않도록 실제 토큰·출처를 검증한다. 원문·후보·재인식의 확인 필요 플래그를 보존하며 단순 문자열 일치로 사람의 승인이나 정답 라벨로 승격하지 않는다.

결과는 추가 후 내용을 변경하지 않는다. 같은 attempt·항목의 저장을 다시 시도하면 기존 결과·근거가 같은지 대조하고 다른 내용으로 덮어쓰지 않는다. DB 커밋 성공 후 응답만 유실돼도 같은 run의 확정 상태를 확인한다. 새 추론의 결과라면 새 attempt나 새 run으로 기록한다.

수입 결과는 `execution_status=imported`, verdict=NULL로 두고 원문의 판정·사유·근거를 보존한다. reason이 없으면 NULL이다. 로컬 처리 완료나 자동 재판정으로 승격하지 않는다. 미지원·오류를 현 API의 `results[].status`로 표시할 때는 응답 어댑터가 `review`와 사유로 투영할 수 있으나 DB 판정값을 임의로 채우지 않는다.

9단계에서 수입 기준/실행 구조의 봉인 지문은 cc-import-projection-v1로 구분했다. 실제 원문 파일 해시·package 지문·원래 상태·실제 ID 대응과 결과 값을 묶으며 알 수 없는 서비스 입력 지문·추론 시각은 NULL이다. 실제 파일/DB 커밋 미확인·늦은 결과·원격 제출 불명의 처리와 최초 BackgroundTasks 시작 복구는 [저장·복구 계약](../../DB_통합설계서.html#source-11)을 따른다.

| `selection_kind` | `VARCHAR(40)` | 필수 | 없음 | `pipeline_final`·`import_projection` |
| `selection_revision` | `BIGINT` | 필수 | 1 | 채택 연결 revision. 첫 단일 실행에서는 1 |
| `selected_at` | `TIMESTAMPTZ` | 필수 | 현재 시각 | 로컬 채택·원문 투영 연결 시각 |

복합 PK는 `(run_id, criteria_item_id)`다. FK는 `(project_id, asset_version_id, criteria_version_id, run_id, criteria_item_id, result_id) → item_results(project_id, asset_version_id, criteria_version_id, run_id, criteria_item_id, result_id)`다. 이 FK로 다른 실행·이미지·기준 버전·항목의 결과를 채택하는 연결을 거부한다.

첫 범위의 `pipeline_final`은 최종 저장 트랜잭션에서 한 번 삽입한다. 모든 채택 결과가 run의 `selected_attempt_id`에 속하는지 확인하고 실패한 이전 시도의 결과를 섞지 않는다. 도착 순서에 따라 채택을 바꾸지 않으며, sealed 실행의 행은 수정·삭제하지 않는다. 일부 항목만 독립 재시도·다중 에이전트 채택하는 기능은 후속 작업 단위·채택 이벤트 테이블 도입 범위다.

수입 원문의 결과 목록을 표시하려고 연결할 때는 구조·ID 대응을 검증하고 `import_projection`으로 구분한다. 이 연결은 출처가 제시한 결과를 표시하는 매핑이며 로컬 재판정·승인을 뜻하지 않는다. 실제 과거 채택 시각을 알 수 없으면 `selected_at`을 과거 시각으로 추정하지 않는다. 모호한 중복 항목은 임의로 마지막 값을 고르지 않고 원문과 불일치 사유를 보존한다.

## 6. 완료 저장과 자동 요약 정책

첫 서비스 경로는 **한 시도에서 모든 선택 기준 항목의 최종 결과를 모아 원자적으로 저장**한다. 항목별 failed/unsupported를 명시적으로 처리한 경우도 결과 행으로 남길 수 있으나, 전체 OCR·출력 계약 실패처럼 유효한 결과 집합을 만들 수 없으면 run failed와 오류를 기록한다. 결과가 없는데 completed/pass를 만들지 않는다.

1. 추론·판정은 DB 잠금 밖에서 수행하고 받은 출력·좌표·ID·유한 점수·입력 해시·실행 버전을 검증한다. 실제 파일 저장은 앞선 파일 설계의 영속화·실패 정리 계약을 따른다.
2. 짧은 트랜잭션에서 run → active attempt를 잠그고 상태·현재 포인터·토큰·필요한 lease를 검사한다. 불일치·만료·이미 마감이면 늦은 쓰기를 거부한다.
3. OCR·토큰·추출·관찰·항목 결과·근거·근거 토큰 연결을 저장한다. 각 항목의 결과를 정확히 하나씩 만든다. 빠진 항목을 조용히 생략하지 않는다.
4. 같은 시도의 전체 결과를 `run_item_selections`에 연결하고, 기준 항목 전체와 결과 항목 집합이 정확히 같은지 검증한다. verdict와 처리 상태의 조합도 검증한다.
5. 정책에 따른 자동 요약과 결과 manifest 지문, selected attempt·sealed/finished 시각·progress=100·completed, attempt succeeded와 현재 포인터 해제, 완료 감사 이벤트를 한 번에 커밋한다.

오류로 일부 저장만 성공한 상태는 커밋하지 않는다. 완료 응답 전에 커밋해야 하며 이후 DB 장애를 JSON 신규 쓰기로 우회하지 않는다. 결과 파일의 일부 원문이 추론 중 먼저 생겨도 완료 기록·최종 채택을 대신하지 않는다. `sealed_at`은 이 로컬 결과 집합 고정의 뜻이고 사람 승인 시각이 아니다.

초기 자동 요약 제안은 **`all_selected_v1`**이다. 현재 UI가 선택한 모든 항목의 상태를 세는 동작에 맞춰, 포함된 항목은 `is_required=true/false/NULL`와 관계없이 모두 요약에 반영한다. `is_required=NULL`를 true로 저장하거나 NULL 항목을 집계에서 빼지 않는다. 추후 필수 항목만으로 요약하는 정책은 새 정책 버전과 검증을 거쳐 도입한다.

| 결과 집합 | `overall_verdict` |
|---|---|
| completed 실행이며 채택 항목 중 완료 verdict=fail이 있음 | `fail` |
| fail은 없지만 verdict=review 또는 failed/unsupported 항목이 있음 | `review` |
| 모든 선택 항목에 completed/pass가 있음 | `pass` |
| queued/running/failed/imported 또는 결과 집합 누락 | NULL. 누락된 서비스 결과 집합은 완료 저장 거부 |

이 정책은 기존 서버에 있던 계산으로 소개하지 않는다. 도입 시 실행의 `aggregation_policy_version`에 고정한다. 항목 failed/unsupported가 있어도 완결된 검수 집합을 만든 attempt는 succeeded일 수 있으며, 이는 모든 항목이 pass라는 뜻이 아니다. 지원하지 않는 검사를 비대상·통과로 처리하지 않는다. 사람의 후속 판단은 이번 26개에 포함되지 않은 별도 승인 영역이다.

## 7. 기존 API와 수입 연결에 넘길 조건

| 현재 응답·저장 항목 | DB 연결·투영 계약 |
|---|---|
| `id/status/stage/progress` | run UUID·실행 상태·현재 단계·실측 단계 진행률. API 필드 이름은 유지 |
| `criteria_version` | 기존 경로는 보존한 브라우저 숫자, 새 경로는 명시한 서버 번호. 내부 기준 UUID를 별도 제공하고 의미를 조용히 교체하지 않음 |
| `criteria[].id`, `results[].criterion_id` | 같은 기준 버전 안의 external_item_id ↔ criteria_item UUID 매핑 |
| `results[].status` | 서비스 verdict의 pass/fail/review. 실패·미지원 표시는 응답 어댑터가 사유와 함께 구분 |
| `observed_text/check_method/reason` | observed_value의 문자열·method_code·실제 reason. 구조화 값을 임의 문자열로 뭉개지 않음 |
| `evidence`, `runtime`, `ocr` | 실제 근거·토큰·시도 runtime·OCR 원문. bbox는 참조 표시 프레임 좌표 |
| `error` | 현 문자열과 목표 안전한 오류 객체의 명시적 호환 변환. 응답 계약 변경은 후속 구현·회귀 검증 |
| 과거 완료·중단 JSON | 현재 JSON 조회 유지, 수입은 명시적 프로젝트·사용자 귀속·dry-run 뒤 별도 수행. 자동 추론 재실행 금지 |

현재 multipart를 신규 DB 접수에 사용하는 어댑터는 가능한 대안이었다. [8단계 전환 계약](../../DB_통합설계서.html#source-10--13-기존-api-경로와-프런트-전환)에서 **첫 DB 쓰기는 v1의 서버 초안→확정→실행 API로 통일**하고 자동 multipart 어댑터는 채택하지 않았다. 단지 브라우저 숫자가 있다는 이유로 legacy/unconfirmed를 신규 실행에 연결하지 않는다. 실제 전환 전에는 기존 JSON 저장을 그대로 사용하며 이번 문서가 DB 저장 전환의 완료를 뜻하지 않는다.

수입의 `execution_status=imported`는 내부 구분이다. 기존 UI에 새 상태를 무조건 전달하지 않고, 보존한 source_status·출처를 함께 사용하는 읽기 전용 응답 계약을 저장 전환 때 정한다. 실제 신규 worker의 queued/running 상태나 로컬 재판정과 혼동하는 투영은 허용하지 않는다.

## 8. 6단계에 넘길 제약과 완료 확인

| 검토 대상 | 다음 단계에서 확정할 사항 |
|---|---|
| 상태·출처별 CHECK | 서비스 요청의 조건부 필수값, origin/executor 조합, verdict·처리 상태, 포인터·종료/동결 시각 |
| 유일 제약·인덱스 | run당 active 시도 하나, queued 인수 시각·lease 만료·프로젝트 이력 조회, FK 대상 복합 키의 비용 |
| 교차 행 검증 | 기준 확정 상태·초안 revision, OCR의 시도 일치·추출본 출처, 채택 결과의 시도·전체 항목 집합 일치 |
| 순환 관계 | run ↔ attempt의 초기 NULL·삽입/마감 순서, 파일 ↔ 인계 순환과 함께 마이그레이션 순서 검토 |
| 불변·권한 | 확정 기준·결과·근거·채택·입력 설정의 변경 차단, 서비스 역할·감사 이벤트 권한 |
| 멱등 범위 | 기준 확정은 버전 행, 검수 생성·재검수는 run 행. 사용자·operation·키와 요청 해시 일치 |
| 실제 DB 검증 | 동시 접수·동시 인수·늦은 heartbeat/결과·전체 저장 롤백·권한·교차 프로젝트/이미지/항목 연결 거부 |

단일 행 CHECK로 다른 행의 상태·모든 기준 항목 존재·OCR 원문·사용자 권한을 검증했다고 표현하지 않는다. FK·유일 제약과 저장 계층의 잠금·조건부 갱신·권한 검사를 구분하고, 실제 PostgreSQL 경쟁 테스트는 후속 구현에서 수행한다. [PostgreSQL 제약 조건](https://www.postgresql.org/docs/17/ddl-constraints.html)

- 기존 4개 테이블의 컬럼 중 1단계에서 미룬 `submission_version_id`, `work_unit_id` 2곳, `agent_execution_id`, `adjudicates_conflict_id`, `reference_check_id`, `selection_event_id`의 **7개 컬럼·FK**만 제외했다.
- 최신 명세에 맞춰 시도 번호를 실행별로 정리하고, 시도 수명·제출 상태·처리 상태·판정을 분리했다.
- 프로젝트·이미지·기준·실행·항목·결과의 복합 FK와 앞선 OCR·근거 연결 키를 맞췄다.
- TEXT 임시 컬럼의 설정·관찰값·한계·오류를 JSONB, 시각을 TIMESTAMPTZ, 채택 revision을 BIGINT로 설계했다.
- 미보고 과거 값 보존을 위해 멱등키·집계 정책 버전·시도 단계·항목 사유의 필수 조건을 생성 경로별로 나눴다.
- 현재 BackgroundTasks 경로와 후속 DB worker를 구분하고 원자적 저장·늦은 쓰기 거부·재실행 경계를 기록했다.
- 실제 ERD 가져오기용 SQL·DB·코드·로그인에는 이번 설계를 적용하지 않았다.
