## 2. 인증·세션·CSRF 동작

| 동작 | 실제 구현 |
|---|---|
| 이메일 로그인 | 전체 trim/lower 후 ASCII 이메일 검증. DNS 확인 없음. email 계정만 조회 |
| 개발 로그인 | admin/admin 유지. 명시 development/test·LOCAL_ADMIN_LOGIN=1·loopback peer/host·허용 출처·forwarded 없음·실제 개발 UUID/owner 구성 필수 |
| 비밀번호 | 실제 Argon2id m=19456 KiB/t=2/p=1, 난수 salt. 발급 15~128·로그인 1~128 코드포인트, 비밀번호 trim/정규화 없음 |
| 실패/부하 | 없는/비활성 계정도 더미 검증·동일 401. 해시 최대 2개, IP 30/60초, 식별자 실패 5/15분 후 15분 냉각. 메모리 키 최대 10000·429/Retry-After |
| 재해시 | 낮은 비용만 로그인 성공 후 교체. 어떤 기존 비용도 낮추지 않음 |
| DB 세션 | 난수 32바이트 토큰, DB에는 SHA256만. 실제 DB 시각 기준 절대 8시간·요청 시 연장 없음 |
| 세션 교체/폐기 | 같은 브라우저 로그인은 이전 세션 폐기. 다른 기기 유지. reset/change-email/활성 변경은 관련 세션 전체 폐기와 같은 commit |
| CSRF | HMAC-SHA256 서명 double-submit. 원문 세션 토큰 또는 HttpOnly pre-auth seed에 결합. 15분·미래 오차 30초·최대 256바이트 |
| Origin | 명시 origin만 허용. Origin 없으면 Referer, 둘 다 없거나 null이면 변경 요청 403 |
| 응답 | allowlist user(id/account_kind/display_name/email), 공통 meta·오류, no-store. 자격 증명/해시/토큰을 JSON/로그에 노출하지 않음 |

Argon2 비용과 제한은 프로젝트의 확정 정책이다. API 사용 방식은 [argon2-cffi 공식 문서](https://argon2-cffi.readthedocs.io/en/stable/api.html), DNS를 사용하지 않는 이메일 형식 검사는 [email-validator 2.3.0](https://pypi.org/project/email-validator/2.3.0/) 기준으로 구현·실행했다. 이메일 형식 검증은 이메일 소유 확인이나 발송 성공이 아니다.

운영은 __Host-baro_session / __Host-csrftoken / __Host-baro_csrf_seed에 Secure·SameSite=Strict·Path=/·Domain 없음, 세션/seed는 HttpOnly다. 개발 HTTP에서는 baro_session / csrftoken / baro_csrf_seed를 사용한다. 기존 baro_local_session은 신뢰하지 않고 새 로그인/로그아웃 때 삭제한다.

새 프로필의 인증 endpoint는 다음 4개다. 다른 관리/업무 API가 구현됐다는 뜻은 아니다.

| 경로 | 응답 |
|---|---|
| GET /api/v1/auth/csrf | csrf_token·developer_login_available·meta, seed 또는 세션에 결합 |
| POST /api/v1/auth/login | email/password 또는 username/password. 성공 user·새 세션/CSRF 쿠키 |
| GET /api/v1/auth/me | DB를 확인한 authenticated/user. DB 장애는 503 |
| POST /api/v1/auth/logout | Origin/CSRF 후 DB 폐기·204·쿠키 제거. DB 실패면 503과 기존 쿠키 유지 |

로그인 JSON은 실제 수신 4096바이트 이내다. 중복 키/잘못된 JSON 400, 크기 413, Content-Type 415, 필드 구조/타입 422를 구분하고 입력을 재출력하지 않는다. /api/v1/health는 checks·limits를 반환한다. DB가 준비돼도 미구현 worker/모델/저장소는 unknown이므로 현재 전체 상태는 degraded다. 준비되지 않은 업무를 ready로 표시하지 않는다.

## 3. 트랜잭션·권한·관리 경계

비밀번호 검증 중 DB Connection/잠금을 유지하지 않는다. 최종 세션 발급은 사용자(이전 쿠키가 다른 사용자이면 UUID 순) → 세션 잠금 후 종류·활성·검증 해시를 다시 확인한다. 로그인보다 reset이 먼저 commit하면 이전 검증 결과를 거부하고, 로그인이 먼저 commit하면 뒤의 reset이 그 새 세션까지 폐기한다. commit 미확인은 성공/자동 재시도로 바꾸지 않는다.

M007의 users UPDATE 가드는 관련 프로젝트 owner를 재검사한다. 따라서 실제 재해시처럼 사용자 행을 바꾸는 경로는 관련 프로젝트를 먼저 잠그고 사용자를 잠근 뒤 프로젝트 목록을 다시 확인한다. 목록이 바뀌면 확인된 rollback 후 최대 3회 순서 전체를 재시도한다. reset·활성 변경·멤버 변경도 같은 프로젝트 → 사용자 → 세션 → 멤버십 순서다. 기존 가드를 변경해 우회하지 않았다.

Authorization은 현재 세션/사용자·활성 멤버십을 매번 확인한다. viewer는 read, editor/owner는 활성 프로젝트 write, owner는 관리/복원을 허용한다. 비소속/타 프로젝트는 404, 소속의 역할 부족은 403, 보관 중 새 write는 409다. 짧은 쓰기에서 프로젝트 잠금과 user/session/member의 FOR SHARE를 사용하여 권한 변경과 직렬화한다. 사용자/요청자 UUID가 접근 권한을 대신하지 않는다.

파일/결과 helper는 URL의 project 주장과 실제 행의 project를 대조한다. 전역 규격의 검증 사용과 실제 파일 소유 프로젝트 접근은 분리한다. 이 helper를 실제 업로드/조회/다운로드 API에서 사용하는 것은 C09/C10이다. C08에서 새 업무 API를 앞당겨 공개하지 않았다.

관리 CLI는 현재 DB owner이고 높은 역할 속성이 없는 연결만 허용한다. create-email-user / reset-password / change-email / set-user-active / set-project-member / bootstrap-development를 구현했다. 마지막 활성 owner 제거는 사용자·소속·세션·감사 전체를 409로 롤백한다. 활성화가 예전 세션을 되살리지 않으며 개발 bootstrap도 비활성 사용자나 기존 소유 구성을 자동 수정하지 않는다. 웹에는 이 관리 endpoint가 없다.

보안 로그는 event/request_id/user_id/reason/operator만 JSON으로 출력한다. 메시지·예외·입력 객체를 통째로 직렬화하지 않는다. 프로젝트 없는 인증 사건은 보안 로그, 관리 변경은 실제 프로젝트의 audit_events에 system·운영 주체·대상·안전한 변경 내용을 기록한다.

## 4. 새 프로필의 실행 준비

아래는 **사용할 수 있게 구현한 명령의 안내**다. 이번 작업에서 일상 DB나 실제 계정을 준비한 것은 아니다. 대상 DB에 검토한 M008이 먼저 적용돼 있어야 한다. C08의 앱/관리 명령은 미완성 스키마를 거부하며 자동 migration/seed/구형 인증 fallback을 하지 않는다. 적용 절차는 [C07c](구현_C07c_권한과최종스키마.md)를 따른다.

```bash
.venv/bin/python -m pip install -r requirements-v1.txt
cp .env.v1.example .env.v1
cp .env.owner.example .env.owner
chmod 600 .env.v1 .env.owner
```

두 파일의 DB 연결 값은 실제 역할과 맞춘다. 웹 파일에는 app 비밀번호만, 관리 파일에는 owner 비밀번호만 넣는다. 기존 Compose .env에는 관리자/owner 비밀이 있으므로 새 웹 파일로 그대로 사용하지 않는다. process 환경 값은 명시 파일보다 우선하며 owner/admin 비밀번호가 웹 환경에 있으면 시작 오류다.

개발 프로젝트 UUID는 한 번 정해 두 파일의 DEV_PROJECT_ID에 같은 값을 기록한다. CSRF_SECRET/CURSOR_SECRET은 서로 다른 난수 비밀로 교체한다. 생성 예시는 다음과 같으며 출력값을 저장소에 넣지 않는다.

```bash
.venv/bin/python -c 'from uuid import uuid4; print(uuid4())'
.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

두 비밀은 생성 명령을 별도로 실행해 각각 공급한다. 예시의 빈 UUID와 change-me 값은 의도적으로 시작 검증을 통과하지 못한다.

```bash
.venv/bin/python -m backend.app.management --env-file .env.owner bootstrap-development
.venv/bin/python -m backend.app.management --env-file .env.owner create-email-user --email '<실제 이메일>' --display-name '<실제 표시 이름>'
CC_APP_ENV_FILE=.env.v1 .venv/bin/python -m uvicorn backend.app.main:create_app --factory --host 127.0.0.1 --port 8000 --workers 1 --no-proxy-headers
```

이메일 생성/재설정은 실제 터미널에서 비밀번호와 확인값을 에코 없이 받는다. --password·환경 비밀번호·stdin 파이프 입력은 제공하지 않는다. 발급된 UUID와 정규화 이메일을 확인한 뒤 필요한 프로젝트 멤버십을 관리 명령으로 따로 지정한다. 새 이메일 계정에 전체 프로젝트 권한을 자동 부여하지 않는다.

```bash
.venv/bin/python -m backend.app.management --env-file .env.owner reset-password --user-id '<사용자 UUID>'
.venv/bin/python -m backend.app.management --env-file .env.owner change-email --user-id '<사용자 UUID>' --email '<새 이메일>'
.venv/bin/python -m backend.app.management --env-file .env.owner set-user-active --user-id '<사용자 UUID>' --active false
.venv/bin/python -m backend.app.management --env-file .env.owner set-project-member --project-id '<프로젝트 UUID>' --user-id '<사용자 UUID>' --role editor --active true
```

운영은 APP_ENV=production·LOCAL_ADMIN_LOGIN=0·정확한 HTTPS origin/host·운영 비밀을 별도로 공급한다. 활성 developer가 남아 있으면 시작을 거부한다. 실제 HTTPS 프록시/브라우저·저장소 capability·단일 서비스 잠금·배포 승인은 C09/C12/C15의 검증 대상이며 이번 API/DB 검증으로 운영 전환을 선언하지 않는다.

## 5. 실제 검증 결과

- 기본 Python **491 passed, 7 subtests passed**. C07c 441개 + C08 단위/정적 50개다.
- 실제 PostgreSQL/API **총 1,158개**. 기존 회귀와 C08 통합 64개를 포함한 1,157개 실행 후, 최종 명시 환경 파일을 사용하는 실제 Uvicorn/HTTP·재시작 검사 1개를 별도로 실행했다. 같은 테스트를 중복 합산하지 않았다.
- 실제 앱 역할의 이메일/개발 로그인·UUID·해시 저장·절대 만료·세션 회전·재시작·다른 기기·expired/repeated logout을 검증했다.
- reset/login의 양쪽 commit 순서, 두 owner 동시 비활성화, 권한 변경과 승인된 짧은 쓰기, 다른 사용자의 이전 쿠키 교체 경쟁을 실제 트랜잭션으로 확인했다. 대기 사례는 pg_blocking_pids를 관찰했다.
- 최초 bootstrap은 두 요청이 모두 developer 없음으로 읽도록 맞춰 실제 유일 충돌을 만들고 같은 UUID/프로젝트로 수렴했다. 비활성 상태는 명시적으로 거부했다.
- 실제 관리 CLI 자식 프로세스와 PTY에서 계정 발급·재설정·이메일·소속·활성 변경을 실행했고 비밀번호가 argv/터미널 출력/로그에 없었다.
- HTTPS ASGI 프로필의 Secure/__Host/HttpOnly/Strict/Domain 조건, DB 장애의 503·logout 쿠키 유지, 요청/해시 제한 429와 안전한 로그를 확인했다. 실제 브라우저 쿠키 정책과 외부 프록시 E2E는 별도다.
- owner 비밀 없는 앱 전용 파일로 Uvicorn을 두 번 실행했다. 실제 loopback HTTP 로그인→프로세스 종료/재시작→동일 세션 me→DB logout을 확인했다.
- 일상 DB의 public 관계/OID/default ACL은 전후 동일하고 임시 DB와 서버 자식 프로세스는 정리했다. 기존 보호 기준 파일 **101개**와 이전 검증/설계 계획의 해시를 보존했다.

설치된 신규 항목은 argon2-cffi 25.1.0, email-validator 2.3.0과 전이 의존성 argon2-cffi-bindings 26.1.0, dnspython 2.9.0이다. PyPI 배포의 yanked=false·macOS arm64 wheel 설치·실제 비용·pip check를 확인했다. 개발 장비 5회씩 측정한 해시/검증 중앙값은 각각 16.098 ms / 15.135 ms였다. 운영 SLA나 부하 검증 수치는 아니다. 직접 버전 고정이 모든 플랫폼의 전이 의존성 잠금이나 전체 보안 감사를 뜻하지 않는다.
