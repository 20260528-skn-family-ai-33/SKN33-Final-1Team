작성일: 2026-10-18

상태: **C07a 구현·격리 PostgreSQL 검증 완료. 아래는 C07a 당시 적용 경계와 실행 기록이다.** 조회 인덱스 25개와 부분 유일 인덱스 2개를 구현하고 합성 데이터의 조회 계획을 확인했다. M007은 C07b와 함께 완성하는 revision이므로 **정식 Alembic head는 M006**으로 유지한다. 기존 API·개발용 admin/admin·JSON 저장은 그대로이며 일상 DB에는 적용하지 않았다.

현재 진행: [C07b — 봉인·전이와 M007](구현_C07b_봉인전이와M007.md)에서 가드를 완성해 정식 M007로 승격·검증했다. 정식 `backend/migrations/versions/`에는 M001~M006만 있다. 루트 metadata도 M006의 테이블·관계만 유지한다. 검증 도우미가 metadata를 복제한 후 인덱스를 등록하므로 기존 revision 검사에 미래 인덱스가 섞이지 않는다.

DB 검사는 migration 디렉터리를 임시 경로로 복사하고 초안을 그 복사본의 versions/에 넣는다. 이때만 Alembic config의 `allow_c07a_index_draft=True`를 지정한다. 일반 CLI에는 이 속성이 없으며, 초안을 임의로 옮겨도 속성 없이 실행하면 거부한다. 테스트 복사본의 `alembic_version=M007`은 **격리 검증용 미완성 상태**이며 배포 가능한 head가 아니다. C07b에서 가드를 완성하고 검증한 뒤에만 정식 revision으로 승격한다.

## 2. 인덱스 정의

이름·테이블·컬럼 순서·ASC/DESC·조건은 [확정 제약 목록 3절](물리설계_06_제약목록.md#3-추가-조회부분-유일-인덱스)을 따른다. 모두 public 스키마의 B-tree다.

| 구분 | 개수 | 내용 |
|---|---:|---|
| 일반 조회 인덱스 | 25 | 회원 소속·세션 만료·자료/기준/실행 이력·근거 역조회·큐·lease 후보 등 |
| 부분 유일 인덱스 | 2 | developer 한 명, run당 active attempt 하나 |
| 조건이 있는 인덱스 | 13 | 일반 조회 11개 + 부분 유일 2개. 위 개수에 포함 |
| 기존 PK/UQ 지원 인덱스 | 67 | PK 26개 + UNIQUE 제약 41개 |
| 초안 적용 후 업무 인덱스 합계 | 94 | 기존 67개 + 추가 27개. alembic_version의 PK 인덱스 제외 |

`uq_users_developer_kind`는 `account_kind='developer'`인 모든 행을 대상으로 한다. 비활성화한 developer도 대상이며 새 developer를 하나 더 만들 수 없다. email 계정은 이 부분 인덱스의 대상이 아니다. 개발 계정 seed나 로그인 로직은 아직 연결하지 않았다.

`uq_review_attempts_active_run`은 `execution_status='active'`인 attempt만 run_id별로 하나 허용한다. 다른 번호의 INSERT와 종료된 attempt를 active로 바꾸는 UPDATE도 충돌하면 23505다. 기존 active가 종료되면 새 active를 만들 수 있다. 두 트랜잭션의 동시 INSERT에서도 하나만 commit되고 다른 하나는 해당 인덱스의 23505로 실패했다. run의 active_attempt_id·종결 상태·worker 인수 전체의 정합성은 C07b/C13에서 추가한다.

조회 키와 기존 PK/UQ 키가 완전히 같은 지원 인덱스를 중복 생성하지 않았다. 큐/lease의 부분 조건에는 now() 같은 시간 함수를 넣지 않았다. 조회 시 DB에서 얻은 cutoff를 매개변수로 전달해 `available_at <= :cutoff`, `lease_expires_at <= :cutoff`를 검사한다.

## 3. 조회 계획 검증 조건

실제 PostgreSQL 17.11에서 FK 81개를 모두 활성화한 상태로 서로 다른 프로젝트·이미지 문맥을 가진 기본 그래프를 먼저 넣었다. 여기에 다음 **추가 합성 행**을 넣었다. 실제 서비스 이용량이나 측정된 운영 분포를 뜻하지 않는다.

| 테이블 | 추가 행 | 분포 |
|---|---:|---|
| review_runs | 6,000 | queued/running/failed/imported와 postgres_worker/background_tasks/imported 혼합 |
| review_attempts | 3,750 | active 750개·imported 3,000개. active의 일부만 lease 있음 |
| assets / audit_events | 각 6,000 | 프로젝트·시간·대상 UUID 분산 |
| users / project_members | 각 2,000 | 합성 email 계정과 active/inactive 소속 |

6개 테이블에 ANALYZE를 실행했다. `enable_seqscan=on`을 확인했으며 인덱스 사용을 강제하지 않았다. 대표 SELECT에 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 실행해 결과가 존재하고 예상 인덱스가 계획에 포함되는지 확인했다. 시간 값은 한 번의 로컬 합성 데이터 실행 결과이며 성능 목표·개선 배율·실서비스 지연으로 해석하지 않는다. [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html)

| 조회 | 확인한 인덱스 |
|---|---|
| 프로젝트 실행 최신순 | ix_review_runs_project_recent |
| 프로젝트의 queued 실행 최신순 | ix_review_runs_project_status |
| 고정 상태 조건과 cutoff를 만족하는 worker 후보 | ix_review_runs_queue |
| active이면서 lease가 만료된 후보 | ix_review_attempts_lease |
| 활성 소속 프로젝트 | ix_project_members_user_projects |
| 프로젝트 자료 최신순 | ix_assets_project_recent |
| 프로젝트 감사 이력 최신순 | ix_audit_events_project_recent |
| 특정 대상의 감사 이력 | ix_audit_events_target |

27개 모두의 정의는 카탈로그로 확인했고, 위 8개 대표 경로의 계획을 별도로 확인했다. 나머지 19개에도 자연 조회 계획이나 운영 성능을 검증했다고 주장하지 않는다.

실행 이력은 `(created_at DESC, run_id DESC)`와 같은 방향의 커서 `(created_at, run_id) < (:time, :run)`를 사용했다. 실제로 페이지 경계 양쪽에 같은 created_at이 오도록 데이터를 구성했다. 20개씩 두 페이지를 합친 결과가 전체 40개와 같고 UUID 누락·중복이 없었으며 같은 최신순 인덱스를 사용했다.

## 4. 부분 인덱스와 매개변수의 조건

부분 인덱스는 계획 시점에 조회 조건이 인덱스 조건을 충족함을 판단할 수 있어야 한다. 큐의 고정 조건은 서버가 작성하는 SQL에 그대로 두고, 시각 같은 실제 입력만 바인딩하는 형태를 후속 worker에서 사용한다. 사용자 입력을 문자열로 붙이거나 전체 매개변수화를 해제하라는 뜻이 아니다. [PostgreSQL 부분 인덱스](https://www.postgresql.org/docs/17/indexes-partial.html)·[SQLAlchemy 부분 인덱스](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html#partial-indexes)

```sql
WHERE origin_kind = 'service_execution'
  AND executor_kind = 'postgres_worker'
  AND execution_status = 'queued'
  AND available_at <= :cutoff
ORDER BY available_at, created_at, run_id
LIMIT 20
```

`plan_cache_mode=force_generic_plan`으로 재현한 두 준비된 문장을 비교했다. 위 세 상태 조건이 고정된 SQL은 `ix_review_runs_queue`를 사용했고, 세 조건까지 `$1/$2/$3`으로 바인딩한 generic plan은 사용하지 못했다. 시간 cutoff만 바인딩하는 것은 이 검사에서 문제가 없었다. custom plan이나 모든 드라이버 실행이 항상 같은 결과라는 뜻은 아니며, 실제 worker 연결 시 해당 쿼리와 준비된 문장 설정으로 다시 확인한다.

## 5. 실행 방법과 검증 결과

기본 회귀·정적 검사는 DB 없이 실행한다.

```bash
.venv/bin/python -m pytest -q
```

DB 검사는 [C01의 명시적 TEST_DB_* 설정](구현_C01_DB연결과트랜잭션.md#4-전용-postgresql-테스트-실행)을 준비한 후 아래 신규 모듈을 선택한다. 일반 .env/업무 DB로 조용히 우회하지 않는다. 각 모듈은 무작위 `creative_checker_test_*` DB만 생성·정리하며 테스트 도우미가 초안 허용 설정을 넣는다. 자격증명 파일을 저장소에 새로 만들지 않았다.

```bash
.venv/bin/python -m pytest backend/tests/test_index_migration_integration.py backend/tests/test_index_query_plans_integration.py backend/tests/test_index_initial_migration_integration.py -m db_integration -q
```

2026-10-18 실행 결과:

- 기본 Python **430 passed, 7 subtests passed**. 기존 425개 + 신규 정적 검사 5개이며 DB 검사 880개는 deselected다.
- 실제 PostgreSQL **880 passed**. 기존 833개 + 신규 47개(인덱스 DB 36개·조회 계획 10개·빈 DB 1개)다.
- 27개 모두 컬럼 순서·내림차순·unique·predicate·valid/ready/live·키/전체 컬럼 수가 일치했다. DESC는 컬럼별 pg_get_indexdef 문자열에 포함되지 않아 pg_index.indoption으로 별도 확인했다.
- 중복 developer/active가 이미 존재하면 생성이 실패하고 원래 중복 행·M006 버전·객체 OID·기본 ACL을 보존했다. 자동 정리·이름이 같은 기존 객체 채택은 하지 않았다.
- 중간 이름 충돌과 초안 마지막 오류 주입은 먼저 만든 인덱스까지 롤백했다. 빈 DB에서 M001→초안 끝 오류는 테이블·인덱스·버전·기본 ACL을 함께 롤백했다.
- 정상 적용은 기존 업무 행·객체·기본 ACL을 보존했다. 빈 DB의 정상 적용에서는 26개 업무 테이블이 모두 비어 있었다. 같은 초안 재요청은 성공하고 파괴적 downgrade는 거부했다.
- app의 업무 테이블 권한은 계속 닫혀 있다. 일상 DB의 public 관계/기본 ACL 전후가 같고 임시 테스트 DB가 남지 않았다.
- M001~M006·기존 연결/설정·API·개발 인증·React·OCR·launcher·이전 검증 JSON의 기준 해시 63개가 그대로다. 패키지 추가 설치는 없었다.

정적 정의와 실제 카탈로그는 [제약 목록](물리설계_06_제약목록.md)을 각각 대조했다. EXPLAIN 원문과 테스트 결과/소스 해시는 [C07a 검증 기록](verification/2026-10-18-implementation-C07a.json)에 남겼다.
