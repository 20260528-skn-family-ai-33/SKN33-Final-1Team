## 2. 규칙과 실제 SQL 객체 수

기준은 [설계의 검증 규칙 30개](물리설계_06_제약목록.md#4-전이추가커밋-검증-규칙)다. 하나의 규칙이 여러 테이블에 붙으므로 객체 개수를 별도로 센다.

| 구분 | 개수 | 대상 |
|---|---:|---|
| BEFORE 전이 트리거 | 9 | schema·파일·인계·OCR·추출·기준 버전/초안·run·attempt |
| BEFORE 자식 추가 gate | 7 | 토큰·관찰·기준 항목·결과·채택·근거·근거 토큰 |
| BEFORE 파일 인계 연결 gate | 1 | stored_files의 최초 인계 연결 |
| 지연 스냅샷/실행/인계/owner 제약 | 11 | OCR/추출/기준 각 1, 실행 관련 4, 인계 1, owner 관련 3 |
| 지연 계보 제약 | 7 | 자료·파일·프레임·인계·추출·기준·재검수 |
| 실제 트리거 합계 | **35** | BEFORE 17 + AFTER ROW·DEFERRABLE INITIALLY DEFERRED 18 |
| PL/pgSQL 함수 | **19** | 규칙에서 공유하는 검사·잠금·트리거 함수 |

schema 정의·OCR 루트·run·attempt의 전이 트리거는 INSERT도 검사한다. UPDATE만 검사하면 잘못된 역할의 규격 파일을 직접 등록하거나, 종료된 run에 새 OCR/attempt를 연결하는 경로가 남기 때문이다. 규칙 이름은 그대로 유지하고 실행 이벤트를 보강했다.

인덱스는 C07a의 고정 DDL과 같다. 업무 테이블 26개·395개 컬럼·PK 26개·UNIQUE 41개·CHECK 77개·FK 81개에 조회/부분 유일 인덱스 27개가 추가된다. PK/UQ 지원 67개를 합치면 업무 인덱스는 94개이며 alembic_version의 PK는 제외한다.

## 3. 강제하는 동작

- OCR·추출·기준은 부모를 미봉인 상태로 만들고 자식 전체를 저장한 뒤 sealed_at을 한 번 기록한다. 커밋 직전 최종 행을 다시 읽으며 미봉인/미완결 루트는 커밋할 수 없다. OCR의 queued/running은 생성 중 상태로만 허용한다.
- 봉인 후 토큰·관찰·항목·결과·채택·근거의 추가를 거부한다. 결과 쪽 gate는 run과 현재 attempt, 필요한 lease까지 확인한다. OCR 입력 파일과 최종 토큰 프레임은 서로 다른 역할로 유지한다.
- 기준은 1~100개, position은 1부터 연속이어야 한다. 새 서비스 확정의 초안 revision/요구사항 복사본은 잠근 현재 초안과 같아야 한다. 새 run도 오래되거나 보관된 초안의 확정을 재사용할 수 없다. 이미 접수한 run은 이후 편집과 별개다.
- running run은 현재 active attempt 하나가 필요하고 queued/terminal에는 active가 없어야 한다. completed는 같은 succeeded attempt의 전체 항목 결과·채택·봉인/manifest를 요구한다. 입력 manifest, OCR의 attempt와 추출본의 OCR을 대조한다. all_selected_v1이면 저장된 항목으로 요약 verdict도 대조한다.
- imported 결과는 imported 묶음과 import_projection으로 연결하고 로컬 구조만 봉인한다. 원문이 confirmed/pass를 보고해도 로컬 확정은 unconfirmed, 실행/항목 verdict와 실행 시각·진행률은 NULL로 유지한다. 봉인을 사람 승인으로 사용하지 않는다.
- 파일 인계 FK는 최초 연결만 허용한다. 인계 completed 전환은 같은 인계에 연결된 stored 상태의 import_manifest를 요구한다. 완료 후의 새 파일 연결은 거부하되, 이후 별도 트랜잭션에서 관찰한 stored↔missing은 허용한다.
- failed 인계의 received 복귀는 소유자 관리 연결과 import.revalidate 감사 기록을 요구한다. 관리 명령·재검증 실제 바이트 검사는 C14에서 연결한다. 완료한 인계의 내용은 수정하지 않는다.
- 부모 체인 7개에서 순환을 거부한다. 추출/기준의 선행 번호는 더 작아야 하고 재검수 원 run은 종료돼 있어야 한다. 직접 자기 참조와 문맥 경계는 기존 CHECK/FK도 계속 검사한다.

규격 파일 역할·제시된 schema 해시와 파일 metadata의 해시, 프레임 파일·역할·치수, OCR/근거의 실제 참조 프레임과 좌표 범위도 대조한다. 이미지 디코딩·파일 바이트·행렬의 실제 변환 결과·Python JSON 해시 계산까지 DB가 검증한 것은 아니다.

## 4. 잠금·격리·실제 경합

프로젝트 owner와 변경 가능한 자료 부모 체인의 검사는 프로젝트 행을 `FOR NO KEY UPDATE`로 잠근 뒤 새 조회로 확인한다. 사용자 변경에 관련된 프로젝트는 UUID 순으로 검사한다. 이 경로는 READ COMMITTED만 지원하고 다른 격리 수준은 cc_guard_isolation으로 거부한다. 함수는 VOLATILE이며 잠금 대기 후 각 SQL의 새 스냅샷을 사용한다. [PostgreSQL 격리 수준](https://www.postgresql.org/docs/17/transaction-iso.html)·[함수 스냅샷](https://www.postgresql.org/docs/17/xfunc-volatility.html)

추가 gate는 대상 루트를 잠그고 봉인·현재 시도·허용 문맥을 검사한다. 독립 worker의 heartbeat·성공·결과 쓰기는 실제 clock_timestamp()로 만료를 검사하고 만료된 lease를 연장해 되살릴 수 없다. dispatch_state는 역행하거나 NULL로 지울 수 없다. 안전 재대기는 postgres_worker, 종료된 failed·retryable 시도, not_dispatched, 고정 max_attempts 1~3의 잔여 횟수를 요구한다. BackgroundTasks 자동 재대기와 제출 후 불명 상태의 자동 재제출은 거부한다.

실제 두 트랜잭션으로 다음을 확인했다.

| 경합 | 결과 |
|---|---|
| 두 owner의 소속 강등 | 하나 commit, 하나 ct_project_owner 거부 |
| 두 owner 사용자 비활성화 | 하나 commit, 하나 ct_project_owner 거부 |
| A→B/B→A 동시 부모 변경 | 하나 commit, 하나 ct_lineage_assets 거부 |
| 완료 저장 중 늦은 결과 INSERT | pg_blocking_pids로 실제 대기 확인 → 완료 commit → 봉인된 최종 상태를 읽고 거부 |

후속 서비스/worker는 attempt UPDATE 전에 run → attempt를 명시적으로 잠가야 한다. UPDATE 대상 attempt의 행 잠금은 BEFORE 트리거보다 먼저 획득되므로 트리거만으로 호출자의 전체 잠금 순서를 대신하지 않는다. 다중 업무 잠금·재시도·토큰 비교와 실제 worker 인수 경쟁은 C10/C13의 저장 진입점에서 검증한다.

## 5. 마이그레이션 안전성과 권한

제약 트리거를 설치해도 과거 행이 자동으로 검증되지 않으므로, M007 끝에서 기존 루트·owner·계보·관련 metadata를 명시적으로 점검한다. 기존의 잘못된 입력 manifest로 M007이 실패했을 때 인덱스·함수·트리거·버전이 모두 롤백되고 M006의 행·객체 OID·기본 ACL이 그대로였다. 테스트 자료의 명시적 수정 후에만 정상 적용했다. migration이 업무 행을 자동 보정하지 않는다.

기존 함수 이름 충돌도 채택·덮어쓰기 없이 42723으로 실패했다. 끝 오류 주입은 M006을 보존했고, 빈 DB→M007 끝 오류는 전체 테이블·인덱스·함수·버전·기본 ACL을 롤백했다. 정상 M007 재요청은 같은 상태를 유지하고 파괴적 downgrade는 거부한다.

함수는 SECURITY INVOKER와 고정 search_path를 사용하며 PUBLIC EXECUTE를 회수했다. 새 테이블 DML 권한이나 app 함수 EXECUTE는 부여하지 않았다. 사용자별 권한·계정/세션·허용 컬럼·추가 전용 테이블 권한은 M008/C08에서 연결한다. 소유자·superuser의 관리 DDL이나 트리거 해제까지 막는다고 주장하지 않는다. [PostgreSQL 지연 트리거](https://www.postgresql.org/docs/17/sql-createtrigger.html)
