# 추가 설계 9단계 — 저장·파일·이전·복구

작성일: 2026-10-17

상태: **9단계 설계 완료.** 파일 확정과 DB 커밋·응답 유실·봉인·실패 정리, 과거 JSON의 명시적 수입, 백업 세트와 복원·되돌리기를 정의한다. 이번 산출물은 문서와 합성 검토 자료이며 실제 파일 이동·삭제·DB 변경·수입·백업·복원을 수행하지 않았다.

## 1. 범위·근거·운영 전제

기준은 [파일 설계 2단계](물리설계_02_사용자와파일.md), [인계·OCR 3단계](물리설계_03_규격과OCR근거.md), [불변 기준 4단계](물리설계_04_검수기준.md), [실행·결과 5단계](물리설계_05_검수실행과결과.md), [제약·봉인 6단계](물리설계_06_전체정합성.md), [인증 7단계](추가설계_07_인증과권한.md), [API·해시 8단계](추가설계_08_API와화면JSON.md)다. 현재 코드의 파일 저장·시작 복구는 [api.py](../../backend/app/api.py), 컨테이너·기초 DB 역할은 [compose.yaml](../../compose.yaml)과 [초기화 스크립트](../../docker/postgres/init/01-create-roles.sh)에서 확인했다.

| 구분 | 현재 | 이번 목표 |
|---|---|---|
| 새 검수 | .runtime/reviews/{id}의 original.bin·normalized.png·snapshot/result/OCR JSON | v1 전용 파일 루트와 PostgreSQL 업무 기록 |
| 상태 기준 | JSON 파일 | 신규 v1 업무는 DB. 작업 저널은 복구 보조 자료 |
| 기존 이력 | JSON 파일을 직접 읽음 | 원본 보존·dry-run·대상 프로젝트 지정 뒤 읽기 전용 수입 |
| 파일/DB 실패 | 현재 로컬 저장 흐름 | 커밋 결과 확인 뒤 정리. 불명확하면 보존 |
| 백업 | DB 준비 단계의 보존 검증 기록만 있음 | 쓰기 중지 상태에서 DB·파일·설정 버전을 한 세트로 확보 |

테이블·키는 **26개 업무 테이블·395개 컬럼·PK 26개·UNIQUE 41개·FK 81개**를 유지한다. 새 범용 멱등/GC/백업 테이블을 추가하지 않는다. 파일 작업 저널·수입 계획·백업 manifest는 운영 파일이며 업무 행·승인·원문을 대신하지 않는다.

첫 저장 운영 프로필은 **단일 호스트의 영속 로컬 파일시스템**이다. API·worker·관리 명령·GC가 같은 저장소 잠금 규약을 따른다. NFS·다중 호스트의 서로 다른 로컬 디스크·실행 중 볼륨 경로 교체는 지원한다고 가정하지 않는다. OS별 프로세스 간 잠금·동일 볼륨 이동·flush의 검증 명세는 [10단계](추가설계_10_구현구조와검증명세.md)에 두고 실제 검증은 C09/C14에서 수행하며 미지원 환경에서는 파괴적 정리와 운영 전환을 허용하지 않는다.

## 2. 파일 경로·불변 바이트·작업 저널

| 경로 역할 | 목표 형태·정책 |
|---|---|
| STORAGE_ROOT | 별도로 설정한 영속 절대 루트. 예시 .runtime/storage-v1, 저장소/정적 웹 공개 대상 아님 |
| staging | staging/{operation_id}/… 수신·생성 중 파일 |
| 최종 파일 | objects/projects/{project_id}/files/{file_id}/payload.bin |
| 작업 저널 | operations/{operation_id}/journal.json·잠금 파일. 파일/리소스 의도 목록 |
| 수입 원문 보관 | intake/{operation_id}/… 실제 받은 파일·dry-run 계획·검사 결과 |
| 미참조 격리 | quarantine/{operation_id}/… 검증 후 옮긴 미참조 파일 |
| 구형 이력 | .runtime/reviews/… 그대로 보존. 새 루트와 섞거나 앱 시작에 이동하지 않음 |
| 백업 | STORAGE_ROOT 밖의 별도 대상. backup_id별 DB 덤프·파일 inventory·완료 manifest |

stored_files.storage_key에는 최종 파일의 STORAGE_ROOT 기준 상대 키만 저장한다. staging/intake/quarantine 경로를 정상 업무 파일 키로 넣지 않는다. 키는 서버 UUID로 만들고 원본 이름·요청 URL·인계 파일명으로 조합하지 않는다. 이름·해시가 같아도 별도 파일/자료를 자동 병합하지 않는다.

파일은 바이트를 닫기 전에 flush·fsync하고 같은 파일시스템의 최종 경로로 이동한다. UUID 경로가 이미 있으면 무조건 덮어쓰는 replace를 하지 않고 같은 작업의 예상 길이/해시인지 검사한다. 디렉터리 엔트리의 내구성 처리도 OS 프로필에 포함한다. 이름 이동의 원자성과 전원 장애 뒤 내구성은 같은 보장이 아니다. [Python flush·fsync 안내](https://docs.python.org/3/library/os.html#os.fsync)

루트와 상위 디렉터리는 서비스 전용 쓰기 권한을 사용한다. 절대 경로·상위 이동·심볼릭 링크·하드 링크·장치 파일을 입력 파일로 허용하지 않는다. 파일을 열 때 실제 디렉터리 경계와 파일 핸들을 확인하여 경로 검사 이후 교체되는 경우도 처리한다. 안전한 열기/게시의 Linux 우선 구현과 portalocker 선택은 [10단계](추가설계_10_구현구조와검증명세.md)에 두며 실제 OS 보장은 구현 검증으로 확인한다.

저널은 contract_version/operation_id/kind/project_id/created_at/updated_at, 예정 file_id·storage_key·role·크기·SHA256, 예정 resource UUID, request 지문/operation(해당할 때), 파일 확정/DB 결과 확인 상태를 기록한다. 비밀번호·토큰·DB URL·원격 비밀을 넣지 않는다. 저널 자체도 임시 파일→동일 볼륨 이동으로 갱신하며 DB와 불일치하면 **실제 DB·실제 파일 확인 결과를 우선**한다. 저널이 committed라고 적혀 있어도 DB 조회를 생략하지 않는다.

수신·OCR·해시 계산은 DB 트랜잭션 밖에서 수행한다. 작업별 파일 잠금은 살아 있는 작업의 staging 정리를 막으며 DB 행 잠금과 구분한다. 부분 산출물 파일은 업무 결과가 아니고 API에서 정적 공개하지 않는다.

## 3. 확정·정리 경합을 막는 규약

파일을 옮긴 뒤 DB 행이 아직 안 보이는 구간과, 프로세스가 종료됐지만 DB 커밋이 끝나는 구간을 모두 보호한다. 시간 유예만으로 이 경합을 해결했다고 표현하지 않는다.

| 조정 수단 | 규칙 |
|---|---|
| 작업 잠금 | operation_id별 OS 파일 잠금. 수신/파일 확정/결과 확인 작업이 소유 |
| 저장소 gate | 최종 파일 확정과 DB 커밋 구간은 공유 잠금, GC·복원·백업의 배타 구간은 배타 잠금 |
| DB 작업 잠금 | 짧은 최종 DB 트랜잭션에서 operation_id에 대응한 transaction-level advisory lock |
| GC 확인 | 배타 gate 아래 작업 잠금을 **비차단** 시도하고, DB 작업 잠금도 비차단 시도. 하나라도 사용 중이면 건너뜀 |
| DB 확인 대상 | 읽기 복제본이 아닌 실제 쓰기 primary, READ COMMITTED의 잠금 획득 후 새 조회 |

DB 작업 키는 `cc-storage-op-v1:`과 operation UUID 문자열의 UTF-8 SHA256 앞 8바이트를 big-endian signed 64-bit로 해석한다. 다른 UUID가 같은 키가 되면 불필요하게 직렬화될 수 있지만 파일 소유 판정은 전체 UUID·예정 파일 목록으로 다시 한다. 이 값을 권한·업무 식별자로 사용하지 않는다.

파일 확정자는 작업 잠금 → 공유 gate → 파일 확정 → 짧은 DB 트랜잭션의 작업 advisory lock → 기존 프로젝트/사용자/세션/멤버십 또는 run/attempt 행 잠금 순서다. GC는 배타 gate 뒤 작업 잠금을 기다리지 않으므로 역순 교착을 만들지 않는다. PostgreSQL 트랜잭션 잠금은 커밋/롤백 시 해제되므로, 이전 프로세스가 죽었어도 아직 끝나지 않은 DB 반영을 GC가 건너뛸 수 있다. [PostgreSQL advisory lock 안내](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)

모든 파일 등록·격리 복원 경로가 같은 gate와 작업 잠금 규약을 사용해야 한다. GC가 배타 gate를 가진 동안 새로운 확정 트랜잭션을 시작하지 않는다. 이 규약을 지키지 않는 외부 스크립트의 직접 DB/파일 변경은 정상 운영 경로가 아니다. 긴 수신·추론 동안 DB advisory/행 잠금을 보유하지 않는다.

일반 DB 저장은 lock_timeout 2초·statement_timeout 10초, 수입 최종 저장은 최대 60초를 초기 한도로 제안한다. deadlock/serialization의 **롤백이 확인된 경우만** 같은 고정 데이터로 최대 3회 저장 재시도를 허용하고 매번 권한·현재 상태를 다시 확인한다. 동기 psycopg/Connection 타임아웃 계약은 [10단계](추가설계_10_구현구조와검증명세.md)에 두고 실제 취소·커밋 미확인 동작은 구현 때 검증한다. 커밋 여부 미확인은 이 재시도 분류에 넣지 않는다.

## 4. 업로드·초안·확정·실행의 커밋 경계

| 진입점 | DB 밖 | 한 트랜잭션의 최종 기록 | 성공 기준 |
|---|---|---|---|
| 프로젝트 생성 | 이름/인증 입력 검증 | 프로젝트·활성 owner·감사 | 201 전 커밋 |
| 이미지 업로드 | 제한 수신·실제 디코딩·EXIF·표시 PNG·길이/해시·파일 확정 | stored_files·asset·version·원본/표시 frame·감사 | 실제 바이트와 모든 연결 커밋 뒤 201 |
| 초안 생성/수정 | JSON 외형·문자/항목 한도 | 프로젝트/권한·대상 일치·expected_revision 검사·초안·감사 | 무변경/증가 revision 확정 뒤 응답 |
| 기준 확정 | 고정 요청 지문 준비 | 재전송 검사→프로젝트/초안 잠금→선택 검증→버전/항목/멱등/감사→봉인 | deferred 검사 포함 커밋 뒤 201/200 |
| 검수 접수/재검수 | 서버의 실제 실행 설정 확인 | 권한/기존 키→고정 입력·요청 지문·run queued·감사 | 커밋 뒤 202/200, 그 뒤 실행 전달 |
| 시도 인수 | 대상 실행 선택 | run→새 attempt→active 포인터·running·토큰·감사 | 커밋 후 잠금 밖에서 추론 |
| 완료 저장 | 출력·좌표·ID·파일·manifest 검증 및 확정 | 토큰/lease 재검사→OCR/추출/결과/근거/채택→attempt/run 최종 상태·봉인·감사 | 전체 커밋. 일부 완료 없음 |
| 실패 마감 | 오류를 안전한 객체로 분류 | run/attempt 현재 권한 검사·failed/unknown·포인터 해제·안전 재대기 또는 최종 실패·감사 | 성공 판정/채택을 만들지 않음 |

파일 확정은 DB INSERT보다 먼저 하며, 모든 실제 바이트·크기·해시 확인은 DB 잠금 밖에서 마친다. 짧은 쓰기에서 7단계의 현재 사용자·세션·역할·보관 상태를 재확인한다. 업로드 수신 중 권한이 바뀌면 DB 저장을 거부하고 미참조 파일 정리 경로로 넘긴다.

새 run은 이미 저장한 image/confirmed criteria를 참조한다. 프로젝트 생성·파일 업로드·초안 확정을 검수 접수 한 요청에서 암묵적으로 다시 만들지 않는다. 이 구분 덕분에 실행 접수 실패가 이미 확정한 이미지·기준을 삭제하지 않는다. 자동 저장용 임의 프로젝트·이메일·기준은 생성하지 않는다.

## 5. 최초 봉인·상태 전이·늦은 쓰기

| 루트 | 생성과 최초 봉인 |
|---|---|
| criteria_versions | sealed_at=NULL의 버전 → 선택 항목 전체 → 초안/기준 지문 → sealed_at 1회. 한 트랜잭션 |
| ocr_runs | terminal completed/failed/imported 및 실제 문맥 → 토큰·원문 연결 → sealed_at. 영속 queued OCR 큐로 커밋하지 않음 |
| poster_extractions | 추출 원문·실제 규격 상태 → 관찰·관찰 근거·토큰 연결 → sealed_at |
| review_runs completed | 현재 attempt의 출력 전체 → run_item_selections → 결과 manifest·selected attempt·completed/finished/sealed → active 포인터 해제 |
| review_runs imported | 확인한 입력·원문·명시적 imported 결과 묶음/채택 연결 → 로컬 구조 manifest·sealed. 원 실행 시각·verdict는 만들지 않음 |

부모 먼저·자식 전체·봉인 순서를 6단계 append gate/지연 제약으로 확인한다. 커밋 시 미봉인 루트를 허용하지 않으며 봉인 이후 자식 INSERT도 거부한다. 기준/항목 UUID와 OCR 외부 문자열/숫자 ID를 실제로 대응한 뒤 저장한다. 결과와 근거의 이미지·attempt·criteria 문맥이 다르면 전체 저장을 거부한다.

파일이 생성돼도 오래된 worker_token·active_attempt_id·만료 lease이면 저장할 수 없다. 독립 DB worker는 잠금 획득 후 DB 실제 시각으로 lease를 확인한다. 로컬 BackgroundTasks도 포인터·토큰을 확인한다. 늦은 결과는 별도 진단/미참조 파일로 보존할 수 있으나 이미 봉인한 결과를 수정하거나 새 추론 결과를 같은 attempt에 덮어쓰지 않는다.

항목 failed/unsupported가 있는 완결 결과는 all_selected_v1에 따라 overall review일 수 있다. 전체 OCR/출력 계약이 깨져 완결 집합을 만들 수 없으면 run failed다. 잘못된 출력을 잘라내서 completed/pass로 저장하지 않는다. 아직 저장하지 못한 원문은 작업 저널과 진단 파일로 남기며 보존 정책을 적용한다.

## 6. 커밋 결과 미확인과 파일 정리 판정

| 상황 | 판정·허용 동작 |
|---|---|
| 수신/디코딩 실패, 최종 파일 확정 전 | 소유한 staging 정리 가능. 업무 파일·기존 버전 삭제 금지 |
| 파일 확정 뒤 BEGIN 전 실패 | 소유한 최종 파일은 미참조 후보. gate/잠금·primary 확인 뒤 격리 |
| DB가 명시적으로 롤백 확인 | 같은 작업의 미참조 파일만 격리. 다른 요청의 같은 해시 파일 건드리지 않음 |
| COMMIT 전송 뒤 연결 단절/타임아웃 | **결과 미확인. 파일 삭제·새 추론·새 키 접수 금지**. 조회로 확인 |
| DB 커밋 성공, HTTP 응답 유실 | 실제 행/지문을 확인해 성공 복원. 확정/실행은 같은 키로 재조회/재전송 |
| 프로세스 종료, DB 작업 잠금 사용 중 | GC 건너뜀. 이전 커밋/롤백이 끝난 뒤 primary에서 다시 확인 |
| DB 조회 불가·잠금/저널 손상·파일 목록 불명 | 보존·운영 점검. 오류를 미참조 확인으로 취급하지 않음 |
| 파일 키/UUID는 같지만 해시·관계가 다름 | 충돌로 중단. 기존 파일/행 덮어쓰기 금지 |
| 이미 봉인한 run과 같은 result manifest | 동일 저장의 성공으로 확인. 재추론 없음 |
| 이미 봉인한 run과 다른 result manifest | 불일치 진단·보존. 새 시도/재검수 없이 기존 결과 교체 금지 |

저널의 미리 발급한 resource UUID와, 적용 대상 요청 키/지문·expected manifest를 함께 사용해 실제 커밋을 확인한다. upload처럼 영속 HTTP 멱등을 제공하지 않는 요청도 운영 저널을 이용해 생성 여부를 찾을 수 있지만 이를 브라우저 API의 exactly-once 보장이라고 소개하지 않는다.

현재 run이 아직 running이고 원 저장의 롤백이 확인되며 토큰/lease가 유효하면 **동일 출력의 DB 저장만** 다시 시도할 수 있다. 토큰을 잃었으면 늦은 쓰기로 거부한다. DB 결과 미확인과 원격 추론 결과 미확인을 다른 오류로 기록한다. 원격 dispatching/submitted/unknown에서는 알려진 job 조회만 허용하고 응답 유실을 이유로 새 유료 job을 자동 제출하지 않는다.

## 7. GC·누락 파일·초기 보존 정책

GC 기본 모드는 dry-run이다. staging/저널/미참조 후보를 보고하고 실제 격리/삭제는 구현 검증을 통과한 별도 관리 실행에서 수행한다. 이번 작업에서는 어느 파일도 정리하지 않는다.

| 대상 | 최초 정책 |
|---|---|
| 살아 있는 작업 | 작업 잠금·공유 gate/DB 작업 잠금 사용 중이면 무조건 제외 |
| staging/미참조 후보 | 파일 확정/최종 수정 후 24시간 유예, primary 확인·저널/소유 대조 뒤 격리 |
| quarantine | 7일 보존 후 같은 잠금/DB 재검사를 통과한 미참조 바이트만 삭제 가능 |
| DB에 등록한 stored/missing 파일 행 | 사용 여부와 관계없이 자동 삭제 대상 아님. 업무 행의 물리 DELETE도 없음 |
| 완료/실패 작업 저널 | DB/파일 결과 확인 뒤 30일. unresolved는 기한만으로 삭제하지 않음 |
| 수입 원문·계획·불일치 진단 | 관련 업무/미해결 수입이 있으면 보존. 자동으로 외부 원문을 삭제하지 않음 |
| 사용자·세션·감사·업무 기록 | 최초 범위에서 자동 물리 삭제 없음. 세션은 expires/revoked로 무효화 |
| 보안 운영 로그 | 최초 30일, 실제 보존·백업 정책은 운영 구성에서 적용 |

GC는 배타 gate 아래 작업 잠금과 DB 작업 잠금을 비차단 획득한 뒤 primary에서 **stored_files의 모든 state**와 예정 리소스를 확인한다. 유예 시각은 단독 소유 증거가 아니다. 작업 저널이 없는 최종 파일은 자동 삭제하지 않고 조사 대상으로 남긴다. 참조 행이 하나라도 있으면 quarantine에서의 최종 삭제도 거부한다. 정상 앱은 이후 기존 미참조 파일 키를 새 행에 재사용하지 않는다.

실제 파일이 없거나 길이/해시가 다르면 기대 바이트를 사용할 수 없으므로 stored_files.state=missing과 감사/진단을 남긴다. 저장한 해시·원본/표시 연결·과거 run/verdict를 바꾸지 않는다. 파일 API는 503 FILE_UNAVAILABLE을 반환하고 새 실행은 필요한 파일이 검증될 때까지 거부한다. 파일 상태를 점검하기 위해 GET에서 업무 행을 몰래 갱신하지 않고 별도 점검 경로를 사용한다.

복구는 동일 예상 SHA256·크기의 실제 바이트를 확보한 경우에만 가능하다. 배타 gate에서 잘못된 파일을 진단 격리하고 검증한 바이트를 같은 키에 안전하게 확정한 뒤 missing→stored와 감사를 기록한다. 다른 내용이면 새 파일/이미지 버전 또는 새 수입이지 과거 파일 복구가 아니다. 이미지를 다시 디코딩·재인코딩한 PNG는 바이트가 달라질 수 있으므로 기존 표시 SHA256과 같다고 추정하지 않는다.

## 8. 시작 복구·BackgroundTasks와 DB worker

첫 DB 저장 연결은 BackgroundTasks·웹 프로세스 1개다. 같은 호스트의 배타 서비스 잠금으로 이전 서비스가 살아 있는 상태에서 새 시작 복구를 동시에 수행하지 않는다. 시작 복구는 DB·저장소 확인과 미확인 커밋 조정 뒤에 수행하고 준비 완료 전 업무 API는 열지 않는다.

| 재시작에서 발견한 실행 | 첫 BackgroundTasks 프로필 |
|---|---|
| completed/failed/imported | 그대로 보존. 파일 가용성만 별도 점검 |
| queued·아직 attempt 없음 | RESTART_BEFORE_START로 failed 마감. 새 추론 자동 재개 없음 |
| running·active attempt 존재 | 현재 권한을 잠그고 failed/unknown 시도로 마감·포인터 해제·run failed |
| 원격 제출 여부 불명·job ID 없음 | outcome_unknown=true·자동 재제출 금지 |
| 이미 DB 최종 커밋이 확인됨 | 성공 상태 유지. 저널만 실제 결과로 조정 |

새 프로세스는 다른 살아 있는 BackgroundTasks의 run을 중단 처리하지 않는다. OS 서비스 잠금을 획득하지 못하면 시작을 중단한다. 독립 postgres_worker 도입 후에는 5단계 lease/heartbeat·현재 토큰에 따라 만료 실행만 회수하며 두 실행 프로필의 queued를 혼용하지 않는다. 복원 모드에서는 queued라도 worker를 자동 시작하지 않고 12절 검증을 먼저 수행한다.

## 9. 과거 JSON·외부 인계의 dry-run 계획

첫 입력 단위는 **단일 논리 포스터/검수의 읽기 전용 디렉터리**다. legacy는 .runtime/reviews/{외부 ID}의 실제 파일, 외부 인계는 실제 받은 manifest와 구성 파일이다. 자동 ZIP 해제·다중 포스터 묶음 분할·부족 파일의 네트워크 다운로드는 첫 범위에서 하지 않는다. 초과/미지원 묶음은 needs_review로 보고한다. 아직 받지 않은 규격/파일을 존재한다고 등록하지 않는다.

초기 intake 한도는 파일 500개·전체 512 MiB, 개별 JSON 20 MiB·이미지는 8단계 한도다. 상대 파일명은 POSIX 표기·UTF-8 255바이트 이하이며 빈 경로·상위 이동·절대/드라이브 경로·역슬래시·링크·중복 경로를 거부한다. NFC/casefold 비교에서 충돌하는 이름도 거부하되 원문 이름을 정규화해 덮어쓰지 않는다. 입력 경로는 보호된 관리 설정의 허용 루트 안에서만 읽는다.

dry-run은 원본 파일을 수정하지 않고 다음 내용을 출력하는 계획이다. DB가 준비됐을 때 대상 존재·권한·중복을 읽기 전용으로 확인하며, 계획 파일 작성은 업무 DB 쓰기가 아니다.

복사 대상은 기존 서비스의 쓰기·시작 복구를 중지한 읽기 전용 스냅샷으로 고정한다. 수입 도구가 api.py의 앱 초기화/구형 복구를 실행해 원본 JSON을 갱신하지 않도록 모듈 경계를 분리한다. 스캔·복사·적용 사이 바이트/목록이 달라지면 INPUT_CHANGED로 중단하고 새 계획을 요구한다.

1. 실제 파일의 이름·바이트 수·SHA256·MIME/이미지 치수·원문 JSON 문법을 확인하고 읽기 전용 intake 복사본을 만든다. 복사 후 같은 해시인지 대조한다.
2. 원래 record/criteria/OCR ID의 값과 타입, 상태·좌표·규격 버전·필드 누락을 수집한다. 실제 바이트와 출처 해시의 matched/mismatch/not_checked를 별도로 보고한다.
3. 대상 프로젝트·인계 namespace·허용한 기존 이미지/기준 연결·변환 profile 버전을 명시한다. 이름 일치나 local-admin 문자열로 프로젝트/작성자를 자동 추정하지 않는다.
4. 새로 만들 로컬 UUID와 별칭 대응, 참조 순서·원문 보존 위치·검증하지 못한 사항을 계획한다. 미확인 UUID·이미지·시각을 채워 넣지 않는다.
5. plan의 의미 내용과 원문 파일 inventory에서 지문을 계산하고 ready/needs_review/rejected와 이유를 출력한다. apply는 이 고정 계획과 일치하는 입력만 사용한다.

첫 legacy 변환에서 새 requester/confirmed_by는 미확인이면 NULL, 원 사용자 문자열은 원문에 보존한다. imported_by는 이번 수입 주체이며 과거 요청자가 아니다. `attempt_no=1, execution_status=imported`는 확인한 결과의 로컬 묶음 순서이지 실제 추론 횟수가 아니다. 원문에 없는 추론 시작/종료·모델 버전·신뢰도·사람 승인을 생성하지 않는다.

| 확인 결과 | 저장/표시 정책 |
|---|---|
| 실제 이미지·기준·결과 ID 대응이 완전 | 로컬 imported/legacy 스냅샷으로 구조 저장 가능 |
| OCR/추출 일부 없음 | 없는 FK·값은 NULL, 원문과 누락 사유 보존. 가상 토큰/추출 생성 금지 |
| 결과 일부만 존재 | 실제 결과만 보존·results_complete=false, 없는 항목의 pass 생성 금지 |
| 이미지/기준 등 필수 FK 대상이 없음 | package needs_review와 intake 원문만 보존, 가짜 업무 그래프 생성 금지 |
| 실제 해시 불일치 | package hash_check_state=mismatch, completed 금지 |
| 원래 좌표 기준·EXIF·스케일/표시본 대응 불명 | 원문 좌표는 보존, 확인되지 않은 정규 bbox/frame 연결·오버레이는 만들지 않음 |
| 외부 schema 파일 미확보 | schema_unavailable/metadata_only 및 실제 수행 검사만 기록 |
| 미지원 숫자 정밀도·단독 surrogate/NUL·모호한 원문 | 파일 원문 보존·needs_review, 손실 변환 뒤 정상 봉인 금지 |

legacy의 브라우저 criteria_version은 source_version_jsonb에 원래 타입으로, 상태·시각은 source_snapshot에 보존한다. 서버 UUID와 프로젝트별 번호는 별도다. imported/legacy 기준은 unconfirmed, run은 imported, 로컬 overall/item verdict는 NULL이다. 봉인은 로컬 구조 완료이며 출처의 completed/pass/confirmed를 재검증한 것이 아니다.

표시본을 새로 생성해야 하면 실제 새 바이트·해시·치수를 등록한다. 제공된 과거 표시본과 같다고 추정하지 않으며 과거 bbox를 새 표시본에 옮기려면 확인한 변환이 있어야 한다. 변환이 불명확하면 원문 JSON의 좌표와 이유를 보존하고 정규 좌표 투영은 NULL로 둔다.

## 10. 수입 지문·중복·단계별 저장

첫 지문 규격은 **cc-import-envelope-v1**다. 8단계 JCS+SHA256 envelope의 contract=cc-import-envelope-v1, kind=import_package를 사용한다. payload는 source_namespace·target_project_id·정렬한 실제 source_files(relative_path,byte_size 십진 문자열,sha256)·projection_profile(name,version,명시한 기존 리소스 연결/정규화 정책)이다. 배열은 relative_path의 UTF-16 순으로 정렬한다.

현재 시각·operation UUID·신규로 발급한 resource UUID·이번 imported_by·입력 디렉터리 절대 경로는 지문에서 제외한다. 같은 입력·대상·변환 결정을 다시 계획해도 같은 지문이어야 한다. 실제 변환/연결 결정을 바꾸면 profile 내용과 지문이 달라지며 별도 수입으로 보존한다. 원문 파일 목록만의 source inventory 지문도 provenance에 별도 남겨 같은 원문의 다른 변환임을 찾을 수 있게 한다.

표시명·기존 묶음 연결처럼 실제 생성/변환 결정에 영향을 주는 관리 입력도 projection_profile에 포함한다. package.hash_check_state=matched는 **고정한 로컬 inventory와 intake/최종 복사 바이트의 대조**가 통과했다는 뜻이다. 제공자 해시가 없으면 외부 대조는 not_checked로 별도 보고하고 출처 진위 확인이라고 부르지 않는다. 제공자 해시가 실제와 다르면 로컬 복사 대조가 맞아도 mismatch/needs_review로 처리해 completed를 허용하지 않는다.

지문 자체를 넣은 생성 manifest와 plan 출력 파일은 source_files에 넣지 않는다. 실제 받은 원문 manifest는 source_files에 포함한다. 따라서 자기 자신을 해시하는 순환을 만들지 않는다. 원문 inventory 지문은 contract=cc-source-inventory-v1, kind=source_inventory, payload={source_files}로 같은 직렬화를 사용한다. 외부 제공 package hash는 reported_validation에 원 규격으로 보존하며 로컬 지문을 덮어쓰지 않는다.

수입 기준과 결과에는 별도 **cc-import-projection-v1**을 사용한다. criteria_versions.hash_version은 이 값, kind=criteria_import이며 payload는 project/set/image UUID·package_fingerprint·실제 기준 원문 파일 SHA256/포인터·원래 버전 값·정규화한 항목 전체다. review_runs.manifest_hash_version도 같은 값, kind=review_import이며 run/이미지/기준/로컬 imported 묶음 UUID·package_fingerprint·원문 결과 파일 SHA256·실제 결과/근거 연결·부분 집합 여부를 묶는다. 실제 원문 값은 파일/스냅샷에 보존하며 로컬 verdict는 NULL이다. source_draft_hash·추론 입력 지문처럼 알 수 없는 서비스 전용 지문은 NULL로 둔다. 새 서비스의 cc-content/manifest-jcs-v1과 외부 제공 해시를 혼용하지 않는다. 합성 검토 자료에 정확한 payload 예제를 남긴다.

| 단계 | 저장 경계 |
|---|---|
| 계획 | 읽기 전용 DB 대조·intake 복사·고정 dry-run 계획. 업무 INSERT 없음 |
| 접수 | 적용 시 현재 관리 권한·프로젝트를 재검사하고 received package·지문/profile/provenance·감사를 짧게 저장 |
| 파일 준비 | 고정된 파일을 staging/최종 UUID 경로로 확정. 업무 그래프는 아직 공개하지 않음 |
| 최종 수입 | package/프로젝트 잠금·고정 입력 재대조→파일/자료/frames→기준/항목→run/로컬 imported 묶음→OCR/추출/관찰/근거/결과/채택→각 봉인→검사 보고/aliases/package completed·감사, 한 트랜잭션 |
| 실패 | 최종 그래프 전체 롤백 확인 후 package failed/needs_review·안전한 진단을 별도 기록. 미확인 COMMIT이면 상태도 추측해 바꾸지 않음 |

접수의 UNIQUE(project_id,source_namespace,package_fingerprint) 충돌은 롤백 후 기존 package를 조회한다. completed면 기존 ID/매핑을 반환하고 새 업무 그래프를 만들지 않는다. received는 현재 작업 소유 여부를 확인해 동시 apply를 거부한다. 재검증은 명시적 관리 실행과 이전 진단 감사를 요구하며 failed→received, needs_review는 같은 상태에서 검사 보강 후 completed/failed 전이를 따른다. 계획 UUID는 기존 접수의 고정 계획을 재사용한다. 같은 접수에서 다른 파일/매핑으로 바꿔 적용하지 않는다.

manifest_file_id는 실제 받은 manifest가 있으면 그 원문 파일에 연결한다. legacy처럼 원문 manifest가 없으면 **로컬에서 생성했다고 명시한 접수 manifest**를 만든다. 파일 해시·생성 주체·원래 manifest 부재를 provenance에 남기며 외부 원문인 것처럼 표시하지 않는다. manifest FK 없이 파일 등록→package FK 연결 또는 received package 먼저 생성→파일/manifest 연결 순서로 두 순환 FK를 만족시킨다. completed 이후 파일 추가·인계 연결 변경은 금지한다.

record_aliases는 실제 namespace/외부 ID/타입을 원문과 함께 대응한다. 동일 외부 ID의 다른 내용은 새 package의 별칭으로 보존하고 기존 대상에 덮어쓰지 않는다. 인계 없는 동일 별칭 충돌도 6단계 NULLS NOT DISTINCT 규칙으로 거부한다. replaces_import_id는 실제 수정본 관계를 확인한 경우만 사용하며 새로운 지문이라는 이유만으로 이전 묶음이라고 추측하지 않는다.

수입 그래프는 package completed 전 일반 v1 이력에 노출하지 않는다. 새 실행은 수입 기준을 직접 재사용하지 않는다. 첫 재확정은 **로그인한 사용자가** 실제 확보한 이미지에 새 v1 editing 초안을 만들고 원문/항목을 확인·저장한 뒤 정상 확정 API로 수행한다. 과거 원문이 없으면 새로 입력받고 이를 과거 원문으로 표시하지 않는다. 첫 UI에는 수입 기준을 한 번에 복제·계보 연결하는 별도 API를 추가하지 않는다. 정상 v1 요청에 없는 source_criteria_version_id는 NULL이며 입증하지 못한 복사 관계를 만들어 넣지 않는다. 운영 관리자가 과거 사용자를 가장하거나 confirmed_by를 임의 지정해 확정하지 않는다.

## 11. DB·파일 백업을 한 세트로 묶기

첫 백업은 짧은 점검 시간의 **쓰기 중지 방식**이다. pg_dump가 DB 내부 일관성을 제공하는 사실만으로 외부 파일도 같은 시점이라고 보지 않는다. 역할·접근 권한은 단일 DB dump만으로 모두 재생성되지 않으므로 역할 구성과 복원 정책을 함께 보관한다. [PostgreSQL SQL dump 안내](https://www.postgresql.org/docs/17/backup-dump.html)

1. 신규 로그인/로그아웃·프로젝트/초안·업로드·접수·관리 쓰기를 점검 모드로 차단한다. worker 인수·GC·수입도 중지한다. health는 점검 상태를 알린다.
2. 진행 중 파일/DB 확정과 실행을 정상 마감하도록 기다린다. 초기 drain 상한은 15분이다. running/active 작업이 남으면 이번 백업을 실패 처리하고 별도 복구 절차를 선택한다. 백업 성공을 만들려고 원격 결과를 성공/실패로 추정하거나 강제 종료하지 않는다. queued·미완료 package는 보존할 수 있으나 자동 실행하지 않는다.
3. 배타 gate와 운영 점검 잠금 아래 DB/파일 쓰기 없음·사용 중 작업 잠금 없음·primary 연결·필수 파일 가용성을 확인한다. DB 스냅샷 전후 임의 수정을 허용하지 않는다.
4. PostgreSQL 17과 호환되는 도구로 **전체 업무 스키마의 custom-format pg_dump**를 생성하고 종료 상태·파일 SHA256·크기를 확인한다. 일부 테이블만의 dump를 전체 백업이라고 부르지 않는다.
5. 같은 정지 구간에서 stored_files의 모든 state별 inventory와 실제 바이트를 복사한다. DB 참조 파일, 수입 intake 원문/계획, 미해결 작업 저널·격리 진단, 구형 JSON 보존본을 명시적으로 분류한다. 단순 Docker 컨테이너 파일 복사나 실행 중 PGDATA 복사는 대체 절차가 아니다.
6. DB dump·파일 inventory·코드/마이그레이션 revision·역할/권한 정책·비밀 없는 설정·파일 한도·진행/미완성 상태·검사 결과의 manifest를 만든다. 모든 구성 파일을 검증한 뒤 세트 complete 표시를 마지막에 기록한다.
7. 부분 파일이거나 검사 실패면 세트 incomplete로 남기고 정상 복원 목록에서 제외한다. 쓰기 재개는 점검 해제 절차로 명시적으로 수행한다.

backup manifest는 contract_version=cc-backup-set-v1, backup_id, captured_at, application/schema revision, PostgreSQL/tool 버전, dump 상대 경로·크기·해시, 파일별 file_id/storage_key/state/크기/해시·가용성, intake/legacy 포함 범위, 표별 행 수·제약 inventory 지문, pending 상태 수, 점검 결과를 포함한다. 자신의 해시는 자신의 본문에 넣지 않으며 별도 완료 레코드가 manifest 바이트 SHA256을 보관한다.

엄격 백업 complete는 필요한 stored 파일 모두의 실제 바이트 대조가 통과한 경우다. missing 행이 있는 기존 DB는 백업할 수 있지만 **degraded 백업**으로 명시하고 건강한 원본과 동등한 복구 보장을 주장하지 않는다. dump나 파일 하나만 있으면 restore_ready가 아니다. 작업 저널 상태는 보조 자료이므로 복원 시 DB 재대조가 필요하다.

백업에는 사용자 비밀번호 해시·업무 원문이 포함될 수 있으므로 별도 접근 권한·암호화 저장·다른 장치/위치 복사로 관리한다. 서비스/DB 평문 비밀은 일반 manifest와 Git에 넣지 않고 별도 보호된 설정 복구 경로로 관리한다. 초기 운영 목표는 하루 1회·배포/수입 전 추가 백업, 일별 7개·주별 4개 보존이다. 마지막으로 검증한 완전 세트와 장애 조사 중 세트는 단순 개수만으로 지우지 않는다. RPO 목표 24시간·RTO 목표 2시간은 제안값이며 실제 복원 훈련 전 달성했다고 보고하지 않는다. PITR/WAL 보관은 첫 범위 밖이다.

## 12. 별도 대상 복원과 공개 전 검증

복원은 **새 DB·새 저장소 루트**에서 수행한다. 기존 운영 DB/볼륨 위에 먼저 덮어쓰지 않는다. 네트워크 외부 호출·worker·공개 API를 끈 복원 모드에서 시작한다.

1. complete 세트·dump·manifest·모든 포함 파일의 해시·가용성·도구/스키마 호환성을 확인한다. degraded 세트는 그 결손을 승인한 별도 복구 판단이 필요하며 자동 선택하지 않는다.
2. template0 기반 빈 복원 DB와 필요한 owner/app 역할을 준비한다. DB dump에 클러스터 역할이 모두 포함된다고 가정하지 않는다. 비밀번호는 별도 안전한 공급 경로로 설정한다.
3. 초기 범위는 pg_restore의 단일 트랜잭션·오류 시 중단 방식으로 전체 구조/자료/후속 제약을 복원한다. source owner/ACL을 그대로 복원할지 명시적 역할 매핑할지 고정하고 6단계 제한 권한을 대조한다. 정상 앱 경로에서 FK/트리거를 꺼서 데이터를 끼워 넣지 않는다. [pg_restore 안내](https://www.postgresql.org/docs/17/app-pgrestore.html)
4. 새 STORAGE_ROOT에 같은 상대 storage_key로 바이트를 복원하고 모든 파일의 실제 크기/해시를 대조한다. 설정 루트만 바꾸며 DB 키/기준 해시를 임의 재작성하지 않는다.
5. 테이블/PK/UQ/FK/인덱스/트리거·migration revision과 표별 행 수를 비교한다. 트리거가 복원 뒤 설치됐다고 과거 모든 행을 재검증한 것으로 보지 말고 루트 봉인·전체 결과/채택·동일 프로젝트/이미지/시도·순환·owner·해시·파일 연결을 **별도 전체 무결성 검사**한다.
6. 공개 전에 복원된 user_sessions의 미폐기 세션을 모두 폐기하고 별도 보안 복구 기록을 남긴다. 백업 시점 이후 폐기한 세션이 되살아나는 것을 막는다. CSRF_SECRET/CURSOR_SECRET도 새 환경 값으로 공급하고 기존 토큰/커서를 신뢰하지 않는다. 이 보안 조치로 바뀐 필드는 원본 덤프 대조와 별도 기록한다.
7. 복원된 queued/running·미완료 package·미확인 저널을 대조한다. BackgroundTasks는 8절 정책으로 마감하고 DB worker의 resume는 별도 운영 시작 절차로 승인한 안전한 대상만 수행한다. 원격 제출 불명은 새 호출 없이 보류/진단한다.
8. 활성 사용자·프로젝트 owner·developer 환경 조건을 검사한다. 운영에서는 developer를 비활성으로 보존하고 필요한 소유권 이전은 명시적 관리 경로로 수행한다. 실제 이메일/비밀번호를 임의 생성하지 않는다.
9. 읽기/이미지/JSON·권한·CSRF·서버 재시작 후 재조회·테스트 사용자 검수 저장을 별도 환경에서 검증한다. 유료 원격 호출은 복원 검증을 이유로 자동 수행하지 않는다.
10. 복원 보고서와 시간·손실 범위·결손·세션 폐기·중단 실행 처리·검증 결과가 갖춰진 뒤에만 점검을 해제하고 대상 설정을 바꾼다. 기존 DB/파일은 보존한다.

정상 복원은 일부 화면이 열리는 것만으로 완료하지 않는다. 별도 검증 DB·파일 루트의 복원 훈련을 통과해야 backup restore_ready=true를 부여한다. custom archive 목록 읽기 성공·SQL 종료 코드만으로 파일·권한·봉인·동시성 검사를 대체하지 않는다.

## 13. v1 전환·되돌리기·수입 취소 경계

| 시점 | 허용되는 되돌리기 |
|---|---|
| v1 쓰기 공개 전 | 원래 코드/설정으로 복귀, 검증용 DB/새 루트는 별도 보존. 원본 JSON 미변경 |
| v1 공개 뒤 새 업무가 이미 저장됨 | 스키마 호환한 이전 v1 코드만 재배포 가능. 구형 multipart를 몰래 다시 열어 이력을 두 갈래로 만들지 않음 |
| DB/파일 무결성 사고 | 신규 쓰기/worker/GC 중지→사고 상태 보존→별도 DB/루트 복원 검증→실제 손실 범위를 알린 뒤 전환 |
| 실패 수입·그래프 미커밋 | package/진단·intake 보존, 원문 수정 없이 명시적 재검증 |
| completed 수입을 잘못 적용 | 완료 행/결과 삭제·원본 덮어쓰기 없음. 프로젝트 보관/접근 제한과 감사로 격리 후 별도 수정본 수입/수동 복구 판단 |

v1 쓰기 시작 전에 pre-cutover 백업, 실제 복원 훈련, 코드/schema 호환 표, 현재 시작/미완료 실행 수, 구형 이력 보호 설정을 확보한다. 전환 뒤 구형 POST는 8단계 410 정책을 사용하고 구형 읽기는 개발 loopback의 명시 모드만 유지한다. DB에 없다는 이유로 운영 API가 임의 legacy 경로를 공개하지 않는다.

이미 저장한 v1 자료가 있으면 이전 DB 스냅샷으로 되돌리는 일은 그 이후 쓰기를 잃는 선택이다. 새 쓰기를 보존·대조하지 않고 단순 코드 롤백과 같다고 표현하지 않는다. 첫 범위는 과거 행을 지우는 자동 downgrade/수입 undo 기능을 제공하지 않는다. 실제 사고 복구 대상 선택·손실 수용은 운영 판단이며 이번 문서가 실행 승인을 대신하지 않는다.
