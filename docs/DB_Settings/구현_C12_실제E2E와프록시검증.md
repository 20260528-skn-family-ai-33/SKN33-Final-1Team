## 2. v1 화면을 같은 출처에서 실행

[C08](구현_C08_인증과계정관리.md)·[C09](구현_C09_파일저장과기준확정.md)의 별도 앱 환경/계정/저장소를 먼저 준비한다. `.env.v1.example`을 복사한 비공개 파일은 **앱 역할 비밀번호만** 받으며 Compose 관리/owner 환경을 웹에 넘기지 않는다.

frontend에서 먼저 빌드한다.

```text
npm run build:v1
```

앱 환경에 `FRONTEND_DIST=/절대경로/frontend/dist-v1`을 지정하고 저장소 루트에서 실행한다.

```text
.venv/bin/python -m scripts.run_v1 --env-file .env.v1 --host 127.0.0.1 --port 8000
```

Windows에서는 `.venv/bin/python` 대신 `.venv\Scripts\python.exe`를 사용한다. 이 v1 실행 진입점의 실제 검증 OS는 macOS 개발/브라우저와 Linux 컨테이너이며 Windows 운영 저장소를 인증하지 않았다. 기본 launcher는 계속 기존 시제품이다.

`--check-only`는 환경/빌드 형식만 확인한다. DB 접속·schema·파일 capability·실제 OCR 준비/추론 성공을 확인했다는 뜻은 아니다. 실제 서버 시작에서 기존 DB/schema·저장소 점검을 수행하며 자동 migration·저장소 초기화·사용자 seed·패키지 설치·모델 다운로드는 하지 않는다.

Vite 개발은 `npm run dev:v1`을 사용한다. API_PROXY_TARGET을 실제 v1 서버로 지정하고 AUTH_ALLOWED_ORIGINS에 **실제 Vite origin과 직접 API origin**을 정확히 나열한다. AUTH_ALLOWED_HOSTS도 명시한다. API는 no-proxy-headers이고 Vite는 Host/Origin을 유지한다. Vite/브라우저가 원래 보낸 Forwarded/X-Forwarded-*가 있으면 개발 계정 허용을 거부한다. 이메일 인증·개발 인증·현재 권한 검사는 서버가 최종 수행한다.

## 3. 빌드·라우팅·HTTPS 경계

Vite는 `cc-frontend.json`에 `{contract:cc-web-v1,profile:v1}`을 생성한다. FRONTEND_DIST를 지정하면 앱 시작에서 marker·index·참조 자산·symlink/이상 경로를 검사한다. legacy 빌드나 부분 빌드는 거부한다. 기본 legacy 빌드 자체와 기존 시제품은 유지한다.

SPA HTML은 `/`, `/login`, `/projects`, `/review/new`와 C11의 **정상 UUID 경로**에만 제공한다. `/api/*`, 없는 `/assets/*`, `.env`, 서버 소스·저장소 경로는 HTML fallback을 받지 않는다. JSON 오류/이미지 MIME을 유지하고 nosniff를 추가한다. 페이지와 API에는 CSP·same-origin referrer·기능 제한을 적용하며 HSTS는 HTTPS 운영 프로필에만 적용한다.

운영 진입점은 APP_ENV=production·LOCAL_ADMIN_LOGIN=0·정확한 HTTPS origin/Host·정확한 TRUSTED_PROXY_IPS를 요구한다. wildcard·CIDR·호스트명 proxy 신뢰 설정은 거부한다. production+개발 주체 활성·비 Linux 파일 운영 프로필 거부도 기존 정책을 유지한다.

[Nginx template](../../deploy/nginx/v1.conf.template)의 CC_SERVER_NAME·CC_TLS_CERT·CC_TLS_KEY·CC_UPSTREAM만 렌더링한다. 예를 들어 envsubst를 쓴다면 **이 CC_* 목록만** 지정해 `$host`·`$scheme` 등 Nginx 변수를 보존한다. API 포트는 private network에 두고 TLS 프록시만 노출한다. API의 TRUSTED_PROXY_IPS에는 그 프록시의 실제 단일 IP를 넣는다. 고정 IP 운영/변경 시 재설정과 실제 인증서는 배포 시 별도 준비한다.

프록시는 `proxy_pass_request_headers off` 후 Host/Origin/Referer/Cookie/CSRF/멱등키/콘텐츠 헤더를 allowlist로 재구성한다. X-Forwarded-For/Proto는 실제 peer/scheme으로 다시 설정한다. 임의 Forwarded/X-Forwarded-Prefix/Evil은 upstream에 전달하지 않는다. 실제 wire probe와 실제 앱 로그인에서 확인했으며 신뢰하지 않은 직접 요청의 HTTPS 위조는 400이었다.

Linux 이미지 생성 예시:

```text
docker build -f deploy/Dockerfile.v1 -t creative-checker-v1:test .
```

이 이미지는 앱 역할·명시적 환경·읽기 전용 v1 빌드 mount·전용 파일 volume을 받는 API 이미지다. 테스트에서 uid 10001·read-only 컨테이너 루트·별도 /tmp·전용 Linux volume으로 실행했다. 저장소 초기화는 별도의 명시적 명령이며 웹 시작이 자동 생성하지 않는다. 모델/가중치/전용 Paddle 환경은 포함하지 않는다. 현재 Linux HTTPS 시험에서는 REVIEW_PIPELINE=disabled였고 새 검수 503을 확인했다. Linux 모델 실행/worker 배포가 준비됐다고 표시하지 않는다.

## 4. 실제 시험 행렬

| 경로 | 실제 계층 | OCR | 확인 결과 |
|---|---|---|---|
| 직접 HTTP | 고정 Chromium → Uvicorn → app 역할 PostgreSQL/전용 파일 | 명시적 test adapter | 저장·확정·완료·근거/OCR/export·재시작 세션 복원 |
| Vite HTTP | 고정 Chromium → 실제 Vite proxy → Uvicorn/DB/파일 | 명시적 test adapter | 이메일/개발 로그인·동일 전체 흐름·위조 헤더/Host/Origin 거부 |
| Linux HTTPS | 고정 Chromium → 실제 Nginx TLS → uid 10001 Linux API → 실제 PostgreSQL/Linux 파일 | disabled | Secure/__Host/HttpOnly/SameSite·CSRF·업로드/확정·모델 미준비 503·API/파일 404·실제 헤더 정제 |
| 실제 Paddle HTTP | 고정 Chromium → 실제 Uvicorn/DB/파일 → 기존 로컬 Paddle 전용 프로세스 | 실제 CPU 모델 | 기존 포스터 1장·18 OCR·1 항목·원자적 결과/근거·서버 export·health 성공 설정 |

API 응답 fixture는 사용하지 않았다. 직접/Vite 경로의 OCR만 APP_ENV=test의 명시적 합성 어댑터였다. 확정 응답 유실 시험은 실제 서버의 201/커밋 뒤 응답 하나만 끊고, 새로고침 후 같은 키로 복구했다. SQL로 해당 초안의 확정본 한 개와 해당 프로젝트의 실행 한 개를 확인했다.

실제 계정은 합성 이메일/비밀번호로 격리 DB에 발급했다. viewer의 조회 허용/재검수 403, 비멤버의 실행·이미지 404, 익명의 401을 확인했다. 새로운 서버 프로세스/포트에서도 같은 host의 DB 세션과 저장된 결과가 복원됐고 명시적 로그아웃이 작동했다.

모든 계층을 PostgreSQL 17.11의 무작위 creative_checker_test_<UUID> DB에서 시험했다. 일상 DB public 관계와 default ACL은 전후 같았고 최종 임시 DB 목록은 비었다. 초기 OCR 진단 중 중단으로 남은 자체 테스트 DB 하나는 해당 실행 로그의 합성 사용자 UUID와 소유 역할·무연결 상태를 대조한 후 정리했다. FORCE나 다른 세션 종료는 사용하지 않았다.

HTTPS 인증서는 시험용으로 임시 생성했다. HTTP 클라이언트는 이 인증서를 CA로 검증했고 브라우저는 시험 인증서 오류만 허용했다. 실제 공인 인증서·외부 DNS·운영 공개·전원 장애 후 내구성·백업/복원 검증으로 확대 해석하지 않는다.

## 5. 실제 모델이 드러낸 두 연결 오류

1. **확장자 없는 저장 키**: C10 저장소는 UUID 키를 쓴다. Paddle의 파일 경로 입력은 확장자로 형식을 고르므로 정상 PNG 바이트도 거부했다. 저장 키를 바꾸거나 원본을 복제해 우회하지 않고 worker가 검증된 이미지 바이트를 RGB로 디코딩한 뒤 Paddle의 기존 OpenCV 경로와 같은 연속 BGR 배열로 전달한다. PNG 파일명/확장자 없는 UUID 둘 다 치수·채널·로컬 모델 설정을 회귀 검사했다.
2. **날짜 범위 tuple**: 기존 multiline 추출기는 groups.values에 내부 tuple을 반환한다. 표준 json.dumps 진단 파일에서는 배열로 보이지만 strict JCS 경계는 tuple을 거부했다. 어댑터에서 내부 sequence만 JSON 배열로 투영하고 원문/출처/미확인 값은 유지했다. 실제 날짜 추출기의 source_ocr_ids와 strict JSON 통과를 검사했다. 임의 객체를 문자열로 바꾸거나 판정을 완화하지 않았다.

최종 실제 모델 실행은 표시 600×848 → OCR 입력 1200×1696, paddle_full_v1·cpu였다. 한 실행에서 adapter wall 7.47초, 모델 load 1.14초, inference 5.94초, worker peak RSS 약 8.0 GiB를 관측했다. 이 숫자는 한 포스터·해당 로컬 환경의 최종 실행이며 준비 상태 점검·브라우저 전체 시간이나 성능 SLA가 아니다. 앞선 진단 실행을 별도 표본 정확도로 합산하지 않았다. OCR 정확도/CER·재현율·GPU/MPS/CUDA·RunPod 비용을 새로 측정하지 않았다.

## 6. 검증 수와 CI

| 검사 | 결과 |
|---|---:|
| Python 기본 | 619 통과 + 하위 7 통과 |
| 기존 PostgreSQL/API/실제 HTTP 회귀 | 1,265 통과 |
| 신규 실제 브라우저/DB | 직접·Vite 2 + Linux HTTPS 1 + 실제 Paddle 1 = 4 통과 |
| 이번 전체 PostgreSQL 연계 사례 | 1,269 통과, 중복 재실행은 합산하지 않음 |
| 기존/새 프런트 단위 | 18 + 35 = 53 통과 |
| legacy/v1 빌드·pip check | 성공 |
| workflow YAML | 실제 parser로 문법 확인. 원격 GitHub Actions 실행은 미실행 |

C12 신규는 web 단위 26개와 기존 Paddle worker의 파일명 파라미터 추가 1개, 통합 4개로 총 31개다. 기본 Python 증가는 592→619다. 기존 C11 합성 API 브라우저 30개는 이번에 다시 실행한 사례 수로 더하지 않는다.

브라우저는 Playwright 1.62.1의 고정 Chromium/headless-shell revision 1234, 151.0.7922.34를 사용했다. 설치된 Chrome channel의 자동 갱신에 의존하지 않았다. 호스트는 macOS arm64, 실제 운영 경계 시험은 Docker의 Linux arm64·Nginx 1.28.3이었다. 버전/이미지 ID·모델 지문·입력 해시·시험별 결과는 [증거 JSON](verification/2026-10-18-implementation-C12.json)에 기록했다.

새 CI job은 일회용 PostgreSQL service에서만 owner/app 역할을 만들고 core→browser→Linux HTTPS를 실행하도록 정의했다. 실제 OCR은 기본 CI에서 설치/추론하지 않으며 명시적 ocr_external opt-in이다. 기존 offline/Windows job에 필요한 v1 패키지도 추가했고 기존 단계·동작을 유지했다. 소스 수정이나 로컬 통과를 원격 CI 통과라고 표시하지 않는다.

## 7. 시험 재현

[테스트 환경 예제](../../.env.test.v1.example)를 복사한 비공개 파일에 명시적 TEST_DB_*를 설정한다. 테스트 관리 역할과 업무 app 역할은 분리한다. 일반 앱 .env로 자동 fallback하지 않는다. 테스트는 임의 이름 DB만 만들고 정리하며, 실행 중 다른 동일 PostgreSQL 시험을 병행하지 않는다.

아래는 저장소 루트 기준이다. TEST_DB_ENV_FILE은 비공개 테스트 설정 파일의 절대경로로 지정한다. Bash와 PowerShell의 환경 변수 문법은 해당 터미널을 따른다. 프런트 npm ci/build와 고정 브라우저 설치를 먼저 완료한다.

```text
npm --prefix frontend ci
npm --prefix frontend run build:v1
```

frontend 폴더에서 고정 브라우저를 설치한다.

```text
npx playwright install chromium --only-shell
```

저장소 루트에서 계층별 실행한다.

```text
.venv/bin/python -m scripts.verify_v1 --suite core --output artifacts/v1/core
.venv/bin/python -m scripts.verify_v1 --suite browser --output artifacts/v1/browser
```

HTTPS는 Linux API 이미지를 먼저 만들고 테스트 설정의 C12_RUN_HTTPS=1·C12_API_IMAGE를 지정한다. macOS Docker Desktop/Ubuntu Docker의 명시한 host-gateway 경로를 사용한다.

```text
.venv/bin/python -m scripts.verify_v1 --suite https --output artifacts/v1/https
```

실제 OCR은 기존 Paddle 전용 환경·고정 모델이 준비된 로컬에서만 C12_RUN_REAL_OCR=1을 지정한다. 선택했는데 미준비하면 실패하며 skip으로 통과시키지 않는다.

```text
.venv/bin/python -m scripts.verify_v1 --suite ocr --output artifacts/v1/ocr
```

`--guard-env /절대경로/일상DB설정파일`을 추가하면 일상 DB public 관계/기본 권한을 **읽기 전용으로 전후 대조**한다. 이 파일의 owner/admin 값을 앱에 전달하지 않는다. 검사별 pytest.xml·summary.json이 출력된다. raw fixture 전체·브라우저 상태/쿠키·인증서/키·앱 환경을 공유 아티팩트로 올리지 않는다. CI도 JUnit/안전한 summary만 업로드한다.
