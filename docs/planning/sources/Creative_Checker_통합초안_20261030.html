팀 검토용 통합 초안 · 2026년 10월 30일 KST · Q1–Q76 논의 반영

이 문서는 기존 진행상황 HTML 자료, 구현·실험 기록, 10월 29–30일 사용자 논의를 하나의 프로젝트 설명서로 통합한다. 설계 제안서이자 현재 근거의 색인이며, 전체 시스템의 구현 완료 증명서는 아니다. 사용자 동의와 팀 확정을 구별한다. 팀 논의가 필요한 항목은 아직 확정 정책으로 적용하지 않는다.

1 문서 사용법과 프로젝트의 한 문장 정의

Creative Checker는 발주서·계약서에서 사람이 승인한 제작 조건을 기준으로 포스터와 숏폼 영상을 검사하고, 근거를 확인하며 수정·재검수·최종 승인까지 연결하는 MCP 기반 다중 에이전트 업무 자동화 서비스를 목표로 한다.

AI가 계약의 법적 효력이나 저작권 적법성을 보증하는 서비스가 아니다. 이 한계 표현도 팀 검토 대상이다. AI가 내놓은 결과를 사람이 승인하는 구조이며, 단순히 모델 호출 여러 개를 연결했다는 이유만으로 협업이 완성되지는 않는다.

1 2 이번 문서에서 변경된 핵심

  • 포스터뿐 아니라 숏폼 영상도 최종 통합의 필수 범위다. 과거 영상 P2 표시는 현 목표에 적용하지 않는다.
  • A01–A08은 설명을 위한 현재 역할 체계다. 에이전트 수, 담당자, 통합·분리 방식은 고정되지 않았다.
  • A02는 Qwen 중심 직접 추출·해석과 코드 추출 후 Qwen 해석 중 비교 후 결정한다. 후자를 이미 선정한 것으로 쓰지 않는다.
  • A04·A05는 Qwen3.5-4B 중심 단독 구성과 OCR 혼합 구성을 시험한다. PaddleOCR 최종 채택도 미정이다.
  • A03 및 VectorDB/RAG의 최종 배치는 보류한다. MCP는 과제 주제상 필수다.
  • 승인 지점은 기준 확정·수정 요청 확정·최종 승인 세 곳을 유지한다.
  • AWS 지원 예산 30만 원은 RunPod·OpenAI 잔여 지원금 합계 500달러와 별도다.

2 서비스 범위 사용자 성공의 기준

2 1 입력과 출력

초기 입력은 전자 문서 한 개와 포스터 또는 숏폼 영상이다. 전자 문서는 텍스트가 있는 PDF, DOCX, HWPX 등 후보를 뜻하지만 실제 지원 확장자와 버전은 시험 후 확정한다. ‘전자 파일’이어도 내부가 스캔 이미지일 수 있으므로 파일명만으로 파싱 가능성을 판단하지 않는다. 스캔 문서 OCR은 향후 확장 방향이며 현재 필수 범위로 간주하지 않는다.

출력은 승인 조건 목록, 조건별 검사 결과와 근거, 사람 확인 항목, 수정 요청 초안, 재검수 결과, 최종 승인 이력이다. 다운로드 보고서/PDF까지 제공할지는 팀 논의가 필요하다.

2 2 역할과 권한

기존 기획에는 발주자·제작자·검수자·선택적 법무 담당·승인자·운영자·평가 개발자 역할이 있다. 기존 구현의 owner/editor/viewer와 같은 권한 이름과 자동으로 같다고 보지 않는다. 누가 어느 팀원인지 배정은 가안이다.

승인은 지정된 승인 권한자가 수행하고 다른 사용자는 초안을 만들 수 있다는 방향에 동의했다. 한 사람이 세 승인 지점을 맡을 수 있으나 상세 권한 정책은 팀이 정한다. 평가자는 AWS에 배포된 환경에 로그인해 사용한다. 평가 계정 사전 준비와 회원가입 병행은 팀 논의 사항이다.

2 3 통합 완료의 기준

중간 데이터를 개발자나 운영자가 수작업으로 복사하지 않아도 다음 흐름이 수행되는 상태를 통합 완료의 기준으로 삼는다.

  1. 로그인 후 프로젝트에 문서와 산출물을 업로드한다.
  2. 시스템이 조건 초안을 추출하고 사용자가 원문 근거와 대조하여 확정한다.
  3. 확정된 기준과 산출물 버전을 고정해 텍스트·시각·영상 검사를 실행한다.
  4. 조건별 근거와 실패·확인 필요 항목을 확인한다.
  5. 사람이 수정 요청을 확정하고 제작자가 새 버전을 제출한다.
  6. 시스템이 새 버전을 재검수하고 최종 승인 및 이력을 남긴다.

사람이 원문을 읽고 승인하는 행위를 없애자는 뜻이 아니다. ‘자동화된 데이터 전달’과 ‘사람의 책임 있는 판단’을 분리한다. 개발 환경 E2E 성공과 AWS 배포 환경 E2E 성공은 다른 단계로 관리한다. 모의 데이터 연결 성공을 실제 모델 통합 성공으로 표시하지 않는다.

4 1 구체적 사용 예

발주서에 ‘발전하는 도시, 전주시 문구를 표시’, ‘행사일 11월 15일’, ‘주최 로고 비율 유지’가 있고 포스터가 업로드되었다고 하자. A02가 세 조건을 제안하고 원문 위치를 보여준다. 사용자가 누락된 조건을 직접 추가할 수도 있다. 확정 후 A04는 문구·날짜, A05는 로고·시각 조건을 검사한다. 문구가 OCR상 다르게 읽혔다면 곧바로 제작 오류로 확정하지 않고 이미지와 인식 근거를 보여줄 수 있어야 한다.

A06은 조건이 모두 검사되었는지, 다른 버전의 이미지 결과가 섞이지 않았는지 확인한다. 수정 요청은 ‘어디를, 현재 어떤 상태에서, 어떤 기준으로 바꿀지’ 설명한다. 제작자가 ‘수정 완료’를 눌러도 이는 재제출이며 최종 승인과 같지 않다.

4 2 기준 승인 화면

문서 미리보기 옆에 추출 조건을 나열한다. 커서를 올리거나 ‘문서상 위치 확인’을 누르면 해당 페이지·영역을 표시한다. 문서 버전, 렌더링 버전, 페이지, 좌표 체계를 함께 관리해야 위치가 어긋나지 않는다. 좌표를 확보하지 못한 경우 정확한 위치를 추측해서 그리지 않는다.

추출된 조건만 읽으면 ‘아예 빠진 조건’을 발견하기 어렵다. 승인자는 원문 전체도 확인할 수 있어야 한다. 사용자 추가 조건은 문서에서 자동 추출한 것과 출처가 다름을 표시한다.

5 1 병렬 구현을 가능하게 하는 규칙

A02 담당과 A04/A05 담당은 내부 코드를 같게 만들 필요가 없지만 서로 주고받는 데이터 계약은 같아야 한다. 필드명뿐 아니라 단위·의미·없을 때 처리까지 합의한다. 예를 들어 ‘날짜’가 행사일인지 납품일인지, bbox가 픽셀인지 0–1 정규화 좌표인지, null이 미측정인지 실패인지 정의해야 한다.

공통 스키마 담당 역할이 변경 조정과 E2E를 책임진다는 방향에 동의했다. 이름은 미배정이다. 계약 샘플과 검증 테스트를 먼저 만들고 각 담당이 같은 샘플로 검증하는 방향에 동의했다. 이와 별개로 모의 데이터로 전체 흐름을 먼저 연결하는 방안은 팀 논의가 필요하다.

5 2 최소 계약 초안

  • 공통 식별자: project_id, document_version_id, asset_version_id, criteria_version_id, run_id, attempt_id.
  • 조건: criterion_id, 원문/정리 문구, 검사 대상, 기대값, 출처, 필수성, 허용 오차, 지원 여부, 관계 정보.
  • 출처: 문서·페이지·표/셀 또는 영역·원문 발췌·사용자 추가 여부.
  • 검사 결과: criterion_id, execution_status, verdict, 관측값, 근거 ID, 제한 사항, 오류 코드.
  • 근거: 이미지/프레임 ID, 시간, 좌표 체계, crop/원본 연결, 텍스트 인식 원문과 정규화값.
  • 실행 환경: 모델·어댑터·프롬프트·전처리·규칙·샘플링·스키마 버전.

이 목록은 구현 지침용 초안이며 현재 DB 필드와 동일하다는 주장이 아니다. LLM 응답은 바로 DB 정답으로 저장하지 않고 백엔드에서 형식과 필수 필드를 검증한다.

6 버전 상태 실패 재시도

6 1 실행 상태와 판정은 다르다

queued/running/completed/failed는 처리 상태이고 pass/fail/review는 검수 판단이다. 모델 실행 실패는 로고 불량이 아니다. 반대로 실행 완료라고 모든 조건을 만족한 것도 아니다. 지원하지 않는 조건, 근거 부족, 비교 불가를 통과로 바꾸지 않는다.

상태 분리·부분 실패 표시 방향은 사용자 동의이나 팀 상세 논의가 필요하다. 기존 all_selected_v1은 선택 조건 중 하나라도 fail이면 fail, 모두 완료·통과일 때 pass인 기록이 있으나, 필수/권장 조건 차이를 반영하는 최종 정책으로 확정된 것은 아니다. 이 pass도 사람의 최종 승인과 다르다.

6 2 고정해야 할 버전

각 실행은 산출물·문서·승인 기준·모델/설정 버전을 고정한다. 기준이 바뀌면 기존 결과를 덮어쓰지 않고 새 실행을 만든다. 최종 승인은 해당 산출물과 기준 버전에 묶이며 이후 변경물에 자동 승계하지 않는다.

수정 후에는 새 asset_version과 이전 수정 요청·실행을 연결한다. 동일 파일 재업로드를 새 asset의 version 1로 생성하던 기존 구현은 ‘수정 버전 이력’과 같지 않으므로 확인이 필요하다.

6 3 실패 복구와 취소

일시적 네트워크·GPU 실패 재시도와 모델 판단의 의미적 재검토를 나눈다. 횟수·시간·비용 한도를 두고 초과 시 실패/확인 필요로 남긴다. 기존 설계의 의미 재검토 총 2회, 일시 실패 총 3회는 설계 후보 수치이며 팀 확정값이 아니다.

저장 상태에서 재개하고 검증된 결과만 재사용하는 방향, 취소 요청과 실제 중단 구별, 늦게 도착한 결과를 자동 채택하지 않는 방향은 팀 논의가 필요하다. UI에서 취소했다고 서버 GPU 작업이 실제 종료됐다고 표시해서는 안 된다.

6 4 중복 캐시 작업 소유권

동일 요청 재전송 방지와 의도적 새 실행은 다르다. 기존 중복 방지는 확정·검수·재시도 일부 경로에만 있고 업로드·초안까지 포괄하지 않는 기록이 있다.

캐시 키에는 권한 범위, 입력·OCR·crop, 모델/어댑터, 프롬프트, 스키마, 기준, 샘플링 버전을 고려한다. 실패 결과를 정상 결과처럼 재사용하지 않는다. 처음에는 전체 기준 재검수를 권장하고 부분 재사용은 누락 위험과 재사용 조건을 검증한 뒤 도입한다.

worker lease/attempt token, LangGraph checkpoint, DB 상태의 책임 경계를 정해야 중복 완료나 유실을 줄일 수 있다. 설정이 바뀐 worker가 예전 queued 작업을 가져가지 않는 경우를 위한 drain/호환 정책도 필요하다.

7 문서 입력과 A02 조건 추출

7 1 반드시 구분할 두 단계

‘문서에서 글자를 꺼내기’와 ‘그 글에서 검사 조건을 해석하기’는 다른 문제다. DOCX/HWPX의 본문·표 데이터를 코드로 읽는 것은 형식 파싱이고, ‘이 날짜가 행사일이며 포스터에 표시해야 한다’는 해석은 의미 처리다. Qwen으로 둘을 넓게 담당시키는 경로와 코드로 앞단을 담당시키는 경로를 비교한다.

후보 처리 흐름 검증할 장점 검증할 위험
A: Qwen 중심 문서를 모델이 읽을 수 있는 입력으로 제공 → 조건 추출·해석·정리 복잡한 배치·표 맥락 활용 가능성 입력 변환 필요, 긴 문서 누락, 환각, 위치 근거·비용
B: 코드+Qwen 형식별 파서로 본문·표 추출 → Qwen 조건 해석 텍스트 보존·재현성·비용·근거 연결 표/읽기 순서/도형 속 텍스트 손실, 형식별 예외
보완 실험 필요 구역에 OCR 또는 렌더링 기반 처리 추가 이미지 안 텍스트·복잡한 배치 보완 인식 오류·지연·중복·좌표 연결

현재 어느 안도 최종 채택으로 표시하지 않는다. 모델이 원본 DOCX/HWPX 바이너리를 그대로 이해한다고 가정하지 않는다. 지원 입력 형식과 변환 과정 자체가 설계·시험 대상이다.

7 2 형식별 기술 후보

  • DOCX: python-docx 등으로 문단·표 접근. 도형·텍스트 상자·각주 등 지원 범위를 별도 확인한다.
  • HWPX: ZIP 내부 XML 구조를 해석하는 방식. HWP 바이너리와 같은 것으로 취급하지 않는다.
  • 텍스트 PDF: PyMuPDF 등으로 텍스트와 위치 추출. 읽기 순서·표 복원은 자동 보장되지 않는다.
  • OCR: 렌더링된 이미지에서 글자와 영역 추출. 이미 정확한 텍스트가 있는 문서를 전부 OCR하면 인식 오류와 처리 비용이 추가될 수 있다. 반면 이미지 안 글자와 시각 배치를 보완하는 후보가 된다.

표는 셀만 납작하게 이어 붙이지 않는다. 열 제목, 행 관계, 병합 셀, 각주를 최대한 유지하고 복원 실패를 표시한다. ‘항목 / 수량 / 단가’ 관계가 사라지면 숫자가 정확히 추출되어도 의미가 달라진다.

7 3 조건 종류와 관계 Q75 Q76

기본안·팀 논의: 추출 항목을 제작물 검수 조건, 업무·일정 조건, 기타 계약 조건으로 구분한다. 예를 들어 ‘대금 지급일 11월 20일’을 ‘포스터에 11월 20일을 표시해야 한다’로 바꾸지 않는다. 검수 미지원 조건도 조용히 버리지 않고 다른 범주나 검토 대상으로 남긴다.

제안·팀 논의: AND/OR, 예외, 선행 조건을 보존한다. ‘A 또는 B를 사용하되 C 상황에서는 제외’는 독립된 A·B·C 필수 항목 세 개가 아니다. 관계를 판단할 수 없으면 확인 필요로 남긴다. 관련 필드·UI·평가 데이터까지 함께 설계해야 한다.

7 4 복수 문서 확장

초기에는 한 문서로 통합된 입력을 처리한 뒤 복수 문서로 확장한다. 계약서는 금액·일정, 발주서는 행사 문구, 로고 가이드는 여백·색상을 규정하는 상황을 고려한다. 같은 날짜가 다르거나 가이드 버전이 충돌하면 출처를 함께 보여주고 승인자가 해소한다. 우선순위 정책이 없는 상태에서 최신 파일명이나 검색 점수로 자동 결정하지 않는다.

7 5 평가 방법

문서별 정답 조건과 비교해 누락·없는 조건 생성·금액/날짜/부정/예외 오류·근거 위치·처리 시간·사람의 수정 시간을 측정한다. 셀 단위 정확도와 문서 전체 조건 완전성은 다르다. 튜닝 문서와 최종 평가 문서를 분리하는 운영 세부 사항은 팀 논의가 필요하다.

8 텍스트 검수와 A04

Qwen 단독과 OCR 혼합을 같은 자료로 시험한다. OCR은 ‘무엇이라고 읽었는지’를 제공하고 최종 요구사항 비교는 별도 규칙 또는 모델 해석이 맡는다. 원문 인식값과 정규화값을 모두 보존한다.

8 1 정규화는 오류를 지우는 기능이 아니다

  • 가격: 10,000원과 10000 원을 동일 금액으로 해석할 수 있으나 통화·부가세·단위 조건은 별도 보존한다.
  • 날짜: 2026.11.15와 2026년 11월 15일을 같은 날짜로 비교할 수 있다. 행사일과 납품일은 같은 필드가 아니다.
  • 정확 문구: ‘발전하는 도시, 전주시’의 오탈자를 검수할 때 임의로 모든 공백·구두점·자모 차이를 지우면 안 된다. 허용할 표기 차이는 조건별로 정한다.
  • 부정·예외: ‘포함하지 않는다’를 ‘포함한다’와 유사하다고 통과시키지 않는다.

OCR이 읽지 못한 것은 문구가 없다는 증거와 다르다. 존재·판독 불가·미검사·없음이 구분되어야 한다. 인식 오류와 실제 제작 오류를 어떻게 사람에게 넘길지는 팀 논의 사항이다.

8 2 문구 순서와 위치

줄 단위 묶기 후 좌우 순서 등 읽기 순서 처리가 필요하다. 고정 12px y구간 같은 임의 경계는 같은 줄의 CITY를 앞으로 옮겨 편집거리를 과장할 수 있었다. 정확 문구 비교의 전처리와 의미상 배치·순서 검수는 별개로 다룬다.

9 시각 검수와 A05

기본 검토 항목은 요구 객체·로고 존재, 다른 것으로 교체, 잘림·가림, 이물질 추가, 비율 변형, 승인된 배치·크기·색상 조건이다. 각 항목을 실제 지원·시험 중·미지원으로 나누고 추가 항목은 팀이 논의한다.

객관적인 승인 조건 위반과 ‘더 예쁘다’ 같은 조언을 구별한다. 가독성도 승인된 기준이 있을 때 객관 검수로 취급하는 방안이 팀 논의 대상이다. 브랜드의 공식 기준 이미지와 허용 변형은 프로젝트 승인 자산으로 관리하는 방안 역시 팀 확인이 필요하다. 수집한 로고 후보가 곧 승인된 공식 기준은 아니다.

Qwen3.5-4B는 중심 후보이며 문서용과 시각용 학습 데이터·선정은 별개다. 로고는 OpenCV·XFeat·ALIKED+LightGlue 등 다른 조합을 연구하고, 만족스럽지 않으면 Qwen 경로도 비교한다. 어느 조합도 현재 서비스 최종 채택이라고 단정하지 않는다.

10 5 다음 시험 제안

  1. 기존 오류 5건과 정상 변형 10건을 회귀 세트로 유지한다.
  2. 흰 여백에 대해 알고 있는 정수 이동량으로 직접 맞춘 결과와 추정 정렬 결과를 비교한다. 정렬 오차인지 마스크·차이 계산 문제인지 분리한다.
  3. 동일한 변환·마스크·차이 계산을 세 특징점 경로에 적용해 매처 차이만 비교한다.
  4. 전경/배경, 겹침/추가/누락, 형태 변형 지표를 분리한다.
  5. 정렬 실패는 비교 불가로 남기고 정상·불량으로 강제 분류하지 않는다.
  6. 정상 오차단과 실제 오류 놓침을 함께 평가한 뒤 임계값을 정한다. 전역 임계값을 높여 0.16% 오탈자를 잃는 방식은 피한다.
  7. 시각화·저장을 별도 계측하고 원인 확인 후 최적화한다.

이는 다음 실험 제안이며 모두 구현·검증 완료되었다는 뜻이 아니다.

11 숏폼 영상 필수 범위와 미정 경계

영상도 포스터와 동일한 승인 기준·수정·재검수·최종 승인 체계를 사용하되 시간 정보가 추가된다. 프레임 ID와 시각, 샘플링 간격, 원본 영상 버전을 보존한다.

  • 음성 전사까지 포함할지, 화면 문자만 검사할지는 팀 논의가 필요하다.
  • ‘3초 이상 노출’ 같은 시간 조건을 필수 지원할지와 판정 방법도 미정이다.
  • 최대 길이·용량·해상도·파일 형식은 미정이다. 과거 30초/50MB는 제안값이다.
  • 일부 프레임만 샘플링했다면 전체 영상에 오류가 없다는 증명이 아니다.

기존 제안인 전체 1초 간격+처음/마지막 3초의 0.2초 간격은 30초 약 54프레임, 60초 약 84프레임이라는 설계 계산이었다. 30초 42–127초·60초 63–194초 처리 예상도 실측 운영 성능으로 쓰지 않는다. 광고 3초·15자 같은 내부 제안은 법정 기준으로 소개하지 않는다.

영상 검사는 구간/프레임 추출 → 텍스트·시각 검사 → 시간 조건 집계 → 근거 구간 표시로 설명하되 샘플링만으로 연속 노출을 확정하지 않는다. 프레임 삭제·보존, 재개, 중복 유료 실행, 긴 영상의 큐 독점 방지는 추가 설계가 필요하다.

12 모델 연구 학습 평가의 공통 기준

12 1 선정 원칙

Qwen3.5-4B는 현재 중심 후보지만 모델 이름이 같다고 역할 성능이 같지 않다. 문서용·시각용 데이터를 분리하여 평가하고 필요 시 별도 어댑터/학습을 검토한다. 먼저 기본 모델과 프롬프트·전처리 개선으로 기준선을 만들고 학습 필요성을 확인한다. 모든 역할을 무조건 학습시키지 않는다.

LoRA는 기반 모델 전체 대신 작은 추가 파라미터를 학습하는 방식이다. 모델을 바꿔 끼우는 것만으로 정답 데이터·평가 설계를 대체하지 못한다. 모델 채택 기준과 학습 여부는 별도 결정이다. 교육 과정의 ML/DL 학습 필수 요구는 공식 과제 조건을 확인해야 한다.

13 검색 VectorDB GraphDB MCP LangGraph의 역할

13 1 VectorDB RAG

VectorDB는 문구를 벡터로 바꾸어 의미가 가까운 자료를 찾는 데 쓴다. RAG는 찾은 근거를 모델 입력에 넣어 답변·설명을 돕는 구성이다. 계약서·발주서를 조각으로 나누어 검색할 수 있지만 검색 상위 몇 개만으로 모든 승인 조건을 검사했다고 할 수 없다.

예: ‘로고 색상 규정’을 검색해 관련 가이드 문단을 보여주는 용도는 후보가 된다. 하지만 검수의 기준 목록은 사람이 승인한 전체 목록과 버전을 별도로 관리해야 한다. A03 독립 역할, A02 외부 공용 도구, PostgreSQL+pgvector 또는 별도 Qdrant 중 선택은 미정이다.

13 2 GraphDB

GraphDB는 프로젝트–문서–조건–산출물–결과–수정 요청 관계를 노드와 연결로 표현한다. 예를 들어 ‘이 기준 변경으로 영향을 받는 승인 결과는 무엇인가’를 탐색할 수 있다. 관계가 있다는 이유만으로 Neo4j가 반드시 필요한 것은 아니다. PostgreSQL 외래 키·조인·재귀 질의와 비교해야 한다.

기존 합성 951관계 시험은 관계 정답 951/951이었지만 PostgreSQL이 9개 질의 중 8개에서 더 빨랐다는 기록이 있다. GraphDB 도입 이유를 속도 일반론으로 쓰지 않는다. 변경 영향 탐색·설명 편의가 실제 이점을 주는지 확인한다.

13 3 검색 시험 근거

기존 수집 4,596건은 검수 83·벤치마크 972·개발 지식 3,541로 구성된 기록이다. 367건 검증·351건 출처 해시 기록과 실제 VectorDB 적재·운영 완료는 다르다. chunk 500토큰/overlap50은 제안값이다.

972후보·1,120질의 검색 시험 중 포스터 280건 Hit@5는 BGE .9607, EG2 이미지 .9393, 혼합 .9786이었다. 문서40건 1/.95/1, 근거320건 1/.875/1 기록도 있다. 이는 주어진 후보에서 검색하는 시험이며 새 이미지 객체 검출 성능이 아니다. 주최자 첫 순위는 0/40인 사례도 있어 Top5만으로 사용자 성공을 설명하지 않는다. 다른 실험에서는 dense .9607보다 1:1 hybrid .9179가 낮아 혼합이 항상 낫지도 않았다. EG2 95.12는 세 과제 Top1의 동일 가중 평균이지 서비스 전체 정확도가 아니다.

16 보안 외부 모델 데이터 정책

‘로컬 모델’에는 자체 운영 RunPod도 포함한다는 사용자 의도다. 그러나 RunPod는 외부 클라우드이므로 사용자 PC 안에서만 처리하는 것과 보안상 같지 않다. 저장·전송·로그·백업을 포함한 전체 경로를 검토한다.

  • 프로젝트별 권한은 검색 결과·미리보기·원본 다운로드·파생 근거에도 적용한다.
  • 기존 애플리케이션 권한 검사와 DB RLS는 같은 것이 아니다. 현재 구현 범위를 확인한다.
  • 외부 LLM API로 자동 fallback하지 않는다. 허용 데이터·측정 기준·비용·보관 조건을 승인한 뒤 사용한다.
  • 사용자 업로드를 학습/평가에 재사용하는 것은 아직 승인되지 않았다. 팀 논의가 필요하다.
  • 원본·파생 파일·임베딩·로그·백업의 보존/삭제 기간은 아직 정해지지 않았다.
  • 승인 후 기준/산출물 변경 시 기존 승인을 자동 승계하지 않는다.
  • 사람의 예외 승인 허용 여부는 팀 논의 대상이다. 허용한다면 기계 판정과 예외 사유·담당자·대상 버전을 별도로 보존하는 안을 검토한다.

OpenAI Decisions API는 고정 질문·선택지·평가 척도 기반 판단을 위한 연구 후보이지 임의 문서 추출의 자동 대체재가 아니다. 이번 프로젝트에서 사용 승인·실제 실행이 확정된 것은 아니다. API의 데이터 보관·ZDR 자격·캐시·지역 처리 조건은 선택한 계정과 시점의 공식 정책으로 확인한다. ‘외부 API를 쓰면 학습에 안 쓰니 아무 자료나 보내도 된다’는 식으로 판단하지 않는다.

20 기술 용어를 팀 공통 언어로 정리

  • 에이전트: 입력을 받아 맡은 판단·도구 실행·출력을 수행하는 논리 역할. 반드시 별도 LLM 한 개와 일대일은 아니다.
  • MCP: 도구·리소스를 일정한 계약으로 연결하는 규약. 모델 정확도나 승인 권한을 대신하지 않는다.
  • 스키마: 필드명·자료형·필수 여부·의미에 대한 약속.
  • RAG: 근거 검색 결과를 모델에 제공하는 구성. 검색 누락 가능성이 있다.
  • 임베딩: 의미 비교용 숫자 벡터. 같은 뜻에 가까워도 정확한 문자 동일성을 보장하지 않는다.
  • GraphDB: 관계를 노드·연결로 저장/탐색하는 데이터베이스. SQL과 비교 후 필요성을 판단한다.
  • checkpoint: 실행 재개를 위한 저장 상태. 업무 승인 기록 전체를 자동으로 대신하지 않는다.
  • lease: worker가 일정 시간 작업을 맡는 권리. 중복 실행·장애 복구를 위한 장치.
  • 멱등성: 같은 요청의 재전송이 중복 효과를 내지 않게 하는 성질. 새 버전 검사는 별도 요청이다.
  • 근거: 원문·이미지·프레임·좌표 등 사람이 판정을 검증할 수 있는 자료. 설명 문장만으로 충분하지 않다.
  • LoRA: 일부 추가 파라미터를 학습하는 미세조정 방식. 데이터와 평가가 필요하다.
  • 인라이어: 추정한 기하 관계와 일관된 대응점. 이미지 전체 동일성의 증거는 아니다.
  • Macro F1: 클래스별 F1의 동일 가중 평균. 정확도와 함께 오류 유형별로 읽는다.
