BACKGROUND · WHAT

광고와 창작물이 많아집니다.

숏츠·인스타그램 릴스·광고 이미지까지, 사람이 제작하거나 AI가 생성한 콘텐츠를 다양한 채널에 납품합니다.

PROBLEM · WHY

조건을 놓칠 수 있습니다.

여러 명세서·계약서·브랜드 가이드를 납품물·수정본과 반복 대조하면 작은 문구 오류나 변경 사항을 놓칠 수 있습니다.

SOLUTION · HOW

기준과 근거를 연결합니다.

문서에서 조건을 추출하고 사람이 확정합니다. 전문 에이전트가 검사·검증하고 수정 요청과 재검수까지 연결합니다.

EXPECTED IMPACT

읽고, 고치고, 결정합니다.

검수자는 근거를 확인하고, 제작자는 수정할 내용을 이해하며, 승인자는 최신 결과로 판단하도록 돕습니다.

서비스 한눈에 보기

문서 접수부터 검수·수정·승인까지
어떤 업무를 돕나요?
광고 납품물의 검수부터 수정 요청과 재검수까지 연결합니다.
누가 사용하나요?
검수 담당자, 광고 제작자, 최종 승인자가 함께 사용합니다.
언제 필요한가요?
최초 납품을 받거나 기준이 바뀔 때, 수정본을 다시 확인할 때 사용합니다.
어디서 확인하나요?
문서·이미지·근거·이력이 모인 웹 화면에서 확인합니다.
어떤 부담을 줄이나요?
반복 대조의 부담을 줄이고, 사람이 놓칠 수 있는 오류를 한 번 더 살피도록 돕습니다.
어떻게 처리하나요?
문서에서 기준을 추출하고, 8개 에이전트가 MCP 도구로 검사와 후속 업무를 나눠 처리합니다.
광고 증가·업무 부담은 기획 배경입니다. 개선 효과는 아직 측정하지 않았으며 실제 사례와 비교 실험으로 검증합니다. 영상은 후속 확장 범위입니다.
02 / 08 · USER JOURNEY

문서를 읽는 순간부터,
수정이 끝나는 순간까지.

딸기라떼 캠페인을 예로 보는 목표 업무 흐름입니다. 아래 단계 버튼을 눌러 확인하세요.

수정할 내용을 설명합니다.

설명용 시나리오입니다. 위 도식은 실제 모델 실행 결과나 성능 증거가 아닙니다.

STEP 01 · 문서 읽기

명세서에서 기준을 읽습니다.

A01이 업무를 배정하고 A02가 문서 전체를 읽습니다. A03은 필요한 조항과 예외 근거를 찾습니다.

이 단계에서 남는 것출처가 있는 기준 초안

상품명 딸기라떼 / 할인율 30% / 브랜드 MORNING CUP

STEP 02 · 기준 확정

사람이 추출 결과를 확인합니다.

원문과 초안을 함께 보고 빠진 조건이나 모호한 표현을 수정합니다. 확정된 기준은 버전을 고정합니다.

이 단계에서 남는 것확정 기준 버전

직접 입력은 추출 결과를 보완하는 용도

STEP 03 · 검수·검증

문구와 시각 요소를 나누어 확인합니다.

A04가 문구를, A05가 외형을 검사하고 A06이 원문·이미지 근거와 결과를 대조합니다.

이 단계에서 남는 것항목별 결과와 근거

기준 30% / 이미지 관찰 20% → 불일치 후보 확인

STEP 04 · 수정 요청

수정할 내용을 구체적으로 남깁니다.

A07이 설명을 작성하고 A08이 수정 요청 초안을 만듭니다. 담당자가 내용을 확인해 업무 요청을 확정합니다.

이 단계에서 남는 것보고서·수정 요청 초안

“할인 문구를 20%에서 30%로 수정해 주세요.”

STEP 05 · 재검수

수정본을 새 버전으로 검사합니다.

A08이 이전 지적과 수정본을 연결하고 A01이 재검수를 배정합니다. 기존 지적 해결뿐 아니라 새 오류도 확인합니다.

이 단계에서 남는 것새 실행 결과와 해결 이력

기준이 바뀌지 않으면 확정 기준 재사용. 변경 시 다시 사람 확인

STEP 06 · 사람 승인

최신 근거로 최종 판단합니다.

자동 검수 결과와 확인 필요 항목을 사람이 검토합니다. 승인 대상의 기준·이미지·실행 버전이 일치해야 합니다.

이 단계에서 남는 것최종 승인 또는 보완 요청

AI의 통과 제안과 사람의 업무 승인은 별개

확정 기준 전체 검사: 검색 상위 몇 개의 조항만 검사하지 않습니다. 기준 변경이 없으면 재검수에서도 같은 기준을 재사용하고, 새 오류까지 확인합니다.
03 / 08 · AGENT TEAM

총괄 1개 + 전문 역할 7개.
판단과 책임을 나누어 협업합니다.

각 에이전트를 누르면 입력·판단·MCP 도구·산출물과 다음 협업을 볼 수 있습니다.

A01

업무 총괄

요청과 진행 상태를 보고 필요한 업무를 배정합니다.

입력
사용자 요청, 요청 분류 모델의 결과, 프로젝트와 실행 상태
판단할 일
신규 검수·재검수·기준 변경·상태 조회를 구분합니다. 정보가 모자라거나 여러 의도가 섞였으면 먼저 확인합니다.
산출물
업무 유형, 실행할 단계, 담당 에이전트, 추가 확인 질문
다음 협업
신규 작업은 A02로, 확정 기준이 있는 재검수는 A04·A05로 연결합니다. 위임·상태 전이는 LangGraph가 수행합니다.
예외·사람 확인
분류 결과만으로 승인·기준 변경을 실행하지 않습니다. 불명확한 요청은 사람 확인으로 보냅니다.
MCP 도구명 제안classify_requestget_project_stateget_run_status
딸기라떼 예시“수정한 이미지 다시 확인해줘” → 이전 실행과 수정본을 조회한 뒤 재검수 배정
A02

문서·기준 분석

명세서와 계약서를 읽어 검사 기준 초안을 만듭니다.

입력
문서 전체, 문서 버전, 캠페인 정보, 기존 기준
판단할 일
조항별로 검사 가능한 조건을 추출하고 누락·충돌·모호한 표현을 찾습니다. 필요한 추가 근거를 A03에 요청합니다.
산출물
항목별 기준 초안, 원문·페이지·조항 위치, 적용 대상, 확인 질문
다음 협업
사람이 기준을 수정·확정하면 고정된 기준 버전을 검사 단계에 전달합니다.
예외·사람 확인
읽지 못한 페이지와 출처 없는 조건을 따로 표시합니다. 모델이 기준을 임의로 확정하지 않습니다.
MCP 도구명 제안read_documentocr_documentget_document_version
딸기라떼 예시계약서의 “딸기라떼 30% 할인” → 상품명·할인율 기준과 원문 위치 추출
A03

근거 검색

관련 조항을 찾고 검색 결과가 충분한지 확인합니다.

입력
확인할 조건·쟁점, 프로젝트 ID, 적용 문서 버전
판단할 일
검색어를 조정하고 Dense·BM25 결과를 결합합니다. 부족하면 질의를 바꿔 재검색하고 원문을 확인합니다.
산출물
관련 조항·출처 ID·버전·검색 기록 또는 근거 부족 표시
다음 협업
A02의 기준 해석과 A06의 검증에 근거를 제공합니다. 검사할 기준 목록을 선택하는 역할은 아닙니다.
예외·사람 확인
다른 프로젝트·구버전 문서를 적용하지 않습니다. 근거가 없으면 그 상태를 반환합니다. 재정렬은 선택 실험입니다.
MCP 도구명 제안search_hybridrerank_candidatesread_source_chunk
딸기라떼 예시할인 예외 조항을 검색하고, 이번 캠페인에 적용되는 버전인지 확인
A04

문구 검수

상품명·할인율·브랜드·필수 문구를 대조합니다.

입력
광고 이미지, 확정된 문구 기준 전체, 이미지 버전
판단할 일
OCR 결과를 비교 도구로 대조합니다. 판독이 불분명한 영역은 잘라서 재검사하고 확인 필요 여부를 판단합니다.
산출물
항목별 관찰값·일치 여부·이미지 좌표·실행 상태
다음 협업
문구별 관찰과 비교 결과를 A06에 전달합니다.
예외·사람 확인
OCR 미검출은 곧바로 문구 누락이라고 단정하지 않습니다. 실패·미실행은 통과로 바꾸지 않습니다.
MCP 도구명 제안ocr_imagecrop_imagecompare_text_fields
딸기라떼 예시기준 30% / 이미지 OCR 20% → 할인율 불일치와 해당 영역 전달
A05

시각 요소 검수

문자 이외의 제품 외형·색상·구성을 관찰합니다.

입력
광고 이미지, 확정된 시각 기준 전체, 필요시 참조 이미지
판단할 일
VLM과 영역 분석 도구를 선택합니다. 가림·겹침·작은 물체로 판별이 어려우면 확대하거나 사람 확인을 요청합니다.
산출물
기준별 시각 관찰, 근거 영역, 불확실한 부분
다음 협업
A04와 병행 가능한 역할이며 결과를 A06에 전달합니다. 실제 동시 실행은 GPU 자원에 맞춥니다.
예외·사람 확인
개수·외관 성능은 별도 평가 후 적용합니다. 객체 탐지는 후보 도구이며, 모델 관찰을 정답으로 확정하지 않습니다.
MCP 도구명 제안inspect_visualcrop_imagedetect_objects
딸기라떼 예시투명한 컵·분홍 우유층·빨간 딸기층 조건을 이미지 영역과 함께 확인
A06

근거·결과 검증

관찰과 판정이 원문·이미지로 뒷받침되는지 확인합니다.

입력
기준 버전, A04·A05 결과, A03 근거, 원본 이미지
판단할 일
근거의 일치·충돌·누락을 확인합니다. 모순이면 필요한 항목의 재검사를 요청하고 해결되지 않으면 사람에게 넘깁니다.
산출물
근거 확인이 끝난 결과, 재검사 요청, 사람 확인 사유
다음 협업
정리된 결과는 A07로, 추가 분석 요청은 A01을 거쳐 해당 검사 역할로 전달합니다.
예외·사람 확인
같은 모델의 재확인이 정확성을 보장하지는 않습니다. 원문·이미지 대조와 사람 확인을 유지합니다.
MCP 도구명 제안read_evidenceread_source_chunkget_inspection_history
딸기라떼 예시30%/20% 차이를 원문과 이미지에서 다시 확인하고 재검사 여부 결정
A07

보고서 작성

검증된 결과를 담당자가 이해할 수 있게 정리합니다.

입력
A06 결과, 근거 ID, 수신자 역할, 기준·이미지·실행 버전
판단할 일
확인된 오류와 미확정 항목을 구분하고 중요도·수정 내용을 정리합니다. 설명 근거가 부족하면 A06에 보완을 요청합니다.
산출물
검수 요약, 항목별 근거, 수정 안내, 확인 필요 목록이 담긴 초안
다음 협업
보고서 초안과 수정 대상 항목을 A08 및 검수 담당자에게 전달합니다.
예외·사람 확인
새 오류나 근거 없는 설명을 만들어 넣지 않습니다. 자동 외부 발송은 초기 범위에서 제외합니다.
MCP 도구명 제안get_verified_resultsread_evidencesave_report_draft
딸기라떼 예시“이미지 할인 문구 20%를 확정 기준 30%로 수정해 주세요” 초안 작성
A08

수정·재검수 관리

수정 요청부터 재제출·승인 대기까지 연결합니다.

입력
보고서 초안, 기존 티켓, 재제출 파일, 현재 기준·이미지 버전
판단할 일
같은 수정 사항을 묶고 중복 요청을 확인합니다. 수정본과 이전 결과를 연결해 재검수 요청을 구성합니다.
산출물
수정 요청 초안, 수정 이력, 재검수 작업, 승인 대기 상태

업무 시스템 연동

수정 요청이 기록으로 남습니다.

1차 연동 대상은 프로젝트 내부의 데모 티켓 서비스입니다. 외부 SaaS와 연결한 것으로 표현하지 않으며, 외부 업무 시스템 필수 여부는 교육 기준 확인 사항입니다.

공통 데이터·상태·재시도 설계 보기
  • 공통 식별자: project_id, request_id, run_id, document_version, criteria_version, asset_version, criterion_id, evidence_id를 결과와 연결합니다.
  • 상태 분리: 실행 상태(성공·실패·미실행)와 항목 판정(일치·불일치·확인 필요)을 구분합니다. 실행 실패를 통과로 표시하지 않습니다.
  • 재검사 제한: 동일 항목 자동 재검사는 최대 2회로 시작하는 설정안을 검증합니다. 해결되지 않으면 사람 확인으로 전환합니다.
  • 중복·버전: 수정 요청·재검수 작업은 중복 방지 키를 사용합니다. 승인 대상 버전 일치는 서버가 검사합니다.
  • 지속성: LangGraph 체크포인트와 MySQL 업무 기록은 역할이 다릅니다. 초기 체크포인트는 별도 저장소를 사용하고 공식 MySQL 연동을 가정하지 않습니다.
  • 검색 갱신: MySQL에 원본 메타데이터와 인덱싱 작업을 기록하고 Qdrant 갱신 완료 여부를 추적합니다. 준비되지 않은 버전은 검색에 사용하지 않습니다.
기준 확정과 최종 승인은 사람의 별도 동작으로 처리합니다. 에이전트는 초안·관찰·재검사 제안을 만들며, 서버가 승인 권한과 상태를 검증합니다.

18개 기술 영역

검색 결과가 없습니다. 검색어를 바꾸거나 전체 버튼을 눌러 주세요.

학습 도구

Transformers · PyTorch

Transformers는 모델 로딩·미세조정·추론 라이브러리이고 PyTorch는 학습·계산 기반입니다. vLLM은 서비스의 LLM 추론을 담당합니다.

검색 방식

Dense · BM25 · RRF

Dense는 의미, BM25는 단어 중심 검색입니다. RRF는 두 검색의 순위를 결합합니다. BGE의 학습된 sparse 표현은 BM25와 다릅니다.

팀 공동개발

개발 PC → 공용 모델 API

Windows·Mac에서 웹과 업무 코드를 개발하고 공용 GPU 서버를 호출합니다. Docker는 실행 구성을 공유하며 GPU 호환을 보장하는 도구는 아닙니다.

팀 공통 설계에는 Mac MLX를 포함하지 않습니다. 현재 시제품의 Mac Vision OCR은 구현 기록으로 남기고, 공통 배포에는 PaddleOCR를 우선 검증합니다. GPU 메모리·동시 요청 수·모델 양자화 설정은 실측 후 결정합니다.

평가 해석

측정 대상을 혼동하지 않습니다.

Ragas의 근거 충실도는 이미지가 실제로 맞다는 증거가 아닙니다. LLM 평가 결과는 사람 검토로 보완하고 실제 검수 오판은 별도 정답으로 평가합니다.
