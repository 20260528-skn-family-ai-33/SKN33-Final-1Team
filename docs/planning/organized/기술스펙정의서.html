전체 구조와 구성 요소의 책임

광고 납품 검수 업무를 구현하기 위한 기술 설계입니다. 8개 역할·18개 기술 영역을 최신 통합 기획서 기준으로 분리했습니다. 모델·검색·업무 처리의 구현 완료를 의미하지 않습니다.

세 영역과 서버 이름은 설계 제안입니다. 초기에는 하나의 실제 MCP 서버에 영역별 도구를 묶고 필요할 때 분리할 수 있습니다. 서버 세 개를 이미 배포한 상태로 표현하지 않습니다.

흐름과 도구 연결

LangGraph가 에이전트 배정과 상태 전이를 관리하고 MCP가 실제 도구 호출 규약을 제공합니다. 해시·저장·숫자 비교는 일반 코드 단계입니다.

업무 시스템 연동

1차 연결 대상은 프로젝트 내부 데모 티켓 서비스입니다. 외부 SaaS 연결 완료로 표현하지 않으며 외부 업무 시스템 필수 여부는 교육 기준 확인 사항입니다.

8개 역할의 입출력과 협업

각 역할은 판단·도구 선택·근거 전달·예외 처리를 담당하는 설계입니다. 역할 이름을 나열하거나 일반 함수를 순서대로 호출하는 것만으로 다중 에이전트 협업 완료를 주장하지 않습니다.

A01 업무 총괄 · A02 문서·기준 분석 · A03 근거 검색 · A04 문구 검수 · A05 시각 요소 검수 · A06 근거·결과 검증 · A07 보고서 작성 · A08 수정·재검수 관리

설계 · 구현 예정

A01 · 업무 총괄

요청과 진행 상태를 보고 필요한 업무를 배정합니다.

실행 계약내용
입력사용자 요청, 요청 분류 모델의 결과, 프로젝트와 실행 상태
판단신규 검수·재검수·기준 변경·상태 조회를 구분합니다. 정보가 모자라거나 여러 의도가 섞였으면 먼저 확인합니다.
출력업무 유형, 실행할 단계, 담당 에이전트, 추가 확인 질문
전달·다음 단계신규 작업은 A02로, 확정 기준이 있는 재검수는 A04·A05로 연결합니다. 위임·상태 전이는 LangGraph가 수행합니다.
예외·경계분류 결과만으로 승인·기준 변경을 실행하지 않습니다. 불명확한 요청은 사람 확인으로 보냅니다.
예시“수정한 이미지 다시 확인해줘” → 이전 실행과 수정본을 조회한 뒤 재검수 배정

MCP 도구 예시: classify_request · get_project_state · get_run_status

설계 · 구현 예정

A02 · 문서·기준 분석

명세서와 계약서를 읽어 검사 기준 초안을 만듭니다.

실행 계약내용
입력문서 전체, 문서 버전, 캠페인 정보, 기존 기준
판단조항별로 검사 가능한 조건을 추출하고 누락·충돌·모호한 표현을 찾습니다. 필요한 추가 근거를 A03에 요청합니다.
출력항목별 기준 초안, 원문·페이지·조항 위치, 적용 대상, 확인 질문
전달·다음 단계사람이 기준을 수정·확정하면 고정된 기준 버전을 검사 단계에 전달합니다.
예외·경계읽지 못한 페이지와 출처 없는 조건을 따로 표시합니다. 모델이 기준을 임의로 확정하지 않습니다.
예시계약서의 “딸기라떼 30% 할인” → 상품명·할인율 기준과 원문 위치 추출

MCP 도구 예시: read_document · ocr_document · get_document_version

설계 · 구현 예정

A03 · 근거 검색

관련 조항을 찾고 검색 결과가 충분한지 확인합니다.

실행 계약내용
입력확인할 조건·쟁점, 프로젝트 ID, 적용 문서 버전
판단검색어를 조정하고 Dense·BM25 결과를 결합합니다. 부족하면 질의를 바꿔 재검색하고 원문을 확인합니다.
출력관련 조항·출처 ID·버전·검색 기록 또는 근거 부족 표시
전달·다음 단계A02의 기준 해석과 A06의 검증에 근거를 제공합니다. 검사할 기준 목록을 선택하는 역할은 아닙니다.
예외·경계다른 프로젝트·구버전 문서를 적용하지 않습니다. 근거가 없으면 그 상태를 반환합니다. 재정렬은 선택 실험입니다.
예시할인 예외 조항을 검색하고, 이번 캠페인에 적용되는 버전인지 확인

MCP 도구 예시: search_hybrid · rerank_candidates · read_source_chunk

설계 · 구현 예정

A04 · 문구 검수

상품명·할인율·브랜드·필수 문구를 대조합니다.

실행 계약내용
입력광고 이미지, 확정된 문구 기준 전체, 이미지 버전
판단OCR 결과를 비교 도구로 대조합니다. 판독이 불분명한 영역은 잘라서 재검사하고 확인 필요 여부를 판단합니다.
출력항목별 관찰값·일치 여부·이미지 좌표·실행 상태
전달·다음 단계문구별 관찰과 비교 결과를 A06에 전달합니다.
예외·경계OCR 미검출은 곧바로 문구 누락이라고 단정하지 않습니다. 실패·미실행은 통과로 바꾸지 않습니다.
예시기준 30% / 이미지 OCR 20% → 할인율 불일치와 해당 영역 전달

MCP 도구 예시: ocr_image · crop_image · compare_text_fields

A05 · 시각 요소 검수

문자 이외의 제품 외형·색상·구성을 관찰합니다.

실행 계약내용
입력광고 이미지, 확정된 시각 기준 전체, 필요시 참조 이미지
판단VLM과 영역 분석 도구를 선택합니다. 가림·겹침·작은 물체로 판별이 어려우면 확대하거나 사람 확인을 요청합니다.
출력기준별 시각 관찰, 근거 영역, 불확실한 부분
전달·다음 단계A04와 병행 가능한 역할이며 결과를 A06에 전달합니다. 실제 동시 실행은 GPU 자원에 맞춥니다.
예외·경계개수·외관 성능은 별도 평가 후 적용합니다. 객체 탐지는 후보 도구이며, 모델 관찰을 정답으로 확정하지 않습니다.
예시투명한 컵·분홍 우유층·빨간 딸기층 조건을 이미지 영역과 함께 확인

MCP 도구 예시: inspect_visual · crop_image · detect_objects

A06 · 근거·결과 검증

관찰과 판정이 원문·이미지로 뒷받침되는지 확인합니다.

실행 계약내용
입력기준 버전, A04·A05 결과, A03 근거, 원본 이미지
판단근거의 일치·충돌·누락을 확인합니다. 모순이면 필요한 항목의 재검사를 요청하고 해결되지 않으면 사람에게 넘깁니다.
출력근거 확인이 끝난 결과, 재검사 요청, 사람 확인 사유
전달·다음 단계정리된 결과는 A07로, 추가 분석 요청은 A01을 거쳐 해당 검사 역할로 전달합니다.
예외·경계같은 모델의 재확인이 정확성을 보장하지는 않습니다. 원문·이미지 대조와 사람 확인을 유지합니다.
예시30%/20% 차이를 원문과 이미지에서 다시 확인하고 재검사 여부 결정

MCP 도구 예시: read_evidence · read_source_chunk · get_inspection_history

설계 · 구현 예정

A07 · 보고서 작성

검증된 결과를 담당자가 이해할 수 있게 정리합니다.

실행 계약내용
입력A06 결과, 근거 ID, 수신자 역할, 기준·이미지·실행 버전
판단확인된 오류와 미확정 항목을 구분하고 중요도·수정 내용을 정리합니다. 설명 근거가 부족하면 A06에 보완을 요청합니다.
출력검수 요약, 항목별 근거, 수정 안내, 확인 필요 목록이 담긴 초안
전달·다음 단계보고서 초안과 수정 대상 항목을 A08 및 검수 담당자에게 전달합니다.
예외·경계새 오류나 근거 없는 설명을 만들어 넣지 않습니다. 자동 외부 발송은 초기 범위에서 제외합니다.
예시“이미지 할인 문구 20%를 확정 기준 30%로 수정해 주세요” 초안 작성

MCP 도구 예시: get_verified_results · read_evidence · save_report_draft

A08 · 수정·재검수 관리

수정 요청부터 재제출·승인 대기까지 연결합니다.

실행 계약내용
입력보고서 초안, 기존 티켓, 재제출 파일, 현재 기준·이미지 버전
판단같은 수정 사항을 묶고 중복 요청을 확인합니다. 수정본과 이전 결과를 연결해 재검수 요청을 구성합니다.
출력수정 요청 초안, 수정 이력, 재검수 작업, 승인 대기 상태
전달·다음 단계사람이 수정 요청을 확정하고, 재제출 후 A01에 재검수를 요청합니다. 최종 승인은 사람이 수행합니다.
예외·경계중복 호출은 같은 작업 ID로 처리합니다. 구버전 결과로 승인하지 않으며, 지적 항목 외 새로운 오류도 검사합니다.
예시20% → 30% 수정본 접수 → 이전 지적 해결과 새 오류 확인 → 승인 대기

MCP 도구 예시: create_ticket_draft · compare_asset_versions · request_reinspection

시각 검수·문구 검수의 역할 분리는 실제 GPU 동시 실행을 보장하지 않습니다. 자원에 맞춰 배정합니다. 동일 모델의 재검증만으로 정확도를 확정하지 않으며 원문·이미지·사람 확인을 함께 사용합니다.

18개 기술 영역과 적용 수준

공통 설계에 포함된 모델도 데이터 적합성과 실행 자원을 검증한 뒤 고정합니다. 아래의 직접 학습·목표 구성은 개발 계획이며 학습 완료·배포 완료 기록이 아닙니다.

영역기술·모델프로젝트 역할적용 수준원문 상태

Transformers · PyTorch

Transformers는 모델 로딩·미세조정·추론 라이브러리이고 PyTorch는 학습·계산 기반입니다. 서비스 LLM 추론은 vLLM이 담당합니다.

Dense · BM25 · RRF

Dense는 의미 검색, BM25는 단어 중심 검색, RRF는 검색 순위 결합입니다. BGE의 학습된 sparse 표현은 BM25와 다른 비교 후보입니다.

팀 공통 실행 환경

Windows·Mac 개발 PC에서 웹·업무 코드를 개발하고 공용 Linux·NVIDIA CUDA 모델 API를 호출합니다. Docker는 실행 구성을 공유하며 GPU 호환 자체를 보장하지 않습니다.

Mac MLX는 팀 공통 설계에서 제외합니다. 기존 Mac Vision OCR은 현재 구현 이력으로 남기며 공통 배포에는 PaddleOCR를 우선 검증합니다. GPU 메모리·동시 요청·양자화·정확한 패키지 버전은 실측 후 결정합니다.

실제 모델 연결의 완료 기준

  • 허용된 공용 CUDA/vLLM 모델 서버에서 실제 응답을 받고 기준·보고서 출력 스키마를 검증한다.
  • 모델 ID·revision·양자화·프롬프트·설정 버전과 원 응답·시간·확보 가능한 사용량을 실행에 연결한다.
  • 파싱 실패·타임아웃·모델 미연결을 별도 기록하고 정상 성공 결과로 채우지 않는다.
  • 모의 응답은 테스트 모드로 표시하고 실제 LLM 실행 완료에 합산하지 않는다. API 키를 브라우저·보고서에 노출하지 않는다.

검색과 기준 목록의 관계

  • 확정 기준 버전의 적용 항목 전체를 DB에서 읽는다. 검색 top-k를 검수 체크리스트로 사용하지 않는다.
  • 기준 초안 추출은 문서 전체를 조항 단위로 순회하고 누락 검토 후 사람이 확정한다.
  • RAG는 기준·예외의 근거 조회와 설명을 지원한다. 프로젝트·문서 버전을 검색 전 필터링한다.
  • 미실행·실패·확인필요를 통과와 구분한다. 필수 항목이 남으면 자동 최종 승인하지 않는다.
  • 재검수는 새 이미지/기준 버전과 새 run으로 저장하고 과거 보고서를 보존한다.
  • 정답키·평가 문항 정답·이 기획서는 서비스 RAG 입력에 넣지 않는다.
  • 모델/프롬프트/검색 설정 버전과 실제 입력·출력을 기록한다. 생성 모델의 자기평가만으로 성능을 확정하지 않는다.
  • MCP는 도구 연결, LangGraph는 실행 흐름을 맡는다. 해시 계산·저장·숫자 비교는 일반 코드 단계다.

인덱스 갱신과 실패 처리

  • MySQL에 문서 버전·조항 청크·인덱싱 작업을 기록하고 대기 → 처리 → 완료/실패 상태를 표시한다.
  • BGE-M3 Dense와 한국어 BM25 검색을 결합하는 최신 목표 구성을 따른다. BGE dense+sparse 적재는 비교 실험에 해당한다.
  • 프로젝트·문서 버전·출처 위치와 모델 revision·청크 설정을 보존하고 완료한 버전만 검색에 노출한다.
  • 동일 키 재시도는 중복 청크·검색 결과를 만들지 않으며 원문과 작업 기록으로 인덱스를 재구축할 수 있게 한다.
  • MySQL과 Qdrant 저장이 동시에 원자적으로 성공한다고 가정하지 않는다. 갱신 중단·미완료·구버전 혼입을 별도 시험한다.

재시도와 멱등성

  • 검수 대상 revision·입력 해시와 실행 ID를 고정하고 체크포인트를 남긴다.
  • 노드 오류나 중단 후 같은 입력에 한해 중단 지점부터 제한된 재시도로 재개한다. 입력 변경은 새 실행으로 처리한다.
  • 동일 요청 키·동일 입력은 기존 처리 결과를 반환하고 같은 키·다른 입력은 충돌로 거절한다.
  • 파일 버전·보완 작업·승인까지 재전송과 동시 호출의 중복 생성을 방지한다.

동일 항목의 자동 재검사는 최대 2회로 시작하는 설정안을 검증합니다. 확정 운영값이 아닙니다. 상한·시간·비용을 넘거나 충돌이 해결되지 않으면 사람 확인으로 넘기고 사유를 남깁니다. 입력이 달라졌다면 새 실행을 생성합니다.

실제 MCP 호출과 추적

  • 초기화·tools/list·tools/call로 문서 조회·측정·비교·저장 도구를 실제 호출한다.
  • 서버에서 권한·발주·스키마·버전을 검증한다.
  • 호출 ID·입력 해시·방법·오류·시간과 원래 응답을 보고서 근거에 연결한다.

모의 JSON을 실호출 완료로 표시하지 않는다. 최종 승인 확정은 사람 도메인 API에만 존재한다.

기준 확정과 최종 승인

  • 승인 직전 권한·파일 해시·검수 기준·보고서·현재 revision과 필수 해결 조건을 서버에서 검증한다.
  • 최신 대상 승인과 이력을 원자적으로 기록한다.
  • 새 버전 접수 후 이전 버전 승인 요청은 STALE_VERSION으로 거절한다.

필수 조건 미충족 또는 검사가 불완전하면 승인 보류. 기본 차단 세부 정책과 예외 승인 허용은 Q08 팀 결정 사항이다. 에이전트가 승인을 확정하지 않는다.

발주별 권한·감사 이력

  • 조회·제출·확정·승인마다 조직·발주·역할 범위를 서버에서 검증한다.
  • 실행·모델·근거·전송 승인·비용·사람 조치를 추적 가능하게 기록한다.
  • API 키와 불필요한 계약 원문·미공개 이미지는 로그에 남기지 않는다.

구체 역할명과 겸임 정책은 제안이며 Q01·Q08에서 확정한다. 감사 이력에도 자료 접근 권한을 적용한다.

독립 평가와 재현 조건

  • 같은 원본의 정상·오류 파생 이미지와 같은 요청의 유사 문장은 같은 그룹으로 묶고 학습·검증·시험을 분리한다.
  • 현재 딸기라떼 6장은 한 개 개발·시연 원본 그룹이다. 독립 원본 6건 또는 일반화 정확도 평가로 표현하지 않는다.
  • 정답·평가 질문의 정답·생성 프롬프트·기획서를 서비스 입력이나 RAG 지식으로 사용하지 않는다.
  • 정답 없는 질문과 구버전 충돌 사례를 평가에 포함하고 실험별 원 응답·검색 근거·설정·평가자 모델 버전을 남긴다.
  • Ragas 평균과 근거 충실도는 이미지 검수 정확도가 아니다. JSON 규칙·OCR/VLM 오판·업무 완료는 별도 정답으로 평가한다.
  • 생성 모델의 자기평가만으로 성능을 확정하지 않고 사람 평가·표본 대조를 병행한다.
  • 해시·OCR·크롭·임베딩·좌표 변환을 코드·설정 버전과 함께 재현하고 처리 실패 사례도 기록한다.

주제 1의 직접 학습 기본 대상은 요청 분류기입니다. 생성형 LoRA/QLoRA는 기본 성능 측정 후 필요한 경우의 선택 실험입니다. 자체 LLM·sLLM 파인튜닝을 이 프로젝트의 필수 완료 항목으로 추가하지 않습니다.

단계별 제출 산출물과 일정은 기획서, 개별 기능 완료 기준은 기능정의서에서 관리합니다.
