4역할의 판단과 도구

기준 확정·최종 승인은 사람의 업무 API로 처리합니다. 에이전트의 도구 선택·추가 요청·종료 판단과 근거 교환을 실제 기록해야 하며, 역할 이름만 붙인 순차 호출을 협업 완료로 표시하지 않습니다.

해결책을 구현하는 구조와 선택안

앞에서 정의한 문제를 해결하기 위한 기술 선택입니다. 제품 이름 자체가 목표는 아니며, 실제 입력으로 효과·비용·제약을 비교한 뒤 확정합니다.

데이터 계약 · 논리 필드 제안

MySQL: 업무 기록의 정본 / Qdrant: 재구축 가능한 검색 인덱스 / 파일 저장소: 원본·근거 이미지 / LangGraph 체크포인트: 중단·재개 상태
초기에는 기존 SQLite로 AI 연결을 검증하고 MySQL로 단계 전환합니다. 초기 체크포인트는 영속 SQLite·단일 워커를 제안합니다.

실행 환경

학습은 RunPod/로컬 CUDA, Mac은 검증한 MLX/MPS 추론 경로를 고려합니다. 모델 서버를 교체해도 업무 계약을 유지하고, 모델 revision·양자화·프롬프트를 기록합니다. 정확한 GPU·메모리·지연 목표는 미정입니다.

공통 실행 계약

구분필드값과 화면 표시적용·지원 범위
항목 판정verdict충족: 충족 / 미충족: 미충족 / 확인 필요: 확인 필요 / null: 미판정 / 해당 없음: 해당 없음（설계·미구현）실행 실패는 null(미판정). 근거 부족·미실행은 충족 또는 해당 없음으로 바꾸지 않는다. 해당 없음은 적용 제외 근거가 확인된 경우의 후속 지원값이다. 기존 미실행 결과의 확인 필요 표시는 읽기 호환 범위로 유지한다.
항목 실행 상태execution_statussucceeded: 실행 완료 / failed: 실행 실패 / not_run: 미실행신규 처리 결과는 succeeded로 저장한다. 도구가 반환한 completed는 호환 입력으로 받아 succeeded로 정규화한다. 과거 저장 결과는 원본을 유지하고 화면에서 completed를 실행 완료로 표시한다. run.status의 completed와 별개이며 실행 완료는 조건 충족을 의미하지 않는다.
검수 실행 상태run.statusrunning: 실행 중 / completed: 전체 실행 완료 / partial: 부분 실행 완료 / failed: 실행 실패전체 실행 완료는 항목 실행 집계이며 최종 승인과 별개다. queued/waiting_human/cancelled는 실제 대기·중단·취소 기능을 구현할 때 추가한다. 완료 결과에 확인 필요 판정이 있다는 이유만으로 waiting_human으로 바꾸지 않는다. 후속 값: queued: 실행 대기（설계·미구현） · waiting_human: 사람 확인 대기（설계·미구현） · cancelled: 취소 완료（설계·미구현）
보완 작업 상태task.statusdraft: 초안（설계·미구현） / confirmed: 요청 확정（설계·미구현） / submitted: 수정본 제출（설계·미구현） / resolved: 해결（설계·미구현）설계 계약·현재 미구현. 수정본 제출만으로 해결 처리하지 않고 새 검수 결과와 사람의 해결 확인을 기록한다.
최종 승인 상태approval.statuspending: 승인 대기（설계·미구현） / approved: 승인（설계·미구현） / on_hold: 보류（설계·미구현）설계 계약·현재 미구현. 최신 기준·납품 버전 및 필수 해결 조건을 확인하고 권한 있는 사람의 결정을 기록한다. 과거 버전의 승인 기록은 보존한다.

항목 분할·병합 또는 의미 변경에는 새 rule_id를 부여합니다. 원본 기준 파일 바이트는 그대로 보존하며, 입력의 id 별칭만 정규화해 기존 criteria_version과 확정 기록을 유지합니다.

반복 한도와 재검수 구분

초기 설계값은 도구 재시도 추가 2회(총 3번 시도), 에이전트 재검사 추가 1회(총 2번 검사)이다. 자동 반복·체크포인트 재개는 현재 미구현이며 현재 실행의 추가 반복은 0회다. Q03에서는 파일·픽셀·전체 실행의 시간·비용 운영 한도만 실측 후 확정한다.

구분초기 설계값허용 사유카운터 범위
도구 재시도추가 2회 / 총 3번같은 논리적 도구 호출의 일시적 통신 오류·과부하run_id + operation_id
에이전트 재검사추가 1회 / 총 2번근거 충돌·판독 불확실성이 있고 영역 확대·다른 방법 등 추가 근거 확보가 가능한 경우run_id + rule_id
  • 조건 미충족·입력 오류·권한 거절·응답 스키마 오류는 단순 반복 재시도 사유가 아니다.
  • 저장·티켓 생성 등의 쓰기 도구는 멱등성 키와 처리 결과 조회가 갖춰진 뒤 재시도한다. 최종 승인은 자동 반복하지 않는다.
  • 횟수 한도와 별도로 전체 실행의 시간·비용 예산을 적용한다. 구체 운영 한도는 Q03에서 실측 후 확정한다.
  • 미해결 항목은 사람 확인으로 넘긴다. 도구 실행 실패의 판정은 null이며 관찰이 불확실한 정상 실행은 확인 필요로 남긴다.
  • 새 이미지·기준·증빙 버전으로 수정본을 제출하면 새 run을 생성하고 previous_run_id로 연결한다.
  • 하나의 검사 도구를 쓰는 항목 기준 중첩 상한은 검사 2번 × 호출 시도 3번 = 최대 6번이다. 여러 도구의 총 호출·시간·비용은 run 공통 예산을 공유한다.
  • 여러 항목을 함께 검사하는 도구 호출은 하나의 operation_id와 공통 재시도 카운터를 사용한다. rule_ids는 영향 항목 목록이며 항목 수만큼 재시도 예산을 부여하지 않는다.
  • 동시 재개에도 시도 횟수와 전체 실행 예산은 호출 전에 원자적으로 증가시키고 동일 논리 작업의 operation_id를 유지한다.
