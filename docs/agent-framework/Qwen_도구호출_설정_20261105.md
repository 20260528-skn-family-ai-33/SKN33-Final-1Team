# Qwen 도구 호출 실행 옵션 적용

2026-11-05 · `feat/37-framework-neo4j-rag` · Qwen3.5-4B / vLLM 0.17.1

## 적용 내용

기존 RunPod의 A02 텍스트 서버에 아래 옵션을 추가하고 정상 종료·재기동했다.

```text
--enable-auto-tool-choice --tool-call-parser qwen3_coder
```

기존 모델 revision `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`, BF16, context 32768, 동시 요청 1개, GPU 사용 한도 0.85, eager, text-only, `enable_thinking=false`, loopback 8015와 인증키를 유지했다. 새 모델·패키지 설치·이미지 서버 전환·공개 포트 개방은 하지 않았다.

파서는 [vLLM Qwen3.5 실행 가이드](https://github.com/vllm-project/recipes/blob/main/Qwen/Qwen3.5.md)의 도구 호출 구성, [0.17.1 파서 등록 소스](https://github.com/vllm-project/vllm/blob/v0.17.1/vllm/tool_parsers/__init__.py), [고정 모델의 도구 호출 템플릿](https://huggingface.co/Qwen/Qwen3.5-4B/blob/851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a/chat_template.jinja)을 대조해 선택했다. 실제 설치 환경에서 `Qwen3CoderToolParser` 로딩을 확인한 뒤 기동했다.

## 저장소 실행 설정

- `deploy/qwen-a02/server.json`: `enable_auto_tool_choice=true`, `tool_call_parser=qwen3_coder` 추가.
- `deploy/qwen-a02/server.py`: 선택한 옵션을 vLLM 실행 인자로 전달하고 불일치한 설정은 기동 전에 거부.
- 옵션 키가 없는 예전 개인 JSON은 기존 A02 전용 동작을 유지한다.
- `plan`은 계속 GPU·모델 실행 없이 계획만 보여 준다. `serve`는 기존 포트·GPU·환경·모델 해시 사전 검사를 유지한다.

```text
python3 deploy/qwen-a02/server.py plan
```

이 변경은 모델이 코드가 제공한 도구를 선택하도록 서버에서 해석을 허용한다. 승인 권한을 추가하거나 PostgreSQL에 임의 승인을 기록하지 않는다. A01은 상태 조회만, A08의 재검수 요청은 기존 사람의 수정 승인과 새 버전 검증을 통과해야 한다.

## 원격 적용과 보존

원격 8015 API PID `320879`와 모델 경로를 확인하고, running/waiting 요청이 모두 0인 상태를 두 번 확인했다. 기존 실행 인자·환경·설정 원본·모델 파일 메타데이터를 전용 비공개 폴더에 백업했다. 해당 API만 SIGTERM으로 정상 종료하고 GPU 메모리 해제를 확인한 뒤 같은 인자에 위 옵션만 추가해 새 PID `331039`로 실행했다.

원격 작업 폴더:

```text
/opt/creative-checker-a02/runtime/operations/tool-calling-20261105-adf09609
```

- `server-tools.log`: 새 서버 로그. 기존 stdout/stderr는 `/dev/pts/1`이었으며 기존 로그 파일을 삭제·덮어쓰지 않았다.
- `change-plan.json`, `new-process.json`, `verification.json`: 실행·보존 확인.
- `original-*`: 원래 서버 실행 파일·JSON·모델 manifest 사본.
- `process-private.json`: 복구에 필요한 기존 환경. 인증값이 있으므로 공유·Git 업로드 금지.
- 폴더 권한 0700, 비공개 백업·로그 0600으로 보존했다.

원격 Git 작업 폴더의 기존 파일은 덮어쓰지 않았다. 저장소의 새 실행 설정은 로컬 작업 브랜치에 반영했고, 이번 원격 실행은 보존한 기존 인자에 두 옵션을 추가하는 방식이다.

현재 옵션으로 수동 재기동할 때 사용할 보조 파일도 원격 전용 폴더에 보존했다. 아래는 **RunPod Linux 터미널** 명령이며, Mac/Windows 호스트에서 직접 실행하는 명령이 아니다.

```bash
/opt/creative-checker-a02/runtime/venv/bin/python \
  /opt/creative-checker-a02/runtime/operations/tool-calling-20261105-adf09609/serve-tools.py --plan
```

실제 시작은 기존 서버를 정상 종료하고 GPU·포트 해제를 확인한 후 위 명령에서 `--plan`을 빼고 실행한다. 보조 파일도 포트·GPU·패키지·모델 해시 검사를 통과해야 시작하며 기존 프로세스를 자동 종료하지 않는다. foreground 실행이므로 실행 터미널을 유지한다. 현재 적용 프로세스는 별도 세션에서 실행되고 있으므로 중복 기동하지 않는다. Pod/OS 재시작 자동화는 이번 범위가 아니다.

## 실모델 재검사 — 서버 옵션 수정 직후

원래 실패했던 `tests/agent_framework/test_agents_live.py` 4개를 수정 없이 재실행했다.

기존 HTTP 400은 해소됐고 인증 모델 조회 200, 자동 도구 선택 활성화 로그, 실제 chat completions HTTP 200을 확인했다. 현재 결과는 **3 passed, 1 failed**다. 모델이 사용하는 실행/승인 도구는 메모리의 합성 Workflow이며 실제 사용자 승인은 아니다.

남은 사례는 모델이 `rereview_requested=false`로 답하면서 `unresolved`에 조건 ID 대신 `human_decision != 'changes_approved'` 같은 이유 문장을 넣어 발생했다. JSON 문법 자체가 아니라 `RereviewDraft`의 ID 목록 계약 검증에 실패한 것이다. 서버 옵션 문제와 별개이며, 이번 작업에서 A08 안내문·계약·판정 로직이나 시험 기대값을 바꾸지 않았다. 후속으로 재검수 요청 단계의 목록 의미를 안내문에 명확히 하고 기존 엄격한 검증을 유지한 채 다시 확인할 필요가 있다.

## A02 호환성 결과

새 도구 옵션이 적용된 서버에서 기존 개발용 전시 PDF를 실제 Qwen으로 다시 추출하고 일회용 PostgreSQL에 저장했다. **1 passed**, 전체 시험 119.27초이며 등록~검증 구간은 116.06초다. 조건 13개·표시 문단 12개·미정 항목 1개, `waiting_criteria`, 승인 0건을 유지했다. 새 API 인스턴스와 DB snapshot·단계 출력 해시 재조회가 일치했다. 실제 추론 응답이며 입력은 Git 추적된 가상 개발 샘플이다. 시험 DB·컨테이너·볼륨·네트워크는 소유 확인 후 정리했다.

시험 실행 `1dae01c7-bf5b-53f3-b494-e3a8ce89c649`는 정리된 시험 DB에 속하며 사용자 개발 DB에 추가한 실행이 아니다. 결과 문구의 의미 정확도·완전성과 최종 승인을 확인한 것은 아니다.

A08 수정 전 확인 범위:

- 로컬 서버 설정·계획·구버전 호환성·옵션 검증: 23개 통과.
- A01·A08 실모델: 3개 통과, A08 요청 거절 답변의 출력 계약 1개 실패.
- 실제 Qwen A02→시험 PostgreSQL 저장·재조회: 1개 통과.
- 원격 새 실행 인자가 기존 인자에 두 옵션만 추가된 것과 인증키 동일 여부를 대조했다.
- 모델 파일의 개수·크기·수정 시각, 원격 저장소의 기존 server.py/server.json/model-manifest.json 바이트가 보존됐다.
- 새 서버 로그에서 자동 도구 호출 활성화와 chat completions 200을 확인했고 기존 도구 요청 400은 해소됐다.
- 실제 사용자 승인·포스터 시각 검사·Windows 실기기·AWS 검증은 수행하지 않았다.
