# PDF 분석 결과를 3. 검수 요구사항에 넣기

2026-11-04 · 기존 Qwen 한 번 호출 · front-v2 데스크톱

Docker 준비부터 이번 전시 PDF·포스터 선택까지의 실제 실행 순서는 [A02 실행·사용 가이드](A02_실행_사용가이드.html)를 따른다. 이 문서는 내부 연결 방식과 검증 경계를 설명한다.

## 동작

**PDF 선택 → 기존 PostgreSQL 프로젝트에 원문 등록 → A02 worker의 Qwen 호출 → 검수 조건과 화면용 문단 동시 생성 → 원문 검증·초안 저장 → 3. 검수 요구사항에 추가**한다.

행사명·기간·장소로 항목을 제한하지 않는다. 모델이 문서의 필수 문구·장소·로고·색상·구성·잘림 금지·글꼴·규격 등 각각의 제목과 표시 값을 결정한다. 코드는 표시 값이 원문과 기존 기대값·단위에 근거하는지 확인한다. 원문에 없는 값은 추가하지 않는다.

같은 검사 대상·원문 범위에서 모델이 동일한 표시 문단을 선택한 경우 화면에서는 한 번 보여주고 내부 조건 ID와 출처는 모두 유지한다. 예를 들어 시작·종료일의 전체 기간이나 가로·세로가 함께 적힌 규격이다. 여러 필수 장소는 각각 보존한다. 원문의 대안·예외·허용 범위는 별도 근거로 함께 전달한다.

확인 중·값 미정 항목은 원본 초안과 `pending` 안내에 유지하고 입력란의 확정된 값 목록에서 분리한다. 화면 반영이 기준 승인이나 원본 초안의 삭제를 뜻하지 않는다. 기존 입력은 보존하고, 중복 문단·한도 초과·취소·실패 응답을 처리한다.

## 모델과 계약

추가 Ollama 서버나 별도 요약 모델은 사용하지 않는다. `pdf_extraction.presentation=true`인 Qwen 의미 구조화 프로필은 같은 한 번의 응답에 `presentation.label`, `presentation.value`를 함께 요청한다. 단순 축약으로 조건을 덜어내지 않도록 전체 요구사항과 금지·대안·수치 범위를 유지하라고 지시한다. 표시 값에는 공백 차이를 허용하되 공백을 제외한 문자·기대값·단위는 원문에 근거해야 한다. 기존 조건의 기대값·원문·비교 연산은 이 표시 정책으로 수정하지 않는다.

새 정책은 `a02-semantic-v4`다. 기존 v3 프롬프트·해시와 저장 결과는 유지한다. `presentation`은 기존 계약에 선택적으로 추가되며 값이 없으면 이전 직렬화 형태를 유지한다. 이전 v3 실행에 모델 문단을 임의로 덧붙이지 않는다. 새 프로필의 새 요청 키로 PDF를 접수한다.

역할·파일 위치:

| 위치 | 역할 |
|---|---|
| `backend/agent_framework/a02_semantic.py` | 모델의 동시 추출·표시 문단 응답 계약과 원문 검증 |
| `backend/agent_framework/requirements_presentation.py` | 검증된 문단을 프론트 DTO로 전달, 미정 안내·출처 유지 |
| `backend/agent_framework/postgres_api.py` | 기존 인증·프로젝트·문서·worker 접수·조회 API |
| `frontend/src/pages/review/frameworkDocument.js` | PDF 등록·단일 접수·실행 조회·문단 조회 |
| `frontend/src/pages/review/ReviewProvider.jsx` | 완료된 최신 요청만 기존 입력에 반영 |
| `frontend/src/pages/review/DocumentInput.jsx` | 저장 프로젝트 선택·PDF 선택·단계 표시 |

## 추가 조회 경로

- `GET /api/framework/v1/projects`: 기존 M008 프로젝트 목록. owner/editor를 선택한다.
- `GET /api/framework/v1/csrf`: 문서 서버에서 발급하는 기존 CSRF 응답.
- `GET /api/framework/v1/runs/{run_id}/requirements`: 원래 A02 초안에서 검증한 문단·출처·미정 안내. 별도 추론·승인을 실행하지 않는다.

쓰기 요청은 기존 세션·프로젝트 권한·CSRF·요청 키 검사를 따른다. API에는 모델 키를 넣지 않고 worker의 기존 비공개 설정을 사용한다. 문단을 담을 새 테이블·DB 마이그레이션은 필요하지 않으며 기존 AF004 JSON 저장소를 재사용한다.

## 실행 설정

API와 worker에 **동일한** presentation 설정을 지정한다. 공개 예시는 `deploy/qwen-a02/worker-config.presentation.example.json`이다. `scripts.prepare_a02_presentation`은 기존 app env·팀 설정을 읽어 원본을 덮어쓰지 않고 별도 설정 복사본을 만든다. 기존 역할·모델 주소·키·제한을 유지하고 문단 출력, 출력 상한, 명시적 로컬 프론트 출처를 준비한다. 실행 중인 기존 컨테이너에는 로컬 소스 수정이 자동 반영되지 않으므로 새 이미지 빌드와 재시작이 필요하다.

기존 웹 서버가 빌드된 프론트를 제공하는 경우에는 프론트 빌드와 웹 서버 재시작도 필요하다. 이 서버에 새 `/api/framework` 브리지가 등록되어야 한다. Vite 개발 화면에서는 새 프록시 설정을 반영한 개발 서버를 사용한다.

준비된 출력 파일이 이미 있으면 준비 명령은 덮어쓰지 않고 종료한다. 해당 파일을 재사용하거나 `--output-env`, `--output-config`로 다른 이름을 지정한다. 11/04에는 별도 presentation 복사본으로 사용자가 이미지·API·worker·프론트를 다시 실행했다. 프론트 프록시와 Qwen health 200, `requirements_presentation=true`를 확인했고 PDF 완료 후 포스터와 12개 기준이 있는 후속 화면을 확인했다. 이후 포스터 검수 실행 화면의 HTTP 500은 별도 후속 연결 문제이며 A02 문단 반영과 구분한다.

프론트의 실제 출처를 API·worker env의 `AUTH_ALLOWED_ORIGINS`에 등록한다. 예를 들어 Vite `http://127.0.0.1:5173` 또는 기존 웹 서버 `http://127.0.0.1:8000`을 사용하면 해당 값을 명시적으로 추가하고, hostname이 `AUTH_ALLOWED_HOSTS`에도 있어야 한다. 와일드카드를 사용하지 않는다. 같은 기존 PostgreSQL 사용자 세션으로 로그인한다. 이메일 입력은 M008의 `email` 로그인 계약으로 전송한다.

Vite는 `/api/framework`를 `FRAMEWORK_API_PROXY_TARGET`으로, 나머지 `/api`를 `API_PROXY_TARGET`으로 전달한다. 기본값은 각각 `http://127.0.0.1:8012`, `http://127.0.0.1:8000`이다. 프레임워크만 확인할 때는 `API_PROXY_TARGET`도 8012로 지정해 그 서버에서 로그인할 수 있다. 이 경우 전체 포스터 검사·이전 업무 API 제공 여부는 별도다.

기존 `backend.app.api`가 빌드된 front-v2를 제공할 때도 `/api/framework/*`를 A02 서버에 전달한다. 서버 전용 `FRAMEWORK_API_ORIGIN` 기본값은 `http://127.0.0.1:8012`이며 Docker 내부에서는 필요에 따라 `http://host.docker.internal:8012`를 명시한다. 이 경로의 Origin·세션·CSRF 검사는 A02의 기존 M008 경계가 수행한다. 모델 주소·키를 프론트에서 지정하지 않는다. 읽기 전용 레거시 앱에는 이 쓰기 연결을 추가하지 않는다.

Mac:

```bash
# 프로젝트 루트 · Docker Desktop 실행 후
python3 -m scripts.prepare_a02_presentation --env-file .runtime/framework-desktop.env --config .runtime/team_config.qwen-600s.json
python3 scripts/framework_desktop.py build
python3 scripts/framework_desktop.py api --env-file .runtime/framework-desktop-presentation.env --config .runtime/team_config.qwen-presentation.json
# 별도 터미널
python3 scripts/framework_desktop.py worker --env-file .runtime/framework-desktop-presentation.env --config .runtime/team_config.qwen-presentation.json
# 별도 터미널 · frontend 디렉터리
API_PROXY_TARGET=http://127.0.0.1:8012 npm run dev -- --port 5173 --strictPort
```

Windows PowerShell:

```powershell
py -3.12 -m scripts.prepare_a02_presentation --env-file .runtime/framework-desktop.env --config .runtime/team_config.qwen-600s.json
py -3.12 scripts/framework_desktop.py build
py -3.12 scripts/framework_desktop.py api --env-file .runtime/framework-desktop-presentation.env --config .runtime/team_config.qwen-presentation.json
# 별도 터미널
py -3.12 scripts/framework_desktop.py worker --env-file .runtime/framework-desktop-presentation.env --config .runtime/team_config.qwen-presentation.json
# 별도 터미널 · frontend 디렉터리
$env:API_PROXY_TARGET = 'http://127.0.0.1:8012'

```

SSH 터널·API·worker 전경 실행 창을 유지한다. 입력 반영 취소는 서버에 이미 접수된 실행을 지우지 않는다. 같은 세션에서 같은 파일을 다시 선택하면 저장한 등록·추출 키와 실행 ID를 재사용한다. 결과 불명·실패 실행을 새 키로 자동 재호출하지 않는다. 새 실행을 의도할 때는 새 검수를 시작한다.

## 검증

단위 검사에서는 여러 필수 장소, 임의의 추가 항목, 잘림 금지 문장, 기간의 출처 결합, 미정 안내 분리, 근거 없는 표시 문장 거부를 확인한다. 브라우저 검사는 테스트 응답으로 PDF 선택부터 실제 `3. 검수 요구사항` textarea 반영·기존 입력 보존·같은 파일 중복 접수 방지를 확인한다. 격리 PostgreSQL 검사는 문단 저장·재시작 조회·권한·기존 승인 경로를 확인한다.

```bash
python -m pytest tests/agent_framework/test_requirements_presentation.py -q
# frontend 디렉터리
npm test
npm run test:requirements:ui
npm run build
npm run typecheck
```

이 검증과 사용자 환경의 새 이미지 적용, 실제 Qwen 응답 품질은 별도로 기록한다. 현재 실행 중인 사용자 API·worker·원본·승인은 변경하지 않는다. 기존 v3 실제 연결 기록은 [11/04 검증 기록](A02_실제연결_검증기록_20261104.md)을 따른다.

### 11/04 확인한 결과

- 실제 RunPod Qwen에 전시 PDF를 보내 한 번의 응답에서 조건 13개와 표시 문단을 받았다. 원문·단위·표시 범위를 검증한 뒤 문단 12개와 미정 안내 1개로 전달했다. 가로·세로는 각각 `가로: 3000픽셀`, `세로: 3000픽셀`로 구분했다.
- 최초 진단에서는 표시 공백·항목 제목·가로/세로 구분 문제를 확인해 기록을 보존했다. 표시 값의 공백 차이는 허용하되 공백 이외의 원문 문자·기대값·단위와 축 구분은 계속 검사한다. 원본 조건의 비교값과 원문을 보정해 성공으로 바꾸지 않는다.
- 실제 Qwen의 검증된 응답 기록을 브라우저에서 재생해 `3. 검수 요구사항`에 12개 문단이 들어가는 것을 확인했다. 테스트용 응답의 여러 장소·새 항목·잘림 금지 조건도 함께 검사했다. 브라우저 테스트의 로그인·HTTP 응답은 시험용이며 사용자 서비스의 새 이미지 배포와 구분한다.
- 격리 PostgreSQL의 관련 3개 모듈 42개가 통과했다. 여기에는 기록된 실제 Qwen PDF 응답을 가짜 HTTP로 재생해 원문 등록·worker 저장·문단 조회·미정 분리·승인 대기 상태를 확인하는 시험이 포함된다. 기존 사용자 DB에는 이 진단 결과를 쓰지 않았다.
- 추출 조건 수나 표시 성공이 전체 요구사항의 누락 없음이나 승인 완료를 보장하지 않는다. 기존 전시 샘플의 납품 수량·제목/안내정보 구분은 별도 원문 대조 검토 항목으로 유지한다.

최종 확인: 프레임워크·브리지 회귀 655개, 설정 복사 원본 보존 검사 2개, 기존 문서 처리 회귀 153개, 관련 격리 DB 42개, 프론트 단위 103개, 데스크톱 브라우저 재생 검사 통과. 프론트 빌드·타입 검사와 별도 태그의 Docker 이미지 빌드/모듈 포함 검사도 통과했다. 이후 사용자 Mac의 새 프로필 실행과 PDF 문단 반영을 확인했으며 상세는 실제 연결 검증 기록을 따른다. Windows 실기기 실행·전체 포스터 업무 연결·운영 배포는 별도 확인 대상이다.
