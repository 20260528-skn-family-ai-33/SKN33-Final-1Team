# 승인 기준으로 포스터 검수·재검수

2026-11-03 · 7단계 · `feat/37-a02-pdf-registration`

## 01. 이번에 연결한 범위

**AF003 승인 기준 조회 → 기존 저장 포스터 선택 → 새 포스터 실행 → 입력 확인 → A04·A05 → A06 → A07 → 사람 결정 → 수정본 재검수**를 연결했다. 기존 M008 사용자·프로젝트·세션·CSRF·이미지 저장과 AF001 실행·단계·승인·worker를 재사용한다. 새 DB 스키마나 이미지 업로드 경로를 만들지 않았다.

검증은 격리 PostgreSQL과 실제 파일 저장소를 사용했다. 포스터 관측은 명시적 합성 sidecar 공급자이며 Qwen/OCR 결과가 아니다. 실제 Qwen 호출, 클라이언트 회신·기준 승인, 운영 DB 적용, front-v2 화면 연결은 수행하지 않았다. 기본 팀 inspector는 미연결 오류를 내며 가짜 통과를 반환하지 않는다.

이번 단계로 개발용 7단계 연결 시험을 마쳤다. 실제 모델 품질·발주자 승인·제품 통합을 완료했다는 의미는 아니다. 원본 시나리오의 관람시간·관람연령·우천 안내는 여전히 실제 회신 전이다.

## 02. 기준과 포스터 실행의 구분

PDF-only 원본 실행은 `waiting_asset`에서 **승인 기준의 출처 실행**으로 보존한다. 원본 A02 초안·완료 단계·승인 기록을 덮어쓰지 않는다. 포스터마다 별도 실행 ID를 만든다.

새 `RunSnapshot.baseline`에는 다음을 고정한다.

| 필드 | 의미 |
|---|---|
| `source_run_id` | 원본 PDF-only A02 실행 |
| `criteria_version_id` | AF003에서 승인한 정확한 기준 버전 |
| `criteria_sha256` | 그 기준 본문·출처의 해시 |
| `approval_id` | 기존 AF001에 저장한 기준 승인 기록 |
| `document_sha256` | 원본 PDF 파일 해시 |

새 실행의 조건은 최초 A02 초안이 아니라 **승인된 보완 기준**이다. 각 조건의 PDF 인용과 별도 `value_source`를 함께 보존한다. A02 단계는 `reused`와 출처 실행 ID를 기록하며 호출 시간·추론 성공을 만들어 넣지 않는다.

처음 포스터 실행에는 `parent_run_id=null`이다. 수정본만 직전 검수 실행을 부모로 연결한다. 여러 최초 제안물을 같은 승인 기준에 연결할 수 있다. 원본 승인 ID를 참조하는 것과 새 포스터의 승인을 자동 복사하는 것은 다르다. 새 실행에는 승인·검사 결과·근거 묶음이 없고 `waiting_criteria`에서 시작한다.

## 03. 기존 이미지 저장소 재사용

포스터는 기존 제품의 POST `/api/v1/projects/{project_id}/images`로 등록한 `asset_version_id`를 사용한다. 파일 저장·정규화·원본 및 display 해시·좌표계는 기존 `Files`와 `LocalStorage`가 맡는다. 포스터 프로필에서는 front-v2의 `/api/framework/v1/projects/{project_id}/images`도 같은 M008 업로드 핸들러와 저장소를 사용한다. 이미지 조회와 확대에는 해당 버전의 display PNG를 사용한다.

서버는 같은 프로젝트의 `public.asset_versions`와 `stored_files`에서 display PNG 참조를 직접 구성한다. 요청에서 임의 파일 경로·파일 해시·관측 문구를 받지 않는다. 파일 크기·실제 바이트 해시·디코딩·가로세로·display 좌표계를 확인한다. worker는 PDF와 포스터 바이트를 공급자 호출 전과 반환 뒤 다시 확인한다.

PDF root는 별도 초기화한 전용 저장소, poster root는 **기존 M008 이미지 저장소**다. 둘을 섞지 않는다. 프레임워크의 poster root 열기는 초기화·복구·GC·기존 leader 기동을 수행하지 않는다. PDF marker가 있는 root는 포스터 저장소로 거부한다.

기존 제품 제한은 최대 변 길이 8,192, 총 1,000만 화소다. 원본 전시 3,000×3,000과 축제 2,382×3,368은 등록·실제 읽기·해시를 확인했다. 연주회 원본 4,500×4,500은 기존 `IMAGE_LIMIT_EXCEEDED`로 거부된다. 원본을 축소·수정하거나 제한을 풀지 않았다. 원본 포스터에는 모델 판정을 수행하지 않았다.

기존 업로드 한 건은 새로운 asset/version ID와 `version_no=1`을 만든다. 수정본도 이 경로로 등록한 새 ID를 사용하며, 프레임워크의 `parent_run_id`로 검수 이력을 연결한다. 동일 논리 asset의 버전 번호 증가 기능을 새로 구현한 것은 아니다.

## 04. 접수와 승인 API

아래 경로의 접두사는 `/api/framework/v1`이다. 기존 로그인 쿠키·CSRF·허용 Origin과 활성 프로젝트 쓰기 권한을 확인한다. 현재 쓰기 권한은 원본 A02 실행 생성자이면서 프로젝트 editor/owner인 사용자다. viewer 조회와 승인 위임은 구분하며 새로운 위임 정책은 추가하지 않았다.

| 메서드·경로 | 처리 |
|---|---|
| GET `/runs/{source_run_id}/criteria-approval` | 정확한 승인 기준·출처·승인 ID 조회 |
| POST `/runs/{source_run_id}/poster-reviews` | 등록 포스터로 새 실행, `waiting_criteria` |
| POST `/runs/{poster_run_id}/approvals` | 새 입력 확인 또는 수정 요청/최종 결정 |
| GET `/runs/{poster_run_id}` | 검수 판정·출처·고정 baseline·승인 이력 조회 |
| GET `/runs/{poster_run_id}/steps` | A02 재사용 및 A04_A05·A06·A07 단계 조회 |
| POST `/runs/{poster_run_id}/poster-revisions` | 수정 요청 승인 후 새 포스터 실행 |

포스터 접수와 수정본 접수의 본문은 같다. `Idempotency-Key` UUID를 함께 전송한다.

```json
{
  "criteria_version_id": "<조회한 승인 기준 UUID>",
  "expected_criteria_sha256": "<승인 기준 응답의 criteria.sha256>",
  "asset_version_id": "<기존 이미지 업로드가 반환한 UUID>"
}
```

꺾쇠 값은 설명용이다. 실제 기준·포스터를 선택해 채우며 관측값·run/actor ID·파일 경로는 제출하지 않는다. 동일 키·동일 입력의 재전송은 기존 실행을 반환한다. 같은 키에 다른 포스터나 해시는 409다. 접수 응답이 불명확하면 기존 키를 유지해 재조회/재전송한다. DB 결과 불명은 503이며 자동으로 새 실행을 만들지 않는다.

새 실행 응답의 `context` 그대로 기존 승인 API에 `decision=approve_criteria`를 제출하면 **해당 포스터와 고정 기준의 확인**을 기록하고 검수 job을 만든다. AF003 기준 승인을 다시 만들거나 다른 기준으로 바꾸지 않는다. 실제 사용자의 확인 의사 없이 이 요청을 자동 전송하지 않는다. 테스트에서만 명시적 합성 결정 입력을 사용한다.

worker는 A04_A05→A06→A07을 수행하고 `waiting_review`에서 멈춘다. 기계 `pass`만 일반 `approve_final`이 가능하다. `fail/review`는 실행 실패와 다르며 자동 최종 승인하지 않는다. A06는 독립 관측값과 기대값을 대조하므로 공급자가 잘못 `pass`를 낸 날짜 오류도 `value_mismatch`로 차단한다. 빈 기대값·불확실 관측 방어는 기존 정책을 유지한다.

수정할 경우 기존 실행에 `approve_changes`를 기록하고 새 포스터 ID로 `/poster-revisions`를 호출한다. 수정 요청 승인 전·같은 포스터 ID·두 번째 자식 생성은 거부한다. 자식은 같은 baseline, 새 run/asset ID, 빈 승인 이력으로 시작하며 새 입력 확인 후 A04_A05·A06·A07을 다시 수행한다. 고정 기준이 있는 실행은 임의 문맥을 받는 구형 `/revisions`로 우회할 수 없다.

같은 논리 PDF의 새 버전이 등록되면 이전 기준의 신규 접수·대기 job은 오래된 문서로 차단한다. 문서/기준 변경은 새 A02→새 기준 승인 흐름을 거친다. 모델 호출 이후 권한·기준이 바뀌면 결과를 성공으로 저장하지 않는다. 완료 단계는 안전한 lease 만료 뒤 재사용하고 결과 불명 호출은 자동 반복하지 않는다.

## 05. 담당자 연결 위치

| 위치 | 담당 작업 |
|---|---|
| `backend/agent_framework/adapters/team_a04_a05.py` | `create_inspector()`가 반환할 실제 검사 객체 |
| `inspect_poster(request, poster)` | 동기식 메서드. 검증된 `VerifiedPoster.content`와 display 크기/좌표계, 승인 조건·근거로 `InspectionResult` 반환 |
| `team_config.poster-review.template.json` | A04_A05 `registered_poster`와 신뢰하는 Python factory 선택 |
| `backend/agent_framework/poster_review.py` | 공통 권한·파일 읽기·기준 고정·접수/수정본 및 결정적 A07 보고 |
| `backend/agent_framework/a02.py` | 등록 PDF 공급자와 등록 포스터 검사기 조립 |
| `tests/agent_framework/test_poster_postgres_integration.py` | 실파일·PostgreSQL·worker 관통 시험 |

factory는 팀이 배포한 설정으로만 지정한다. HTTP 요청으로 factory나 모델 관측을 교체할 수 없다. 비동기 factory/메서드는 이 동기 포트에서 거부한다. 팀은 모델명·revision·추론 설정을 별도로 고정해야 한다. 공통 `runtime_sha256`은 프레임워크 Python 코드만 고정하므로 외부 factory/가중치 revision을 대신하지 않는다.

포스터 검사기는 worker의 CC_QWEN_BASE_URL에 연결한다. A06이 관측값을 검증하면 팀 A07 보고기가 조건별 설명과 수정 요청을 만든다. 선택적인 모델 문장 다듬기가 실패해도 검증된 판정과 근거는 보고서에 남는다.

## 06. 실행과 테스트

프로젝트 루트에서 실행한다. 의존성 정본은 `pyproject.toml`·`uv.lock`이며 설치는 [프레임워크 안내](README.md)를 따른다. 이번 단계는 새 의존성을 추가하지 않았다. AF003이 명시적으로 적용된 개발 DB, app 전용 설정 파일, 기존 PDF와 이미지 root를 준비한다. owner 설정은 worker/API에 넘기지 않는다.

front-v2의 PDF·직접 입력 검수에는 아래 통합 설정을 API와 worker 양쪽에 지정한다. `worker-config.poster.example.json`은 실제 A04·A05와 A07 구현, Qwen 의미 추출·문단 출력을 지정한다. PDF 전용 `worker-config.example.json`과 개발용 mock template은 전체 검수용으로 사용하지 않는다. 직접 입력 저장에는 AF004 이상이 필요하며, 기존 스키마를 자동으로 변경하지 않는다.

두 프로세스는 같은 DB, 전용 원문 저장소, 초기화된 M008 이미지 저장소를 사용한다. worker 전용 env에 CC_QWEN_BASE_URL을 지정하고 인증이 필요한 서버라면 A02_QWEN_API_KEY와 CC_QWEN_API_KEY를 설정한다. 예제의 A02 endpoint와 이 주소는 같은 모델 서버를 가리켜야 한다.

```bash
uv run python -m backend.agent_framework postgres-serve --env-file .runtime/framework-app.env --config deploy/qwen-a02/worker-config.poster.example.json --pdf-storage-root /absolute/existing/framework-pdf --poster-storage-root /absolute/existing/m008-images --port 8012
uv run python -m backend.agent_framework worker --env-file .runtime/framework-worker.env --config deploy/qwen-a02/worker-config.poster.example.json --pdf-storage-root /absolute/existing/framework-pdf --poster-storage-root /absolute/existing/m008-images
```

Windows·Mac의 Docker Desktop에서는 같은 설정 파일을 scripts/framework_desktop.py의 api·worker에 넘긴다. --volume에는 기존 PDF 볼륨, --poster-volume과 --poster-subdir에는 M008 이미지 저장소를 지정한다. 호스트 터널 주소는 컨테이너에서 host.docker.internal로 변환된다.

```text
python scripts/framework_desktop.py api --env-file .runtime/framework-app.env --config deploy/qwen-a02/worker-config.poster.example.json --volume EXISTING_DOCUMENT_VOLUME --poster-volume EXISTING_IMAGE_VOLUME --poster-subdir images
python scripts/framework_desktop.py worker --env-file .runtime/framework-worker.env --config deploy/qwen-a02/worker-config.poster.example.json --volume EXISTING_DOCUMENT_VOLUME --poster-volume EXISTING_IMAGE_VOLUME --poster-subdir images
```

위 볼륨 이름과 이미지 하위 경로는 기존 저장소의 실제 값으로 바꾼다. API와 worker에는 같은 이미지 빌드·설정·볼륨을 사용한다. front-v2의 `FRAMEWORK_API_PROXY_TARGET`은 해당 API 주소를 가리킨다.

모델 서버는 이미지 입력을 받아야 한다. 기존 `deploy/qwen-a02/server.json`은 텍스트 전용 설정으로 유지한다. 포스터용 `server-poster.json`은 같은 모델·revision·포트·GPU 제한을 사용하면서 `language_model_only`만 false로 바꾼다. RunPod의 기존 환경에서 다음 명령으로 설정을 확인한다.

```bash
python deploy/qwen-a02/server.py plan --config deploy/qwen-a02/server-poster.json
python deploy/qwen-a02/server.py check --config deploy/qwen-a02/server-poster.json
```

실제 전환은 기존 작업과 서버 종료 시점을 확인한 뒤 `serve --config deploy/qwen-a02/server-poster.json`으로 수행한다. 설정 파일 추가는 서버 재시작·가중치 다운로드·실모델 검증을 뜻하지 않는다. 이미지 인코더를 적재할 때의 GPU 메모리와 실제 이미지 추론은 전환 환경에서 확인해야 한다.

입력 화면에서 요구사항을 저장할 프로젝트를 선택한다. 직접 입력은 **검수 항목 확인하기**를 누르면 텍스트 원문 저장과 A02 추출을 거쳐 기준 검토 화면으로 이동한다. PDF는 분석 후 **PDF 검수 기준 확인하기**를 누른다. PDF 문구에 내용을 추가하거나 편집한 경우 두 동작을 구분한다.

- **원문 기준 승인하기**: 기존 PDF 실행에서 기준 보완·제외와 변경 사유·회신 출처를 기록하고 새 기준 버전을 승인한다.
- **입력문으로 새 기준 분석**: 입력란 전체를 별도의 텍스트 원문으로 저장해 다시 분석한다. 원래 PDF와 실행 이력은 보존하며, PDF 출처나 이전 승인을 새 입력에 자동으로 붙이지 않는다.

포스터와 기준 검토 영역에서 원문과 기대값을 확인해 기준 버전을 저장하고 승인한다. 보완이 필요한 항목이 있으면 승인이 차단된다. 담당자가 제외하기로 결정한 항목은 사유를 입력해 새 기준 버전에 기록한다. 포스터를 등록한 뒤 기준과 이미지를 확인하고 검수를 시작한다. 두 입력 경로 모두 A04·A05 → A06 → A07을 거친다.

결과 화면은 기존 front-v2의 항목 목록·포스터·상세 근거를 3열로 표시한다. **보고서·담당자 승인**을 누르면 A07 보고서와 수정 요청, 담당자 확인·승인 화면으로 전환된다. **기준 다시 확인하기**에서는 승인된 기준과 원문을 읽기 전용으로 확인한다. 결과 JSON 저장에는 화면 표시용 데이터가 아니라 원래 실행 결과를 담는다.

보고서에서 수정 요청을 승인하면 새 이미지를 자식 실행으로 접수할 수 있다. 자식도 같은 승인 기준으로 검수를 다시 시작해야 한다. 화면 주소의 실행 ID로 새로고침 후에도 결과 화면에서 보고서와 승인 상태를 다시 열 수 있다. 과거 `/api/reviews` 결과 조회는 유지하지만 새 검수는 그 경로로 접수하지 않는다.

`/api/framework/v1/health`의 `poster_review_ready`는 역할 설정과 저장소 준비 여부이며 `poster_review_blockers`에는 누락 사유 코드가 담긴다. 화면은 이 값을 확인해 미설정 상태의 검수 접수를 막고, 직접 입력에는 `free_text_registration`도 확인한다. 이 값은 worker 가동이나 모델 서버의 이미지 추론 성공을 보증하지 않는다. 실제 실행에서는 단계 기록과 오류도 확인한다.

브라우저 검사는 격리 PostgreSQL 17, 프런트 의존성, Playwright 브라우저가 필요하다. frontend에서 npm run build로 기본 화면을 빌드한다. 기존 db_integration 환경에서 FRAMEWORK_BROWSER_NODE에 Node 실행 파일, FRAMEWORK_BROWSER_CHANNEL에 chrome 또는 msedge를 지정한 뒤 다음 명령을 실행한다. 모델의 HTTP 응답만 시험용으로 대체한다.

```bash
python -m pytest -m db_integration tests/agent_framework/test_front_v2_poster_integration.py
```


API와 worker의 구성·공통 코드 revision은 같아야 한다. 코드/구성 변경 전에 접수한 job은 새 worker가 조용히 다른 설정으로 실행하지 않는다. 이전 코드를 유지해 처리하거나 새 입력을 접수하는 정책을 정한다. 승인된 원본 PDF 실행을 새 포스터 프로필로 재사용할 때는 역할 factory가 달라도 저장된 A02 단계·기준·PDF 해시를 재검증한다.

HTML은 Mac·Windows에서 상대 경로로 읽는다. Python 명령은 `uv run python` 형식을 쓸 수 있지만 파일 저장소는 POSIX 기반이며 **Windows 네이티브 백엔드 실행은 미검증**이다. Windows에서 `C:\...`로 경로만 바꾸면 저장소 호환이 보장된다고 설명하지 않는다.

```bash
uv run pytest tests/agent_framework -q
TEST_DB_ENV_FILE=/absolute/path/to/test-only.env uv run pytest tests/agent_framework -m db_integration -q
```

DB 테스트 설정은 [PostgreSQL 실행 가이드](에이전트_프레임워크_PostgreSQL_실행가이드.html)를 따른다. 테스트 전용 서버에서만 무작위 DB를 만들고 제거한다. 환경 파일의 암호는 Git에 올리지 않는다. CI의 PostgreSQL job도 이 전체 DB 테스트 묶음을 실행하도록 수정했으며 원격 CI 실행 결과는 아직 확인하지 않았다.

## 07. 시험 자료와 판정의 한계

[시험 포스터 12장](../poster-baselines/2026-11-03/workflow/poster-tests/index.html)은 새 SVG 코드로 만든 개발 자료다. 원본 전시·연주회·축제 포스터를 편집하지 않았다. 사례별 제목·날짜·필수 안내 3개 조건만 명시적으로 보완하고 다른 조건은 제외 사유를 기록한 **합성 승인 기준**을 사용한다. 원래 검토표 36개가 실제 승인됐다는 뜻이 아니다.

| 시험 | 독립 sidecar 관측 | 확인한 배선 결과 |
|---|---|---|
| 정상 | 제목·날짜·안내가 일치 | pass → 합성 최종 결정 저장 |
| 날짜 오류 | 2099-01-16, 기준은 2099-01-15 | 공급자가 pass를 주장해도 A06 fail, 일반 최종 승인 차단 |
| 안내 누락 | 명시적으로 확인한 부재 sentinel | fail, 일반 최종 승인 차단 |
| 수정본 | 정상 필드 + 구분 가능한 새 이미지 바이트 | 수정 요청 승인 → 새 실행 확인 → 전체 재검사 → pass |

sidecar는 실제 저장된 display 이미지 해시로 관측값을 찾으며 기대값을 복사하지 않는다. 하지만 테스트가 미리 설정한 값이며 OCR/모델 측정·실제 원본 포스터 정답·일반화 성능이 아니다. `synthetic=true` 계보를 승인·출처·근거·결과에 유지한다. 실제 사람 승인 0건, 실제 모델 호출 0회다.

무결성 실패, PDF 교체 후 대기 job 차단, CSRF·권한, 접수/수정본 중복, 완료 검사 재사용, 별도 worker 프로세스, 새 API 인스턴스 재조회를 함께 검증했다. 자세한 현재 수치는 [7단계 검증 기록](../poster-baselines/2026-11-03/workflow/07_검증기록.json)을 따른다.
