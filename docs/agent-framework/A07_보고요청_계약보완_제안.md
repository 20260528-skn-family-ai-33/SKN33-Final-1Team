# A07 보고 요청 계약 보완 제안

2026-11-03 · 제안(합의 전) · `feat/a07-reporter` · A07 담당 → 공통 기반 담당

## 01. 요약

보고 요청 `ReportRequest`에 **승인 조건(`criteria`)과 포스터 검사 관측(`inspection`)을 선택 필드로 추가**하자는 제안이다.

- 두 값은 실행 기록 `RunSnapshot`에 이미 있다. 보고 요청을 만들 때 넘기지 않을 뿐이다.
- 필드를 추가하기만 한다. 기존 필드, 판정 규칙, 다른 역할의 계약은 바뀌지 않는다.
- 새 필드는 비어 있어도 된다. 그래서 기존 fixture와 저장된 실행 기록을 그대로 읽을 수 있다.
- 바꿀 공통 코드는 네 곳이다: 계약 1곳, 경계 검사 1곳, 요청을 만드는 곳 2곳. 그리고 생성 산출물을 다시 만든다.

[README 계약 변경 규칙](README.md#계약-변경-규칙) 1번에 따라, 영향받는 역할·필드·예제·소비자를 적어 먼저 합의를 요청한다.

## 02. 지금의 문제

지금 A07이 받는 것은 문맥, A06 검증 결과(조건 ID·판정·사유 코드), 근거 묶음(문서 원문 인용)뿐이다. 공통 코드의 [`validate_report_request`](../../backend/agent_framework/validation.py#L138) 설명에도 같은 한계가 적혀 있다.

> ReportRequest lacks full criteria, required/optional flags and observations.

그래서 A07 보고서에 쓸 수 없는 정보는 다음과 같다.

| 쓸 수 없는 정보 | 있어야 하는 이유 |
|---|---|
| 기준값·비교 방식·단위 (`expected`, `operator`, `unit`) | 무엇과 비교했는지 보여 주기 |
| 필수·권장 (`required`) | 승인을 막는 항목과 참고 항목 구분하기 |
| 검사가 읽은 값 (`observed`) | "어떻게 다른지" 쓰기 |
| 포스터 위치 (`image.bbox`) | 고칠 곳 가리키기 |
| 검사 불확실성 사유 (`uncertainty`) | 확인 요청에 구체적인 이유 달기 |

팀 시험 데이터의 실제 값으로 비교하면 다음과 같다. 조건과 관측은 `checks/A06.fail.json`, 보고 요청은 `checks/A07.fail.json`에서 가져왔다.

**지금 A07 보고**
```text
수정 요청 [requirement-number] 포스터를 기준에 맞게 고쳐 주세요.
기준 원문: "포스터에는 딸기 3개가 표시되어야 합니다." 사유: 포스터에서 읽은 값이 기준과 다릅니다.
```

**제안대로 바뀐 뒤의 A07 보고**
```text
[불충족·필수] requirement-number
  조건: "포스터에는 딸기 3개가 표시되어야 합니다." (숫자 · 같음 · 기준값 3개)
  검사 모델이 읽은 값: "2" (포스터 가로 12%~78%, 세로 35%~82%)
  사유: 포스터에서 읽은 값이 기준과 다릅니다.
[통과·필수] requirement-text
  조건: "포스터에는 MORNING CUP 문구를 정확히 표시해야 합니다." (문구 · 같음 · 기준값 MORNING CUP)
  검사 모델이 읽은 값: "MORNING CUP" (포스터 가로 8%~88%, 세로 8%~24%)
```

## 03. 제안 변경

### 계약 ([contracts.py](../../backend/agent_framework/contracts.py#L175))

```python
class ReportRequest(RoleRequest):
    context: Context
    validated: ValidatedResult
    evidence: EvidenceBundle
    criteria: tuple[Criterion, ...] = ()           # 추가: 이번 실행의 승인 조건
    inspection: InspectionResult | None = None     # 추가: A04_A05 관측(모델의 주장)
```

### 요청을 만드는 곳

| 위치 | 바꿀 내용 |
|---|---|
| [runtime.py `_report`](../../backend/agent_framework/runtime.py#L363) | `criteria=_copy(record.snapshot.criteria.criteria)`, `inspection=_copy(record.snapshot.inspection)` 추가 |
| [durable_worker.py `stage_request`](../../backend/agent_framework/durable_worker.py#L30) | A07 분기에 `criteria=snapshot.criteria.criteria`, `inspection=snapshot.inspection` 추가 |

### 경계 검사 (`validate_report_request`에 추가)

새 필드가 있을 때만 검사한다. 오류 코드는 되도록 기존 코드를 다시 쓴다.

| 검사 | 오류 코드 |
|---|---|
| 조건 ID 집합이 검증 항목 ID 집합과 같은가 | `REPORT_CRITERIA_MISMATCH` (새 코드) |
| 조건 원문의 문서 버전·해시·중복 (기존 `_criteria` 재사용) | `CRITERION_DOCUMENT_MISMATCH`, `SOURCE_HASH_MISMATCH` 등 기존 코드 |
| 관측 문맥이 요청 문맥과 같은가 | `CONTEXT_MISMATCH` (기존) |
| 관측 조건 ID가 검증 항목 안에 있고 겹치지 않는가 | `UNKNOWN_OBSERVATION_CRITERION`, 중복 검사 (기존) |
| 관측 이미지 버전이 `context.asset_version_id`와 같은가 | `OBSERVATION_ASSET_MISMATCH` (기존) |

`validate_report`는 바꾸지 않는다. 판정 보존(`REPORT_CHANGED_VERDICT`)과 인용 규칙은 그대로다.

## 04. 호환성과 버전

- 새 필드에는 기본값이 있다. 그래서 기존 2.0.0 JSON(fixture, 저장된 단계 기록, 예제)을 그대로 읽을 수 있다.
- 모든 계약이 `extra="forbid"`라서, 옛 코드는 새 필드가 든 JSON을 거부한다. 같은 저장소에서 함께 갱신하므로 문제는 없다고 본다. 다만 저장소 밖에 고정된 소비자가 없는지는 공통 담당 확인이 필요하다.
- README 규칙 2는 필드 제거와 이름·의미·타입 변경만 호환되지 않는 변경으로 본다. 필드 추가는 호환되는 변경이다.
- 버전은 **2.0.0 유지**를 제안한다. 올리면 모든 fixture의 `contract_version`이 바뀌는 부담이 있기 때문이다. 최종 결정은 공통 담당이 한다.
- A07 팀 어댑터는 새 필드가 비어 있으면 지금 방식으로 보고한다.

## 06. 안전장치

- **관측값은 사실이 아니다.** 검사 모델이 읽은 값은 모델의 주장이다. 보고서에는 "검사 모델이 읽은 값"으로 적고, 판정은 A06 결과를 그대로 쓴다.
- **포스터 글자는 신뢰할 수 없는 데이터다.** 나중에 Qwen으로 문장을 다듬을 때 포스터에서 읽은 글자는 지시가 아니라 데이터로 넘긴다. 조건 ID·판정·원문 같은 사실 칸이 바뀌지 않았는지는 코드로 확인한다.
- **다른 포스터의 관측은 받지 않는다.** 관측 이미지 버전을 현재 산출물 버전과 대조한다.
- **과거 기록은 지금처럼 다룬다.** 과거 기록 근거를 현재 기준으로 쓰지 않는다.

## 08. 결정 요청 (공통 기반 담당)

1. `ReportRequest`에 `criteria`·`inspection` 선택 필드를 추가하는 방향에 동의하는가
2. 버전 표기: 2.0.0 유지, 또는 올림
3. 공통 코드 수정을 누가 하는가: 공통 담당이 직접 하거나, A07 담당이 PR을 올리고 공통 담당이 검토하거나
4. `inspection`을 통째로 넘기는가, 필요한 칸(조건 ID·`observed`·`bbox`·`uncertainty`)만 넘기는가
