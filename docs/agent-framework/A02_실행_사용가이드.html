1. 이 가이드에서 실행하는 것

기존 Qwen3.5-4B가 PDF의 검수 요구사항과 화면용 문단을 한 번에 생성한다. API는 원문·파일 버전·접수·조회를, worker는 모델 호출과 검증된 초안 저장을 맡는다. 결과는 기존 PostgreSQL에 저장하고 front-v2의 3. 검수 요구사항에 추가한다.

이번 실행 구성은 A02 추출과 화면 반영 확인용이다. 포스터 이미지는 비교할 자료로 화면에 준비한다. 이미지 업로드나 요구사항 표시만으로 A04·A05의 실제 포스터 검사, 사람의 기준 승인, 최종 승인이 완료된 것은 아니다. AWS 배포나 실행 자동화는 이 문서에서 수행하지 않는다.

기존 환경을 다시 켤 때는 아래 순서로 진행한다. 처음 준비하는 팀원은 3절의 설정·DB 준비부터 확인한다.

Uvicorn의 0.0.0.0:8012는 컨테이너 내부 안내다. PC에서는 http://127.0.0.1:8012로 연결한다. Docker 내부의 Qwen 주소는 실행기가 임시 설정에서 host.docker.internal:18015로 변환한다. 원본 JSON은 PC의 127.0.0.1:18015를 유지한다.

SSH 터널과 Qwen 서버는 서로 다른 프로세스다. SSH 터널 창을 다시 켜는 것은 모델을 다시 적재하는 작업이 아니다. ssh -N이 조용히 대기하는 것은 정상이며 Ctrl+C를 누르면 터널이 끊긴다.

3. 최초 준비와 기존 설정 재사용

필요 도구는 Docker Desktop의 Linux 엔진, Python 3.12 또는 3.13, Node.js와 npm, OpenSSH Client다. 프론트의 Node.js 조건은 ^20.19.0 또는 >=22.12.0이다. Windows에서는 Docker Desktop의 Linux 컨테이너와 본인의 SSH 키를 사용한다.

모든 PC 명령은 저장소 루트에서 실행한다. Mac의 현재 프로젝트 위치는 다음과 같다.

BASH
cd /Users/choejiheum/SK_AI/SKN33-Final-1Team

Windows PowerShell에서는 본인이 Git으로 받은 저장소 폴더에서 터미널을 연다. 개인 PC의 Mac 절대 경로를 붙여 넣지 않는다. 이후 PDF·이미지·설정 경로는 모두 저장소 상대 경로다.

다른 조원의 Windows PC에서 처음 실행할 때

이 문서의 Windows PowerShell 명령으로 같은 Linux 컨테이너 구성을 실행한다. 다만 작성자의 Mac 설정과 파일 저장소가 다른 PC에 자동 복제되는 것은 아니다. 최초 준비 후에는 본문의 같은 실행 순서를 따른다. Windows 실기기의 전체 실행은 아직 별도 검증 대상이다.

  1. 이번 A02 코드와 문서가 게시된 브랜치·커밋을 받는다. 작업 브랜치는 feat/37-a02-pdf-registration이며, A02·문단 연결·회원가입은 345d802에 커밋했다. main 통합의 기준·검증·기존 설정 처리 방법은 병합 검증 기록을 따른다. 로컬 병합 결과는 push 전까지 다른 PC에서 받을 수 없다.
  2. Docker Desktop의 Linux 엔진, Python 3.12, Node.js·npm, OpenSSH Client를 준비한다. 본인의 저장소 폴더에서 PowerShell을 연다.
  3. 본인의 SSH 공개 키를 RunPod 접속에 등록하고 개인 키는 본인 PC에 둔다. 기존 RunPod Qwen 서버가 실행 중이면 함께 사용하고 추가 서버를 켜지 않는다.
  4. 개발 DB 접속과 로그인 계정·프로젝트 권한을 준비한다. host.docker.internal은 그 Windows PC를 가리키므로 작성자 Mac의 DB를 자동으로 가리키지 않는다. 공용 DB를 쓴다면 담당자가 제공한 실제 접속 주소·app 계정을 사용한다.
  5. 아래 절차로 본인 app env와 presentation 설정을 만든다. 비밀 설정은 Git에 없으며, 새 설정에는 기존 RunPod 서버와 같은 Qwen 인증 키가 필요하다.
  6. 이미지 빌드 후 해당 PC의 새 PDF 볼륨을 한 번 초기화한다. 4절의 최초 초기화 명령을 따른다. 기존 저장소는 재초기화하지 않는다.

여러 PC가 같은 DB를 사용하는 경우

cc-framework-data는 각 Docker 엔진 안의 로컬 볼륨이다. 이름이 같아도 Mac과 Windows의 PDF 파일이 공유되지 않는다. 현재 worker는 같은 설정·런타임 해시의 DB 작업을 가져오며 PC별 파일 보유 여부로 큐를 나누지 않는다. 따라서 공용 DB에 각 PC의 API·worker를 동시에 연결하면 다른 PC가 등록한 PDF를 읽지 못할 수 있다.

각자 독립 실행할 때는 담당자가 준비한 별도의 개발 DB와 각 PC의 파일 볼륨을 사용한다. 공용 실행 환경을 사용하는 경우에는 원문 파일을 읽을 수 있는 공용 API·worker·저장소 구성을 마련해 그 서버를 이용한다. 이 문서의 로컬 실행 명령만으로 다중 PC의 공유 파일 저장소·작업 라우팅이 구성되지는 않는다.

PostgreSQL 로그인 계정기존 계정 또는 새 API의 로그인 화면에서 회원가입. 비밀번호는 문서·Git에 기록하지 않음

현재 사용 중인 Mac에는 두 presentation 복사본이 준비돼 있다. 기존 파일이 있으면 준비 명령을 반복하지 않고 재사용한다. .runtime의 비밀 파일은 Git으로 공유하지 않으며 팀원은 본인 접속 설정을 별도로 준비한다.

새 PC에 원본 app 설정이 아직 없다면 공통 실행기의 init-config로 새 파일을 만들고, 기존 개발 DB의 app 접속값과 별개의 CSRF·cursor 비밀을 채운다. worker의 A02_QWEN_API_KEY는 RunPod의 기존 VLLM_API_KEY와 같은 값을 사용한다. 키나 DB 비밀번호를 채팅·명령 인자·공유 문서에 넣지 않는다.

Mac, 원본 설정이 없을 때 한 번:

BASH
python3 scripts/framework_desktop.py init-config

Windows PowerShell, 원본 설정이 없을 때 한 번:

POWERSHELL
py -3.12 scripts/framework_desktop.py init-config

presentation 복사본을 처음 준비할 때는 프로젝트 패키지가 있는 Python 환경이 필요하다. 기존 개발자는 현재 .venv를 재사용한다. 새 팀원은 저장소 루트에서 uv sync --locked --group dev로 개발 환경을 준비하고 Mac·Windows 공통 실행 가이드를 따른다. 다른 이름의 가상환경을 선택했다면 아래 .venv 경로를 본인의 실행 파일로 바꾼다. 일반 framework_desktop.py 실행은 호스트 표준 Python으로 Docker를 호출한다.

Mac, 두 presentation 출력 파일이 모두 없을 때:

BASH
.venv/bin/python -m scripts.prepare_a02_presentation --env-file .runtime/framework-desktop.env --config deploy/qwen-a02/worker-config.presentation.example.json

Windows PowerShell, 두 presentation 출력 파일이 모두 없을 때:

POWERSHELL
.\.venv\Scripts\python.exe -m scripts.prepare_a02_presentation --env-file .runtime/framework-desktop.env --config deploy/qwen-a02/worker-config.presentation.example.json

공개 예시는 A02 전용 설정이다. 기존 팀 설정에 별도 역할 연결이 있으면 --config에 그 기존 Qwen 설정을 지정해 복사한다. 준비 도구는 출력 파일을 덮어쓰지 않는다. 출력 파일 한 개만 있거나 다른 설정을 준비하려면 별도 출력 이름을 정해 API·worker에 동일하게 지정한다.

새 DB의 계정·M008·AF004·저장소 준비는 Mac·Windows 공통 실행 가이드를 따른다. DB가 준비되지 않았다는 이유로 새 DB나 기존 볼륨을 지우지 않는다. 마이그레이션은 DB 전체 백업 후 별도 owner 설정으로 명시적으로 수행하고, API·worker에는 app 설정만 전달한다. 기존 환경에서는 초기화·마이그레이션을 매번 반복하지 않는다.

main 병합 뒤 기존 2.0.0 설정을 사용하는 경우

main의 새 계약은 3.0.0이다. 기존 2.0.0 설정·저장 실행은 자동 변환하거나 새 코드로 재개하지 않는다. 기존 개인 파일과 실행 기록은 보존한다. 새 공개 presentation 예시로 별도의 v3 설정 복사본을 만들고 새 PDF 추출을 접수한다. 이 작업에는 추가 DB 마이그레이션이 없다.

Mac, 두 v3 출력 파일이 없을 때:

BASH
.venv/bin/python -m scripts.prepare_a02_presentation --env-file .runtime/framework-desktop.env --config deploy/qwen-a02/worker-config.presentation.example.json --output-env .runtime/framework-desktop-presentation-v3.env --output-config .runtime/team_config.qwen-presentation-v3.json

Windows PowerShell, 두 v3 출력 파일이 없을 때:

POWERSHELL
.\.venv\Scripts\python.exe -m scripts.prepare_a02_presentation --env-file .runtime/framework-desktop.env --config deploy/qwen-a02/worker-config.presentation.example.json --output-env .runtime/framework-desktop-presentation-v3.env --output-config .runtime/team_config.qwen-presentation-v3.json

이 경우 아래 check·API·worker 명령의 env와 config를 각각 .runtime/framework-desktop-presentation-v3.env, .runtime/team_config.qwen-presentation-v3.json으로 바꿔 같은 쌍으로 실행한다. 기존 역할을 추가 연결한 사용자는 자기 역할 설정도 계약 3.0.0으로 명시적으로 준비한다. 원본 2.0.0 기록을 새 모델 실행이나 새 승인 기록으로 표시하지 않는다.

4. Docker 실행 확인과 이미지 빌드

Docker Desktop을 열고 엔진이 준비될 때까지 기다린다. 기존 PostgreSQL도 Docker 컨테이너로 사용 중이라면 Docker Desktop의 Containers에서 해당 기존 DB 컨테이너를 시작한다. 새 DB나 새 볼륨을 대신 만들지 않는다. 저장소 루트에서 확인한다.

BASH
docker version

Client와 Server 정보가 모두 나오면 다음으로 진행한다. Docker 연결 오류가 나오면 Desktop 실행·Linux 엔진 상태부터 확인한다.

Mac:

BASH
python3 scripts/framework_desktop.py doctor
python3 scripts/framework_desktop.py build

Windows PowerShell:

POWERSHELL
py -3.12 scripts/framework_desktop.py doctor
py -3.12 scripts/framework_desktop.py build

doctor의 정상 예시는 docker_engine=linux다. model_server_verified=false는 이 명령이 Qwen을 검사하지 않는다는 뜻이다. 모델 오류로 해석하지 않는다.

빌드 대상은 deploy/agent-framework/Dockerfile, 결과 태그는 creative-checker-framework:local이다. API·worker용 Python 의존성은 이미지 안에서 pyproject.toml·uv.lock으로 설치한다. 빌드가 오류 없이 종료돼야 다음으로 진행한다. 이 빌드는 GPU 모델 가중치를 설치하거나 DB를 초기화하지 않는다.

새 소스로 빌드해도 실행 중인 이전 컨테이너는 바뀌지 않는다. 기존 API·worker 실행 창이 있으면 각각 종료한 뒤 7·8절 명령으로 새 이미지를 실행한다. 입력을 처리 중이라면 해당 실행 상태를 먼저 확인한다.

새 PC의 새 PDF 저장 볼륨에만 이미지 빌드 후 한 번 초기화한다. 이번에 이미 사용한 Mac 볼륨에서는 이 단계를 건너뛴다.

Mac, 새 볼륨만:

BASH
python3 scripts/framework_desktop.py init-pdf

Windows PowerShell, 새 볼륨만:

POWERSHELL
py -3.12 scripts/framework_desktop.py init-pdf

정상 출력은 storage=framework_pdf, initialized=true다. 이미 초기화됐다는 오류가 나오면 기존 볼륨을 그대로 사용한다.

5. RunPod Qwen 서버 확인

이 절은 RunPod Jupyter Terminal 또는 RunPod에 SSH 접속한 Linux Bash에서 실행한다. PC의 Mac 터미널·Windows PowerShell과 실행 위치를 구분한다.

BASH
curl --noproxy '*' --connect-timeout 3 --max-time 10 -sS -o /dev/null -w 'HTTP %{http_code}\n' http://127.0.0.1:8015/health

HTTP 200이면 이미 실행 중이므로 서버를 추가 기동하지 않는다. 현재 모델은 Qwen/Qwen3.5-4B, 고정 revision은 851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a다. 이 A02 서버는 텍스트 전용이며 포스터 이미지 검수 모델 서버와 구분한다.

서버가 중지되어 있고 기존 코드·전용 가상환경·고정 모델 파일이 준비되어 있을 때만 아래를 실행한다. 원격 환경이 사라졌다면 Qwen 서버 준비 가이드의 설치·파일 검증부터 확인한다.

BASH
export A02_ROOT=/opt/creative-checker-a02
export A02_REPO="$A02_ROOT/repository"
export A02_PY="$A02_ROOT/runtime/venv/bin/python"
export VLLM_API_KEY="${VLLM_API_KEY:-${A02_SERVER_API_KEY:-}}"
if [ -z "$VLLM_API_KEY" ]; then
  read -r -s -p '기존 Qwen 서버 API 키: ' VLLM_API_KEY
  export VLLM_API_KEY
  printf '\n'
fi
"$A02_PY" "$A02_REPO/deploy/qwen-a02/server.py" serve

키 입력은 화면에 표시되지 않는다. worker에 설정한 기존 키와 같은 값을 사용하며 임의로 새 키를 생성하지 않는다. serve는 모델 해시·GPU 여유·포트 등을 검사한 뒤 전경에서 실행된다. Application startup complete가 나온 뒤 내부 health 200을 확인한다. GPU 여유 부족·포트 점유 오류가 나면 담당 서비스를 확인하며 다른 프로세스를 일괄 종료하지 않는다.

11. 크롬에서 실제로 사용하는 순서

  1. 검수 자료 입력 화면을 연다.
  2. PostgreSQL에 등록된 이메일·비밀번호로 로그인한다. 계정이 없으면 로그인 화면 아래 회원가입에서 이름·이메일·비밀번호·비밀번호 확인을 입력한다. 비밀번호는 기존 정책인 15~128자다. 가입 완료 후 로그인 화면으로 돌아오면 이메일·비밀번호로 로그인한다. 회원가입 API가 포함된 새 이미지를 빌드하고 API를 재시작해야 실제 가입이 가능하다.
  3. PDF를 저장할 프로젝트에서 쓰기 가능한 프로젝트를 선택한다. 이번 사용자는 A02 연결 확인 · 전시 포스터를 선택했다.
  4. 프로젝트가 없으면 위의 1. 프로젝트 이름 선택 입력란에 이름을 적고 위 이름으로 프로젝트 만들기를 누른다. 등록할 DB 프로젝트와 검수 화면의 이름 입력을 혼동하지 않는다.
  5. PDF 파일 추가로 10절의 제작의뢰서 PDF를 선택한다.
  6. 처리가 끝나면 3. 검수 요구사항에 항목별 문단과 PDF 원문 출처가 추가됐는지 확인한다. 기존에 입력한 문장은 유지된다.
  7. 왼쪽 2. 검수할 이미지 → 파일 선택으로 10절의 poster.jpg를 선택한다. 이미지가 보이는지 확인한다.
  8. PDF와 표시 문단을 대조한다. 값이 미정인 항목은 확인 필요로 검토하고 임의의 값으로 채우지 않는다.

회원가입은 기존 사용자 테이블에 Argon2 비밀번호 해시를 저장한다. 기존 프로젝트의 권한을 자동으로 부여하지 않으므로 자신의 프로젝트를 만들거나 해당 프로젝트 담당자에게 참여 권한을 받는다. 이메일 소유 확인·비밀번호 재설정은 이번 간단한 가입 기능에 포함하지 않는다. 별도 DB 마이그레이션은 필요하지 않다.

PDF의 표기 대상은 행사명·기간·장소 세 종류로 고정되지 않는다. 이 전시 의뢰서에는 전시명·연도·개막일·요일·장소·사진 콜라주·색상 구성·파일 형식·가로/세로·색상 모드가 있다. 확인했던 문단 예시는 다음과 같다. 모델 응답에 따라 항목명·순서·묶음이 달라질 수 있으므로 숫자만으로 완전성을 판단하지 않는다.

TEXT

이 A02 전용 실행의 완료 확인은 PDF 문단 반영과 이미지 준비까지다. 프론트의 기준 확인·검수 실행 버튼을 누른 사실을 PostgreSQL의 기준 승인 기록이나 A04·A05 실제 판정 완료로 기록하지 않는다. 후속 기준 보완·명시적 승인·승인 결과 재조회는 기준 보완·승인 가이드의 별도 흐름이다.

12. 진행률과 완료 기준

화면 표시의미
5%PDF 원문·버전 저장
15%·20%분석 접수·worker 대기
60%실행 상태 extracting, 검수 항목과 문단 정리 단계
95%저장된 결과·근거·표시 문단 조회
100%요구사항 입력란 반영 완료

진행률은 처리 단계 표시이며 페이지·토큰의 실제 완료 비율이 아니다. Qwen 응답을 기다리는 동안 60%에 머물 수 있다. 준비된 설정의 모델 응답 대기는 600초, 화면 요청 대기는 630초다. 오류나 결과 불명은 기록으로 남기며 성공으로 표시하지 않는다.

A02 완료 시 확인할 사항:

  • 프론트에서 요구사항 문단과 원문 출처를 확인할 수 있다.
  • API 실행 상태는 waiting_criteria다. 기준 검토 대기이며 자동 승인 상태가 아니다.
  • 새 설정의 모델 정책은 a02-semantic-v4다. requirements_presentation=true를 사용한다.
  • 원본 PDF·조건·미정 기록은 보존한다. 문서에 없는 필수 조건을 임의로 추가하지 않는다.
  • 표시 문단 수와 원본 조건 수는 다를 수 있다. 미정 안내 분리·동일 문단 묶음이 기준 제외를 뜻하지 않는다.

11/04 개발 환경에서는 프론트·프록시 health·Qwen 터널 200과 requirements_presentation=true를 확인했다. 사용자가 새 빌드·API·worker·프론트를 실행하고 PDF 완료를 알렸으며, 후속 화면에서 poster.jpg와 12개 기준을 확인했다. 이후 포스터 검수 실행 화면에서는 HTTP 500이 표시됐다. 이 관찰을 실제 포스터 모델 검사·기준 DB 승인·최종 승인·AWS 배포 완료로 확대하지 않는다.

창을 새로고침하거나 닫으면 입력 반영 대기가 끊길 수 있다. 화면 반영 취소는 이미 접수한 서버 실행을 삭제하지 않는다. 재시도 전 기존 실행 상태와 요청 키를 확인한다. 자세한 정책은 문단 연결 가이드를 따른다.

14. 다음 실행과 문서 관리

같은 환경을 다시 켤 때는 Docker·기존 DB → RunPod 서버 확인 → SSH → API → worker → 프론트 순서다. 코드가 바뀌면 이미지를 다시 빌드하고 API·worker를 재시작한다. 기존 설정·DB·PDF 볼륨을 재생성하지 않는다.

작업 완료 후 종료할 때는 프론트·worker·API·SSH 각 창에서 실행을 종료한다. 진행 중인 모델 호출이 있다면 완료 상태를 먼저 확인한다. PC 창의 종료가 RunPod 모델 서버 종료나 named volume 삭제를 뜻하지 않는다.

이 문서는 저장소에 포함된 MD와 오프라인 HTML로 공유한다. 실제 개인 env·쿠키·모델 키·DB dump·SSH 개인 키는 공유 대상이 아니다. 별도 ZIP은 생성하지 않는다.

HTML 재생성, 저장소 루트:

BASH
python3 -m scripts.build_a02_usage_guide
POWERSHELL
py -3.12 -m scripts.build_a02_usage_guide

명령·경로·HTML 구조는 문서 생성 시 검사한다. Windows 명령은 같은 Linux 컨테이너 실행기를 사용하지만 실제 Windows 장치의 전체 동작 확인과는 구분한다.
