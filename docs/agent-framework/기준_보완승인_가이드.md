# 기준 보완·승인·재조회

2026-11-03 · 6단계 · `feat/37-a02-pdf-registration`

## 01. 연결한 업무 흐름

**PDF-only A02 초안 → 보완·범위 검토 → 새 기준 버전 → 명시적 승인 → 포스터 대기 → 승인 기준 재조회**를 연결했다. A02 원본 초안·완료 단계·원본 PDF는 덮어쓰지 않는다. 보완과 제외 사유는 새 버전에 보존하고, 승인에는 대상 버전 ID와 정확한 해시를 기록한다.

새 PDF 전용 경로는 승인 후 `waiting_asset`이 된다. 포스터 참조를 만들거나 검수 worker를 자동 접수하지 않는다. 기존 PDF+포스터 실행·승인 경로는 유지하며, 기준 승인과 포스터 최종 승인을 구분한다.

검증은 기존 운영 DB와 분리한 PostgreSQL 17에서 **개발용 보완·승인 입력**으로 수행했다. 실제 클라이언트의 회신이나 사용자의 기준 승인으로 기록하지 않았다. 실제 Qwen 서버 호출은 여전히 0회다. 진행 신호 `1`은 기능 구현 지시이며 승인 API 요청이나 보완 답변이 아니다.

## 02. 원본과 사람의 보완 출처

기준 버전은 원래 A02 실행·PDF 버전·파일 해시·추출 초안 해시와 연결한다. 각 조건의 PDF `source`는 최초 원문 인용을 유지한다. 값을 보완하면 별도의 `value_source`에 다음을 저장한다.

- 제출자가 입력한 출처 설명 `reference`와 회신/확인 문장 `quote`
- 그 문장의 SHA-256과 서버가 만든 기록 ID
- 현재 로그인한 제출자 ID와 DB 시각
- `human_review` 또는 `synthetic_test` 목적, 계승한 `synthetic` 표시

보완값을 PDF에서 추출한 문구로 가장하지 않는다. 기대값과 지정 단위는 보완 인용문에 실제 문자로 포함되어야 한다. 다만 출처 설명과 회신 문장은 제출자가 제공한 진술이다. 서버가 이메일·메신저 원본을 가져오거나 실제 발주자의 신원을 독립적으로 확인한 증거가 아니다.

필요한 조건은 `amend`로 종류·연산자·기대값·단위·필수 여부를 정리한다. 검수 범위에서 제외할 때는 `exclude`와 사유·출처를 남긴다. 제외한 조건을 되살릴 때도 새 버전의 `amend`로 기록한다. 모든 조건을 제외한 빈 기준은 만들 수 없다. 제외 이력이 있으므로 검수 범위 축소를 숨기지 않는다.

모의 추출에서 출발한 기준이나 `synthetic_test` 보완은 이후에도 `synthetic=true`를 유지한다. 요청 목적을 `human_review`로 바꿔도 실모델·실제 발주 승인으로 바뀌지 않는다. 승인 근거 묶음에도 PDF 인용과 보완 출처를 함께 고정한다. PostgreSQL·Neo4j 관계 검색을 실행했다고 표시하지 않는다.

## 03. 저장소와 명시적 AF003 적용

기존 M008 사용자·프로젝트·세션·CSRF와 AF001 실행·단계·승인·이벤트 저장을 재사용한다. AF003은 같은 DB의 `agent_framework` 스키마에 다음 두 테이블을 추가한다.

| 테이블 | 역할 |
|---|---|
| `criteria_versions` | 변경 불가능한 기준 버전·부모·보완/제외 이력·본문 스냅샷·해시 |
| `criteria_approval_bindings` | 기존 AF001 승인 ID와 선택한 기준 버전·해시·고정 근거 묶음 연결 |

기존 public M008 및 AF001·AF002 SQL을 수정하지 않는다. 앱에는 새 테이블의 SELECT·INSERT만 허용하고, UPDATE/DELETE는 DB trigger로도 차단한다. 실제 승인자·승인 시각은 기존 `agent_framework.approvals`에 기록하며 별도 승인 원장을 중복으로 만들지 않는다.

API가 시작될 때 자동 마이그레이션하지 않는다. 기존 별도 owner/app 설정을 준비한 개발·검증 환경에서만 아래 명령을 명시적으로 실행한다. 이번 작업으로 운영 DB를 적용한 것은 아니다.

```bash
.venv/bin/python -m backend.agent_framework migrate-postgres --env-file .runtime/framework-owner.env --revision AF003
.venv/bin/python -m backend.agent_framework postgres-check --env-file .runtime/framework-app.env
.venv/bin/python -m backend.agent_framework postgres-serve --env-file .runtime/framework-app.env --config examples/agent_framework/team_config.pdf-mock.json --pdf-storage-root "$PWD/.runtime/framework-pdf" --port 8012
```

M008에 AF003을 처음 적용하면 AF001→AF002→AF003을 순서대로 추가한다. 이미 AF003이면 낮은 revision 요청으로 되돌리지 않는다. 기본 마이그레이션 대상은 이전 호환을 위해 AF001이므로 새 기능에는 `--revision AF003`을 명시한다. AF001/AF002 API는 기존 기능을 유지하고 새 기준 검토 경로는 503으로 비활성화한다.

PDF root는 [PDF 등록 가이드](PDF_등록_버전저장_가이드.html)대로 이미 초기화한 전용 경로를 사용한다. 등록·추출·기준 확정에 같은 app 계정을 사용하며 owner 파일을 API/worker에 넘기지 않는다. 실제 파일 저장 구현은 POSIX 기반이며 Windows 네이티브 백엔드 실행은 아직 미검증이다. HTML·문서 링크는 상대 경로로 열람할 수 있다.

## 04. 보완 버전 API

모든 경로는 `/api/framework/v1` 아래다. 기존 로그인 쿠키·CSRF·허용 Origin을 사용한다. 현재 쓰기 정책은 **해당 A02 실행 생성자이면서 활성 프로젝트 editor/owner인 사용자**다. 다른 사용자에게 승인을 위임하는 정책은 추가하지 않았다. 권한 있는 viewer는 조회할 수 있다.

| 경로 | 용도 |
|---|---|
| GET `/runs/{run_id}/criteria-review` | 첫 초안 해시, 최신 보완 버전과 해시, 승인 상태 |
| POST `/runs/{run_id}/criteria-versions` | 보완·제외를 새 불변 버전으로 저장 |
| GET `/runs/{run_id}/criteria-versions` | 과거 버전을 포함한 전체 이력 |
| GET `/runs/{run_id}/criteria-versions/{version_id}` | 특정 버전·해시·승인 차단 사유 조회 |

쓰기에는 `Idempotency-Key` UUID를 보존해 전송한다. 첫 버전은 `parent_version_id=null`, `expected_base_sha256`은 overview의 `source_draft_sha256`이다. 다음 버전은 최신 `criteria_version_id`와 응답의 `sha256`을 부모로 지정한다.

```json
{
  "parent_version_id": null,
  "expected_base_sha256": "<overview의 source_draft_sha256>",
  "purpose": "human_review",
  "edits": [
    {
      "criterion_id": "<보완할 조건 ID>",
      "action": "amend",
      "reason": "<확인한 내용과 변경 사유>",
      "source": {"reference": "<회신을 식별할 설명>", "quote": "<실제로 받은 확인 문장>"},
      "resolution": {"target": "poster_text", "field": "viewing_hours", "kind": "text", "operator": "contains", "expected": "<그 문장에 포함된 확인값>", "unit": null, "required": true}
    }
  ]
}
```

위 꺾쇠 내용은 형식 설명용 자리다. 실제 값을 대신 만들어 제출하지 않는다. 개발 시험에서는 `purpose=synthetic_test`와 명시적인 합성 회신을 사용한다. 제출자·시각·synthetic flag는 요청으로 지정할 수 없고 서버가 정한다. 요청 JSON은 기존 256KiB 제한·중복 키·스키마 검사를 재사용한다. 큰 수정은 새 부모 버전을 지정해 나눠 제출한다.

동일 키·동일 입력은 최초 버전을 반환한다. 같은 키에 다른 내용은 409다. 최신 부모나 해시가 다르면 409로 막아 동시 편집에서 기준이 분기되지 않게 한다. 원문 PDF의 같은 논리 문서에 새 파일 버전이 등록되면 이전 추출을 새로 보완·승인하지 못한다. 새 PDF 버전으로 A02를 다시 접수해야 한다.

`target`과 `field`는 함께 지정한다. 위 예시는 포스터에 적힌 관람시간이며, 다른 조건은 실제 검사 대상과 항목에 맞게 지정해야 한다. 두 필드를 생략하면 현재 버전의 분류를 유지하지만, `target=unspecified`인 조건은 기대값만 채워도 승인할 수 없다. 값만 보완하면 원문 인용과 추가 조건을 유지하며, 날짜·시각 요소·파일 정보 등은 A06의 지원 범위에 따라 확인 필요로 남을 수 있다.

2026-11-05부터 조건 자체가 바뀐 회신은 `resolution.replacement_text`에 전체 조건 문장을 넣는다. 이때 `target`·`field`도 명시해야 한다. 변경 문장 전체가 회신 `source.quote`에 포함되어야 하며, 기대값과 지정 단위도 변경 문장에 있어야 한다. 새 버전의 `text`를 바꾸고 이전 조건의 `qualifiers`를 해제하되, 원본 초안·PDF 인용·과거 버전은 보존한다. 새 문장에도 허용·예외·대안이 있으면 자동 통과시키지 않는다. 이미 승인한 기준은 수정할 수 없으므로 새 추출·보완·승인을 거친다.

front-v2의 **기준 보완**에서 검사 대상·항목, 보완값, 사유, 회신 출처·원문을 입력한 뒤 **검토한 기준 버전 저장**을 누른다. 저장된 보완 회신과 전체 기준을 확인하고 승인한다. 저장 전에는 이전 버전을 승인할 수 없으며, 저장 요청이 실패하면 입력 내용이 남는다.

조건 전체를 바꿀 때는 **회신에 따라 조건 자체를 변경**을 선택하고 **변경한 전체 조건**을 입력한다. A04·A05에는 현재 조건·기대값과 보완 회신·출처를 함께 전달하므로 원문의 “확인 중”과 확정값을 구분할 수 있다.

### 포스터 검수의 담당자 직접 확인

A06이 `review`로 남긴 날짜·파일 정보·납품·허용 범위·관측 불확실성은 현재 포스터를 직접 확인한 담당자가 판단과 근거를 기록할 수 있다. `POST /runs/{run_id}/approvals`의 기존 `approve_final`·`approve_changes`에 선택 필드 `human_reviews`를 추가한다. 각 기록은 다음 형태이며 승인 전체의 `reason`도 비어 있으면 안 된다.

```json
{
  "criterion_id": "<확인한 보류 조건 ID>",
  "verdict": "pass",
  "observed": "<현재 포스터에서 직접 확인한 내용>",
  "reference": "<확인한 위치·자료 출처>",
  "reason": "<충족 또는 불충족으로 판단한 이유>",
  "checked_asset": true
}
```

담당자 확인은 기계 판정·관측·보고서를 바꾸지 않는다. 필수 보류 항목을 모두 `pass`로 확인하고 확정 위반이 없어야 최종 승인할 수 있다. `fail`로 확인하면 수정 요청으로 연결한다. 확정 위반, 기준·기대값 누락, 근거 인용 오류, 불완전한 근거 묶음은 이 입력으로 우회할 수 없다. 미검사·판독 불가는 기존 결과를 통과시키는 대신 새로운 직접 확인 내용과 근거가 필요하다. 이전 포스터의 확인 기록은 수정본에 승계하지 않는다.

화면의 **담당자 직접 확인**에서 항목별 판단·확인 내용·위치·사유를 입력하고 현재 포스터를 확인했음을 표시한다. 기존 작성자·프로젝트 권한과 승인 원장을 재사용하며 승인자·DB 시각·실행·포스터 버전과 함께 저장한다. 새 SQL 마이그레이션은 필요 없다. 이 기록은 담당자의 진술이며 외부 자료의 진위를 서버가 독립적으로 증명한 것은 아니다.

A07의 선택적 문장 다듬기에 실패해도 규칙 기반 보고서와 승인 흐름은 유지한다. 보고서의 `polish_status=failed|outcome_unknown`과 안내 문구로 실패를 구분하며, 모델을 자동 재호출하지 않는다. A06 판정과 수정 요청의 근거는 그대로 남는다.

## 05. 명시적 기준 승인과 재조회

| 경로 | 용도 |
|---|---|
| POST `/runs/{run_id}/criteria-approvals` | 최신 버전 ID·해시와 검토 의사로 승인 |
| GET `/runs/{run_id}/criteria-approval` | 승인자·서버 시각·정확한 기준·보완 출처·근거 묶음 재조회 |
| GET `/runs/{run_id}/approvals` | 기존 승인 이력. 새 기록에도 승인 대상 버전·해시가 포함됨 |

```json
{
  "criteria_version_id": "<승인할 최신 기준 UUID>",
  "expected_sha256": "<그 기준 응답의 sha256>",
  "purpose": "human_review",
  "reason": "<원문과 보완 내용을 확인한 근거>",
  "reviewed_all_criteria": true
}
```

이 요청은 사용자의 실제 검토·승인 의사가 있을 때 보낸다. 일반 대화의 `1`이나 기능 실행 성공으로 자동 생성하지 않는다. 빈/공백 기대값, 수동/미지원 조건, 유효하지 않은 숫자가 하나라도 남으면 승인하지 않는다. 버전 응답의 `approval_blockers`를 확인한다. 제외한 범위와 대안·예외·허용치도 원문과 대조해야 하며, 서버의 문자열 검사가 의미 정확도나 범위 완전성을 보증하지는 않는다.

서버는 원본 PDF 무결성과 최신 문서 버전, 현재 계정·프로젝트 권한, 실행/설정, 최신 기준 ID·해시를 다시 확인한다. 승인 기록·대상 연결·근거 스냅샷·실행 상태는 하나의 트랜잭션으로 확정한다. 승인 뒤에는 `waiting_asset`이며 검수 job을 만들지 않는다.

`RunSnapshot.context`와 `criteria`는 최초 A02 실행의 고정 입력·원본 초안이다. 승인 대상은 `approved_criteria_version_id`를 통해 새 버전으로 조회한다. 승인 기록의 `approved_criteria_version_id`와 `criteria_sha256`에도 정확한 대상을 보존한다. `human_decision=unreviewed`는 포스터 최종 승인 상태이며 기준 승인과 다르다.

승인 후 기존 기준을 수정할 수 없다. 바꿀 내용은 새 A02 실행과 기준 승인으로 처리하고 이전 승인 이력은 보존한다. 같은 키와 같은 승인 요청은 기존 승인을 반환한다. 응답을 못 받았으면 새 키로 반복 승인하지 말고 기존 키·대상·해시를 유지해 조회/재전송한다. DB 결과가 불명확하면 503을 반환하며 자동 쓰기 재시도를 하지 않는다.

새 무작위 테스트 DB에서 M008→AF003 직접 적용, AF002→AF003 반복 적용, 보완 버전과 출처 저장, 샘플 3종의 개발용 승인과 새 API 인스턴스 재조회, 경쟁 요청, 오래된 버전·변조 PDF·권한 거부, 저장 중단의 rollback, commit 응답 불명 뒤 중복 없는 재전송을 확인했다. 기존 A02·PDF 등록·검수·worker 흐름도 함께 시험했다.

테스트는 한 개의 개발용 조건을 보완하고 나머지 조건의 제외 사유를 명시하는 사례를 포함한다. 실제 포스터의 전체 조건이나 원래 검토표 36개가 승인됐다는 뜻이 아니다. 원본 의뢰서의 관람시간·관람연령·우천 안내 3건은 실제 답변을 받지 않았으며 사람의 기준 승인은 여전히 미완료다. 운영 DB·Qwen 서버·front-v2·원격 CI·실제 Windows 실행은 이 검증 범위가 아니다.

공통 담당 연결 파일은 `criteria_contracts.py`, `criteria_review.py`, `AF003.sql`, `postgres_schema.py`, `postgres_api.py`다. `contracts.py`의 선택적 `value_source`와 승인 대상 필드는 값이 없을 때 기존 JSON에 null 필드를 추가하지 않는다. 공통 최신 JSON Schema를 함께 사용한다.

후속 7단계는 [포스터 검수·재검수 가이드](포스터_검수재검수_가이드.html)에서 이어진다. 승인 기준 버전·해시·원문과 보완 출처를 기존 저장 포스터와 별도 실행에 고정하고 새 입력 확인 후 검수한다. 6단계 자체는 포스터 대기까지이며, 7단계의 합성 관측/승인 시험도 실모델 품질·실제 사람의 결정을 증명하지 않는다.
