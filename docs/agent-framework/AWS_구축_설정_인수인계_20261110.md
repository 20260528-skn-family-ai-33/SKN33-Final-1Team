# Creative Checker AWS 구축 설정 인수인계

작성일: 2026-11-10 · 대상: AWS와 RunPod 환경을 이어받는 팀원

EC2 접속부터 EFS 공유 저장소, PDF·포스터 모델, 영상 워커 2개, 프론트 자동 배포와 장애 복구까지 설정 순서대로 설명한다. 서버 구성값은 11/09 적용 기록, 사이트·GitHub 확인은 11/10 08:58 기록을 기준으로 한다. 주소와 실행 버전은 작업 직전에 다시 확인한다.

**이미 운영 중인 환경을 이어받는 경우에는 각 단계의 확인 명령부터 실행한다.** 새 리소스 생성·DB 마이그레이션·모델 설치·저장소 초기화를 반복하지 않는다. 새 서버를 만드는 경우에는 해당 단계의 설정 절차를 수행한다. 기존 업로드·DB·모델·환경 파일과 11/06 문서는 보존한다.

## 3. EC2와 네트워크 설정

새 환경은 같은 VPC에 API·worker·Neo4j를 구성한다. 11/09 구성은 Ubuntu 24.04, API t3.medium, worker t3.large, Neo4j t3.medium이다. 기존 환경을 이어받는 경우 새 인스턴스를 만들지 않고 상태와 용도를 먼저 확인한다.

| 대상 인바운드 | 포트 | 허용할 출처 |
|---|---|---|
| 관리 SSH | TCP 22 | 담당자의 고정 IP 또는 승인된 관리 접근 경로 |
| API HTTPS | TCP 443 | 현재 CloudFront 원본 접근 정책에 맞는 출처 |
| RDS | TCP 5432 | API·worker 등 실제 DB 사용 서비스의 보안 그룹 |
| Neo4j Bolt | TCP 7687 | 실제 그래프를 사용하는 API·worker 보안 그룹 |
| EFS mount target | TCP 2049 | API·worker 보안 그룹 |

API 서비스 포트 8012·8013·8016·8018과 터널 포트 18015·18791·18792는 인터넷에 직접 게시하지 않는다. DB·Neo4j·GPU 워커도 공개 접속 대상으로 만들지 않는다. 보안 그룹 출처와 HTTPS 원본의 비밀 헤더 검사를 함께 유지한다.

**각 EC2에서:**

```bash
sudo docker --version
sudo docker compose version
sudo docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
df -h
free -h
```

Docker가 없는 새 Ubuntu에는 [Docker 공식 Ubuntu 설치 절차](https://docs.docker.com/engine/install/ubuntu/)로 Engine과 Compose 플러그인을 설치한다. 기존 서버에서는 설치·업그레이드보다 현재 버전과 실행 컨테이너부터 확인한다.

## 5. RDS와 Neo4j 연결

### 5.1 기존 RDS 확인

앱은 `creative_checker_app`, 명시적 스키마 변경은 별도 owner 계정을 사용한다. DB TLS는 `sslmode=verify-full`과 RDS CA를 사용한다. 기존 운영 DB에는 M008과 AF001–AF005가 적용된 상태이므로 11/06 문서의 빈 DB 초기화 순서를 다시 실행하지 않는다.

**API EC2에서 기존 컨테이너를 이용한 읽기 전용 검사:**

```bash
sudo docker exec creative-checker-framework-main-ca7f01c \
  /app/.venv/bin/python -m backend.agent_framework postgres-check \
  --env-file /run/api.env
```

정상 기준은 DB 접속·기존 M008·프레임워크 revision 준비 검사 통과다. 실패하면 DB 호스트, 보안 그룹, 앱 계정, CA 마운트와 권한을 확인한다. 새 DB인 경우에는 DB 백업·대상·owner 권한을 확인하고 저장소의 PostgreSQL 실행가이드에 따라 M008 이후 AF migration을 적용한다. 실행 결과가 불명확하면 현재 revision을 조회한 뒤 이어간다.

### 5.2 Neo4j와 동기화 확인

**Neo4j EC2:**

```bash
sudo docker compose -f /home/ubuntu/creative-checker-neo4j/compose.yaml ps
```

기존 named volume `cc-aws-neo4j-data`와 인증 파일은 유지한다. API·worker 설정에서 Bolt 주소가 `172.31.1.222:7687`인지 확인하고, graph용 환경으로 인증 질의·`graph-check`를 수행한다. projector의 outbox 처리와 동기화 지연도 확인한다. TCP 연결 성공만으로 RAG가 준비됐다고 판단하지 않는다. `graph-init`·재구축은 상태 조회 명령이 아니므로 일상 점검에 사용하지 않는다.

## 6. EFS 공유 저장소 설정

### 6.1 마운트 준비

AWS 콘솔의 EFS에서 `fs-0f05f47f8a4bd01db`를 확인한다. API가 있는 AZ와 worker가 있는 AZ에 mount target을 두고, EFS 보안 그룹의 2049 출처를 두 EC2의 보안 그룹으로 지정한다.

**API EC2와 worker EC2에서 각각:**

```bash
command -v mount.efs
findmnt -M /mnt/creative-checker-efs
```

새 Ubuntu에 mount helper가 없으면 [AWS EFS 클라이언트 설치 안내](https://docs.aws.amazon.com/efs/latest/ug/installing-amazon-efs-utils.html)에 따라 `amazon-efs-utils`를 설치한다. TLS 연결에는 EFS mount helper를 사용한다. [AWS 마운트 절차](https://docs.aws.amazon.com/efs/latest/ug/mounting-fs-mount-helper-ec2-linux.html)

**신규 호스트에서만**, 해당 경로를 사용하는 컨테이너가 없고 마운트 지점 아래에 보존할 로컬 파일이 없는지 확인한 후:

```bash
sudo install -d /mnt/creative-checker-efs
sudo mount -t efs -o tls fs-0f05f47f8a4bd01db:/ /mnt/creative-checker-efs
findmnt -M /mnt/creative-checker-efs
```

이미 마운트돼 있으면 반복 실행하지 않는다. 다른 EFS를 사용한 새 환경에서는 ID를 교체하고 양 서버가 같은 파일 시스템을 가리키는지 확인한다.

### 6.2 자동 마운트와 데이터 경로

기존 `/etc/fstab`을 백업한 후 **같은 항목이 없을 때만** 아래 내용을 추가한다. EFS ID와 경로가 기존 운영값인지 다시 확인한다.

```fstab
fs-0f05f47f8a4bd01db:/ /mnt/creative-checker-efs efs _netdev,noresvport,tls,nofail 0 0
```

`_netdev`는 네트워크 준비 이후 마운트를 지시한다. `nofail`은 EFS 실패 시에도 OS 부팅을 허용하므로 앱 기동까지 안전하게 막아주지는 않는다. [AWS 자동 마운트 안내](https://docs.aws.amazon.com/efs/latest/ug/mount-fs-auto-mount-update-fstab.html)

서비스 시작 전에는 다음처럼 마운트와 파일 시스템 종류를 확인한다.

```bash
mountpoint -q /mnt/creative-checker-efs && \
test "$(findmnt -n -o FSTYPE -M /mnt/creative-checker-efs)" = nfs4
```

실패하면 API·worker·영상 API를 시작하지 않는다. 부팅 자동화에도 동일한 검사와 마운트 의존성이 필요하다. Docker의 자동 재시작만으로 이 순서를 보장하지 못하므로 재부팅·미마운트 복구는 별도 시험 대상으로 남아 있다.

| 호스트 경로 | 컨테이너 경로 | 내용 |
|---|---|---|
| `/mnt/creative-checker-efs/service-storage/pdf` | `/data/pdf` | PDF 원본·버전·마커 |
| `/mnt/creative-checker-efs/service-storage/poster` | `/data/poster` | 포스터 원본·버전·마커 |
| `/mnt/creative-checker-efs/video-aws-test` | `/video-data` | main·test 공용 영상·결과 |

**양 EC2에서 확인:**

```bash
sudo stat -c '%u:%g %a %n' \
  /mnt/creative-checker-efs/service-storage \
  /mnt/creative-checker-efs/service-storage/pdf \
  /mnt/creative-checker-efs/service-storage/poster
```

포스터 루트는 UID 10001, 권한 700을 기준으로 확인한다. 기존 경로에는 이미 저장소 마커가 있으므로 `init-pdf-storage`, 포스터 `storage init`, 폴더 삭제를 다시 하지 않는다. 완전히 새 저장소는 새 경로에 한 번 초기화한 뒤 API와 worker에 같은 경로를 연결한다.

완료 기준은 양 서버에서 동일 테스트 파일의 해시가 같고, 앱 UID로 읽기·쓰기가 가능하며, 짧은 동시 접근 시 잠금·저장 결과가 정상인 것이다. 11/09 짧은 EFS 시험과 PDF 해시 대조는 통과했지만 장기 부하·장애 복구까지 검증한 것은 아니다.

### 8.1 API 연결

**Python 환경이 없는 새 Pod에서만** 인계한 코드와 CUDA 12.8 PyTorch 기본 환경을 확인한 뒤 아래 순서로 설치한다. 기존 환경은 지우지 않는다.

```bash
export UV_CACHE_DIR="$cc_video_root/uv-cache"

각 명령이 성공한 뒤 다음 명령을 실행한다. `uv`와 Python 3.12가 필요하며 worker 의존성은 검증된 `torch==2.8.0+cu128`, `torchvision==0.23.0+cu128` 환경을 전제로 한다. `/workspace` 캐시에서 권한 오류가 났던 환경은 위처럼 전용 `/opt` 캐시를 사용했다.

두 워커와 AWS API가 **동일한 기존 worker token**을 읽도록 안전하게 전달한다. worker token을 새로 만들었다면 AWS 쪽도 함께 갱신해야 한다. 영상 토큰과 포스터 Qwen 인증키는 서로 다른 용도다.

**영상 Pod에서 아래 환경을 준비한다.** `set -x`를 켜지 않고 토큰 값을 출력하지 않는다.

export VIDEO_OCR_PYTHON="$cc_video_root/paddle-gpu-venv/bin/python"
export VIDEO_OCR_DEVICE=gpu
```

기존에 8791·8792가 열려 있으면 새 프로세스를 띄우지 않는다. 유휴 상태에서 복구할 때는 **워커별 Terminal 또는 tmux 세션**에서 같은 환경을 준비한 뒤 다음 명령을 각각 실행한다.

```bash
# 첫 번째 세션
"$cc_video_root/worker-venv/bin/python" -m uvicorn \
  backend.app.video_logo_worker:app --host 127.0.0.1 --port 8791
```

```bash
# 두 번째 세션
"$cc_video_root/worker-venv/bin/python" -m uvicorn \
  backend.app.video_logo_worker:app --host 127.0.0.1 --port 8792
```

셸 세션마다 위 변수와 작업 디렉터리를 설정한다. 로그를 저장할 때는 워커별 파일을 분리한다. 수동 Terminal 프로세스는 세션 종료 시 중단될 수 있으므로 기존 프로세스 관리 방식과 로그 경로를 인계받아 유지한다. Pod 재생성 후 자동 복구는 별도 설정·시험이 필요하다.

토큰 환경이 준비된 세 번째 Terminal에서 인증 health를 확인한다.

```bash
python3 - <<'PY'
import json, os, urllib.request
token = os.environ['VIDEO_LOGO_WORKER_TOKEN']
for port in (8791, 8792):
    req = urllib.request.Request(f'http://127.0.0.1:{port}/health',
                                 headers={'X-Worker-Token': token})
    with urllib.request.urlopen(req, timeout=10) as response:
        result = json.load(response)
    print(port, {k: result.get(k) for k in ('ready', 'busy', 'detail')})
PY
```

준비 완료의 기본값은 두 워커 모두 `ready=true`, 유휴 상태 `busy=0`이다. 이어서 실제 프레임 OCR과 로고 처리를 검증한다. A40 한 장에 프로세스가 두 개이므로 다른 vLLM 프로세스가 VRAM을 차지하면 OOM이 날 수 있다. 다른 팀원의 모델을 임의로 종료하지 않는다.

## 10. 영상 터널과 AWS API 연결

### 10.1 두 터널 연결

**API EC2**가 영상 RunPod로 터널을 연다. 포스터 터널은 worker EC2에 있으므로 위치를 혼동하지 않는다.

| API EC2 수신 | 영상 Pod 목적지 | systemd 서비스 |
|---|---|---|
| `127.0.0.1:18791` | `127.0.0.1:8791` | `creative-checker-video-test-tunnel.service` |
| `127.0.0.1:18792` | `127.0.0.1:8792` | `creative-checker-video-test-tunnel-2.service` |

```bash
systemctl is-active creative-checker-video-test-tunnel.service \
  creative-checker-video-test-tunnel-2.service
systemctl is-enabled creative-checker-video-test-tunnel.service \
  creative-checker-video-test-tunnel-2.service
ss -ltn
```

정상 기준은 두 서비스 active·enabled와 두 loopback 포트 수신이다. 새 호스트는 인계된 unit의 사용자·키·known_hosts 경로를 맞추고 `ssh -N -T`, `ExitOnForwardFailure=yes`, `ServerAliveInterval=30`, `ServerAliveCountMax=3`, `StrictHostKeyChecking=yes`를 유지한다. 두 번째 터널은 로컬 포트와 원격 목적지 포트를 모두 바꾼다. unit 변경 후 `daemon-reload`, 대상 unit 재시작, `enable`과 연결 확인 순서로 진행한다.

### 10.2 영상 API 설정

영상 API 컨테이너는 `creative-checker-video-aws-test`, host port 8013이며 현재 main·test 공용이다. 기존 서비스 환경에 다음 값을 반영한다.

```dotenv
VIDEO_LOGO_WORKER_URL=http://127.0.0.1:18791
VIDEO_LOGO_WORKER_SECONDARY_URL=http://127.0.0.1:18792
VIDEO_MAX_ACTIVE=2
```

`AUTH_ALLOWED_HOSTS`, `AUTH_ALLOWED_ORIGINS`에는 main·test의 정확한 도메인·HTTPS Origin을 넣고 wildcard로 넓히지 않는다. API의 기존 로그인·CSRF·프로젝트 권한 검사는 유지한다. 영상 저장소는 EFS `video-aws-test`를 `/video-data`에 마운트한다.

컨테이너 내부 진입점은 `scripts.framework_video`이며 실행 옵션은 다음 형태다.

```text
--aws-test --env-file /run/api.env --port 8013
--storage-root /video-data --worker-token-file /run/video-worker-token
```

`--aws-test`는 기존 보안·저장소 실행 모드의 이름이며 현재 main에서도 같은 API를 사용한다. API는 한 프로세스만 실행한다. 같은 EFS의 `.service.lock`을 사용하는 API를 두 개 띄워 동시 한도를 늘리지 않는다. 두 워커 설정과 `VIDEO_MAX_ACTIVE=2`를 함께 적용해야 한다.

이미지 빌드는 `deploy/agent-framework/Dockerfile.video-aws-test`를 사용한다. 기본 이미지 `creative-checker-migration:f819ce1`에 의존하므로 새 호스트에는 호환 런타임 이미지도 먼저 전달해야 한다. 코드만 복제하면 이 로컬 이미지가 자동 생성되지 않는다. 새 이미지에서 앱 패키지와 FFmpeg 실행을 확인한 후 교체한다.

교체 순서는 **신규 POST 접수 제한 → OCR·후보·정밀 대조 유휴 확인 → 설정·이미지·JSON 해시 백업 → 이전 API 정지·보관 → 새 API 하나 기동 → 두 슬롯 ready 확인 → 접수 재개**다. GET 결과 조회와 기존 파일을 보존하고, 이전 API가 아직 저장소를 사용 중일 때 새 API를 함께 띄우지 않는다.

## 11. CloudFront와 HTTPS 경로 설정

### 11.1 원본과 API 경로

CloudFront 기본 원본은 각 사이트의 비공개 S3다. S3 Block Public Access와 OAC를 유지한다. API 원본은 HTTPS로 `api.kimqq.site`에 연결하고, 원본 검증용 비밀 헤더는 기존 값을 인계받아 유지한다.

| 경로 | 처리 대상 |
|---|---|
| `/api/video-reviews`, `/api/video-reviews/*` | 영상 API 8013 |
| `/api/video-logos`, `/api/video-logos/*` | 영상 API 8013 |
| `/api/poster-logos`, `/api/poster-logos/*` | 영상 API 8013 |
| `/api/framework/v1/` 아래 | Nginx의 사이트 구분에 따라 main 8018 / test 8016 |
| 나머지 `/api/*` | 기존 일반 API·인증 8012 |
| 기본 동작 | 각 S3의 프론트 파일 |

표의 8013 경로 6개를 포괄적인 `/api/*`보다 앞에 배치한다. API 캐시를 끄고 로그인 쿠키, CSRF 헤더, `Idempotency-Key`, 필요한 query와 영상 재생 Range 요청을 전달한다. Origin/Host는 현재 원본 전달 정책과 Nginx의 신뢰 경계에 맞추며 클라이언트가 보낸 임의 헤더로 사이트를 선택하게 만들지 않는다.

Nginx는 `/api/framework/v1/`만 사이트별 포스터 포트로 연결한다. [8013 Nginx 설정](../../deploy/agent-framework/aws-video-routes.conf)의 요청 상한은 `1150m`이며, [영상 서비스 환경 설정 예시](../../deploy/agent-framework/video.aws-test.env.example)는 180초·1GiB·두 작업 슬롯과 PaddleOCR을 지정한다. 두 파일은 로컬 조치 브랜치의 반영 후보이며 실제 서비스의 값은 배포 후 인증된 상태 API에서 확인한다. 설정을 반영할 때는 `sudo nginx -t` 성공을 확인한 다음 reload한다.

### 11.2 새로고침 처리

저장소의 `deploy/agent-framework/aws-test-spa-rewrite.js`를 기준으로 test `aws-test-spa-rewrite`, main `main-spa-rewrite` Function을 사용한다. 콘솔에서 코드를 저장·시험하고 LIVE로 게시한 뒤 **기본 동작의 viewer-request에만** 연결한다. [CloudFront viewer-request URL 변경 예제](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/example_cloudfront_functions_url_rewrite_single_page_apps_section.html)

로컬 조치 브랜치의 코드는 GET/HEAD의 `/login`, `/review/new`, `/review/tasks`, `/review/logo`, `/video`, `/video/logo`, `/modeltest`를 `/index.html`로 변경한다. query string은 유지한다. API·정적 파일·POST는 변경하지 않는다. 최신 프론트에서는 모델 테스트 화면이 제거됐으므로 해당 경로의 HTML 응답과 기능 제공 여부는 별개다.

새 페이지 경로를 추가하면 Function allowlist도 별도 갱신한다. 전체 403·404를 index.html로 바꾸면 인증·API 오류가 숨겨질 수 있으므로 적용하지 않는다. 배포 상태 Deployed와 필요한 캐시 무효화 완료 후 아래를 직접 확인한다.

```bash
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://d3navmtcjn23y2.cloudfront.net/review/tasks
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://d2fu4nse4xovsn.cloudfront.net/video
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://d3navmtcjn23y2.cloudfront.net/api/video-reviews/status
```

화면 경로는 200 HTML, 비로그인 영상 API는 401 JSON이 정상이다. 없는 JS 파일의 403은 화면 새로고침 오류와 구분한다. API 내부 직접 조회에는 실제 설정에 맞는 Host와 `X-Forwarded-Proto: https`가 필요하다.

## 12. GitHub Actions 자동 배포 설정

### 12.1 역할과 저장소 변수

1. IAM에서 `token.actions.githubusercontent.com` OIDC 공급자를 조회하고 audience `sts.amazonaws.com`을 확인한다. 기존 공급자가 있으면 재사용한다.
2. main·AWS_TEST용 배포 역할을 각각 만든다. 신뢰 정책은 해당 저장소·브랜치의 정확한 `sub`로 제한한다.
3. 역할 권한은 대상 프론트 S3 업로드·목록·multipart 취소와 해당 CloudFront 설정 조회·무효화로 제한한다.
4. GitHub Settings → Secrets and variables → Actions → **Variables**에 아래 역할 ARN을 등록한다.

| 브랜치 | 역할 | 변수 | S3 / CloudFront |
|---|---|---|---|
| AWS_TEST | `CreativeCheckerAwsTestFrontendDeploy` | `AWS_TEST_DEPLOY_ROLE_ARN` | `creative-checker-frontend-test-20261108-jh` / `ESI2WHFLU88QT` |
| main | `CreativeCheckerMainFrontendDeploy` | `AWS_MAIN_DEPLOY_ROLE_ARN` | `creative-checker-frontend-20261106-jh` / `E1LYR5RFZBQOT8` |

이 저장소에서 확인한 AWS_TEST subject는 다음과 같다. 다른 저장소를 새로 만들면 ID를 그대로 재사용하지 않는다.

```text
repo:20260528-skn-family-ai-33@288865373/SKN33-Final-1Team@1391545254:ref:refs/heads/AWS_TEST
```

main 역할은 마지막 브랜치가 `main`인 subject를 사용한다. 상세 정책 JSON은 저장소의 `docs/AWS_TEST_프론트_CI_CD.md`를 따른다. OIDC 목록 조회가 비어도 생성 시 `EntityAlreadyExists`라면 계정·profile·공급자 단건 조회를 확인한다. AttachedPolicies가 비어 있는 것과 inline 권한 정책이 없는 것은 다르다.

### 12.2 배포 실행과 확인

`AWS_TEST` push는 `aws-test-frontend.yml`, main push는 `aws-main-frontend.yml`을 실행한다. 흐름은 `npm ci → npm test → npm run build → S3 업로드 → /와 /index.html 무효화 요청`이며 `VITE_API_PROFILE=legacy`로 빌드한다.

**Mac 또는 관리용 CLI에서 읽기 전용 확인:**

```bash
gh run list --repo 20260528-skn-family-ai-33/SKN33-Final-1Team \
  --workflow aws-test-frontend.yml --limit 3
gh run list --repo 20260528-skn-family-ai-33/SKN33-Final-1Team \
  --workflow aws-main-frontend.yml --limit 3
```

대상 커밋의 **build와 deploy 둘 다** 성공했는지 확인한다. test 역할 변수가 없으면 deploy가 건너뛰어지고 main 역할 변수가 없으면 실패한다. 브라우저 새로고침은 배포 작업을 실행하지 않는다. Actions 이후 캐시 전파·실제 화면을 확인한다.

프론트 자동 배포는 API·worker 이미지, RunPod 프로세스, Nginx, CloudFront Function을 갱신하지 않는다. backend 변경은 8·10절의 별도 배포 절차가 필요하다. 11/10 08:58에는 PR #77이 미병합이었으며, 이후 main 병합 여부는 GitHub에서 다시 확인한다.

## 13. 설치 후 실제 검수 확인

health와 포트 확인 뒤 아래 순서로 서비스 동작을 확인한다. 자료는 기존 자료와 구분되는 테스트 프로젝트에 넣고, 승인·제외·최종 판단은 담당자가 결정한다.

1. **로그인:** main·test 각각 로그인, 로그아웃, CSRF 유지와 다른 계정의 결과 접근 차단을 확인한다.
2. **PDF:** 지정한 PDF를 올리고 대기→추출→기준 확인 전환, 원문·기대값·미정 항목을 확인한다.
3. **포스터:** 담당자가 기준을 검토·승인한 다음 포스터를 등록한다. 검사→보고서→담당자 확인까지 연결되는지 본다. 미정 항목을 임의로 통과시키지 않는다.
4. **영상 한 건:** 짧은 MP4와 자막 기준으로 GPU OCR, 결과·근거 프레임·재생을 확인한다.
5. **로고:** 원본 로고 업로드→후보 찾기→위치 확정→정밀 대조를 별도로 확인한다. 영상의 완료 표시만으로 로고 완료를 판정하지 않는다.
6. **영상 두 건:** 각기 다른 영상·로고를 동시에 접수한다. `worker_slot`, OCR `runtime.device`, 각 단계 결과와 실제 처리 시간 중첩을 확인한다.
7. **작업 관리:** 자기 종료 이력 숨김·복원을 확인한다. 대기 취소는 워커가 가져가기 전 자기 작업만 가능하며 처리 중이면 거절돼야 한다.

11/09에는 전시 PDF→12개 기준 승인→포스터 보고서, 짧은 PDF 병렬·EFS 동시 접근, 7초 1080p 영상 두 건의 OCR·로고 대조가 확인됐다. 포스터 결과는 확인 필요 12개였으며 최종 담당자 승인은 하지 않았다. main 준비 반영 이후의 새 실모델 전체 흐름, 긴 영상 부하, 포스터·영상 교차 동시 완료와 재부팅 복구는 후속 확인 대상이다.

## 14. 재시작과 장애 복구

### 14.1 서버 재시작 후 순서

1. RDS와 Neo4j 상태, EC2 주소·DNS를 확인한다.
2. API·worker EC2의 EFS 마운트와 저장 루트·권한을 확인한다.
3. 각 RunPod의 모델·worker와 인증 health를 확인한다.
4. worker EC2의 Qwen 터널, API EC2의 영상 터널 2개를 확인한다.
5. API·worker의 이미지와 digest를 확인하고 해당 배포 구성으로 기동한다.
6. CloudFront 경유 health·로그인·기존 결과 조회를 확인한 뒤 새 작업을 접수한다.

Pod 재생성 시 `/opt`의 코드·venv·token·프로세스가 사라질 수 있다. 영속 볼륨 상태를 먼저 확인하고 정상 모델 파일은 재사용한다. 바뀐 SSH 주소·호스트 지문·제한 공개키를 반영한 뒤 터널을 다시 연결한다.

### 14.2 증상별 첫 확인

| 증상 | 먼저 확인 | 피할 조치 |
|---|---|---|
| PDF가 계속 queued | 해당 runtime·설정 digest worker, EFS, 터널 | 다른 환경의 worker를 무작정 추가 |
| 약 2분대 A02_RESPONSE_INVALID | run ID의 오류·응답 필드, 수정 이미지 반영 | 시간만 보고 timeout 증가 |
| QWEN_OUTCOME_UNKNOWN | 실제 서버 처리·응답·이력 | 같은 모델 요청 자동 재접수 |
| 영상 OOM | 실제 GPU 프로세스·VRAM, worker 수·할당 | 다른 팀 모델 강제 종료 |
| 새로고침 AccessDenied | URL·메서드·응답 형식, Function 연결 | S3 전체 공개·모든 API 오류 HTML 처리 |
| failed 로그 누적 | 실행 ID·시각·attempt·현재 대기 수 | DB·EFS 전체 삭제 |

11/09 PDF 오류 수정은 기대값이 없는 미정 `field=unspecified` 항목을 `target=unspecified`, `kind=unsupported`로 보존한 것이다. 응답 검증 전체를 끈 수정이 아니다. 실패 작업은 자동 재검사되는 것이 아니며, 종료 이력은 `/review/tasks`에서 삭제 없이 숨김·복원한다.

**worker EC2에서 새로운 로그만 확인:**

```bash
sudo docker logs --follow --tail 0 --timestamps creative-checker-worker-worker-main-1
```

`Ctrl+C`는 조회만 끝낸다. `framework_worker_ready`는 시작 준비이고 `framework_worker_cycle completed`는 한 작업의 처리 결과다. 사람의 최종 승인을 뜻하지 않는다. 실제 중단·재실행을 하는 예전 `debug-worker.sh`는 읽기 전용 진단으로 사용하지 않는다.

### 14.3 배포 롤백과 데이터 보존

11/09 복구 자료는 다음 위치에 있다. 비밀값을 포함할 수 있으므로 root 전용 권한으로 유지한다.

- API EC2: `/var/backups/creative-checker/main-ca7f01c-3pp4b8y3`
- worker EC2: `/var/backups/creative-checker/main-ca7f01c-6xo5zrwb`
- 보관한 이전 영상 API: `creative-checker-video-aws-test-before-main-ca7f01c`

포스터는 Nginx의 **해당 사이트 포스터 경로**만 이전 포트로 복구하고 `nginx -t` 후 reload한다. 새 runtime의 작업이 남아 있으면 새 worker는 유지한다. 영상은 접수를 제한하고 모든 영상 단계가 유휴인 뒤 현재 API를 정지하고 이전 API 하나만 복원한다. 이전 영상 API의 허용 Origin은 test만일 수 있어 main 연결도 함께 확인한다.

CloudFront 복구는 현재 설정·ETag를 새로 읽고 변경분을 비교한 뒤 적용한다. 다른 팀의 후속 변경을 과거 전체 설정으로 덮어쓰지 않는다. DB·EFS·Neo4j는 앱 롤백을 이유로 초기화하지 않는다. 데이터 복원은 별도 백업·복원 계획과 실제 복구 시험이 필요한 작업이다.
