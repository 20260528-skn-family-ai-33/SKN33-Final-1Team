01. 이번에 연결한 범위

AF003 승인 기준 조회 → 기존 저장 포스터 선택 → 새 포스터 실행 → 입력 확인 → A04·A05 → A06 → A07 → 사람 결정 → 수정본 재검수를 연결했다. 기존 M008 사용자·프로젝트·세션·CSRF·이미지 저장과 AF001 실행·단계·승인·worker를 재사용한다. 새 DB 스키마나 이미지 업로드 경로를 만들지 않았다.

검증은 격리 PostgreSQL과 실제 파일 저장소를 사용했다. 포스터 관측은 명시적 합성 sidecar 공급자이며 Qwen/OCR 결과가 아니다. 실제 Qwen 호출, 클라이언트 회신·기준 승인, 운영 DB 적용, front-v2 화면 연결은 수행하지 않았다. 기본 팀 inspector는 미연결 오류를 내며 가짜 통과를 반환하지 않는다.

이번 단계로 개발용 7단계 연결 시험을 마쳤다. 실제 모델 품질·발주자 승인·제품 통합을 완료했다는 의미는 아니다. 원본 시나리오의 관람시간·관람연령·우천 안내는 여전히 실제 회신 전이다.

02. 기준과 포스터 실행의 구분

PDF-only 원본 실행은 waiting_asset에서 승인 기준의 출처 실행으로 보존한다. 원본 A02 초안·완료 단계·승인 기록을 덮어쓰지 않는다. 포스터마다 별도 실행 ID를 만든다.

새 RunSnapshot.baseline에는 다음을 고정한다.

필드의미
source_run_id원본 PDF-only A02 실행
criteria_version_idAF003에서 승인한 정확한 기준 버전
criteria_sha256그 기준 본문·출처의 해시
approval_id기존 AF001에 저장한 기준 승인 기록
document_sha256원본 PDF 파일 해시

새 실행의 조건은 최초 A02 초안이 아니라 승인된 보완 기준이다. 각 조건의 PDF 인용과 별도 value_source를 함께 보존한다. A02 단계는 reused와 출처 실행 ID를 기록하며 호출 시간·추론 성공을 만들어 넣지 않는다.

처음 포스터 실행에는 parent_run_id=null이다. 수정본만 직전 검수 실행을 부모로 연결한다. 여러 최초 제안물을 같은 승인 기준에 연결할 수 있다. 원본 승인 ID를 참조하는 것과 새 포스터의 승인을 자동 복사하는 것은 다르다. 새 실행에는 승인·검사 결과·근거 묶음이 없고 waiting_criteria에서 시작한다.

03. 기존 이미지 저장소 재사용

포스터는 기존 제품의 POST /api/v1/projects/{project_id}/images로 등록한 asset_version_id를 사용한다. 파일 저장·정규화·원본 및 display 해시·좌표계는 기존 Files와 LocalStorage가 맡는다. 프레임워크 API는 업로드 서버를 추가하지 않는다. 프레임워크 인증 앱은 기존 모델 leader·이미지 GC를 실행하지 않으므로 업로드는 기존 제품에서 수행한다.

서버는 같은 프로젝트의 public.asset_versions와 stored_files에서 display PNG 참조를 직접 구성한다. 요청에서 임의 파일 경로·파일 해시·관측 문구를 받지 않는다. 파일 크기·실제 바이트 해시·디코딩·가로세로·display 좌표계를 확인한다. worker는 PDF와 포스터 바이트를 공급자 호출 전과 반환 뒤 다시 확인한다.

PDF root는 별도 초기화한 전용 저장소, poster root는 기존 M008 이미지 저장소다. 둘을 섞지 않는다. 프레임워크의 poster root 열기는 초기화·복구·GC·기존 leader 기동을 수행하지 않는다. PDF marker가 있는 root는 포스터 저장소로 거부한다.

기존 제품 제한은 최대 변 길이 8,192, 총 1,000만 화소다. 원본 전시 3,000×3,000과 축제 2,382×3,368은 등록·실제 읽기·해시를 확인했다. 연주회 원본 4,500×4,500은 기존 IMAGE_LIMIT_EXCEEDED로 거부된다. 원본을 축소·수정하거나 제한을 풀지 않았다. 원본 포스터에는 모델 판정을 수행하지 않았다.

기존 업로드 한 건은 새로운 asset/version ID와 version_no=1을 만든다. 수정본도 이 경로로 등록한 새 ID를 사용하며, 프레임워크의 parent_run_id로 검수 이력을 연결한다. 동일 논리 asset의 버전 번호 증가 기능을 새로 구현한 것은 아니다.

04. 접수와 승인 API

아래 경로의 접두사는 /api/framework/v1이다. 기존 로그인 쿠키·CSRF·허용 Origin과 활성 프로젝트 쓰기 권한을 확인한다. 현재 쓰기 권한은 원본 A02 실행 생성자이면서 프로젝트 editor/owner인 사용자다. viewer 조회와 승인 위임은 구분하며 새로운 위임 정책은 추가하지 않았다.

메서드·경로처리
GET /runs/{source_run_id}/criteria-approval정확한 승인 기준·출처·승인 ID 조회
POST /runs/{source_run_id}/poster-reviews등록 포스터로 새 실행, waiting_criteria
POST /runs/{poster_run_id}/approvals새 입력 확인 또는 수정 요청/최종 결정
GET /runs/{poster_run_id}검수 판정·출처·고정 baseline·승인 이력 조회
GET /runs/{poster_run_id}/stepsA02 재사용 및 A04_A05·A06·A07 단계 조회
POST /runs/{poster_run_id}/poster-revisions수정 요청 승인 후 새 포스터 실행

포스터 접수와 수정본 접수의 본문은 같다. Idempotency-Key UUID를 함께 전송한다.

JSON
{
  "criteria_version_id": "<조회한 승인 기준 UUID>",
  "expected_criteria_sha256": "<승인 기준 응답의 criteria.sha256>",
  "asset_version_id": "<기존 이미지 업로드가 반환한 UUID>"
}

꺾쇠 값은 설명용이다. 실제 기준·포스터를 선택해 채우며 관측값·run/actor ID·파일 경로는 제출하지 않는다. 동일 키·동일 입력의 재전송은 기존 실행을 반환한다. 같은 키에 다른 포스터나 해시는 409다. 접수 응답이 불명확하면 기존 키를 유지해 재조회/재전송한다. DB 결과 불명은 503이며 자동으로 새 실행을 만들지 않는다.

새 실행 응답의 context 그대로 기존 승인 API에 decision=approve_criteria를 제출하면 해당 포스터와 고정 기준의 확인을 기록하고 검수 job을 만든다. AF003 기준 승인을 다시 만들거나 다른 기준으로 바꾸지 않는다. 실제 사용자의 확인 의사 없이 이 요청을 자동 전송하지 않는다. 테스트에서만 명시적 합성 결정 입력을 사용한다.

worker는 A04_A05→A06→A07을 수행하고 waiting_review에서 멈춘다. 기계 pass만 일반 approve_final이 가능하다. fail/review는 실행 실패와 다르며 자동 최종 승인하지 않는다. A06는 독립 관측값과 기대값을 대조하므로 공급자가 잘못 pass를 낸 날짜 오류도 value_mismatch로 차단한다. 빈 기대값·불확실 관측 방어는 기존 정책을 유지한다.

수정할 경우 기존 실행에 approve_changes를 기록하고 새 포스터 ID로 /poster-revisions를 호출한다. 수정 요청 승인 전·같은 포스터 ID·두 번째 자식 생성은 거부한다. 자식은 같은 baseline, 새 run/asset ID, 빈 승인 이력으로 시작하며 새 입력 확인 후 A04_A05·A06·A07을 다시 수행한다. 고정 기준이 있는 실행은 임의 문맥을 받는 구형 /revisions로 우회할 수 없다.

같은 논리 PDF의 새 버전이 등록되면 이전 기준의 신규 접수·대기 job은 오래된 문서로 차단한다. 문서/기준 변경은 새 A02→새 기준 승인 흐름을 거친다. 모델 호출 이후 권한·기준이 바뀌면 결과를 성공으로 저장하지 않는다. 완료 단계는 안전한 lease 만료 뒤 재사용하고 결과 불명 호출은 자동 반복하지 않는다.

factory는 팀이 배포한 설정으로만 지정한다. HTTP 요청으로 factory나 모델 관측을 교체할 수 없다. 비동기 factory/메서드는 이 동기 포트에서 거부한다. 팀은 모델명·revision·추론 설정을 별도로 고정해야 한다. 공통 runtime_sha256은 프레임워크 Python 코드만 고정하므로 외부 factory/가중치 revision을 대신하지 않는다.

기본 inspector는 ADAPTER_NOT_CONFIGURED로 실패한다. 실제 Qwen 이미지 호출·관측 구조화는 담당자가 붙인다. A07 기본은 검증 결과에서 요약·근거 ID·수정 사유를 만드는 결정적 코드이며 LLM 보고 생성이 아니다. 실검색/RAG·Neo4j는 이번 단계에 새로 연결하지 않았다.

06. 실행과 테스트

프로젝트 루트에서 실행한다. 의존성 정본은 pyproject.toml·uv.lock이며 설치는 프레임워크 안내를 따른다. 이번 단계는 새 의존성을 추가하지 않았다. AF003이 명시적으로 적용된 개발 DB, app 전용 설정 파일, 기존 PDF와 이미지 root를 준비한다. owner 설정은 worker/API에 넘기지 않는다.

macOS에서는 이미 존재하는 절대 root를 실제 경로로 바꿔 다음과 같이 실행한다. 기본 template는 모델 미연결 상태이므로 실제 검사 역할을 연결하기 전에는 통과하지 않는다.

BASH
uv run python -m backend.agent_framework postgres-serve --env-file .runtime/framework-app.env --config examples/agent_framework/team_config.poster-review.template.json --pdf-storage-root /absolute/existing/framework-pdf --poster-storage-root /absolute/existing/m008-images --port 8012
uv run python -m backend.agent_framework worker --env-file .runtime/framework-app.env --config examples/agent_framework/team_config.poster-review.template.json --pdf-storage-root /absolute/existing/framework-pdf --poster-storage-root /absolute/existing/m008-images

API와 worker의 구성·공통 코드 revision은 같아야 한다. 코드/구성 변경 전에 접수한 job은 새 worker가 조용히 다른 설정으로 실행하지 않는다. 이전 코드를 유지해 처리하거나 새 입력을 접수하는 정책을 정한다. 승인된 원본 PDF 실행을 새 포스터 프로필로 재사용할 때는 역할 factory가 달라도 저장된 A02 단계·기준·PDF 해시를 재검증한다.

HTML은 Mac·Windows에서 상대 경로로 읽는다. Python 명령은 uv run python 형식을 쓸 수 있지만 파일 저장소는 POSIX 기반이며 Windows 네이티브 백엔드 실행은 미검증이다. Windows에서 C:\...로 경로만 바꾸면 저장소 호환이 보장된다고 설명하지 않는다.

BASH
uv run pytest tests/agent_framework -q
TEST_DB_ENV_FILE=/absolute/path/to/test-only.env uv run pytest tests/agent_framework -m db_integration -q

DB 테스트 설정은 PostgreSQL 실행 가이드를 따른다. 테스트 전용 서버에서만 무작위 DB를 만들고 제거한다. 환경 파일의 암호는 Git에 올리지 않는다. CI의 PostgreSQL job도 이 전체 DB 테스트 묶음을 실행하도록 수정했으며 원격 CI 실행 결과는 아직 확인하지 않았다.

07. 시험 자료와 판정의 한계

시험 포스터 12장은 새 SVG 코드로 만든 개발 자료다. 원본 전시·연주회·축제 포스터를 편집하지 않았다. 사례별 제목·날짜·필수 안내 3개 조건만 명시적으로 보완하고 다른 조건은 제외 사유를 기록한 합성 승인 기준을 사용한다. 원래 검토표 36개가 실제 승인됐다는 뜻이 아니다.

시험독립 sidecar 관측확인한 배선 결과
정상제목·날짜·안내가 일치pass → 합성 최종 결정 저장
날짜 오류2099-01-16, 기준은 2099-01-15공급자가 pass를 주장해도 A06 fail, 일반 최종 승인 차단
안내 누락명시적으로 확인한 부재 sentinelfail, 일반 최종 승인 차단
수정본정상 필드 + 구분 가능한 새 이미지 바이트수정 요청 승인 → 새 실행 확인 → 전체 재검사 → pass

sidecar는 실제 저장된 display 이미지 해시로 관측값을 찾으며 기대값을 복사하지 않는다. 하지만 테스트가 미리 설정한 값이며 OCR/모델 측정·실제 원본 포스터 정답·일반화 성능이 아니다. synthetic=true 계보를 승인·출처·근거·결과에 유지한다. 실제 사람 승인 0건, 실제 모델 호출 0회다.

무결성 실패, PDF 교체 후 대기 job 차단, CSRF·권한, 접수/수정본 중복, 완료 검사 재사용, 별도 worker 프로세스, 새 API 인스턴스 재조회를 함께 검증했다. 자세한 현재 수치는 7단계 검증 기록을 따른다.

실제 파일·격리 PostgreSQL 검증 · 관측/승인 입력은 합성 개발 자료
실제 Qwen·클라이언트 승인·front-v2·운영 DB 적용은 수행하지 않았습니다.
