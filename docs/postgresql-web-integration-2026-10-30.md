# 신규 웹 검수 PostgreSQL 자동 저장·조회 연결

2026-10-30 로컬 웹앱에 적용하고 실제 브라우저 및 Docker PostgreSQL로 검증했다. 이전 JSON 이력과 앞서 이관한 데이터는 보존했다.

## 적용된 동작

1. 기존 화면에서 이미지와 기준을 확정하고 검수를 시작한다.
2. 로그인한 DB 사용자로 프로젝트·이미지·기준 버전·검수 실행을 생성한다. 접수 응답 전에 `queued` 실행이 PostgreSQL에 커밋된다.
3. 기존 PaddleOCR·조건 비교 흐름을 실행하면서 DB 상태를 `running`으로 갱신한다.
4. OCR·관찰값·항목 판정·출처 원문·근거 연결·최종 요약을 기존 업무 테이블에 저장하고 완료 상태를 커밋한다.
5. 화면의 결과 조회는 PostgreSQL에서 읽는다. URL의 `review` 실행 ID로 새로고침 후 기준·원본·결과를 다시 복원한다.

새 실행은 `origin_kind=service_execution`이며, 앞선 JSON 이관 자료의 `imported` 상태와 구분된다. 화면에서 확정한 기준 버전의 사용자와 시각도 기록한다. 이것은 검수 기준 확정이며, 담당자의 최종 납품 승인을 생성하는 작업은 아니다.

기존 JSON은 시작 시 수정하지 않는다. 개발 계정에서 과거 URL로 계속 읽을 수 있다. 신규 JSON은 진단용 사본으로 남기지만, DB 조회 실패 시 이 사본을 성공 결과로 대신 반환하지 않는다. DB 저장이 실패한 검수도 완료로 표시하지 않는다.

## 실제 검증 결과

기존 샘플 포스터를 실제 브라우저에서 검수하고, 서버 재시작 후 DB에서 원본과 기준을 복원해 한 번 더 검수했다. 새 검수 URL에 실행 ID가 자동으로 기록되는 것도 확인했다.

| 측정 항목 | 검수 1 | 검수 2 | 합계 |
|---|---:|---:|---:|
| 기준 항목 | 7 | 7 | 14 |
| 항목 결과 | 7 | 7 | 14 |
| OCR 토큰 | 18 | 18 | 36 |
| 항목 근거 | 7 | 7 | 14 |

- 두 실행 모두 DB에서 `completed`로 확인했다. 원문 결과 JSON과 `source_result_jsonb`, OCR과 JSONB 저장값이 일치했다.
- 입력·결과 manifest, 기준 해시, 외래키, 관계 연결을 검증했다. 원문 결과는 별도 원문 파일 해시와 JSONB 비교로도 확인했다.
- 서버를 재시작해도 같은 결과가 브라우저에 복원됐다. 복원한 원본으로 재검수했으며, 두 업로드의 원본 SHA-256도 같았다.
- 첫 검수의 신규 `result.json` 사본을 잠시 다른 이름으로 보존한 상태에서도 브라우저를 새로고침해 DB 결과와 원본을 조회했다. 검증 후 사본은 같은 경로에 같은 바이트로 돌려놓았다.
- 작업 전 파일 472개와 기존 DB 행, 기존 `.env`가 변경되지 않은 것을 해시로 확인했다.
- DB 등록 파일 307개의 존재·크기·SHA-256을 확인했다.

각 실행의 자동 출력은 충족 6개·확인 필요 1개였다. 이번 검증은 저장·조회 정합성 검증이며, 이 숫자를 모델 정확도나 사람 검증 결과로 해석하지 않는다.

## 저장 구조

스키마는 기존 `M008`, 업무 테이블 26개를 재사용한다. 새 테이블이나 컬럼을 만들지 않았다.

| 테이블·필드 | 저장 내용 |
|---|---|
| `stored_files`, `asset_versions` | 원본·표시 이미지의 파일 참조, 크기, 해시 |
| `criteria_drafts`, `criteria_versions`, `criteria_items` | 기준 원문, 확정 사용자·시각, 버전, 해시 |
| `criteria_items.expected_value`, `source_locator` | 유효한 PDF 조건의 기대값과 실제 제공된 출처 |
| `review_runs` | 접수·진행·완료·실패 상태, 입력 스냅샷, 실행 설정, 결과 해시 |
| `review_attempts.actual_runtime` | 실제 실행 메타데이터와 제공된 모델 메타데이터 |
| `ocr_runs`, `ocr_tokens` | OCR 결과와 좌표, 원문 레코드 |
| `item_results.source_result_jsonb` | 원래 판정·이유·추가 모델 분석·메타데이터 검사 전체 |
| `evidence_records`, `evidence_ocr_tokens` | 결과와 실제 OCR 근거 연결 |

PDF 구조가 없는 과거 항목에 `document_condition:null`을 임의 추가하지 않도록 기존 직렬화 방식과 해시 호환성도 유지했다. 새 웹 결과 원문과 정규화된 결과 그래프는 각각 검증한다.

## 실행 및 설정

기존처럼 저장소에서 `./run.sh`로 실행한다. 현재 저장소의 `.runtime/postgres-web.env`를 자동으로 선택한다. 다른 설정 파일을 지정하려면 `CC_WEB_POSTGRES_ENV_FILE`을 명시한다. 설정 파일이 없는 별도 개발 환경은 기존 JSON 모드로 동작한다. 선택된 PostgreSQL 설정이 잘못되거나 DB에 연결할 수 없으면 PostgreSQL 시작을 실패 처리하며 JSON 모드로 자동 전환하지 않는다.

- 현재 연결 주소: `http://127.0.0.1:8000`
- 앱 계정: 기존 제한된 `creative_checker_app`. 웹 설정에는 owner/admin 비밀번호를 넣지 않았다.
- `.runtime/postgres-web.env`는 `0600` 권한이며 Git에 포함하지 않는다. 기존 `.env`는 수정하지 않았다.
- 비공개 파일 저장소는 기존 DB 파일들이 있는 `STORAGE_ROOT`를 계속 사용한다. 다른 머신으로 옮길 때는 DB와 이 파일 저장소를 함께 옮기고 해당 머신의 절대 경로로 설정한다.
- 새 환경에는 `requirements-v1.txt`의 DB·인증·파일 저장 의존성이 필요하다. 실행기가 패키지나 모델을 자동 설치하지 않는다.
- 기존 개발 계정의 세션도 DB에 저장하며, 검수 요청에 로그인과 CSRF 검증을 적용한다.

## 검증 범위와 제한

- 기존 API·PDF·메타데이터 단위 검사 121개 통과.
- 기존 기준·검수 DB 회귀 검사와 신규 경로 검사 110개 통과. 이후 재시작·manifest 검사를 보강한 신규 경로 6개 및 기존 이관 검사 27개도 통과했다. DB 검사는 격리된 임시 DB에서 수행했다.
- 프론트엔드 검사 49개 및 프로덕션 빌드 통과.
- 실제 검수는 현재 로컬 CPU PaddleOCR 경로로 검증했다. 별도 원격 Qwen 실험을 다시 실행한 것은 아니다. 추가 실행 경로를 사용할 때는 해당 경로의 런타임·좌표 계약을 검증해야 한다.
- 실행기는 현재 `BackgroundTasks`다. 중단된 실행을 재시작 시 DB에서 실패로 종료하며, 자동으로 모델 추론을 반복하지 않는다. 완료 기록은 계속 조회할 수 있다.
- 기존 웹 요청에는 프로젝트 ID가 없으므로 각 접수에 독립된 프로젝트를 만든다. 같은 표시명을 가진 다른 검수를 임의로 합치지 않는다.
- Neo4j 동기화와 운영 배포는 이번 작업에 포함하지 않았다.
- 변경 전 DB 덤프를 생성하고 덤프 목록 조회를 확인했다. 전체 복구 리허설은 수행하지 않았다. 기존 예비 기준 묶음의 별도 백업 포맷까지 포함한 전체 백업 검증과 신규 두 검수의 manifest 검증은 구분한다.

검증 산출물은 이번 작업 폴더의 `verification.json`, `new-path-tests.xml`, `json-independence-proof.json`, `db-result-proof.png`에 남겼다. 연결 설정 파일에는 비밀번호가 있으므로 공유 자료에 포함하지 않는다.
