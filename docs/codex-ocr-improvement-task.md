## 1. 실행 요청

이 문서를 작업 지시서로 삼아 현재 프로젝트의 OCR 개선을 구현하고 검증해 주세요.

먼저 현재 코드와 프로젝트 지침을 확인하고, 기존 구현과 제안 기능을 구분해 변경 지점을 간단히 설명한 뒤 작업을 진행하세요. 기존 React/FastAPI 검수 흐름을 유지하면서 고객마다 다른 포스터에 대응하도록 개선하세요. 이번 작업에서 기존 Django/PostgreSQL 설계 문서의 구조 전환까지 함께 수행하지 않습니다.

로컬 모델 준비와 비교 실험, 필요한 코드·테스트·문서 변경을 진행하세요. 설치·네트워크·시스템 작업은 Codex 실행 환경의 권한 절차를 따르세요. 로컬 실패를 이유로 유료 API나 RunPod로 자동 전환하지 않습니다.

## 2. 현재까지 확인한 사실

2026-10-13에 확인한 내용이며, 작업을 시작할 때 다시 확인하세요.

- 프로젝트는 EasyOCR 한국어·영어 모델과 PyTorch를 사용한다. 로컬 장치 선택은 CUDA → MPS → CPU 순서다.
- 웹 OCR 입력은 EXIF 방향과 투명 배경을 정규화한 RGB 이미지의 2배 확대본이다.
- 과거 실행 실패의 직접 원인은 프로젝트 `.venv`의 `easyocr`, `torchvision` 누락이었다. 의존성 설치 후 사용자가 정상 동작을 확인했다.
- 당시 Mac 환경은 ARM64, 메모리 24GB였다. 이 정보가 모델 속도나 추론 성공을 보장하지는 않는다.
- 당시 최신 김천김밥축제 검수는 `completed`, MPS OCR 성공, 충족 2개·확인 필요 5개였다.
- 현재 행사 정보 추출기는 제한된 한 줄 규칙을 사용하며, 여러 줄 결합과 일반적인 포스터 레이아웃 처리가 부족하다.
- 현재 시각 항목은 항상 `review`로 남는다. 담당자가 항목을 확인하고 판정을 저장하는 기능도 아직 없다.

| 확인 필요 항목 | 관찰된 원인 | 개선 방향 |
|---|---|---|
| 행사명 | `김천김밥축제`를 `캠터롭발숙시`로 오인식 | 탐지된 제목 후보 영역을 다른 설정·모델로 재인식 |

| 친환경생태공원 | `생태`를 `생대`로 오인식 | 장소 후보 재인식, 원본과 근거 대조 |

## 4. 구현할 처리 흐름

### 4.1 이미지마다 글자 영역을 자동 탐지

1. 전체 이미지에서 글자 후보의 사각형·다각형 좌표를 탐지한다.
2. 탐지 결과로 각 이미지의 인식 영역을 만든다. 고객별 고정 좌표나 ‘제목은 상단’ 같은 필수 규칙을 두지 않는다.
3. 글자 높이·방향·거리 등을 사용해 인접 영역을 묶는다. 두 줄 제목과 나뉜 날짜를 처리하고, 원래 탐지 박스와 묶은 근거를 함께 보존한다.
4. 재인식용 영역에는 적절한 여백을 포함한다. 회전·원근 보정이나 확대를 적용한 경우 변환 정보를 기록한다.
5. OCR 입력·crop·정규화 원본 사이의 좌표 변환을 관리한다. 화면 근거 박스는 현재 API가 사용하는 정규화 원본 좌표와 일치해야 한다.

글자 위치 탐지와 글자 인식은 별도 단계다. 내용을 틀리게 읽어도 위치는 찾을 수 있다. 위치 자체를 놓칠 수도 있으므로 필수 항목 미추출 시 전체 이미지 재검토 경로를 둔다.

### 4.2 글자를 읽은 뒤 행사 정보를 추출

- 먼저 글자 후보를 읽고, 이후 행사명·기간·장소 후보를 분류한다.
- 위치와 글자 크기는 보조 단서로 사용하고, 후보가 여러 개면 하나로 임의 확정하지 않는다.
- 여러 줄을 결합할 때는 연결된 OCR ID와 좌표를 남긴다. 서로 다른 문구를 잘못 합친 경우를 검증한다.
- 날짜는 표현을 정규화한 뒤 실제 날짜, 시작·종료 순서, 관찰된 요일을 검증한다.
- 포스터 전체를 읽는 단계에서 날짜 전용 문자 제한을 적용하지 않는다. 날짜 후보 영역의 재인식에만 제한 설정을 실험한다.

### 4.3 불확실한 영역을 선택적으로 재인식

재인식 조건은 낮은 OCR 신뢰도뿐 아니라 필수 항목 미추출, 기준과의 문구 불일치, 후보 간 충돌도 포함한다. `생대`처럼 높은 신뢰도로 틀린 글자를 읽을 수 있기 때문이다.

- 기존 EasyOCR의 영역별 재인식, `beamsearch`, 대비·여백 설정을 비교한다.
- 한국어 PaddleOCR 모델로 같은 영역을 읽어 비교한다.
- Qwen 이미지 모델에는 후보 영역과 필요 시 전체 이미지 문맥을 전달한다.
- 모델별 원시 결과와 선택 사유를 보존한다. 모델끼리 일치한다는 이유만으로 정답으로 간주하지 않는다.
- 전체 이미지 재검토가 필요하면 출력·시간·시도 수를 제한한다. 무제한 반복 추론을 만들지 않는다.

추출 프롬프트에는 기준의 기대 문구, 정답 라벨, 파일명에 포함된 정답을 전달하지 않는다. 검수 기준과의 비교는 추출 이후 별도 단계에서 수행한다.

프롬프트 예시:

> 이미지에 실제로 보이는 글자를 그대로 읽어라. 행사명·기간·장소 후보를 추출하되, 판독하기 어려운 값은 null로 반환하라. 추측으로 날짜나 기관명을 보정하지 마라.

## 5. 모델 준비와 채택 방법

| 후보 | 역할 | 적용 주의점 |
|---|---|---|
| 기존 EasyOCR | 기준선, 위치 탐지와 인식 | 현재 동작과 결과를 먼저 기록 |
| `PaddlePaddle/korean_PP-OCRv5_mobile_rec` | 한국어 영역 재인식 비교 | 글자 인식용 모델이다. 전체 파이프라인에는 위치 탐지도 필요 |
| Ollama `qwen3-vl:4b` | 어려운 영역 재인식과 전체 이미지 검토 비교 | 이미지 입력을 지원하는 로컬 모델로 사용 |

- Ollama는 로컬 실행 도구이며, Hugging Face는 모델 저장소다. 모델 파일만 내려받으면 현재 코드에 연결되는 것은 아니다.
- Ollama가 설치되어 있다면 `ollama pull qwen3-vl:4b`로 준비한다. 설치되어 있지 않으면 운영체제와 권한에 맞게 준비한다. 공식 4B 배포 파일은 약 3.3GB이며 실행 메모리는 별도로 필요하다.
- PaddleOCR 비교 환경은 기존 `.venv`와 분리해 의존성 충돌을 피한다. 설치 버전과 실제 추론 장치를 기록한다.
- 한국어 인식 모델을 명시적으로 선택한다. 최신 기본 모델이 모든 언어를 지원한다고 가정하지 않는다.
- 먼저 4B와 한국어 PaddleOCR을 비교한다. 8B 비교는 4B 결과와 자원 사용량을 보고 필요할 때 진행한다.
- 정확도, 잘못된 충족 판정, 누락, 처리 시간, 메모리를 비교해 운영 경로를 선택한다. 개선되지 않은 후보도 실험 결과로 기록한다.

선택한 모델을 연결할 때는 OCR 호출 어댑터, 엔진·모델 메타데이터, 좌표 형식, 오류 처리, 결과 JSON을 함께 갱신하세요. API의 엔진 허용값이 현재 `easyocr`로 제한된 부분도 확인하세요. 다른 엔진을 실행하고도 `easyocr`로 기록하지 마세요.

## 6. 판정과 데이터 보존

- 충분한 근거가 있는 경우에만 `pass`, 위반 근거가 있는 경우에만 `fail`, 불확실하면 `review`를 사용한다.
- OCR confidence와 VLM의 자기 평가 점수를 같은 척도로 취급하지 않는다. VLM 결과에 임의의 높은 confidence를 넣어 기존 통과 조건을 만족시키지 않는다.
- 추출값과 자동 판정, 실행 상태, 향후 담당자 확인을 구분한다. `completed`는 추론 완료이며 승인 완료가 아니다.
- 원본 이미지·기준 스냅샷·이전 결과를 보존하고 개선 버전의 실행은 새 기록으로 남긴다.
- 이미지·crop 해시, 모델명·버전, 실제 장치, 전처리, 원시 출력, 근거 좌표, 시간, 시도·실패 이력을 기록한다.

로고는 기준 로고와의 대조 및 근거 영역이 필요하다. 잘림은 전체 이미지와 ‘문구/필수 요소의 잘림 금지’, ‘장식 요소의 의도적인 잘림 허용’ 등의 정책이 필요하다. 1차 OCR 개선에서 근거 없는 시각 항목을 자동 충족으로 바꾸지 말고, 별도 구현안과 필요한 입력·평가 자료를 보고하세요.

담당자 확인 기능을 후속 구현한다면 자동 결과를 덮어쓰지 않고 판정·사유·근거 영역·확인자·확인 시각을 별도로 저장하는 구조로 제안하세요.

## 7. 실행 순서와 검증

1. 현재 환경과 의존성, 모델 캐시, 기존 검수 결과를 확인하고 기준선을 기록한다. 서버 시작 및 health에서 준비 부족 원인을 구분할 수 있도록 개선한다. 공개 응답에는 비밀값·경로·traceback을 노출하지 않고 서버 진단에는 원인을 남긴다.
2. 고정 좌표 없이 다양한 입력을 받는 비교 실행 경로와 실행별 산출물 폴더를 만든다.
3. 자동 탐지 영역 재인식, 한국어 PaddleOCR, Qwen 4B를 같은 입력에서 비교한다.
4. 근거 좌표를 보존하는 추출·재인식 경로를 구현하고, 평가 결과를 보고 사용할 엔진을 연결한다. 성능 평가가 충분하지 않다면 선택 기능으로 제공하고 기본값 변경의 한계를 명시한다.
5. 의미 있는 계약·회귀 테스트와 실제 로컬 추론을 확인한 뒤 실행 안내(현재 [실행가이드](../실행가이드.md))와 비교 보고서를 갱신한다.

평가에는 저장소에서 사용 가능한 포스터 중 배치·글꼴·방향·정보량이 다른 5~10장을 선정하세요. 행사명·날짜·장소 정답과 위치 근거를 별도로 준비하고, 사람 확인 전 라벨은 초안으로 유지하세요. 모델 선택용과 최종 확인용 입력을 분리하세요. 자료나 확정 라벨이 부족하면 그 한계를 명시하고 임시 진단을 일반 성능으로 보고하지 마세요.

필수 검증 사례:

- 제목·기간·장소 위치 변경, 두 줄 제목, 나뉜 날짜, 장식 글꼴, 회전 글자, 여러 행사 후보, 실제 정보 누락.
- crop·확대·회전 후 원본 좌표 복원, EXIF 방향, 투명 배경, 잘못된 박스와 모델 응답.
- 모델·런타임 미설치, 응답 실패·timeout, fallback 및 시도 수 제한.
- 잘못된 문구를 충족으로 처리하지 않는지, 시각 항목과 실패·미실행 항목이 근거 없이 충족되지 않는지.

현재 프로젝트의 기본 확인 명령은 다음과 같습니다. 실제 작업 시 변경 범위와 기존 지침에 맞춰 사용하세요.

```bash
.venv/bin/python -m backend.app.ocr_runtime
.venv/bin/python -m pytest -q
npm --prefix frontend test
npm --prefix frontend run build
```

모의 테스트와 실제 추론을 구분하세요. MPS/CUDA/RunPod는 실제 확인한 환경만 검증 완료로 기록하세요.
