도구 테이블 alembic_version은 위 업무 테이블 수에서 제외했습니다. 실제 구조는 물리 ERD ↗와 M008 계약 ↗를 따릅니다.

상태 흐름
실행: queued → running → completed / failed
시도: active → succeeded / failed / unknown
항목 표시: pass / fail / review
사용자 재검수: 새 run + retry_of 관계
  • completed는 자동 실행 완료입니다. 사람의 승인·학습 라벨 확정과 분리합니다.
  • 동일 요청 재전송은 같은 Idempotency-Key를 사용합니다. 다른 요청 내용에 같은 키를 재사용하면 409입니다.
  • worker heartbeat는 15초, lease는 90초입니다. 호출 전임이 확인된 작업만 총 3회까지 5/30초 간격으로 재대기합니다.
  • 호출 여부나 결과가 불명확한 작업은 추론을 자동 반복하지 않습니다. 유료 원격 fallback도 없습니다.
  • 이미지 원본과 표시 이미지를 분리하며, 결과 좌표는 표시 이미지 기준으로 보존합니다.

예제의 change-me-... 값은 실제 비밀로 교체해야 합니다. 파일은 리터럴 KEY=value 형식이며 셸용 따옴표를 추가하지 않습니다. 프로세스 환경 값이 파일보다 우선하므로 이전 터미널에서 export한 설정도 확인하세요.

2. DB 기동 → M008 적용 → 구조 검사

DB를 처음 준비할 때만 .env 예제를 복사하고 세 비밀번호를 편집합니다. 이미 DB 볼륨이 있다면 그 역할과 비밀번호를 사용합니다.

새 DB 설정 파일 준비 · 실행 후 내용을 편집
test -e .env || cp .env.example .env
chmod 600 .env

기존 볼륨의 비밀번호
DB 초기화 스크립트는 빈 볼륨에서만 동작합니다. .env를 바꿔도 이미 생성된 PostgreSQL 역할의 비밀번호는 바뀌지 않습니다. Healthy는 M008 적용이나 앱 계정 검증의 완료를 뜻하지 않습니다.

owner/app 설정의 DB 이름과 역할을 확인한 뒤 아래 마이그레이션을 명시적으로 적용합니다. 기존 데이터가 있는 DB는 해당 데이터의 백업과 적용 대상 확인을 먼저 합니다.

터미널 · 저장소 루트

.venv/bin/python -m scripts.check_schema --env-file .env.v1

두 번째 명령이 schema_ready와 M008을 반환해야 합니다. 앱 시작은 migration을 자동으로 실행하지 않습니다.

3. 개발 프로젝트와 이메일 계정 발급

admin/admin도 사용할 개발 환경에서는 새 UUID 하나를 .env.owner와 .env.v1의 DEV_PROJECT_ID에 동일하게 적고, 두 파일에 development·LOCAL_ADMIN_LOGIN=1을 설정합니다. CSRF/CURSOR 비밀은 각각 별도로 생성합니다.

로컬 터미널 · UUID 1개와 서로 다른 비밀 2개 생성

.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))'

출력한 비밀은 해당 비공개 설정 파일에만 저장합니다. worker는 LOCAL_ADMIN_LOGIN=0을 유지합니다.

터미널 · 저장소 루트
.venv/bin/python -m backend.app.management --env-file .env.owner bootstrap-development

터미널 · 저장소 루트
.venv/bin/python -m backend.app.management --env-file .env.owner set-project-member --project-id '<DEV_PROJECT_ID>' --user-id '<발급된 사용자 UUID>' --role editor --active true

이메일 로그인만 사용할 때는 두 파일의 LOCAL_ADMIN_LOGIN=0, DEV_PROJECT_ID 빈 값으로 두고 bootstrap-development를 생략할 수 있습니다. 계정 발급 자체는 기존 프로젝트의 권한을 자동 부여하지 않습니다.

08

일상 실행·개발·종료

터미널 1 · 새 v1 API + 빌드된 화면
.venv/bin/python -m scripts.run_v1 --env-file .env.v1 --host 127.0.0.1 --port 8000
터미널 2 · 독립 worker
.venv/bin/python -m backend.app.worker --env-file .env.worker

http://127.0.0.1:8000/login에서 이메일 또는 허용된 개발 계정으로 로그인합니다. 웹·worker의 터미널을 유지합니다. DB를 포함한 전체 서비스를 run_v1 하나로 시작하지는 않습니다.

  • 이메일 계정으로 로그인하고 자신의 프로젝트가 표시된다.
  • 이미지를 업로드하고 초안을 저장한 뒤 기준을 확정할 수 있다.
  • 새 검수가 queued → running → completed로 진행되거나 명시적 실패 사유를 표시한다.
  • OCR 텍스트·근거·표시 이미지·JSON 내보내기를 확인할 수 있다.
  • 새로고침과 웹/worker 재시작 후에도 저장한 이력을 다시 조회할 수 있다.

React를 수정할 때만 Vite 개발 서버 사용

.env.v1의 AUTH_ALLOWED_ORIGINS에 http://127.0.0.1:5173과 사용할 localhost origin을 추가하고 API를 재시작합니다. API를 다른 포트에서 띄웠다면 API_PROXY_TARGET도 맞춥니다.

터미널 3 · 선택 사항, 기본 5173
npm --prefix frontend run dev:v1

이 경우 Vite가 출력한 주소로 접속합니다. 이미 사용 중인 포트 때문에 5174 등으로 바뀌면 정확한 origin을 허용하거나 5173을 비우고 재시작합니다. 배포용 화면은 수정 후 build:v1을 다시 실행해야 합니다.

중지와 재시작

  • 로컬에서는 새 검수 접수를 멈추고 웹과 worker 터미널에서 Ctrl+C를 사용합니다. worker가 현재 작업을 마무리할 시간을 둡니다.
  • worker가 없으면 작업은 queued로 남을 수 있습니다. 웹 재시작만으로 독립 worker가 자동 시작하지 않습니다.
  • 코드 또는 모델을 바꾸면 새 worker config 파일을 생성하고 웹 설정도 함께 갱신합니다. 옛 설정의 대기 작업을 임의로 새 모델에 넘기지 않습니다.
  • 기존 시제품과 v1은 같은 포트를 동시에 사용할 수 없습니다. 포트를 바꾸면 허용 origin과 프런트 프록시도 일치시킵니다.
기존 시제품 실행은 별도
./run.sh 또는 .\run.cmd는 기존 시제품입니다. 새 v1을 실행하려고 기본 launcher를 사용하면 이메일 DB 로그인·v1 이력 화면이 나오지 않습니다.

Linux 배포 준비와 전환 순서

실제 Linux OCR은 다음 검증 대상입니다
C15는 Linux의 실제 API·HTTPS·DB·파일·큐·백업/복원 동선을 합성 OCR로 검증했습니다. 아래 worker 이미지 빌드와 실제 모델 추론은 준비 절차이며 완료 기록이 아닙니다.
파일역할
deploy/compose.v1.yamlapi · worker · proxy. DB 생성·migration·계정 발급을 수행하지 않음

1. 배포 대상과 파일 준비

  • 운영 서버 아키텍처, 도메인/TLS, 사설 DB 주소, 영속 볼륨과 서비스 UID 10001 권한을 정합니다.
  • 웹/worker production 환경 파일을 따로 준비합니다. LOCAL_ADMIN_LOGIN=0, 활성 developer 없음, 실제 이메일 owner가 필요합니다.
  • 웹: STORAGE_ROOT=/data/storage, FRONTEND_DIST=/web, REVIEW_EXECUTOR=postgres_worker, REVIEW_PIPELINE=disabled, REVIEW_CONFIG_FILE=/run/worker-config.json.
  • worker: 같은 DB app/비밀번호·STORAGE_ROOT, REVIEW_EXECUTOR=postgres_worker, REVIEW_PIPELINE=paddle-only, RUN_TARGET=local.
  • 웹의 정확한 HTTPS origin/host와 TRUSTED_PROXY_IPS를 지정합니다. 프록시 고정 IP·서브넷·인증서 이름과 일치시킵니다.
  • 모델·v1 빌드·worker config·TLS cert.pem/key.pem을 준비합니다. Compose 선택 파일은 .env.deploy.example을 기준으로 채웁니다.
DB 주소와 env 파일
컨테이너의 127.0.0.1은 컨테이너 자신입니다. DB 사설 연결을 실제 호스트에서 확인해야 합니다. 서비스 env_file의 format: raw는 비밀번호 안의 $, 따옴표, #가 변형되지 않도록 유지합니다.

새 대상에 복원하고 공개 보류 해제

복원 대상은 원본과 다른 이름의 template0 기반 빈 DB·같은 역할 이름·새 파일 루트이며, 서로 다른 새 CSRF/CURSOR 비밀 두 개가 필요합니다. restore는 DB 자체를 생성하는 명령이 아닙니다. 복원 대상 전용 owner/app 파일과 PostgreSQL 17 도구 설정을 먼저 준비합니다.

터미널 · 저장소 루트

구조·행·파일 전체 검사와 세션 폐기 뒤에도 validated_held로 보류합니다. 실제 계정/권한과 운영 설정을 확인하고 아래 명령으로 다시 검사해 보류를 해제합니다. API/worker 시작이나 기존 환경 전환은 자동 수행하지 않습니다.

터미널 · 저장소 루트

상세 대상 준비·실패 보존·보류 정책은 C14 전체 절차 ↗를 따릅니다.

문제가 생겼을 때

증상먼저 확인할 내용
이메일 로그인 화면이 안 보임run.sh는 기존 시제품입니다. run_v1과 dist-v1을 선택했는지 확인합니다.
v1 설정 거부change-me 값, DEV_PROJECT_ID, origin/host, 절대 경로, worker config를 확인합니다. 웹에 owner/admin 비밀이 섞였는지도 확인합니다.
DB는 Healthy인데 앱 시작 실패앱 비밀번호·역할·DB 이름과 M008/schema_ready를 확인합니다. 컨테이너 Healthy는 업무 스키마 검사가 아닙니다.
admin/admin 로그인 실패개발 모드, LOCAL_ADMIN_LOGIN=1, loopback, bootstrap과 DEV_PROJECT_ID를 확인합니다. production에서는 허용하지 않습니다.
로그인은 되는데 프로젝트 없음계정 발급만으로 기존 프로젝트에 참여하지 않습니다. 새 프로젝트를 만들거나 멤버십을 부여합니다.
CSRF 403 / Vite 변경 요청 실패실제 브라우저 origin·포트와 AUTH_ALLOWED_ORIGINS가 같은지, 같은 origin을 유지했는지 확인합니다.
검수가 queued에 머묾별도 worker 실행, 같은 DB/저장소, 코드·모델·worker config 일치 여부를 확인합니다. 새 검수를 반복 접수하지 않습니다.
REVIEW_RUNTIME_UNAVAILABLEworker config와 Paddle 환경·검증 모델을 확인합니다. 웹 disabled 값만 바꾸어 해결하지 않습니다.
FILE_UNAVAILABLE원본 파일 누락·크기/해시 불일치를 점검합니다. 임의 파일 대체나 DB 해시 수정 대신 관리 복구 절차를 따릅니다.
설정 파일 비밀번호를 바꿨는데 DB 접속 실패기존 DB 볼륨의 역할 비밀번호는 자동 변경되지 않습니다. 실제 DB 역할과 파일 값을 맞춥니다.
포트 충돌 / 잘못된 화면기존 서버를 중지하거나 다른 포트와 정확한 origin/API_PROXY_TARGET을 사용합니다.
health가 degraded 또는 worker unknown개별 DB·storage 상태를 확인합니다. 관측되지 않은 worker/model 상태이며 실제 검수 성공으로 별도 확인합니다.
