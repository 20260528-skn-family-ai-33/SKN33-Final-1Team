# data/logos — 로고 레퍼런스 시드

영상 검수(영상 트랙)의 **로고 검사**와 **타 플랫폼 워터마크 탐지**가 맞춰 보는
기준 이미지(원본 PNG)를 여기에 둔다. **시드(원본) 위치**이며, 실제 검수가 읽는
런타임 저장소는 아니다(아래 "런타임과의 관계" 참고).

## 폴더 구조
```
data/logos/
  <brand>/<variant>.png     # 브랜드가 "있어야 할/올바른" 로고
  _watermarks/<platform>.png # "있으면 안 되는" 타 플랫폼 워터마크 (tiktok, reels …)
```
- `<brand>` : 브랜드 식별자(소문자·영문/숫자/하이픈). 예) `gimcheon-city`
- `<variant>`: 색상·형태 변형을 1장씩. 예) `color.png`, `white.png`, `mono.png`

## 이미지 규칙 (프레임과 반대로 다룬다)
- **원본 PNG 그대로.** 축소·JPEG 변환 금지 — 로고 매칭은 선명한 경계와 **투명도(알파)**가 필요하다.
- 변형마다 **한 파일씩**(한 브랜드에 여러 장).
- 파일명·폴더명에 개인정보/고객사 비밀이 드러나지 않게 한다.

## git (용량 주의)
- 이 프로젝트는 이미 `data/img/`에 이미지 200여 장(~69MB)을 **git에 그대로 커밋**한다(LFS 미사용).
  로고도 같은 방식으로 **git 추적 OK** — 보통 로고는 장당 수십~수백 KB라 소수면 문제없다.
- 기준: 로고가 **많아지거나(수백 장+) 고해상도·자주 교체**되면 git 히스토리가 영구히 커지므로,
  그때는 **Git LFS**로 돌리거나, **repo 밖(STORAGE_ROOT/공유 저장소)에 두고 매니페스트(CSV/JSON)만 git**에 둔다
  (이 repo의 `data/poster_sources_*.csv`가 그 매니페스트 방식의 예).
- 커밋 전 각 PNG는 필요한 해상도로만 최적화(투명도 유지), 불필요한 변형 남발 금지.
- 로고는 민감정보가 아니고, 사용자 업로드 영상과 달리 **파기 대상이 아니다** — 영구 레퍼런스.

## 런타임과의 관계 (중요)
이 폴더는 **원본일 뿐**이다. 검수 실행이 실제로 읽는 곳은 프로젝트의 잠긴 객체 저장소다:
```
<STORAGE_ROOT>/objects/projects/<project_id>/files/<file_id>/payload.bin
```
- 사람이 경로를 정하지 않고 UUID 키로 강제된다. "어떤 로고인지"는 DB 행이 기억한다.
- `/data`(또는 `.runtime/storage-v1`)에 직접 복사하면 안 된다 — marker·저널·동일볼륨 확정 검사가 있다.
- 그래서 **등록 스크립트**가 이 시드를 스토리지 연산으로 올리고 DB 행을 만든다(미구현).
