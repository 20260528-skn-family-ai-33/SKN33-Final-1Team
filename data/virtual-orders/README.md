# 가상 발주 데이터 3건 (F&B · 페스티벌 · 가상인물)

실제 외주를 맡길 때 필요한 문서 묶음을 기준으로 만든 **합성(가상) 발주 사례 3건**이다. 회사·인물·연락처·금액·서명은 모두 가상이며 실존과 무관하다(우연한 유사성 가능).
작성 2026-10-06. **AI(Claude Code)가 작성했고 사람 검토는 아직 하지 않았다(pending).** 실제 팀 업무 자료나 독립 평가 사례로 취급하지 않는다.

| 사례 | 유형 | 가상 발주 | 점검하는 것 |
|---|---|---|---|
| `VO-01-fnb` | F&B | 온기식탁 · 들깨 버섯 리조또 세트 | 원산지·알레르기 표기와 글자 크기, 근거 없는 최상급 표현, 가격 정합성, 증빙 제출 |
| `VO-02-festival` | 페스티벌 | 달빛누리 뮤직 페스타 2026 | 출연진 명칭, 출연자 사진 동의, 후원사 로고 승인 목록, 주최 표기, 현수막 한정 조건(해당 없음) |
| `VO-03-virtual-person` | 가상인물 | 모아 워치 S1 · 가상 인간 ‘서하’ | 가상 인물 설정서 일치, AI 생성물 표시, 모델 초상·음성 허락 범위(기간·매체·지역), IP·AI 도구 증빙 |

각 사례에는 **3단계 문서**(1 기획·요청 → 2 계약 → 3 수행·검수) 9~10종, 납품 이미지 6장, 증빙 문서, 정답이 들어 있다.
어떤 문서를 왜 만들었는지는 [required-documents.md](required-documents.md)에 정리했다.

## 폴더 구조

```text
data/virtual-orders/
├─ README.md · required-documents.md
├─ registry.csv      자료 등록부(출처·해시·허용 작업·권리 상태)
├─ labels.csv        항목별 정답 전체(264행)
├─ scripts/          생성·검증 스크립트
└─ VO-0N-*/
   ├─ case_sheet.md  사례 설계 시트(문서·이미지·조건·정답 요약·수정 시나리오)
   ├─ input/         서비스 입력으로 쓸 수 있는 자료
   │  ├─ docs/       3단계 문서 PDF + MD
   │  ├─ deliveries/ 납품 이미지 D1~D6 (PNG)
   │  ├─ evidence/   납품 증빙 문서(버전별)
   │  └─ case_input.json
   └─ gold/          평가 전용 정답 (서비스 입력·RAG 코퍼스에 넣지 않는다)
      ├─ criteria_gold.json   확정 기준과 근거 문서·쪽·문구
      ├─ observations.json    문자·객체·로고의 실제 좌표와 판독 가능성
      ├─ judgments.json       이미지 × 조건 판정과 사유
      └─ workflow.json        수정·재검수 시나리오의 기대 결과
```

## 사례마다 같은 납품 이미지 구성

| ID | 유형 | 목적 |
|---|---|---|
| D1 | 정상 | 모든 조건·증빙 충족 |
| D2 | 단일 오류 | 한 가지 편집으로 어떤 조건이 흔들리는지 |
| D3 | 복합 오류 | 여러 오류가 한 번에 있는 경우 |
| D4 | 판독 불확실 | 작은 글씨·저대비·가림. 사람도 확정하기 어려워 `확인 필요`가 되어야 하는 경우 |
| D5 | 증빙 문제 | 이미지는 정상이나 증빙이 없거나 범위가 부족한 경우 |
| D6 | 수정본 | D3(VO-01·02) 또는 D5(VO-03)에 대한 수정 제출 |

판정은 `충족 / 미충족 / 확인 필요 / 해당 없음` 네 가지이고, `해당 없음`에는 반드시 근거가 붙는다.
정답 수량: 문서 28개(+MD 사본 28), 증빙 11개, 납품 이미지 18장, 문자 영역 142개, 판정 264건
(충족 231 · 미충족 21 · 확인 필요 6 · 해당 없음 6).

## 정답이 만들어진 방식과 검증

- 이미지는 코드로 그렸으므로 **문자 위치와 객체 개수는 렌더링 시점의 실제 값**이다. 사람이 읽은 정답이 아니라 생성 정답이라는 점이 한계이기도 하다(실제 OCR이 읽기 쉬운 깨끗한 합성 이미지).
- 판정은 `gold/criteria_gold.json`의 기준과 `observations.json`의 관찰값을 규칙으로 비교해 계산한다.
- `scripts/verify_vo.py`가 아래를 자동 확인한다. 현재 **문제 0건**.
  - 등록부 파일과 SHA-256 일치
  - 각 기준의 근거 문구가 명시한 문서·쪽에 실제로 있는지(PDF 텍스트 추출)
  - 증빙 PDF의 기간·지역 값이 정답에 쓴 메타와 일치하는지
  - 문자 영역이 캔버스 안에 있고 서로·객체와 겹치지 않는지
  - 바이트가 같아야 하는 파일(VO-03 D5·D6 이미지)은 같고, 달라야 하는 파일은 다른지
  - 설계 의도(어느 이미지가 어느 조건에서 실패해야 하는지)와 엔진 판정의 일치
  - 사례마다 3단계 문서가 모두 있는지
- 사람 검토(권리·내용·표기)는 **아직 하지 않았다.** 앱 연결과 실제 OCR 실행은 아래 "앱 주제로 연결"을 본다.

## 한계와 주의

- 독립 그룹은 **3개**이고 각 사례의 이미지 6장은 같은 원본의 파생이다. 일반화 성능 평가용 독립 18건이 아니다.
- 원산지·알레르기 26px, AI 표시 24px 등은 **가상 발주사의 내부 기준**이며 법정 기준이 아니다. 법령 관련 서술은 2차 출처 요약이라 원문 확인이 필요하다.
- 이미지의 글꼴은 Noto Sans/Serif KR(SIL OFL 1.1로 알려져 있으나 글꼴 파일의 license 문구 재확인 필요), 문서 PDF의 글꼴은 맑은 고딕(Windows 시스템 글꼴, 외부 배포 조건 미확인)이다. 그래서 `registry.csv`의 `public_redistribution`은 `unknown`이다. 외부 공유·공개 저장소 게시 전에 확인한다.
- 팀의 `data/collection/`(합성 자료 수집 체계)과 **분리했다.** `data/collection/scripts/validate_collection.py`가 `raw/` 아래 `.md`·`.png` 개수를 고정값으로 검사하므로 거기에 섞지 않았다. 통합이 필요하면 팀 계획에 맞춰 별도로 결정한다.

## 앱 주제로 연결 (로컬 개발용)

`scripts/make_topics.py`가 3건을 앱의 주제로 내보낸다. 코드 변경은 `app/topics.py`에 주제 3개를 등록한 것뿐이다.

| 주제 ID | 원본 | 규칙(text / manual) |
|---|---|---|
| `fnb-ongi-v1` | VO-01-fnb | 8 / 1 |
| `festival-dalbit-v1` | VO-02-festival | 7 / 1 |
| `virtual-seoha-v1` | VO-03-virtual-person | 5 / 2 |

- `data/topics/<주제 ID>/images/sample-01~06.png`는 납품 이미지 D1~D6을 **변경 없이 복사**한 것이다(바이트 동일, 테스트로 확인). 원본은 이 폴더에 있으므로 원본을 바꾸면 `make_topics.py`를 다시 실행한다.
- `criteria.json`의 문구 영역은 레이아웃(정답 좌표)에서 계산한 비율 좌표이며 판정 정답(`judgments.json`)은 읽지 않는다. 각 영역에 의도한 글자 하나만 들어가는지 생성 시 자동 확인한다.
- **앱이 검사하는 것은 문구(OCR) 비교뿐이다.** 개수·로고·가상 인물 설정·증빙 제출·표시 의무·글자 크기·최상급 표현은 앱이 지원하지 않아 규칙에 넣지 않았거나 `manual`(확인 필요/미실행)이다.
- 앱은 "글자가 없음"과 "OCR이 못 읽음"을 구분하지 못해 둘 다 `확인 필요`로 둔다. 정답의 `text_missing`(미충족)은 앱에서 `확인 필요`가 되는 것이 정상이다.
- 테스트 `tests/test_virtual_orders.py`는 정답 좌표를 완벽한 OCR로 가정해 규칙 설정이 정답과 맞는지 확인한다(실제 OCR 성능 검증이 아님).

**실제 OCR 실행 결과** (RapidOCR PP-OCRv5 한국어 · ONNX CPU, 2026-10-06, 개발용 합성 이미지 18장 — 일반 성능 평가가 아니다)

| 주제 | 문구 규칙 판정 | 정답과 일치 |
|---|---|---|
| `fnb-ongi-v1` | 48건 | 44건 |
| `festival-dalbit-v1` | 42건 | 42건 |
| `virtual-seoha-v1` | 30건 | 30건 |

- 불일치 4건은 모두 `fnb-ongi-v1`이다. 기간의 `~`를 OCR이 읽지 못해 보류한 3건(D1·D4·D5)과, 메뉴명을 `내버섯`으로 잘못 읽어 **미충족으로 오판한 1건(D2, 실제 표기는 정확함)** 이다.
- 첫 실행에서는 메뉴명·기간 규칙에 `join_lines`(같은 줄 조각 합치기)가 없어 11건이 불일치(모두 `확인 필요`로 보류)였다. 이 옵션은 기존 `festival-v1` 제목 규칙도 쓰며 틀린 글자를 맞게 만들지 않는다. 실행 결과를 본 뒤 추가한 설정이므로 이 사실을 함께 적는다.
- OCR 오독은 실제 내용 오류와 다를 수 있다. 결과를 정답에 맞춰 보정하지 않았다.

## 다시 만들기

생성 스크립트는 Windows에 설치된 글꼴 경로를 쓰며 PyMuPDF·fonttools(프로젝트 `requirements`에 없음)가 필요하다.
Pillow는 프로젝트 의존성에 이미 있다. 가상환경에 한 번 설치한 뒤 아래를 실행한다. (다시 만들어 비교해 보니 이미지·MD·정답 JSON은 바이트가 같고, PDF 39개만 생성 시각 메타 때문에 해시가 바뀐다. `registry.csv`도 함께 갱신된다.)

```powershell
uv pip install --python .\.venv\Scripts\python.exe pymupdf fonttools
.\.venv\Scripts\python.exe data\virtual-orders\scripts\build_vo.py
.\.venv\Scripts\python.exe data\virtual-orders\scripts\verify_vo.py
```
